# Retrieval relevance heads: bound acquisition before truncating the question

## Decision and scope

The optional Tier 2 relevance judge already limits each file's head in its question. Its input producer does not use that limit when acquiring the head: it reads the entire file and converts the whole byte slice to a string before slicing. A wide candidate pool therefore performs whole-file acquisition for a deliberately small-head judgment, even when keyword retrieval is warm. The narrow improvement is to acquire and own only the admitted head, preserve honest extent metadata, and observe cancellation while preparing the pool—not to remove relevance judging, reduce useful context, or cache stale excerpts.

This is a static source finding at main [`388205138ba6d47c1cff0c5e97c896dfa642a391`](https://github.com/theRebelliousNerd/codenerd/commit/388205138ba6d47c1cff0c5e97c896dfa642a391), checked on October 30, 2026. No application code, tests, inference, performance experiment or repository mutation was performed. The source establishes avoidable whole-file acquisition; it does **not** establish measured RSS, physical disk traffic, latency, provider spend, task failure or a permission bypass.

The distinction matters: `RelevanceHeadBytes` is documented as a bound on the head **in a relevance question**, not a promised host-memory or file-read limit. The question bound works. This is a downstream efficiency integration gap, not a claim that the documented configuration contract is violated. [Configuration contract and defaults](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/config/typesafe.go#L104-L140)

## Production path and exact work boundary

1. **This is optional, real production wiring.** The system factory creates the shared sparse retriever, derives the task-retrieval configuration, and installs the task retriever on the session executor. An absent/unresolvable TypeSafe section or disabled retrieval relevance leaves the judge off. A healthy configured section supplies the judge, drop threshold, pool factor and head size. [Factory installation](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/system/factory.go#L2696-L2710), [configuration adapter](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/system/factory_task_retrieval.go#L11-L39), [use resolution](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/turnjudge/relevance.go#L24-L45)
2. **The executive still decides whether a task retrieves.** `TaskRetriever.Retrieve` requires the kernel's `Wanted` decision, then supplies the shared retriever and relevance tuning to `SeedIssueFacts`. The seed constructs a fresh tiered builder under the pass context. The default seed timeout is five seconds. This is not every task or every model request. [Task admission and handoff](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/retrieval/decisions.go#L319-L356), [timeout](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/retrieval/facts.go#L58-L65), [builder handoff](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/retrieval/facts.go#L224-L245)
3. **The judge deliberately sees more files than Tier 2 retains.** Default `MaxTotal=50` and `Tier2Budget=0.40` yield twenty Tier 2 slots. With the configured default pool factor six, `searchKeywordFiles` ranks up to 120 files for judging, separately from the forty-file candidate-evidence ranking. `RankFiles` honors the passed limit and uses deterministic score/path ordering. Already-added files are skipped before head acquisition. [Tier defaults and slot calculation](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/retrieval/tiered_context.go#L91-L151), [pool construction](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/retrieval/tiered_context.go#L399-L442), [ranking limit](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/retrieval/sparse.go#L386-L460)
4. **All heads are acquired before judgment begins.** `judgeTier2` loops over that pool and appends each `relevanceCandidate` to `asks`; only after the loop does it call `Relevance(ctx, request, asks)`. The helper has no context parameter. It calls `os.ReadFile`, assigns `ExcerptOf=len(data)`, computes `head := string(data)`, and only then applies the positive head-byte limit and UTF-8 cleanup. There is no acquisition-loop cancellation check. [Exact producer and ordering](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/retrieval/relevance.go#L42-L91)
5. **The model does not receive the discarded tail.** The TypeSafe default is a 3,000-byte head and twenty questions per batch. The adapter passes the excerpt as `head` and, when appropriate, an extent note. It then judges in parallel batches; any failed batch fails the entire judgment, preserving keyword order rather than applying partial probabilities. For 120 supplied candidates at these defaults, this is six logical batches—not 120 provider requests. Provider transport retries and actual billing remain separate measurements. [Configured tuning](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/config/typesafe.go#L121-L169), [question construction](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/turnjudge/relevance.go#L48-L104), [batch implementation](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/turnjudge/batch.go#L3-L38)

## Bounded counterexample and what it does not show

Use a stable workspace with 120 ordinary admitted text files, each exactly 1 MiB, each containing a small number of short-line matches for the same extracted keyword, and with valid ASCII in the first 3,000 bytes. No files are already added by Tier 1. Keep the configured relevance judge on, the default tier allocation and tuning, and a healthy, complete warm keyword-cache entry for this unchanged workspace domain. Require each subsequent file read to succeed. This intentionally avoids high-occurrence/long-line fixtures from the earlier native-scanner allocation finding.

The native scanner's size check excludes files **larger** than 4 MiB, so this fixture fits its existing cutoff; 120 sparse hits are also below the hit caps. The source path will reread all 120 files during head preparation if those calls finish, even though a warm keyword lookup need not rescan their contents. The resulting accounting is:

| Quantity | Source-derived value under the stated conditions |
|---|---:|
| Successful whole-file head acquisitions | 120 |
| Logical file bytes returned across those reads | 120 × 1,048,576 = 125,829,120 bytes (120 MiB) |
| Total head-string lengths presented for judgment | 120 × 3,000 = 360,000 bytes |
| Default logical judgment batches | 6 batches of 20 questions |
| Maximum Tier 2 files finally selected | 20, potentially fewer after judgment |

[Native size/hit controls](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/retrieval/scan_native.go#L26-L45), [native admission and read](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/retrieval/scan_native.go#L140-L155), [warm-cache reuse](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/retrieval/search.go#L73-L99)

The arithmetic is not a measured 120 MiB resident footprint or physical disk-read claim: the OS cache, allocation lifetime and compiler matter. Nor must every real pool contain 120 large files. One successful large-file acquisition establishes the narrower gap; the wide pool illustrates scaling. The 4 MiB limit is an upstream native-scanner control under this stable fixture, not a universal bound enforced by `relevanceCandidate` itself. File mutation and other search backends should not be smuggled into the simple witness.

Go's `os.ReadFile` reads the complete contents, which supports the acquisition claim independently of string allocation details. The inspected `strings.ToValidUTF8` implementation returns its input unchanged on the valid-input fast path. Thus truncation is not necessarily an ownership boundary: an ASCII head can remain a substring backed by the larger converted string. That is an additional memory-retention risk to verify against the actual build toolchain, not a claimed exact allocation count or measured heap result. [Go whole-file read implementation](https://go.dev/src/os/file.go#L866), [Go UTF-8 conversion fast path](https://go.dev/src/strings/strings.go#L769)

Cancellation is a related preparation-boundary issue, not a promise of an unbounded hang. The seed timeout is passed to the judge, and timeout reporting exists, but it is not checked while these whole-file reads are being gathered. Once the pool is available, cancellation does not itself interrupt this loop. A slow preparation can consume the remaining pass time before judgment, potentially leaving less time for later tiers; an expired context may make judgment fail and trigger the existing fallback. No model send or later-tier failure is guaranteed by that possibility.

## Existing controls, overlap and counterevidence

- Optional configuration, kernel admission, pool limits, Tier 1 deduplication, native size/hit limits, keyword-domain validation, and write-triggered cache invalidation all remain useful. The proposal must preserve them. An unconfigured judge, empty pool, skipped already-added files, short files, or failed file reads narrows or removes this acquisition cost. Existing tests cover exclusion of mentioned files, reorder/drop behavior, failure fallback and relevance facts; they are meaningful controls, not evidence of bounded acquisition. ## Proposed refinement and its costs

For a positive head limit, open the current file and acquire the admitted prefix, allowing only a documented constant-size truncation probe if needed, with owned storage proportional to that prefix. Convert only admitted bytes to a string; preserve the current long-file UTF-8 boundary behavior. Its empty replacement removes invalid byte runs, including a code point cut by the byte limit. Close the handle on every path. Check the context before each candidate and around bounded acquisition, and decline further judgment cleanly when preparation is canceled. Ordinary regular-file reads are not magically preemptible merely because the helper accepts a context.

Preserve honest extent information. The current `ExcerptOf` is the number of bytes actually returned by a full read. Replacing it with a pathname `Stat` from another moment can pair a new head with an old size. Prefer metadata from the same open handle, explicitly qualify its observation semantics, and define what happens if the file changes, reports an unreliable size, or fails during the read. If exact total-byte identity is essential, use an existing immutable snapshot mechanism or mark extent unknown; do not regain the efficiency by asserting a false exact snapshot. Opening and statting the same handle is better association, not an atomic snapshot of concurrently mutable contents.

UTF-8 and error parity need deliberate handling. Today cleanup happens only when the full string exceeds the limit; short invalid input is not passed through that same cleanup branch. EOF on a short file is normal. A new bounded read cannot discover an error that would only occur in the discarded tail, so claiming universal error parity with `ReadFile` would be false. Define a trustworthy-prefix policy or conservatively omit unavailable head evidence; never silently equate a partial failed read with a complete successful snapshot. Preserve keyword fallback and avoid partial probability application.

This does not require caching heads across tasks, narrowing the pool, altering Mangle relevance rules, dropping the judge, or modifying source files. Fresh acquisition should remain fresh. A defensive `strings.Clone` after slicing could address retained backing storage but would leave the whole-file read and conversion work; it is not the complete acquisition repair. Generic-builder zero/unbounded-head behavior must be an explicit compatibility decision, not accidentally changed by a production-default optimization.

Costs include additional bounded-read/extent state, cancellation and error handling, file-handle discipline, metadata work and tests. The normal path still opens candidates and may issue metadata operations. Wider pools, provider judgment work, final context expansion and all task execution costs remain. More early judgments finishing before a deadline could increase model work while improving context; that trade must be counted rather than hidden as a local memory win.

## Fair evaluation, not run

1. **Deterministic acquisition accounting:** compare baseline and proposed producer using the same stable ranked pool. Cover one and 120 large files, short and empty files, no judge, already-added files, read failures, complete warm keyword cache and cold cache. Count successful file bytes acquired separately from physical I/O and scanner work. Preserve all candidate paths, head bytes, extent semantics, selected files and relevance facts for the stable successful cases.
2. **Boundary semantics:** exercise limits one byte below/equal/above file length; multibyte UTF-8 split at the boundary; malformed bytes before and after it; zero/unbounded direct configuration; short EOF, mid-prefix error, tail-only error, concurrent replacement/truncation/growth and cancellation before/between reads. Explicitly test the chosen mutable-source and unavailable-evidence contract instead of asserting impossible universal snapshot parity.
3. **Actual ownership and provider accounting:** use the repository's real Go toolchain for heap/allocation profiles and peak-live memory; inspect whether full backing storage survives, without inferring it from head length alone. Separate preparation time, metadata calls, cache hits, logical judgment batches, actual transport attempts/retries, input/output/cache tokens and failure fallback. Hold configuration and provider behavior fixed; never compare “judge on” against “judge off” as if it isolated bounded acquisition.
4. **Complete tasks:** pair repositories and requests at equal authority, selection budgets and verification requirements. Evaluate useful-file recall/precision, honest degraded-retrieval reporting, task correctness, repair turns, total model/tool tokens, provider cost, wall time and cost per verified successful task. Include failed and canceled passes. For stable source and an unconstrained deadline, unchanged question payloads with less acquisition is the target; under deadlines, any changed selected context requires a quality check. Small-file and fast-cache workloads may show negligible end-to-end benefit.

**Acceptance criterion:** positive head budgets bound head acquisition and owned head storage, source/extent evidence stays honest, fallback and selection quality remain sound, and the full task cost is reported. A shorter string or cheaper microbenchmark alone is not sufficient.
