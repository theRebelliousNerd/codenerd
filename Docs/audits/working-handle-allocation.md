# Working-context handles: decouple ordinal allocation from archive size

## Finding and evidence boundary

Every newly stored working observation computes its next short recall handle by aggregating the numeric casts of existing handles in that scope. The declared indexes order the handle as text, not by that numeric expression. This is a concrete repeated-work opportunity in durable result recording: investigate an indexed numeric lookup or transactional allocator instead of repeatedly reconstructing the high-water mark.

Reviewed public main `486db57ce490302c65d7f484e7f6070ee0e70862`. No application, SQL, EXPLAIN, test, benchmark, model inference or training was executed. The selected SQLite query plan, actual rows visited, workload prevalence and user-visible benefit remain unmeasured. This document does not claim an observed performance incident or a correctness failure in ordinary handle allocation.

## 1. Producer, storage and consumer

Native and Piggyback batches share `executeAndRecordToolCall`. After execution/accounting it invokes `recordWorkingResult`, and a storage error travels back as an error rather than being silently ignored. [Shared boundary](https://github.com/theRebelliousNerd/codenerd/blob/486db57ce490302c65d7f484e7f6070ee0e70862/internal/session/executor_tools.go#L1019-L1111).

For an ordinary result, the recorder hashes call identity, request kind, body, revision and a nanosecond timestamp to form the observation identity. It saves the record, retrieves the short handle, and remembers the call-to-record mapping. An owned successful recall instead reuses its existing observation and returns before this insertion path. [Recall reuse](https://github.com/theRebelliousNerd/codenerd/blob/486db57ce490302c65d7f484e7f6070ee0e70862/internal/session/working_context.go#L333-L372), [new record](https://github.com/theRebelliousNerd/codenerd/blob/486db57ce490302c65d7f484e7f6070ee0e70862/internal/session/working_context.go#L431-L454).

`WorkingStore.Save` starts a transaction and first checks whether that scope/record ID already exists. Existing records keep their handles without consuming another ordinal. For a new record it performs:

```sql
SELECT COALESCE(MAX(CAST(handle AS INTEGER)), 0) + 1
FROM working_records
WHERE scope=? AND handle != ''
```

It inserts the decimal string generated by `strconv.FormatInt(next, 10)` in the same transaction. [Allocator](https://github.com/theRebelliousNerd/codenerd/blob/486db57ce490302c65d7f484e7f6070ee0e70862/internal/context/working_store.go#L260-L294).

The schema declares `handle TEXT`, a primary key on `id`, `working_entity(scope,entity,step DESC)`, and unique `working_handle(scope,handle)`. There is no declared numeric-expression index. `SetMaxOpenConns(1)` limits each store's connection pool. [Open/schema](https://github.com/theRebelliousNerd/codenerd/blob/486db57ce490302c65d7f484e7f6070ee0e70862/internal/context/working_store.go#L48-L120).

Handle consumers require identity stability: `Handle`, `ResolveHandle`, `Search` and paged `Read` expose or resolve the short strings. Renumbering existing records is not a permissible optimization. [Consumers](https://github.com/theRebelliousNerd/codenerd/blob/486db57ce490302c65d7f484e7f6070ee0e70862/internal/context/working_store.go#L221-L258), [lookup and recall](https://github.com/theRebelliousNerd/codenerd/blob/486db57ce490302c65d7f484e7f6070ee0e70862/internal/context/working_store.go#L296-L397).

## 2. Why bounded active context does not bound this work

Each scope has its own database named by the hash of the scope. This is not a claim that all campaign tasks share one ever-growing database. `beginWorkingLoop` constructs a scope from session ID, shard ID and a random executor-local component; that random component is assigned only once. Repeated turns with the same components reopen the same archive. [Scope construction](https://github.com/theRebelliousNerd/codenerd/blob/486db57ce490302c65d7f484e7f6070ee0e70862/internal/session/working_context.go#L204-L257).

The active ledger archives a result by rendering its recall handle, not by deleting its durable record. The session executor retains its scope for the process lifetime. Task clones retire their scopes, and whole-archive retention removes archives whose owners are gone or retired. These are valuable bounds, but they do not make insertion cost independent of the number of observations accumulated within a live session scope. [Lifetime and retirement](https://github.com/theRebelliousNerd/codenerd/blob/486db57ce490302c65d7f484e7f6070ee0e70862/internal/session/working_context.go#L260-L292), [ledger projection](https://github.com/theRebelliousNerd/codenerd/blob/486db57ce490302c65d7f484e7f6070ee0e70862/internal/session/working_context.go#L659-L689), [retention implementation](https://github.com/theRebelliousNerd/codenerd/blob/486db57ce490302c65d7f484e7f6070ee0e70862/internal/context/working_retention.go).

## 3. Cost hypothesis, not a measured query plan

The text index can narrow or cover a scope, potentially avoiding body-page reads. It does not itself provide numeric ordering of decimal strings: lexical order places `9` after `10`. The SQL explicitly requests a maximum over a cast expression.

[SQLite's optimizer documentation](https://www.sqlite.org/optoverview.html#the_min_max_optimization) describes a single-lookup MIN/MAX optimization for an appropriately indexed aggregate argument. [Expression-index documentation](https://www.sqlite.org/expridx.html) explains that expression indexing and expression matching are explicit. These support investigating the mismatch; they do not establish the plan chosen by the exact SQLite library shipped with this binary.

If the current aggregate visits all k existing handles in the selected scope, n sequential novel inserts starting from an empty archive entail `0 + 1 + ... + (n-1)` candidate visits: `n(n-1)/2`. This is a conditional algorithmic model, not a measured SQLite instruction count, disk-read count or wall-clock bound. Confirm the actual plan and work counters before presenting the scan as an observed fact. Database caching, covering-index access, transaction and durability costs, body size and other recording work can dominate elapsed time.

Duplicate-ID saves and successful owned recalls avoid the allocation query. Separate short-lived scopes and retirement also reduce exposure. A small ordinary archive may not justify additional schema complexity. Replacing this code cannot directly reduce model token counts when emitted handles and prompt bytes remain unchanged.

## 4. Proposed options

### A. Explicitly indexed numeric maximum

Retain string handles at the external boundary while introducing an indexed numeric ordinal or a matching expression index and an explicitly indexable highest-ordinal query. Confirm that the selected query uses the intended bound and ordering with the actual SQLite version. Do not replace numeric MAX with text MAX. Keep allocation and insertion atomic under the existing transaction contract.

This option adds index storage, insert maintenance and migration work. A numeric column needs validation and backfill; an expression index retains cast semantics and must deliberately handle any malformed legacy values. Neither should silently renumber published handles. Avoid asserting that merely adding an index guarantees a particular planner choice.

### B. Durable per-scope allocator state

Initialize a high-water mark from accepted legacy rows once, then update it transactionally with insertion. Existing-record checks must preserve the current no-new-ordinal behavior. Rollback, cancellation, a failed insert and repeated opening must not detach the allocator from accepted records. Define integer exhaustion explicitly.

This exchanges repeated aggregation for another durable state invariant and potentially another row write. Separate `WorkingStore` objects can open the same scope even though each limits its own pool to one connection; do not treat that pool setting as a global lock. Design transaction ordering and contention behavior accordingly. A process-local Go counter alone is insufficient without a supported ownership, reopen and concurrency contract.

### C. Keep the current implementation

This remains reasonable if authorized measurement shows small scopes and negligible full-path cost. It preserves a simple derived allocator with no extra persistent counter. Do not shorten retention or delete recoverable evidence merely to make the aggregate cheaper: retention is a separate policy decision.

All alternatives leave Mangle's relevance, retention and eviction decisions unchanged. This is storage bookkeeping, not an opportunity to move executive policy into Go or alter permitted tools.

## 5. Unrun validation and acceptance

The current tests establish intended legacy backfill and idempotent-save contracts in source; they were read, not run. They use tiny fixtures and do not establish scale behavior. [Existing tests](https://github.com/theRebelliousNerd/codenerd/blob/486db57ce490302c65d7f484e7f6070ee0e70862/internal/context/working_store_test.go).

Proposed validation:

| Case | Required result |
|---|---|
| Empty scope, ordinary sequential inserts, decimal digit boundaries | Unique correct short handles; numeric ordering remains correct at 9/10, 99/100 and larger boundaries. |
| Duplicate save | Original handle/body preserved; no ordinal consumed under the existing contract. |
| Reopen and legacy migration | Existing handles unchanged; next handle derived or initialized consistently; repeated migration is idempotent. |
| Two open stores for one scope | No duplicate committed handles or corrupt allocator; contention has an explicit outcome. |
| Cancellation, rollback, failed insert, process interruption | Accepted record/allocator state remains coherent; no claim that uncommitted output was durable. |
| Overflow or malformed legacy ordinal | Explicit refusal or specified migration policy, never wraparound or silent aliasing. |
| Search and paged recall after migration | Exact original record identity, payload and scope isolation retained. |
| Active-ledger compaction with a large retained archive | No evidence deletion or altered policy decision; allocation cost measured independently of active-window size. |

Before timing a repair, inspect `EXPLAIN QUERY PLAN` and appropriate VM/work counters on the actual linked SQLite implementation. Sweep retained record counts separately from body sizes and repeated-save ratios. Compare current SQL, indexed numeric lookup and durable allocator with the same durability settings and data. Include cold and warm cache conditions where relevant, clearly labeled.

Measure total insertion and result-recording latency, CPU, allocations, rows/VM steps, index and database bytes, migration time, WAL growth, transaction duration, contention failures and cancellation latency. Include the extra writes/index maintenance of the proposed options. End-to-end request latency and verified task completion are separate observations; do not infer them from a microbenchmark. Report the small-scope crossover, not only a large synthetic win. No numerical saving is claimed here.
