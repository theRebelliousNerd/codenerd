# Oversized approval previews need metadata, not file-sized placeholder bytes

## Finding

**The local deletion-approval path bounds retained source content, then defeats that bound by allocating a zero-filled slice the size of the entire oversized file. The preview builder interprets that placeholder as binary content.** For a readable, stable, ordinary text file of size `N > K`, where `K` is the configured preview limit, this introduces an unnecessary `N`-byte allocation and, if construction succeeds, the wrong reason for withholding the diff.

This is not a claim that the file's full diff is displayed, that the preview claims completeness, or that the placeholder authorizes different source bytes. The result remains explicitly incomplete, with no diff. The defect is at the boundary between content acquisition and preview representation: “content intentionally not retained because it exceeds the limit” is encoded as fabricated content rather than metadata. [Bounded retention during revision reading](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/session/human_approval.go#L103-L160) [Deletion preview adapter](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/session/human_approval.go#L248-L275) [Classification and withholding](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/approval/preview.go#L114-L145)

The finding is conditional static analysis at the pinned commit. No tests, application/model inference, allocation measurements, or repository edits were performed. There is no claim of a reproduced crash, malicious actor, credential exposure, permission bypass, or measured performance improvement.

Use an untracked or modified file that was not created by the current turn, so ordinary recoverability does not automatically admit its deletion. The effective tool catalog and earlier write guard must admit the request for consideration; the constitutional gate must deny it in an approvable way rather than hard-refuse it. ## Exact size and content flow

Let `K > 0` be `PreviewMaxBytes`, and let `N > K` be the number of bytes actually read successfully to EOF. Assume the file does not change during this schedule.

1. **Hash all bytes, retain only a bounded prefix.** `readRevision` opens the file and calls `io.Copy(io.MultiWriter(hash, limitWriter), file)`. The limit writer keeps at most `K + 1` bytes and reports the full input write length even after its retained prefix is full. The hash therefore continues over all `N` bytes. The function sets `rev.size = N` and the SHA-256 digest; it sets `rev.content` only when `N <= K`. For this witness, `content == nil`. This is bounded retained content, **not bounded total input or hashing work**. [Reader and limit writer](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/session/human_approval.go#L127-L160)

2. **Re-expand the omitted content into zeros.** The adapter initially uses `Before: r.content`. Because the file exists, is not a directory, and has nil retained content, it replaces `Before` with `make([]byte, r.size)`. The allocation is sized by `N`, not `K`. Its purpose appears to be carrying length to the generic builder, but its type says these are actual before-bytes. [File-sized placeholder](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/session/human_approval.go#L264-L270)

3. **Classify the placeholder, not the file.** `BuildPreview` checks binary content before checking the length limit. Its binary test is the presence of a zero byte. The newly allocated nonempty byte slice contains zero values, so it takes the binary branch and never reaches the oversize message. For a NUL-free UTF-8 source, the resulting “binary” reason is false. [Branch order and binary predicate](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/approval/preview.go#L114-L145)

4. **Withhold, seal, and show.** The selected branch sets `Complete=false`, appends an incomplete reason, and leaves `Diff=nil`. The digest seals those preview fields. The TUI displays the reason under review limits; it does not recompute content classification. The deletion effect still includes the actual byte count, so the request is not wholly devoid of size information. [Withholding state](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/approval/preview.go#L94-L103) [Preview seal](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/approval/preview.go#L137-L154) [Actual-size effect text](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/session/human_approval.go#L259-L263)

These conclusions follow from code plus standard Go semantics: `make` creates the requested slice length with zero-valued elements, and `io.Copy` continues to EOF or error. They are not allocation measurements. Physical residency, allocator behavior, GC pressure, failure thresholds, and latency depend on runtime and environment. [Go slice allocation and initialization](https://go.dev/ref/spec#Making_slices_maps_and_channels), [Go zero values](https://go.dev/ref/spec#The_zero_value), [Go copying contract](https://pkg.go.dev/io#Copy).

At the default `K = 262,144` bytes, a text file of `K + 1` bytes is already sufficient to establish the wrong reason. Larger files establish increasing requested placeholder allocation, but no particular file size is claimed to crash a process. The configured default is 256 KiB, with validation requiring at least 1 KiB; the inspected configuration check supplies no upper bound. This is an operator-configured display/content bound, not a documented total-process memory budget. [Configuration meaning and defaults](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/config/approval.go#L15-L31) [Configuration checks](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/config/approval.go#L62-L95)

## Timing and resource scope

The allocation happens **before the broker creates the request**. `awaitHumanApproval` freezes and builds the preview first; `Broker.open` later stamps `CreatedAt` and `ExpiresAt = now + TTL`. Consequently, the approval request TTL is not a preview-construction budget. The executor's per-tool timeout context is also constructed later, after approval and intervening gates. [Preparation ordering](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/session/human_approval.go#L290-L310) [Request deadline creation](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/approval/broker.go#L253-L271) [Tool timeout creation](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/session/executor_tools.go#L2744-L2755)

The parent execution context may have its own lifetime, but `readRevision` takes no context and this synchronous copy/allocation path performs no cooperative context check. It is inaccurate to claim that merely canceling the parent preempts this work. A repair should distinguish a storage operation still in progress from a request that is actually awaiting a person, without promising that ordinary filesystem reads are universally interruptible.

**Whole-path counterevidence is important.** Production's earlier accounting wrapper already calls `readPreImage`, which uses `os.ReadFile` and retains content, and `snapshotEffectTargets` also reads a target to compute identity. The deletion backend reads the full file again before removal. Thus removing the approval placeholder does **not** make the entire deletion request O(K) in memory or eliminate all full-file reads. It removes one redundant N-sized representation at this specific boundary. Those other consumers serve recovery/effect evidence and need their own contracts, not silent removal to improve a benchmark. [Earlier snapshots](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/session/executor_tools.go#L1040-L1047) [Preimage retention](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/session/executor_tools.go#L1153-L1178) [Full preimage read](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/session/preimage.go#L101-L112) [Effect identity read](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/session/tool_effects.go#L138-L170) [Backend preimage read](https://github.com/theRebelliousNerd/codenerd/blob/8a90d4d9d27b6f207052102972d451a412ae25fb/internal/tools/core/file_ops.go#L664-L680)

The placeholder is not stored as a full byte array in `Preview` or the journal: the binary branch produces a compact notice and no diff. This is transient construction allocation, not proof of a persistent N-byte journal leak. Even when a later decision rejects the deletion, the preparation work has already happened.

## Proposed representation contract and alternatives

**Contract:** omitted source bytes must be represented as omission metadata, not synthetic content. Preview preparation must preserve the exact source identity while retaining only the declared content budget; every displayed withholding reason must be supported by observed evidence.

A focused design would carry file size, existence/type, retained-content status, and withholding reason separately from optional actual before/after bytes. The adapter can then say “N bytes exceeds K; diff not shown” without allocating N bytes. Size and hash should describe the same successful read; a stat size alone is not an equivalent revision witness. The preview digest should cover the resulting explanation, and the subject should retain its full-content revision binding.

For oversized inputs, report the proven size reason without asserting that the file is binary or text unless the acquisition path actually establishes that property. If binary information is desirable, the existing full streaming pass can track NUL presence as metadata. Sampling only a prefix cannot prove the entire file is NUL-free; it must not be labeled a full-content classification. Metadata validation must distinguish empty, absent, unreadable, directory, withheld, and genuinely retained content.

Alternatives have different limits:

- **Reorder size before binary in the builder:** corrects the sentinel's reason but leaves the N-sized allocation. It is incomplete.
- **Use a K+1 sentinel:** bounds that allocation but still fabricates bytes, loses the true N if length is the only metadata, and preserves classification coupling. Explicit metadata is clearer.
- **Refuse oversized review entirely:** can bound review work more aggressively if done before full reading, but changes availability and the exact-review contract. State that the operation was not authorized and preserve a safe manual-review path.
- **Stream or page full review:** potentially useful for a separate product requirement, but requires immutable revision binding, incomplete-page disclosure, operator effort and storage/cleanup ownership. It is not needed to repair the placeholder.

Do not truncate the source digest to K, replace it with an unverified size/mtime pair, remove consent, or weaken revalidation to claim a memory saving. Moving hashing outside a deadline or adding a goroutine alone does not cancel an underlying read. A separately specified preparation budget should return a refusal/unknown-preparation result on failure, never manufacture a complete preview.

The general excessive-size-allocation category is described by [MITRE CWE-789](https://cwe.mitre.org/data/definitions/789.html). That is conceptual guidance for checking size before allocation, not proof of an adversarial exploit or a severity rating for this repository.

## Costs and fair proposed evaluation

An explicit metadata path can avoid this placeholder while keeping full-source hashing O(N) and retained preview bytes O(K), plus ordinary buffers and bounded-input diff work. It adds state validation, API changes, reason precedence and compatibility tests. If persisted preview fields change, old journal records and their digests need a deliberate compatibility rule. Limits on aggregate concurrent preparations, maximum configured K, hashing work, and total retained request data are separate policies; a per-side limit is not a global bound. Raising a runtime memory limit is not this repair: Go documents its memory limit as soft, not a guaranteed per-request allocation cap. [Go GC memory-limit guidance](https://go.dev/doc/gc-guide#Memory_limit).

Measure both the component and the full production entry path. Keep all recovery snapshots, effect accounting, admission checks, digest guarantees and backend work equivalent. Model calls need not be part of a deterministic preview fixture, but any later whole-task study must count model/reviewer time, rejected work, retries and verification, rather than claiming a token saving from fewer allocated bytes.

**Exit criterion:** the real oversized deletion-preview producer passes size/omission metadata rather than N fabricated bytes; the user sees the true review limitation; complete previews, exact revision checks and ordinary authorization remain intact. Any claimed cost improvement must be measured on that equivalent contract.
