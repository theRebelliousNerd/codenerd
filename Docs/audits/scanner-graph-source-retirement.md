# Retire scanner-owned graph edges when their source support disappears

## Decision and evidence boundary

At current main [`9dcb01b9736bf4763aa3ac391d29f133d73c6611`](https://github.com/theRebelliousNerd/codenerd/tree/9dcb01b9736bf4763aa3ac391d29f133d73c6611), a successful source refresh can remove an import from the live world model while leaving its previously persisted `depends_on` edge in `knowledge_graph`. That durable edge has production readers: graph-memory retrieval appends it to the session's dependency data, and direct graph queries return it without a currentness check. Prompt exposure is narrower: the inspected articulation renderer uses this dependency list in its **legacy/fallback branch**, not after successful JIT compilation.

**Proposal:** give scanner-derived graph edges a source-owned replacement/retirement contract, or stop treating that historical projection as current dependency context. Preserve unrelated manual and document-ingest relationships. Do not fix this by globally deleting graph edges or rehydrating the entire graph into Mangle.

This is static inspection on **2026-10-29**. No tests, application, models, benchmarks or training were run. The finding establishes stale persistent graph answers and a reachable stale session-context field under the conditions below. Prompt exposure additionally requires the articulation fallback route to receive that field. It does not establish normal successful-JIT contamination, a wrong patch, failed verification, or inevitable model error. Root guidance explicitly requires source changes not to leave stale evidence presented as current truth. [Guidance](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/agents.md#L17-L23)

Main and active Mangle/store lane remained unchanged during this pass. The lane [`a53cfc308e8836c72370adaa46deba3f7b00180d`](https://github.com/theRebelliousNerd/codenerd/compare/9dcb01b9736bf4763aa3ac391d29f133d73c6611...a53cfc308e8836c72370adaa46deba3f7b00180d) batches graph writes into a transaction but retains upsert-only projection semantics. It is not the origin of this finding.

## Concrete producer–consumer path

### 1. Refresh already retires the world-model facts correctly

For changed/deleted files, the incremental scanner loads prior cached facts into `RetractFacts`. Its resolved imports are deliberately stored with the owning file, so an import removal can retract the old edge. The returned result carries both old and new facts, and the kernel applier retracts the old facts before loading the new ones. Successful file-cache updates replace file-owned `world_facts`; deletion removes `world_facts` and `world_files`. These are important working mechanisms, not missing functionality. [Old facts and import ownership](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/world/incremental_scan.go#L336-L378), [result and persistence](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/world/incremental_scan.go#L588-L634), [kernel delta](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/world/apply_incremental.go#L55-L78), [file deletion](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/store/local_world.go#L279-L318)

### 2. The separate graph mirror consumes additions, not replacement scope

The chat scan applies that result to the kernel, then passes only `res.NewFacts` to `PersistLinkFacts`. The helper maps `dependency_link(From, To, Import)` to a `depends_on` edge and `symbol_graph(Symbol, ..., File, ...)` to `defined_in`. Metadata records the scanner label, and optionally the import path, but not a source revision or complete replacement scope. Its store call is `INSERT OR REPLACE` for the new triple; it does not retire other triples whose source support vanished. [Scan call site](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/cmd/nerd/chat/helpers_scan.go#L170-L198), [projection](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/core/virtual_store_predicates.go#L143-L186), [upsert](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/store/local_graph.go#L46-L80)

## Minimal source-supported witness

Use a small workspace with one active source file, valid parsing and successful database/kernel operations:

1. A source file `a.go` imports a local package containing `b/b.go`. A successful scan persists the canonical edge `a.go —depends_on→ b/b.go`.
2. A permitted edit removes that import while leaving `a.go` present. A successful subsequent scan replaces its cached/live facts; its current `dependency_link` no longer includes that target.
3. The old canonical graph triple does not conflict with any different new triple and is not deleted. Repeated scans with no such import cannot remove it by upsert.
4. A direct outgoing graph query still returns the old edge. If the session also has canonical `modified("a.go")` and the local store attached, its next context-data assembly adds that edge to `DependencyContext`.
5. For a prompt-level witness, that populated SessionContext must reach articulation while JIT is disabled/unavailable or compilation fails and legacy assembly runs. Keep the context small enough to survive its budgets. The successful-JIT path is a negative control, not an asserted affected serving path.

Canonical active-file identity is not merely a hand-asserted possibility: the normal VirtualStore file-edit result emits `modified(v.factPath(path))`; `factPath` canonicalizes relative to the workspace. Other paths may supply different spellings, so exact endpoint identity remains a condition. [Edit fact](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/core/virtual_store_file_actions.go#L373-L389), [canonicalization](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/core/virtual_store.go#L822-L834)

The stronger absence witness is an import-free, successfully parsed replacement file: it still produces topology/symbol facts, so there is no need to depend on an entirely empty scan result. The issue persists even when the world cache and kernel refresh have both worked correctly.

## Counterevidence and non-claims

- **Live Mangle impact/activation remains separate.** Stock knowledge policy explicitly relies on live world `dependency_link` for scanner dependency activation. The durable graph is not bulk-hydrated by normal learning hydration. This finding does not claim stale graph triples corrupt those live derivations or overflow the kernel at boot. [Policy distinction](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/core/defaults/policy/knowledge.mg#L42-L68), [no bulk hydration](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/core/virtual_store_predicates.go#L638-L647)
- **Existing cleanup is narrower.** Startup migration deletes malformed dependency labels and absolute-path edges. A valid canonical edge whose import was later removed does not match that predicate. [Migration](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/store/local_core.go#L781-L811)
- **Upsert is correct for its generic API.** The graph's unique triple prevents repeated identical scans from duplicating that edge. The problem is the missing lifecycle of a derived projection, not SQL `REPLACE` being intrinsically wrong. The table also contains non-scanner knowledge that must survive source refresh. [Schema](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/store/local_core.go#L166-L180)
- **Visibility is conditional.** No matching active file/local store means no graph-memory addition. Successful JIT does not render this dependency list through the inspected path; fallback additionally needs the populated context and enough budget. An entry beyond a context cap may not be rendered. Independent current-source views can reveal the truth, and the model may ignore stale context. The audit stops before model behavior.
- **Existing tests are useful but different.** The main projection test checks one-shot edge labels and nil-store behavior. The lane's new tests check batched insertion and rejection of invalid edges, not a source revision removing a formerly valid edge. These are inspected definitions, not execution results. [Main test](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/core/virtual_store_link_facts_test.go), [lane batch tests](https://github.com/theRebelliousNerd/codenerd/blob/a53cfc308e8836c72370adaa46deba3f7b00180d/internal/store/local_graph_batch_test.go)

## Proposed currentness contract

For each completed scanner-owned source scope S and source revision R, the current derived-edge set should equal its admitted projection:

`CurrentScannerEdges(S, R) = Project(CompleteSourceFacts(S, R))`.

An empty projection after a successful parse is a replacement, not “nothing to do.” An incomplete scan is not proof of absence.

1. **Carry ownership and scope explicitly.** Give the projection the canonical owner file, producer family, revision/generation and coverage/completion status, plus the replacement edge set. A scanner label such as `scan-path` is not enough to identify a replacement scope. Dependency ownership normally follows the importing file; definition ownership follows the defining file.
2. **Replace only admitted support.** Retire previous support for a fully refreshed file and publish new support transactionally in the same database where practical. Full scans may retire absent files only after a complete authoritative census. Partial scans affect only their completed scopes; cancellation, read/membership failures and parser-incomplete cases must not masquerade as successful empty projections. Preserve the existing world-scan failure contract. [Scoped guidance](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/world/agents.md#L3-L18)
3. **Preserve independent support.** Manual memory, document-ingest edges, and another valid producer may support the same triple. The current unique triple plus replaceable metadata does not represent multiple owners. Either separate derived edges from durable human/ingest knowledge, or retain per-owner support and expose the edge while any valid support remains. Do not delete all `depends_on`/all edges incident to a refreshed file.
4. **Fence readers when publication fails.** A scan warning does not make the old graph current. If kernel/world-cache and graph updates cannot commit together, expose projection revision/status and refuse or label stale scanner-derived rows at read time. Do not promise a cross-memory/SQL atomic transaction that does not exist.
5. **Separate history from current dependencies.** If old graph edges are intentionally valuable history, keep them in a historical view with provenance rather than feeding them unqualified into current dependency context. This does not require erasing history or expanding user-memory deletion authority.

A simpler alternative for this particular prompt socket is to derive scanner dependencies only from the already-current world/kernel relation and reserve graph-memory context for independently owned non-scanner knowledge. That reduces duplicate representation but must retain useful manual/ingest relations, avoid source-only filters that silently erase valid support, and account for the broader graph query/campaign consumers. Read-through projection from current `world_facts` is another option; its codec, indexes and query cost need evaluation.

## Costs, failure modes and fair evaluation

A source-owned projection adds ownership/revision metadata, indexes, migration rules, transactional work and a recovery protocol. Support tables increase row count when one edge has several owners. Replacement writes can amplify I/O compared with pure upsert; diffing old/new support saves writes but requires reads. A full rebuild is simpler to reason about but costs O(current corpus edges) and must not destroy unrelated graph data. Existing legacy rows cannot always have their ownership reconstructed from the last writer's metadata; adoption needs a conservative quarantine/rebuild rule, not guessed ownership.

Today repeated identical edges are deduplicated, but distinct past targets can accumulate into a lifetime union. `QueryLinks` materializes all matching rows before context caps are applied, so stale degree can add SQL/decoding/allocation work as well as compete with useful context. No measured speedup or token saving is claimed: a fixed-size context may simply replace stale entries with useful ones.

If evaluation is later authorized:

- Run an end-to-end source-refresh fixture through the real scan, persistence and graph/session-context readers, then the explicitly admitted articulation fallback path. Compare current main, active batched-upsert lane, and proposed retirement under identical source history.
- Check add → remove, target change, symbol rename/deletion, import-free replacement, file deletion, repeated unchanged scan, reopening, partial scan, full scan and alternate path spellings. The oracle is current parsed source with declared coverage, not old graph row counts.
- Verify the old edge leaves current graph/context while valid new edges remain; retain the current kernel behavior as a control. Evaluate successful JIT separately to confirm this fallback-specific exposure is not silently generalized. Include small fallback contexts below caps so truncation cannot hide failure.
- Preserve manual/ingest edges and another owner's support for the same triple. Refuse stale publication and retain explicit unavailable/partial status on canceled reads, failed parse, failed SQL commit and incomplete census.
- Exercise the other graph readers separately; do not count a prompt-only filter as durable projection repair.
- Measure query/transaction latency, writer hold time, rows read/written, allocations, database growth, context composition and stale-current admissions over repeated edits. For any later model study, hold model, tools and budgets fixed and measure verified task quality and total retries/cost—not just fewer context entries.
