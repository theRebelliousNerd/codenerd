# Campaign phase admission is skipped by the normal pending phase route

## Finding and scope

At main `6cbe3962fbdb24a1639b26e71f8096e4f4330048`, a normally planned pending phase can be selected and executed without entering the function that owns phase-start lifecycle work and the enabled Northstar phase assessment. The kernel deliberately derives `current_phase` for the lowest-order eligible pending phase; `Run` treats that result as ready for `runPhase`. It invokes `startNextPhase` only when there is no current phase. The two interfaces disagree about whether selection has already performed admission. [Phase selection rules](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/core/defaults/policy/campaign_phases.mg#L29-L55), [normal run routing](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/orchestrator_execution.go#L177-L294).

This is an **absent phase assessment and lifecycle transition**, not evidence that a live blocked verdict was returned and overridden. Campaign-start risk assessment still runs. Task permissions, task checks, phase checkpoints and final acceptance remain separate controls. No production incident, harmful edit, incorrect model judgment or falsely passing behavioral witness is established here.

This is a focused integration continuation of the repaired module-scope transport, with a separate older transition-rollback defect explicitly credited below. Inspection was static: no CodeNERD execution, tests, model calls or repository modifications. Main was rechecked at the cited revision on 2026-10-30.

## Production path and the missing edge

The route is not limited to a fabricated phase status or a direct helper invocation:

1. The production decomposer initializes generated phases as `PhasePending`. `Campaign.ToFacts` emits those phases under the owning campaign, and `Phase.ToFacts` preserves the status in `campaign_phase`. [Plan construction](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/decomposer_planning.go#L412-L428), [fact projection](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/types.go#L598-L627).
2. The chat factory supplies a real campaign observer; the normal background campaign owner calls `orch.Run(ctx)`. The observer builder acquires the shared Guardian, wires its model and kernel/querier and initializes it, returning nil on initialization failure. [Factory](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/cmd/nerd/chat/campaign_planning.go#L112-L136), [run owner](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/cmd/nerd/chat/campaign.go#L127-L148), [observer construction](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/northstar/campaign_observer.go#L44-L78).
3. `Run` performs risk preflight once. On successful admission, it normalizes dangling in-progress phases/tasks, marks the campaign active and enters the loop. Restart normalization also creates pending phases; it does not repair the missing phase-start edge. [Preflight and initialization](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/orchestrator_execution.go#L48-L104), [restart normalization](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/orchestrator_lifecycle.go#L142-L211).
4. With an active campaign, no in-progress phase and a pending phase whose hard dependencies are complete, the policy derives that phase as eligible. If it has the lowest eligible order, it also derives `current_phase`. `getCurrentPhase` resolves that identity directly to the in-memory phase; it does not require `PhaseInProgress`. [Rules](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/core/defaults/policy/campaign_phases.mg#L16-L55), [lookup](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/orchestrator_phases.go#L13-L45).
5. A nonnil result skips the entire `startNextPhase` branch. Context paging occurs, then `runPhase` calls `runPhaseTasks`. Neither installs phase-start admission. The scheduler obtains eligible tasks, acquires a write-set lease where required, promotes task status and launches `runSingleTask`. [Run branch](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/orchestrator_execution.go#L253-L294), [phase wrapper](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/orchestrator_tasks.go#L55-L81), [dispatch](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/orchestrator_tasks.go#L250-L293).
6. This dispatch is consistent with existing task policy: `eligible_task` requires `current_phase`, pending task status and its ordinary blocker checks, but not a separately admitted phase-start outcome. The kernel remains authoritative; this is not the old in-memory eligibility fallback. [Task policy](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/core/defaults/policy/campaign_tasks.mg#L98-L113), [kernel-only task selection](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/orchestrator_phases.go#L67-L106).

By contrast, `startNextPhase` owns the phase's in-progress update, start timing, `OnPhaseStart` call and started event. Its production caller is the nil-current-phase branch above. Thus those operations are not reached on the healthy pending-selection route. This statement does not require the function to be unreachable under every query failure, malformed fact, concurrent mutation or direct test call. [Transition owner](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/orchestrator_phases.go#L343-L447).

## A bounded witness

Use a valid two-phase campaign with unique phase orders and a hard dependency from phase two to phase one. Both begin pending; each has at least one legitimately eligible task. Require healthy policy/fact loading and persistence, an uncancelled run, positive scheduler admission and successful predecessor task/checkpoint completion. Require risk preflight to **succeed while retaining the configured Northstar observer**, plus a defined vision and enabled phase checks. Do not use force-allow or a below-threshold campaign as evidence of an enabled gate being omitted.

The trace is:

- Campaign-start assessment runs and is accepted.
- The kernel selects pending phase one. Its task runs without `OnPhaseStart`.
- If phase one's tasks and checkpoint succeed, normal completion marks it completed and rolling-wave processing returns control to `Run`.
- The hard dependency is now satisfied, so pending phase two becomes current and its task can run by the same route, again without `OnPhaseStart`.

The finding is visible before requiring final campaign completion: the phase-two worker is dispatched without a phase-start callback or phase-gate request. No particular verdict needs to be invented. [Phase completion and rolling wave](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/orchestrator_tasks.go#L153-L247), [phase status publication](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/orchestrator_phases.go#L517-L588).

First-phase reuse is an important control, not a counterexample. `StartCampaign` clears observer phase state and retains assessed start coverage. An actual `OnPhaseStart` updates the phase and resets its task counter even when it can reuse that coverage. Reuse is limited to the first phase and matching covered paths/roles and vision/module digests; subsequent phase starts perform a phase-gate check when enabled and a vision exists. With the hook absent, the observer never advances its phase identity on this route. [Observer start and phase logic](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/northstar/observer.go#L56-L124).

The immediate impact is missing phase-specific assessment, lifecycle publication and phase attribution. Whether an omitted check would have disagreed with campaign-start approval is a separate empirical question. Scope expansion during rolling-wave refinement or changed strategic context can make reassessment more valuable, but neither is needed to establish the missing callback.

## Protections and counterevidence

- **The observer is conditional.** Risk preflight explicitly clears the runtime observer when auto-wiring is disabled, strict gating is off, Northstar is not selected, or force-block is applied. A configured observer alone does not establish the witness. Missing reviewer/observer dependencies on protected surfaces are refused. [Risk selection](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/risk_scoring.go#L247-L386).
- **Initial risk is real.** The run returns a preflight refusal and records failed campaign state. This report does not claim that no alignment check occurs in the campaign. [Run preflight enforcement](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/orchestrator_execution.go#L48-L77).
- **Task execution has independent gates.** Mutating tasks enter the snapshot/rollback wrapper, explicit task or campaign risk overrides can refuse them, and microcheckpoints still run. Successful auto-wired preflight does not itself hard-block every mutating task afterward. These controls do not call the missing phase hook. [Transaction wrapper](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/orchestrator_task_transaction.go#L52-L79), [task risk semantics](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/risk_scoring.go#L928-L960).
- **Post-task checks are not phase admission.** Periodic and high-impact checks can still run after successful tasks. They receive task scope, but use the observer's current phase and task counter. Their caller discards the returned check/error by the existing advisory contract. They neither restore a missing pre-dispatch phase assessment nor justify turning all task advice into a new hard gate. [Task observer](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/northstar/observer.go#L148-L198), [caller](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/orchestrator_tasks.go#L694-L696).
- **Phase and campaign verification still matter.** Checkpoint failures keep the phase open or close it unverified after bounded attempts; hard dependents remain blocked. Declared final acceptance must settle before campaign completion. An aligned phase is not a behavioral witness or tool permission. [Checkpoint outcomes](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/orchestrator_tasks.go#L173-L227), [final acceptance](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/campaign/orchestrator_execution.go#L179-L205).

## Repair direction

Separate **phase selected for consideration** from **phase admitted for task execution**, while keeping selection and admission policy in the kernel. Publish typed phase-assessment observations through the existing Guardian adapter; derive the allowed, advisory, blocked or waiting disposition under the existing contract. Task eligibility must require the appropriate admitted phase identity, not infer admission merely because a pending phase is current.

A narrower implementation may retain `current_phase` for selection, but must funnel its pending result through a single phase-start owner before dispatch. Do not independently reselect an arbitrary `phase_eligible` row and accidentally start a different phase. Do not rerun an expensive check on every poll or every checkpoint retry. Scope any reusable admission to the phase/run or plan identity and the scope/source context it actually assessed; define how resume and rolling-wave changes invalidate it.

Preserve the existing distinction: phase unknown/unassessed outcomes are advisory where currently specified; explicit blocked outcomes are not. Do not broaden this report into a policy that blocks all unavailable assessments. Complete fallible admission before publishing runnable status, or provide a durable policy-visible hold that cannot disappear on the next iteration. Cancellation, failed publication and restart must not leave a selected phase treated as admitted. Release orchestration locks around external assessment, as the current transition code already does. The old QA rollback issue should be repaired in the same work rather than rediscovered after connecting the route.

## Costs and fair unrun evaluation

This is primarily a capability/assurance repair, not a claim of lower token use. Correctly invoking previously omitted checks adds work. For a clean P-phase run with enabled checks, a vision, complete reusable first-phase coverage and no intervening invalidations, the intended observer path adds P minus 1 phase-gate invocations compared with the absent-hook route. Each successful healthy check includes scope resolution, prompt construction, a logical model completion, parsing, history persistence and logging; provider retries or rejection change actual request and token costs. Incomplete first-phase coverage can add its own check. [Guardian check pipeline](https://github.com/theRebelliousNerd/codenerd/blob/6cbe3962fbdb24a1639b26e71f8096e4f4330048/internal/northstar/guardian.go#L368-L438).

Resetting task counters at real phase starts also changes periodic scheduling. Therefore additional phase checks are not an exact prediction of the net change in all Guardian calls. Count periodic/high-impact calls, scope queries, storage, snapshots, policy evaluation, cancellation handling and retries too. Potential savings from avoiding misaligned downstream tasks are conditional; no latency, quality, dollar or token benefit is measured here.

No evaluations below were run. Prefer deterministic request/dispatch capture through the production constructor, normal `Run` and real policy before any separately authorized live-model study.

| Case | Required observation |
|---|---|
| Two pending phases, phase two hard-depends on phase one, enabled observer and accepted preflight | Phase-start lifecycle occurs before each phase's first task; first reuse is allowed, phase two receives a phase-gate assessment |
| Capture at first task dispatch | The phase identity, admitted status/receipt and started event agree; no pending phase dispatch merely because it is current |
| Phase assessment explicitly blocked | No task from that phase starts; state and user-facing reason remain blocked/paused as designed across another loop and restart |
| Unknown, no vision, disabled phase checks, or runtime observer intentionally disabled | Preserve each existing policy distinction; do not manufacture a passing assessment or unnecessary model request |
| Matching first-phase coverage versus expanded scope or changed vision/module digests | Retain legitimate reuse and require assessment when reuse is not valid |
| Multiple eligible phases or tied orders | The selected and admitted phase identities agree; no extra independently selected phase is started |
| Checkpoint recheck/remediation and ordinary scheduler polling | Do not repeat unchanged admission just because the scheduling loop resumes |
| Cancellation, kernel publication failure and resume | No runnable state without the required admission; no live worker left outside the owner |
| Task and final verification failure | Existing microcheckpoint, dependency, phase-unverified and final-acceptance controls continue to refuse completion |

For the two-phase diagnostic, count both callbacks and actual phase-gate model requests: first-phase reuse can correctly produce a callback without a request. Hold task outcomes and initial risk inputs fixed. Record task dispatch order, observer phase identity, state/facts/events, assessment coverage, all model attempts/tokens and total elapsed work. Success means the enabled transition contract is reached exactly when needed and enforced consistently, not that the model blocks more work.
