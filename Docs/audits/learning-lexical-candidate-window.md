# Learning lexical candidate window audit addendum

## Conclusion and scope

LearningStore lexical recall ranks keyword coverage only after each shard has selected its newest `limit * 3` matching rows. An older row can therefore score higher under the existing lexical scorer than every returned row yet never enter the global ranking. With JIT's lexical limit of five, fifteen newer matching rows in the same shard are sufficient to exclude it. This is a source-derived, conditional candidate-coverage finding, not an observed task failure or evidence that older knowledge is more useful.

The narrow question is whether this reader intentionally implements a recent-match window or should return the highest-scoring lexical matches across eligible rows. Rank-before-limit is not a new optimization proposed by this addendum. The sibling KnowledgeAtom reader already scores before limiting and explicitly addresses weak matches hiding a whole-query match. This addendum identifies a separate LearningStore application of that known concern. [LearningStore candidate selection and ranking](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/store/reflection_search.go#L221-L260), [per-shard query](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/store/reflection_search.go#L367-L428), [KnowledgeAtom precedent](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/store/knowledge_lexical_db.go#L85-L103).

## The current reader contract

### Saved learning and keyword candidates

`Save` accepts learning rows and builds a semantic handle synchronously. The table's `(fact_predicate, fact_args)` uniqueness and conflict reinforcement matter: saving an identical learning can refresh `learned_at`, rather than supply another distinct competing row. Any candidate-window fixture must therefore use distinct rows and control their timestamps. The producer need not malfunction. As an optional production route, DreamRouter saves procedural learning through the same LearningStore adapter, using `approach_learned` as its saved learning label. This does not make that label an authoritative Mangle predicate. [Save and reinforcement](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/store/learning.go#L180-L236), [shared adapter](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/system/factory.go#L1642-L1655), [procedural save](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/core/dream_router.go#L143-L182).

Lexical search uses up to four whitespace-separated query words whose lengths are at least four. It visits all listed shard types. Within each shard, the SQL predicate ORs escaped `LIKE` matches across `semantic_handle`, `fact_predicate`, and `fact_args` for those keywords. Matching rows are ordered by `learned_at DESC` and limited to `limit * 3`. Only afterward does the reader construct a legacy handle if necessary and calculate its existing keyword-coverage score over handle, predicate, and serialized arguments. The score is the fraction of query keywords found by case-insensitive substring matching, with a floor of `0.3`. Row-iteration errors are checked. [Keyword extraction and scoring](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/store/reflection_search.go#L482-L517), [SQL window and legacy handling](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/store/reflection_search.go#L367-L428).

The outer reader appends the per-shard results, sorts them by descending score, and applies the final limit. That global sort cannot recover a row excluded by a shard's earlier recency window. Nonmatching newer rows do not consume this SQL window, and matching rows in a different shard do not consume this shard's allocation. [Global ranking](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/store/reflection_search.go#L221-L260).

### JIT consumption and semantic rescue

JIT forms a lexical query from `IntentTarget`, `SemanticQuery`, and the expanded query, always requests five lexical results, and optionally requests semantic results when a vector searcher exists. It merges those sources into five learning hits by interleaving and deduplicating `(shard, id)`, not by comparing their scores. It then hydrates complete saved bodies by ID and wraps them with source, confidence, and timestamp information as optional retrieved context bound to the shard. [JIT retrieval and hydration](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/prompt/compiler_db.go#L481-L582).

Semantic retrieval can rescue an omitted row if its semantic rank survives the hybrid cap and downstream admission; presence anywhere in semantic top five is insufficient. A supported boot state has no attached vector searcher: embedding initialization can leave the engine unset while boot continues, whereas LearningStore is attached independently. This is not a claim that an explicit disable setting was verified. For a precise proposed JIT fixture, an empty `IntentTarget` and the exact four-word `SemanticQuery` below make those the first four lexical terms while query expansion remains nonempty. [Optional embedding setup](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/system/factory.go#L1702-L1735), [conditional vector attachment](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/system/factory.go#L1791-L1795), [independent learning attachment](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/system/factory.go#L1859-L1860), [semantic query expansion](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/prompt/query_expansion.go#L125-L156).

## Conditional sixteen row witness

Use the ASCII query `walcheckpoint eviction replay recovery`, a limit of five, and one healthy shard. Let `K` be an older, short, valid learning containing all four keywords. Add fifteen distinct newer valid learnings in the same shard, each matching only `eviction`; differing innocuous text prevents uniqueness reinforcement. Use strictly ordered timestamps and ensure their other searched fields introduce none of the other three words.

| Row group | Matching keywords | Existing lexical score | SQL window result |
| --- | --- | --- | --- |
| Older learning K | All four | 1.0 | Excluded |
| Fifteen newer distinct learnings | Only eviction | 0.3 each | Included |

The SQL stage admits the fifteen newer matches and excludes `K` before coverage scoring. The downstream sort consequently cannot return `K`, although its score would outrank every admitted row. With only fourteen newer matches, `K` is inside the fifteen-row candidate window. These are deductions from the inspected selection order, not executed results. [Selection and score definitions](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/store/reflection_search.go#L367-L428), [score floor](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/store/reflection_search.go#L501-L517).

To isolate the same omission through JIT, use a fixture with no attached vector searcher, keep collection healthy, and provide sufficient whole-atom prompt budget. No database error, stale cache, failed index repair, malformed handle, or model behavior is necessary. This demonstrates exclusion under the existing lexical score, not semantic relevance or task truth. A newer one-word match may be correct and useful while an older four-word match is stale or wrong. No inspected contract promises exhaustive global lexical top-k recall, and the source alone does not establish task failure.

## Counterevidence and retained guarantees

Existing regression definitions cover freshly saved no-embedding recall after reopening, batch saves, and null or empty legacy handles. They are meaningful evidence of intended lexical availability and compatibility; they are not measurements from this audit. The stated cases do not establish behavior at the fifteen-newer-match boundary. [Regression definitions](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/store/learning_recall_regression_test.go#L13-L166).

Current store guidance requires recallability after reopening, explicit query limits, provenance, cancellation, and full-fact hydration. Recallability establishes a path to retrieval, not a promise that every saved row occupies an arbitrary top five. Prompt guidance separately preserves bounded retrieval, retrieved-context classification, Mangle context and conflict rules, dependencies, and whole-atom budgeting. ## Policy options and preservation requirements

1. **Rank coverage before the fetch cap.** Score all matching eligible rows before selecting the lexical candidate set, with recency explicitly retained as a tie-break or declared weight. Preserve keyword, raw-predicate and argument, normalization, legacy-handle, and score-floor semantics, or deliberately version a different ranking. Legacy handles synthesize a natural phrase and shard prefix before sanitization: copying SQL coverage expressions over raw columns need not reproduce that effective score. SQL lowercase handling also needs Unicode parity with Go. The KnowledgeAtom reader establishes precedent, not semantic equivalence. [Legacy handle construction](https://github.com/theRebelliousNerd/codenerd/blob/9dcb01b9736bf4763aa3ac391d29f133d73c6611/internal/store/learning_reflection.go#L271-L315).
2. **Keep the recent-match window intentionally.** Document the bounded policy and report enough coverage information to distinguish recent-window recall from global lexical top-k. This accepts the witness rather than claiming to repair it.
3. **Combine bounded recent and coverage pools.** Define each pool, its allocation, deduplication, and the final budget explicitly. This trades recency against coverage without calling the result complete recall.

Merely increasing the multiplier postpones the boundary. Whichever policy is chosen, retain sanitized, non-authoritative handles; complete saved-body hydration; cancellation, timeout, and error behavior; source, confidence, and time; and `(shard, id)` identity. Do not bypass Mangle admission, conflict and dependency handling, or whole-atom fit to improve a retrieval metric. No option requires an additional embedding or LLM call merely to evaluate keyword coverage.

## Costs and fair proposed evaluation

Rank-first SQL can add score-expression and sorting work relative to recency ordering. The existing leading-wildcard `LIKE` predicates alone do not establish a query plan or prove the incremental cost is small. Avoid replacing a bounded reader with unbounded Go materialization. Any index or schema option adds legacy compatibility and maintenance obligations. Larger candidate pools can increase memory, downstream hydration, and—if more material is admitted—tokens and fit competition. Coverage diagnostics add representation, tracing, and policy work. No latency, cost, or quality improvement has been measured here.

Compare the current policy, rank-first coverage, and an explicitly bounded two-pool policy with the same final five-hit allowance, whole-prompt budget, query terms, corpus, and system configuration. Keep semantic retrieval conditions fixed within each comparison. First propose deterministic cases for the sixteen-row witness; fourteen versus fifteen newer matches; newer nonmatches; separate shards; timestamp ties; duplicate reinforcement; legacy handles; case, Unicode, and escaped wildcards; malformed rows; cancellation and timeouts. Then separately exercise no-semantic retrieval and successful semantic rescue, and verify context-conflict and whole-atom-fit rejection remain valid outcomes.

Quality evaluation must include both useful older full matches and stale or wrong full matches competing with useful fresh weak matches. Treat lexical coverage as a retrieval metric, not an answer oracle. Assess independently judged correctness, missed useful evidence, and false use alongside candidate inclusion. Record SQL CPU, rows processed, latency, memory, hydration, prompt tokens, retries, embedding calls, and total cost. Only such paired evidence can justify choosing a policy; this source-only addendum supports neither a deployed recommendation nor an empirical task-success claim.
