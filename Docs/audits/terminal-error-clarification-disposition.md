# Terminal errors must not become clarification requests through diagnostic text

## Finding and scope

The generic TUI error handler still treats an error message containing the lowercase substring `clarification`, or the substring `USER_INPUT_REQUIRED`, as a request to pause for user input. A terminal failure can therefore enter clarification mode even though no operation requested clarification and no pending continuation was supplied.

A concrete normal-entry witness is `/tool run clarification_missing` when that generated tool does not exist. Registry lookup returns a terminal missing-tool error containing the requested name. The TUI displays that error under “I need some clarification,” creates an empty-context clarification state, and interprets the next submission through the clarification-response handler. Under the conditions below, that handler passes the reply into ordinary input processing instead of resuming the failed tool operation. The missing tool still does not execute. The defect is **diagnostic text acquiring workflow-control meaning**, not a demonstrated authorization bypass or successful execution of an unavailable tool.

The narrow repair is to keep generic failures terminal and require an explicit, structured ask-user outcome for a real pause. Preserve the existing knowledge-synthesis fix, actual clarification producers, diagnostic visibility, session history, and normal permission checks.

## Reachable production witness

Use an ordinary initialized, idle chat session with the input box focused, no live foreground turn, no pending clarification, no staged learning-confirmation candidate, and no held or resumed intent. Autopoiesis and its ordinary dependencies are initialized; the tool registry lacks `clarification_missing`; the operation lock is available; evaluation and feedback recording return normally. These conditions avoid unrelated startup, cancellation, learning, and proposal branches.

1. **Submit the command normally.** Idle Enter selects `handleSubmit`. Its slash arm calls `handleCommand`; the `/tool` arm calls `handleToolCommand`. This path needs no favorable language-model classification. [Enter dispatch](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/cmd/nerd/chat/model_key_handler.go#L253-L265), [slash submission](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/cmd/nerd/chat/model_handlers.go#L109-L132), [tool command arm](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/cmd/nerd/chat/commands.go#L246-L247).
2. **Attempt the named lookup.** The run handler takes the third command field as the tool name, displays an execution notice, clears the input, sets loading, and schedules `runTool`. It does not reject the name merely because it contains this substring. [Run handler](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/cmd/nerd/chat/commands_handlers.go#L849-L871).
3. **Fail safely before tool execution.** `OuroborosLoop.ExecuteTool` acquires its operation lock, checks the registry, logs the missing tool, and returns `tool not found: clarification_missing`. This return precedes both the execution-count increment and `executeByPolicy`. No generated-tool body executes in this witness. [Lookup and execution boundary](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/autopoiesis/ouroboros.go#L1131-L1167).
4. **Preserve the error through evaluation.** `ExecuteAndEvaluateWithProfile` marks feedback unsuccessful, retains the error text, evaluates and records feedback, and returns the original error. `runTool` then emits `errorMsg` with the message `tool execution failed: tool not found: clarification_missing`. The feedback path is real work; this report does not assume that the entire command has no evaluation or model cost merely because the tool body did not execute. [Evaluation wrapper](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/autopoiesis/autopoiesis_profiles.go#L43-L73), [TUI error producer](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/cmd/nerd/chat/helpers_tools.go#L118-L134).

An otherwise identical absent name without either trigger, such as `missing_tool`, is a useful negative control. Both operations fail for the same reason. Their UI dispositions should not differ because one diagnostic happens to contain a workflow word.

## Where the terminal disposition changes

The `errorMsg` case applies `strings.Contains` to the complete rendered error. This is neither a typed error check nor an exact protocol-marker check. It accepts lowercase `clarification` anywhere, including inside an identifier; its alternative accepts `USER_INPUT_REQUIRED` anywhere without requiring the colon that the question extractor recognizes. [Lexical dispatch](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/cmd/nerd/chat/model_update.go#L286-L302).

When matched, the branch clears loading and streamed state and returns a command producing `clarificationMsg` with only `Question` and empty `Options`. `extractClarificationQuestion` returns the full diagnostic when it finds no `USER_INPUT_REQUIRED:` delimiter. The missing-tool witness therefore retains its diagnostic, but receives no `Context`, `PendingIntent`, or `DeliberationID`. [Question extraction](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/cmd/nerd/chat/model_helpers.go#L214-L221).

The subsequent clarification message installs `InputModeClarification`, creates the state from those fields, changes the placeholder, adds the clarification question to history, and schedules persistence. Its renderer prefixes the diagnostic with “I need some clarification.” This is a real state transition, not merely unfortunate wording. [State transition and persistence](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/cmd/nerd/chat/model_update.go#L261-L284), [renderer](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/cmd/nerd/chat/model_handlers.go#L550-L570).

Ordinary terminal failure handling instead shows the error panel, logs a TUI error, records the error UX metric when configured, emits the chat audit error, adds a failed assistant response, and persists. The matched error skips that consumer path and instead records the clarification metric. This does **not** mean all evidence or logging disappears: the registry failure has already been logged, evaluation feedback records failure, and the clarification text itself enters history. [Normal terminal failure path](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/cmd/nerd/chat/model_errors.go#L14-L33).

## What the next submission does and does not establish

Idle Enter now invokes `handleClarificationResponse` before normal submission dispatch. That handler records a nonempty response, restores normal input mode, and announces resumption. Since the fabricated clarification has no deliberation ID, it does not resume a persisted deliberation thread. [Input dispatch](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/cmd/nerd/chat/model_key_handler.go#L253-L261), [response handler](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/cmd/nerd/chat/model_handlers.go#L427-L490).

With an initialized kernel, no staged learning candidate, and a successful clarification-fact assertion, `processClarificationResponse` uses the reply alone as `clarifiedInput`: the context is empty, and there is no pending intent to copy into `resumeIntent`. It calls `processInput` on that reply. There is no retained missing-tool execution to continue at this boundary. [Clarification processing](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/cmd/nerd/chat/model_handlers.go#L493-L546).

**History and context caveat:** this is not an assertion that all conversational context is erased or that the model must misunderstand the reply. The execution notice and displayed diagnostic remain in history. `processInput` builds perception history from the current conversation, leaving selection to perception's window and budget, and supplies it to the perception firewall or transducer. A later model could infer what happened and offer a useful recovery. That possibility is different from an explicit continuation of the failed operation, and its quality was not evaluated here. [History handoff and intent selection](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/cmd/nerd/chat/process.go#L191-L252).

No permanent deadlock, data loss, wrong eventual answer, automatic mutation, or privilege escalation is established. The immediate evidence supports a false pause, misleading disposition, changed next-input routing, and conditional human or model recovery cost. Normal policy mediation still governs any later operation. A user can submit a new explicit request; doing so should not have been required to resolve a pause that no producer actually requested.

## Preserve genuine ask user behavior

There are real ask-user semantics to retain. `VirtualStore.handleAskUser` checks cancellation and returns an `ActionResult` containing a `USER_INPUT_REQUIRED` error field, the question as output, question/options metadata, and an `awaiting_user_input` fact. Those structured fields distinguish an intentional request from an arbitrary error string. This producer alone does not prove every adapter currently carries every field end to end; implementation must trace those adapters before removing a compatibility path. [Ask-user producer](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/core/virtual_store_actions.go#L1021-L1040).

The TUI also already has a typed deliberation question carrying the original request, original intent, and deliberation ID. The response handler recognizes the ID and resumes that thread. Reuse this distinction between a real pending operation and a terminal failure; do not replace it with a larger vocabulary of diagnostic trigger words. [Typed deliberation question](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/cmd/nerd/chat/deliberation.go#L53-L55), [resume selection](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/cmd/nerd/chat/model_handlers.go#L482-L489).

The existing question-extraction unit test checks delimiter extraction and plain-text fallback. It does not establish that a terminal tool failure should become a clarification or exercise normal command entry. Keep useful formatting coverage, but place the behavioral oracle at the producer-to-UI boundary. [Extractor test](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/cmd/nerd/chat/model_helpers_test.go#L94-L104).

## Proposed contract and implementation choices

Start with the owning chat and core capability specifications. These are proposed requirements, not claims that the current code implements them:

1. **Terminal errors are data, not pause instructions.** A generic error remains terminal regardless of identifiers, provider prose, nested causes, capitalization, or protocol-looking text in its diagnostic. Rendered text must not select the workflow disposition.
2. **A pause has a declared producer and pending subject.** A typed ask-user message or typed error recognized through a structured adapter carries its question/options and identifies what is awaiting the answer. Use existing deliberation or operation identity where available. A retry suggestion after terminal failure is not itself a resumable pause.
3. **Resume exactly that pending subject.** Validate that the pending continuation is current and unsettled before accepting an answer. Preserve its original request, applicable intent and restrictions; do not reconstruct executive state from the latest diagnostic or most recent request. A missing or expired continuation receives an honest disposition and recovery instruction, not a fictional resume.
4. **Preserve real producer semantics during migration.** Inventory adapters from `ActionAskUser` and existing typed clarification producers. Translate the structured result at a known boundary, preserving options and ownership. If legacy errors need temporary compatibility, use an identifiable type or explicit origin-bound envelope; merely narrowing the same global substring check is not sufficient. Do not assume that matching the exact marker in untrusted prose establishes origin.
5. **Keep failure settlement and policy controls.** Reuse `handleTurnError` for known terminal failures and retain the synthesis lane's direct call. Preserve context cancellation, bounded diagnostics, original error causes, upstream feedback, history, and permission gates. Go transports and validates typed outcomes; existing policy decides whether proposed work may proceed. No automatic retry or extra model judgment is needed to decide whether the missing-tool error is terminal.

A minimal tool-specific change could send this producer's known terminal error directly through the terminal path, paralleling synthesis. That is a useful containment option but leaves the generic lexical admission rule available to other producers. A complete boundary repair distinguishes terminal errors from real ask-user outcomes once, while retaining compatibility deliberately. Do not make a repository-wide message-framework rewrite or a new persistence schema a prerequisite for this correction unless tracing demonstrates it is needed.

## Costs and fair evaluation

No latency, token saving, or failure-frequency estimate is claimed. Typed dispatch should not require an additional model call. The principal engineering cost is producer/adapter inventory, compatibility handling, and tests proving real pauses still resume. Carrying a small continuation identity adds bookkeeping and retention obligations; broad copies of history or tool output are unnecessary. If a stronger durable pause representation is introduced, measure serialization, hydration, expiry, and migration costs separately rather than presenting them as free consequences of removing a string match.

For a fair comparison, keep repository state, tool registry, initialization, permissions, provider/model settings, evaluator, history, world-model/CodeDOM configuration, and user-response policy matched. Compare pinned main, minimal producer containment, and the typed-boundary repair. Count the entire original command and any user-authorized recovery, including feedback evaluation, model calls, input/output tokens, persistence, human turns, and time to an accurate disposition. Do not claim savings by counting only the failed lookup and excluding recovery from the misleading prompt, or penalize the repair for recording a failure honestly.

Proposed validation must run through the ordinary input box and Enter handling, command dispatch, actual missing-tool lookup, production error wrapper, scheduled message delivery, and subsequent input dispatch. A test that injects only `errorMsg` can isolate the consumer but cannot establish producer reachability. Script dependencies where needed for determinism; do not bypass the production registry failure by manufacturing the final diagnostic.

| Case | Required observation |
|---|---|
| Missing `clarification_missing` versus missing `missing_tool` | Both remain terminal failures; no clarification state or pending continuation is invented; neither tool body executes |
| Diagnostic containing `USER_INPUT_REQUIRED`, with and without a colon | Text alone cannot acquire pause authority; original diagnostic stays available |
| Follow-up after terminal failure | Normal input dispatch remains active; an explicit new request is not consumed as an answer to a nonexistent pause |
| Real ask-user result through its production adapter | Question and options survive; the correct pending subject receives the answer once; cancellation and rejection remain effective |
| Existing deliberation pause and resume | Original intent/request/thread binding survives; ordinary options and custom replies work |
| Fixed knowledge-synthesis error, cancellation and panic | Terminal failure and answer ownership remain correct; no extra synthesis or consultation |
| Delayed or duplicate ask-user outcome, expired pending state | No unrelated request or current pause is overwritten; stale state receives an explicit disposition |
| History, audit and enabled UX metrics | Failure is presented and counted as failure; genuine clarification is counted as clarification; retained diagnostics are not mistaken for resumed authority |

Use deterministic transport/state assertions as the primary oracle. A supplementary normal-production recovery study may assess whether users or models recover from the misleading baseline prompt, with context systems enabled and the same task distribution. That study must report successful inference from history separately from a correctly bound continuation; a helpful eventual answer does not retroactively make the earlier false pause legitimate.

## Acceptance boundary

The gap is closed when the real missing-tool producer and other generic terminal producers cannot enter clarification mode solely because of diagnostic text, while genuine ask-user producers still display their questions and resume their own pending work. The existing synthesis protection, safe missing-tool rejection, policy controls, diagnostic retention, and history handoff must remain intact. Close the specification and audit entries only after the normal-entry regressions and compatibility checks have actually run; none were run for this report.
