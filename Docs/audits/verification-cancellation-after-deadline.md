# Verification cancellation after a parent deadline

## Decision and evidence boundary

Preserve independently budgeted verification, but give it an explicit cancellation connection to a still-live operation owner. A soft inference deadline and a hard owner stop are different events. Once the former expires, polling its context cannot discover the latter. An intentionally independent verifier budget is not itself a bug; the defect is that the implementation promises explicit cancellation after deadline expiry without retaining a channel capable of delivering it.

This is a source-only research proposal against the revision above, not an implemented fix or a reproduced incident. No tests, model calls, commands, or benchmarks were executed. The production witness below is conditional, with its admission requirements stated explicitly. The principal evidence is the [verification supervisor](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/internal/session/verify_outcome.go#L90-L162), rather than an assumption about observed user frequency.

## The cancellation promise cannot survive the first deadline

The helper deliberately permits verification after an already-expired parent deadline. It creates its command context from `context.Background()`, optionally adds a verifier budget, and supervises the parent separately. When the parent reports `context.Canceled`, it cancels that command context, joins the runner, and produces `VerifyCanceled`. When the parent instead reports `context.DeadlineExceeded`, it disables the parent-done arm and starts a 50 ms ticker, repeatedly checking whether the same parent's error has become `context.Canceled`. See the [entry checks and supervisor](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/internal/session/verify_outcome.go#L90-L162).

For standard Go contexts, that transition cannot happen. The context API specifies that, after `Err` first becomes non-nil, subsequent calls return the same error. The implementation's cancellation path also returns without replacing an existing error. These are a durable API contract and its supporting implementation, not a claim about codeNERD's exact installed Go runtime: [Go context contract](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/context/context.go#L110-L115), [first-error retention](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/context/context.go#L547-L558).

Production build and test budget variables currently default to zero. The older documentation's four-minute description must not be substituted for that source fact. The runners use `exec.CommandContext` and collect combined output; the test path additionally applies `processutil.NonInteractive`. Thus there need not be an independent configured verifier timeout to close this window. This finding concerns delivery of cancellation to the runner context, not whether canceling that context reliably cleans up every descendant process. See [budget defaults and runners](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/internal/session/verify_outcome.go#L38-L78).

The intended distinction is worth keeping: [verification-gate documentation](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/Docs/architecture/session/09-VERIFICATION-GATES.md#L177-L179) explicitly promises that an expired parent deadline does not abort verification while explicit cancellation does. Fixing this promise does not require imposing an arbitrary fixed timeout on all builds.

## A reachable, conditional CLI witness

The `nerd fix` command enters `runDirectAction` with `/fix`. That function first obtains an operation context from `context.Background()`, then places `signal.NotifyContext` around it for SIGINT and SIGTERM, deferring both cleanup functions. It synchronously calls `SpawnTaskObservedWithTarget`. A positive `--timeout` makes the operation context a timed context; the flag describes a whole-command limit. See [command registration](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/cmd/nerd/cmd_direct_actions.go#L44-L55), [context construction](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/cmd/nerd/cmd_direct_actions.go#L310-L319), [synchronous dispatch](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/cmd/nerd/cmd_direct_actions.go#L398), [timeout helper](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/cmd/nerd/operation_context.go#L19-L26), and [flag contract](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/cmd/nerd/main.go#L205-L208).

The normal factory [creates a JIT executor](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/internal/system/factory.go#L2697) and [exposes it on Cortex](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/internal/system/factory.go#L2931-L2937). The observed executor receives the same context and verb through the [system factory](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/internal/system/factory.go#L575-L591). The default isolated-verb list contains research, implement, refactor, and campaign—not `/fix` or `/create`. Ordinary inline selection reaches synchronous `ProcessWithIntent` on a clone; it does not gain the isolated worker's early-return behavior. See [delegation policy](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/internal/core/defaults/policy/delegation.mg#L513-L519) and [executor selection and inline invocation](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/internal/session/task_executor.go#L395-L441).

The tool loop establishes terminal verification, including a no-tool final-answer route, then dispatches build/test checks. Build verification checks its configuration, workspace, and toolchain before invoking the shared runner. These gates matter: a timeout alone does not prove admission to a running verifier. See [terminal verification](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/internal/session/executor_tools.go#L229-L236), [final-answer route](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/internal/session/executor_tools.go#L400-L402), [verification dispatch](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/internal/session/executor_tools.go#L484-L550), and [build runner admission](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/internal/session/build_verify.go#L165-L178).

A sufficient witness is therefore:

1. A user supplies a finite `--timeout`; boot succeeds with the default kernel and JIT executor.
2. An authorized write-oriented `/fix` reaches enabled post-edit verification in a valid Go workspace before the deadline.
3. The verification command remains running when that deadline becomes the parent's first terminal error.
4. An external supervisor subsequently sends SIGTERM or SIGINT to the codeNERD process itself, while the verifier has not independently terminated.

The CLI is still synchronously waiting, but the signal context cannot change its already-recorded deadline error. Moreover, Go's `NotifyContext` starts a goroutine selecting between a signal and context completion; the timed parent can end that goroutine before the later signal arrives. Signal registration remains until `stop`, suppressing the corresponding default behavior in the meantime. Merely repairing the verifier's polling loop cannot repair this upstream ownership problem. See [Go signal context implementation and stop contract](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/os/signal/signal.go#L270-L309).

A legitimately large build is sufficient to provide the pending window; no malicious fixture is necessary. This is not a universal permanent-hang claim. Normal command exit, a tool-owned timeout, or other OS termination can settle the operation. Terminal Ctrl+C often targets the entire foreground process group and can independently kill the child, unlike the PID-targeted witness. Nor is all chat cancellation broken: ordinary TUI processing uses a shutdown-derived cancelable context without adding a turn timeout, while isolated tasks have a separate wait-and-stop path. See [TUI context](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/cmd/nerd/chat/process.go#L76-L92) and [isolated wait](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/internal/session/task_executor.go#L693-L724).

## Scope and novelty

Explicit cancellation before deadline expiry works; an already-canceled parent skips subprocess admission, and a no-deadline cancelable parent remains usable for cancellation. Existing tests inspect deadline-only and cancellation-only/pre-cancellation cases separately. The inspected section does not compose deadline expiry with a later independent owner stop: [verification tests](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/internal/session/verify_outcome_test.go#L421-L483). None were run for this proposal.

A fresh source-text screen of the 92 current audit Markdown files, followed by reading adjacent audits, found no exact treatment of this frozen-error/ticker composition. The distinction is from [task terminal ownership](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/Docs/audits/task-terminal-ownership.md), [delegated failure settlement](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/Docs/audits/delegated-turn-failure-settlement.md), [side-turn ordering and cancellation ownership](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/Docs/audits/side-turn-ordering-and-cancellation-ownership.md), and [verification applicability and progressive evidence](https://github.com/theRebelliousNerd/codenerd/blob/95654a64562f02c00040ac28ca9cda4733c96fd9/Docs/audits/verification-applicability-and-progressive-evidence.md). This proposal addresses owner-to-verifier cancellation composition, not worker publication, retirement, partial-result settlement, generation ownership, or evidence freshness. Branch inventory covered current main and lane branches; older research branch names were absent. It does not establish review of every outstanding PR.

## Proposed ownership contract

**Classify lifetimes explicitly.** Separate hard owner cancellation, an explicitly hard user wall-clock budget, and genuinely soft inference/verification budgets. The advertised whole-command `--timeout` cannot silently become a soft inference deadline. Either enforce that hard boundary or deliberately revise its public contract. Regardless of that policy decision, a soft child deadline must not destroy the ability to stop its owner.

**Keep the owner alive.** Register signals against a live operation-owner root, then derive timed task children separately. Pass a typed owner-cancellation handle into every verification consumer. Do not rediscover cancellation by inspecting the expired child's `Err` or `Cause`; both retain the first terminal event. `WithoutCancel` alone also supplies no later stop channel. Preserve task metadata and the permission envelope: finishing previously authorized verification does not authorize new model calls, tools, or mutations after a deadline.

**Settle honestly.** On owner cancellation, cancel the process context, join the runner, retain available partial output, and return `VerifyCanceled`. Specify the completion/cancellation race so an already-observed command verdict remains truthful and cancellation is never reported as a pass. Preserve the existing five-valued outcome distinction, indeterminate budget expiry, and retention of known failures. Keep deterministic supervision in Go and existing Mangle completion/outcome authority, rather than introducing model-mediated cancellation decisions.

**Centralize the plumbing.** Cover native and Piggyback consumers wherever the same deadline-bearing context reaches the helper, including closure/recheck and baseline/import/vet verification helpers. Avoid a second ad hoc supervisor loop. Make signal-registration cleanup and worker joining explicit ownership obligations. Descendant-process cleanup remains a separate issue; this change must not claim to solve it merely by delivering cancellation to `CommandContext`.

| Checkable gap | Required evidence for closure |
| --- | --- |
| Owner lifetime ends with soft child | Independent owner stop still closes after the child deadline; hard user budgets retain their declared semantics. |
| Supervisor polls immutable error | Owner stop cancels runner context, joins completion, and preserves canceled outcome plus partial diagnostics. |
| Integration coverage is conditional | Real inline dispatch and each shared-helper consumer are exercised, with TUI and isolated-task controls. |

## Costs and fair evaluation plan

The design needs O(1) owner-handle/channel state per active operation and plumbing across helper callers. Its chief costs are lifetime complexity and regression risk: an incorrectly shared root could cancel siblings. It requires no extra LLM or embedding calls and no inherent token overhead. Removing the 50 ms ticker removes up to 20 scheduled ticks per second per deadline-expired verifier, but no CPU benefit has been measured. Earlier cancellation may discard a potential future verdict; that is the operator's intent, not an efficiency defect. No arbitrary default cap is proposed.

Future evaluation should first use a cooperative fake runner with channel handshakes, not sleep-dependent ordering. Cover cancellation before deadline, deadline then owner cancellation, pre-expired task then owner stop, successful completion after a soft deadline, unlimited normal completion, and explicit verifier-budget expiry. Assert runner-context cancellation, joined completion, retained diagnostics/outcomes, and no spawn for pre-canceled ownership. Exercise simultaneous completion/cancellation under the specified race rule.

Then traverse the normal `nerd fix` production path using a deterministic model double, an authorized Go edit, and a controlled verifier. Establish admission before a finite deadline, deliver a PID-targeted signal after expiry, and compare baseline with proposal. Include no-deadline, cancellation-first, process-group-signal, isolated-worker, and ordinary-TUI controls. Repeat for build/test, vet/closure, and other shared-helper consumers across native and Piggyback modes. Report POSIX and Windows signal behavior separately rather than generalizing between them.

Keep inputs, configuration, and platform fixed. Record admission through settlement, cancellation-request-to-child-done latency with p50/p95, active children and goroutines after return, peak memory, CPU, total duration, retained diagnostics, and verdict correctness. Also record model calls, tokens, and tool counts; they should not increase. A fast-stop score alone is insufficient: uncanceled controls must still verify completion, late success must not become false failure, known failure must not disappear, and no duplicate effects may be introduced. Until that evidence exists, the conclusion is a source-supported cancellation gap and a proposed repair contract—not a measured reliability or performance improvement.
