# User memory renewal and archival lifecycle

## Finding and scope

Explicit long-term preference promotion and generic cold-to-archive maintenance have an unresolved integration boundary. Reaffirming an identical remembered value updates its modification timestamp, but not the access timestamp used for archival. Normal preference hydration deliberately leaves access accounting untouched. Consequently, an old, low-access preference can leave the active tier despite successful reaffirmation or repeated hydration. Fresh hydration then misses it, while ordinary scoped forgetting cannot resolve its archived copy. This is a policy and ownership gap, not evidence that all archival is incorrect. The causal chain is visible in [promotion](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/context/memory_ops.go#L64-L92), [upsert and readers](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/store/local_cold.go#L63-L212), [archival selection](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/store/local_cold.go#L241-L326), and [forget resolution](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/context/memory_forget.go#L76-L140).

## The access clock does not express reaffirmation

When the understanding adapter recognizes a remember request with a nonempty target, it constructs a preference promotion; recognized forgetting uses the host user-memory domain. These are conditional interpretation routes, not literal slash-command guarantees. Shared promotion calls `StoreFact(op.Key, []any{op.Value}, "preference", 10)`. TUI processing invokes shared memory operations after reflection and before dreaming, and the helper reports dispositions and forget receipts. [Recognition](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/perception/understanding_adapter.go#L699-L719), [promotion](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/context/memory_ops.go#L64-L92), [ordering](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/cmd/nerd/chat/process.go#L367-L384), [helper](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/cmd/nerd/chat/process_helpers.go#L67-L79).

Cold rows are unique by `(predicate, args)` and begin with an access count of zero. A new insertion initializes `last_accessed`; a conflicting insertion updates only `fact_type`, `priority`, and `updated_at`. Exact reaffirmation therefore preserves the old access clock and count. A different value produces different arguments and is not this witness. [Schema](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/store/local_core.go#L419-L451), [upsert](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/store/local_cold.go#L63-L94).

The distinction between readers matters. Bound `LoadFacts(predicate)` updates successfully decoded rows with the current access time and increments their access counts, in chunks of 999 IDs. `LoadAllFacts` explicitly does not update access and selects only cold rows, optionally filtered by type. The control case here assumes the bound reader's accounting update succeeds; the finding does not require accounting-write failure. [Bound reader](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/store/local_cold.go#L97-L163), [bulk reader](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/store/local_cold.go#L166-L212).

`QueryAllLearned` uses that no-touch bulk reader. `HydrateLearnings` asserts preferences as `learned_preference`, subject to its store, kernel, and error guards. The session executor hydrates before observation; learned hydration occurs once per executor lifetime, alongside per-turn session hydration. The production adapter delegates to this implementation, and the TUI has its own hydration call. None of these facts establishes actual prompt use. [Query and hydration](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/core/virtual_store_predicates.go#L57-L85), [assertions](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/core/virtual_store_predicates.go#L559-L636), [executor ordering](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/session/executor.go#L1255), [hydration lifetime](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/session/executor_memory.go#L57-L83), [adapter](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/system/factory_adapters.go#L511-L524), [TUI](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/cmd/nerd/chat/process.go#L831-L837).

The existing `TestAccessTracking` definition reinforces that this distinction is intentional: it calls `LoadFacts` three times, then uses `LoadAllFacts` to inspect without incrementing the count, and expects three accesses. The definition was inspected, not run. Repair caller or domain retention policy rather than globally turning `LoadAllFacts` into a write. [Access-tracking test](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/store/archival_test.go#L153-L191).

## Maintenance is reachable but not universal

Fresh boot through `GetOrBootCortex` starts a maintenance scheduler. It waits for a 30-minute tick rather than running immediately. Maintenance configures archival after 90 days with `MaxAccessCount` five, and archived-row purging after 365 days. However, ordinary TUI shared boot calls `BootCortexWithConfig` directly; the inspected path does not establish that this direct boot starts the scheduler. It would therefore be incorrect to claim ordinary TUI use automatically archives preferences. [Boot route](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/system/factory.go#L254-L279), [scheduler start](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/system/factory.go#L363-L367), [tick](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/system/factory.go#L760-L796), [configuration](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/system/factory.go#L831-L860), [direct TUI boot](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/cmd/nerd/chat/session_shared_boot.go#L87-L90).

A concrete long-lived route nevertheless exists: CLI chat boots through `GetOrBootCortex`, uses `SessionExecutor.Process`, and waits for additional input within one runtime lifetime. This supports a sequential same-workspace witness without simultaneous SQLite writers: successfully reaffirm an old preference through TUI, close it, keep a freshly booted CLI chat runtime alive through a successful maintenance tick, then open a fresh TUI or CLI kernel. This is a source-derived scenario, not an executed reproduction. [CLI runtime](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/cmd/nerd/cmd_chat.go#L139-L165), [lifetime and input loop](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/cmd/nerd/cmd_chat.go#L193-L248).

`ArchiveOldFacts` selects by old `last_accessed` and sufficiently low `access_count`, without filtering `updated_at`, preference type, or priority. Under a write lock and transaction it inserts selected records into the archive, deletes successfully moved cold rows, and commits, with transaction and iteration errors checked. The witness requires successful movement; archival is not immediate erasure. [Archival implementation](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/store/local_cold.go#L241-L326).

More precisely, the starting preference must have `last_accessed` older than 90 days and count at most five. Exact reaffirmation and passive hydration do not disqualify it. A young row, successful bound-read refresh, count above five, different-value insertion, absent scheduler, runtime ending before a tick, or failed archival transaction breaks the corresponding witness condition. Subsequent explicit restoration or re-promotion also changes the outcome. These controls follow the [upsert and readers](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/store/local_cold.go#L63-L212), [selection](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/store/local_cold.go#L241-L326), and [restore transaction](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/store/local_cold.go#L424-L485).

## Fresh recall and scoped forgetting diverge from storage

`UserPreferences` defines long-term preferences through cold storage and calls `LoadAllFacts`. Its legacy adoption path also concerns cold rows, not archive restoration. After archival, fresh preference hydration has no cold row to read. Archive query APIs and transactional restoration exist, with restoration resetting access time and removing the archived copy, but no normal hydration fallback appeared in the bounded call-path search. This is not a claim that archived data is universally inaccessible. [User-memory store](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/store/user_memory.go#L9-L67), [archive APIs](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/store/local_cold.go#L329-L485).

Scoped user-memory forgetting resolves candidates from `UserPreferences`. No match produces `StageUnresolved`; deletion and exact kernel retraction occur only after resolving one match. An archive-only preference therefore leaves its archive copy untouched and receives an honest unresolved outcome, not a falsely successful receipt. Preserve the existing host scope, exactness, and protection against broad deletion. [Forget resolver](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/context/memory_forget.go#L76-L140).

Archival itself performs no kernel retraction, so a previously hydrated projection may survive until a fresh kernel, while the fresh kernel lacks the cold source. This describes method semantics, not a demonstrated stock-TUI live-forget incident. Later purge is a separate, conditional maintenance action based on archive age; it does not make the initial move immediate permanent loss. [Archive transaction](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/store/local_cold.go#L241-L326), [hydration assertions](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/core/virtual_store_predicates.go#L559-L636), [purge and cleanup](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/store/local_cold.go#L488-L546).

## Contract decision and bounded repair

Owners should distinguish explicit reaffirmation, passive hydration, and actual reasoning use. Decide whether explicitly remembered preferences stay active until forgotten or follow a clearly communicated per-domain expiration policy. Neither choice follows automatically from the word “long-term.” A narrow preferred repair is typed user-memory renewal, refreshing the relevant clock or adding `last_reaffirmed`, rather than changing every generic upsert's retention semantics.

If archival remains valid for user memory, semantic record identity should span active and archived copies for authorized read, list, and forget operations. Preserve bounded matching, ambiguity refusal, transactional deletion, exact live-projection settlement, and truthful partial receipts. Review already archived preferences under an explicit migration or restoration policy; do not blanket-restore or aggressively purge them. This is not a promise to erase transcripts, backups, or physical media. No new race evidence here justifies reopening generic tombstone proposals.

Avoid treating every hydration as counted use. With the current lifetime count threshold, repeated bulk hydration could eventually exempt all such rows from archival. Likewise, an unconditional archive union could enlarge kernel and prompt memory or revive intentionally expired records. If admission-based touching is chosen, define actual admission, bounded batching, journal flush and crash behavior, and lock costs. These design cautions derive from the [no-touch reader](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/store/local_cold.go#L166-L212) and [count-based archival predicate](https://github.com/theRebelliousNerd/codenerd/blob/9d26d9c3af600a5d01f904b138974e02ec7838c4/internal/store/local_cold.go#L267-L272), not measured regressions.

## Costs and future evaluation

A deterministic clock or domain-identity repair requires no extra LLM call. Its costs still need measurement: write frequency, WAL volume and locking; touching every hydrated row versus batching; cold-store growth, kernel RAM, fixpoint work and scan latency if records remain active; schema, index and migration work for per-domain policy; and ambiguous legacy classification. Cross-tier lookup also introduces query, duplicate-identity, deletion-transaction and live-cache-generation work. Restoration creates operator burden. Prefer aggregate observability over duplicating user text. No numerical latency or savings claim is warranted, and more retained memory is not automatically better.

All proposed evaluations below are **UNRUN**. Use a fixed fixture and controlled clock, not a real 90-day wait, through the actual producer adapter, shared memory operations, store, real hydration, maintenance, fresh kernel, and exact forget resolver. Compare before and after with identical facts, time and memory budgets. Separate deterministic lifecycle policy from stock natural-language recognition accuracy; successful classification can be a fixture precondition.

Cover reaffirmation-only, hydration-only, successful bound-read refresh, young rows, count six, changed values, short CLI lifetime, direct TUI boot, transaction failure, restoration and re-promotion. Exercise the batching branch separately. Check archive-only forgetting against today's honest unresolved receipt and the chosen replacement contract; multiple values and ambiguous matches must not trigger broad deletion or affect unrelated executive facts or constraints.

Include close/reopen ordering, maintenance after initial hydration, idempotent restoration and deletion, and, only if later execution is authorized, races within one single-writer process. Measure SQL operations, WAL and lock behavior, storage and RAM, actual context size, retention errors, and p50/p95 latency. End-to-end prompt delivery and downstream quality require separate evaluation before claiming behavioral impact. The acceptance decision should establish a coherent user-memory lifecycle, not merely maximize retention.
