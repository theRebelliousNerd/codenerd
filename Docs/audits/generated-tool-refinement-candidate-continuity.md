# Generated-tool refinement needs a source-bound proposal owner

## Finding and scope

At main [`388205138ba6d47c1cff0c5e97c896dfa642a391`](https://github.com/theRebelliousNerd/codenerd/commit/388205138ba6d47c1cff0c5e97c896dfa642a391), automatic post-execution refinement is wired far enough to purchase a JIT model completion, but not far enough to preserve or govern its proposed improvement. The factory calls `RefineTool(ctx, toolName, "")`: it supplies no original code and discards the returned `RefinementResult`. The orchestrator forwards that empty source unchanged. The refiner builds and parses a proposal; it does not compile, register, publish, or otherwise adopt that proposal. A successful return therefore ends this automatic path without a retained candidate or explicit adoption/rejection/defer decision.

This is a **production integration gap at the automatic caller**, not a claim that a proposal-producing API should secretly deploy code. Not applying unvalidated model output is the safe behavior. The missing contract is ownership: either automatically requested proposals must enter a bounded, source/version-bound review and admission workflow, or automatic proposal generation should be explicitly deferred when no such owner is available.

**Review basis:** static source inspection only, 2026-10-30; no builds, tests, model inference, runtime probes, or repository modifications. Main, repository guidance, the audit queue, and active research branches were checked first. Main and the implementation queue were unchanged; `research-main-20261030-1147` was [`921628ea7b1af635cb9c99d4055f6feed2a5efeb`](https://github.com/theRebelliousNerd/codenerd/commit/921628ea7b1af635cb9c99d4055f6feed2a5efeb), four documentation commits ahead of main. Independent static challenge corroborated the narrow caller/source/proposal-disposition mechanism. The scenarios and evaluations below are proposed, not executed.

The source-level distinction is important: `Success` on `RefinementResult` indicates that the refinement response was accepted by its parser. It does not establish compilation, safety, behavioral improvement, registry replacement, or even a retained candidate. The result's `ExpectedGain` is model-supplied, not measured improvement. The existing log “Tool refined successfully with JIT” must not be interpreted as evidence that the serving tool changed.

## Narrow, normally reachable witness

The following is a source-derived scenario, not a reproduced incident:

1. A normal boot has an admitted generated tool, a healthy kernel, working durable feedback storage, and an enabled, ready JIT assembler. Ordinary catalog, permission, binary identity, and preflight checks still apply.
2. Three distinct calls to that tool start and genuinely fail. Their terminal outcomes are durably recorded. Failed execution receives quality `0.1` in the profile-aware evaluator before any optional quality judgment; the non-profile evaluator has the same early failure treatment. With these as the tool's initial three outcomes, its average is 0.1, published as percentage 10, so the real policy can derive `tool_needs_refinement` without a fabricated kernel answer. See [`quality.go:221–239`](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/autopoiesis/quality.go#L221-L239), [`quality.go:269–287`](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/autopoiesis/quality.go#L269-L287), and the policy links above.
3. Once the factory's background check sees that eligibility, it supplies only the tool name plus the empty source argument to `RefineTool`. Recent outcomes still reach the request; the gap is not missing all feedback.
4. The model returns a well-formed, nonempty proposed replacement. The refiner returns it successfully, but the factory discards it. No candidate owner receives the returned source or test suggestions; no governed admission decision or serving-tool replacement occurs through this path.

This does not require a second process, a short lease, a crash, failed persistence, or a durable replay ambiguity. It also does not show that a model cannot produce useful code from feedback alone. It shows that the automatic request lacks the exact source it purports to refine, and that even a useful response has no disposition in the inspected caller.

If JIT is unavailable, policy is ineligible, the context is canceled, or the model call fails, this successful-proposal witness does not occur. Current `Refine` has **no legacy prompt fallback**; the factory context helper's “legacy or JIT” comment and older architecture descriptions do not override the implementation. Later distinct executions may request another proposal while policy remains eligible, but this review makes no claim of an infinite loop, a particular request frequency, unbounded simultaneous model calls, or measured spend.

## Controls and working adjacent paths that must be preserved

- **Durability and effect separation:** recording is attempted only after a process starts, and this automatic trigger follows successful durable feedback. Live duplicate calls share/replay their terminal receipt rather than executing the binary again. Feedback retry is separate from effect execution. Do not obtain refinement evidence by rerunning an already-started tool. See [`factory_tool_executor.go:90–160`](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/system/factory_tool_executor.go#L90-L160) and [`182–225`](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/system/factory_tool_executor.go#L182-L225).
- **Lifetime and budget ownership:** closed/canceled adapters reject refinement admission; the goroutine belongs to the adapter's wait group, observes its lifetime, and receives the configured per-call timeout when positive. Preserve these controls, rather than detaching a new adoption worker or introducing a separate unbounded model budget.
- **The separate Ouroboros repair loop works differently:** its safety-retry branch calls `RegenerateWithFeedback` with the previous generated tool, and that method passes `previousTool.Code` to generation. The returned generated tool re-enters the loop's checks. It does **not** consume `RefinementResult` from this post-execution path. Credit [`ouroboros.go:452–524`](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/autopoiesis/ouroboros.go#L452-L524) and [`tool_generation.go:141–220`](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/autopoiesis/tool_generation.go#L141-L220); do not collapse the two feedback loops into one.
- **Existing publication is not a raw overwrite:** `commitTool` acquires per-tool coordination, snapshots the source, tests, binary and identity, writes and compiles, registers only after compilation, and restores snapshots on failures. Any eventual candidate admission must preserve these protections, workspace/protocol identity, and existing execution authority. See [`ouroboros.go:851–925`](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/autopoiesis/ouroboros.go#L851-L925).
- **An existing code-admission method is not a drop-in refinement contract:** `GenerateToolFromCode` already performs purpose/duplicate checks, safety checking, and coordinated commit. Its duplicate check can intentionally refuse a purpose already served by an existing tool. A replacement workflow needs an explicit, version-bound replacement decision; do not blank the purpose, disable the check, or call a low-level writer to force a proposal through. Nor should this method be described as having every stage of the full generation loop. See [`ouroboros.go:1337–1423`](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/autopoiesis/ouroboros.go#L1337-L1423).
- **Other learning consumers remain useful:** recording refreshes active generation learning context and asserts kernel facts. The dropped proposal does not imply that execution feedback is entirely unused.

## A bounded contract for completing the handoff

Choose an explicit product policy: reviewable proposals only, or policy-authorized validated replacement. Both are legitimate. Automatic application of model output is not the required fix.

1. **Resolve and bind the source before paying for a proposal.** Obtain the current tool's source from a trusted host-side source of record, with a bounded size and a digest tied to the registered tool identity/version and workspace. Distinguish a missing source, a source/identity mismatch, and an intentionally source-less operation. Do not infer original source from output or silently pass an empty placeholder. If source cannot be established, report/defer that refinement with a reason.
2. **Give each admitted proposal an owner.** Carry a candidate ID, base tool identity and source digest, relevant execution/evidence IDs, prompt/model provenance, candidate digest, and disposition. Retain the proposed code in a bounded quarantined artifact store or deliver it to a defined review surface. A log line alone is not a handoff. If there is no consumer, stop automatically purchasing these proposals and expose that refinement is unavailable/deferred.
3. **Make states honest.** Distinguish eligible, deferred, proposal requested, proposal generated, rejected, superseded, admitted, and published. Do not report a parser-success proposal as an improved serving tool. Generated test cases and expected gain are untrusted suggestions, not safety or quality certificates.
4. **Use governed replacement admission.** If a person or policy approves a candidate, run the applicable safety, purpose, compilation/testing, and evaluation gates before publication. Express that it replaces this exact existing tool version. Preserve the existing commit rollback and per-tool coordination. Recheck the base identity immediately before replacement; an intervening legitimate update must supersede or rebase the candidate rather than be silently overwritten. Holding a tool lock across model generation is not a suitable substitute for a version check.
5. **Bound demand and retention separately.** Coalesce equivalent pending requests by tool/base version and evidence cohort, preserve legitimate new evidence, cap pending candidate bytes/count/age, and maintain explicit terminal dispositions. These are proposed admission protections, not an assertion that all current calls are concurrently unbounded. Avoid introducing another indefinite full-body history while solving this continuity gap.
6. **Keep cancellation and outcomes independent.** A canceled/deferred proposal must not change the recorded execution outcome, replay its effect, or lose the existing durable acknowledgment. Shutdown must join any admitted proposal or publication activity under an explicit owner, and failed publication must leave the prior tool usable under the existing rollback contract.

A low-cost first increment is explicit deferral plus truthful status when no proposal consumer exists. A richer increment is a quarantined reviewable candidate. Automatic validated replacement is a larger product and safety commitment and should be evaluated separately.

## Cost and operational trade-offs

The present path conditionally spends prompt assembly and one completion on a result that its caller discards. The amount and frequency of that cost were not measured. Supplying the original source increases prompt bytes and potentially latency; cap source/evidence inputs and count them inside the existing request budget rather than treating source as free context.

A candidate store adds disk usage, lifecycle/migration work, review noise, and potential exposure of generated source and execution evidence. Retain bounded references where possible and preserve provenance without indefinitely duplicating full feedback bodies. A queued review path can improve auditability but does not itself improve tool behavior. Full validation/replacement adds compiler, test, sandbox and optional judgment costs, and may require more user latency or background capacity. Coalescing can reduce duplicate work but must not permanently suppress a new base version or materially new evidence.

The main benefit to establish is not a speculative percentage quality gain. It is that every purchased automatic proposal has the correct base source and a visible terminal disposition, with a safe path to adoption when authorized. A decision to reject or defer can be the correct outcome.

## Fair evaluation plan — not run

1. **Reach the real automatic boundary.** Use the real factory/VirtualStore generated route and real policy. Supply three distinct, durably recorded started failures for one tool; do not force `tool_needs_refinement` in a fake kernel. Verify the threshold and enabled JIT prerequisites. A deterministic model double is appropriate for the proposal bytes, provided the normal policy and handoff are not replaced by direct helper calls.
2. **Inspect the exact source handoff.** Assert that the request contains the admitted tool's source and matching base digest, not merely a name or a nonempty placeholder. Cover unavailable, oversized, and mismatched source with explicit deferral and no unauthorized completion or replacement.
3. **Prove candidate ownership before deployment.** Return a valid distinct candidate and assert a retained/reviewable artifact plus disposition. In proposal-only mode, verify the existing source, binary, identity and registry remain unchanged. Reject malformed/empty proposals explicitly. Check observability separates generated from published.
4. **Exercise an authorized replacement end to end.** Only in a separately authorized evaluation, carry an approved candidate through the intended gates and existing commit boundary, then resolve/execute the new registered version. Verify failed safety checks, compile/tests, or registration preserve old behavior and artifacts. A returned `Success` flag or changed `.go` file alone is insufficient evidence.
5. **Challenge stale bases and budgets.** Replace the original tool while a proposal is outstanding; ensure stale publication is refused or explicitly rebased. Exercise repeated evidence, new evidence, another tool, queue limits, retention, per-call cancellation, and Cortex shutdown. Confirm coalescing does not serialize unrelated tools or create a second model budget.
6. **Protect feedback and identity controls.** Preserve one recorded outcome per admitted execution identity, feedback-only retry without re-execution, pre-start refusal semantics, pinned workspace/protocol identity, and rollback guarantees. Cover failed durability and disabled JIT as negative controls, not as proof that the successful-proposal path is unreachable.
7. **Measure fairly.** Compare current proposal-only/discard behavior, explicit deferral, retained-review proposals, and governed adoption separately. Track completion count/tokens, candidate bytes and wait time, disposition coverage, stale-candidate refusal, gate rejection rates, and measured task outcomes after authorized adoption. Do not substitute the model's expected gain for independently observed outcomes.

The existing [`TestGeneratedFactoryCortexCloseJoinsRefinement`](https://github.com/theRebelliousNerd/codenerd/blob/388205138ba6d47c1cff0c5e97c896dfa642a391/internal/system/factory_generated_feedback_test.go#L400-L485) is valuable: it installs a ready assembler, forces the eligibility query through a kernel wrapper, blocks the model, and checks cancellation/join. It does not establish real eligibility, original-source delivery, proposal ownership, or adoption. Refiner unit tests that supply source and inspect a returned result establish the proposal API, not the factory's consumption of it. Retain those tests and add the missing boundaries rather than weakening them.

**Acceptance boundary:** an eligible automatic request either declines with an explicit bounded reason, or generates from the identified current source and hands its proposal to a named, observable owner. A serving-tool change is claimed only after separately authorized, validated, version-safe publication. Nothing in this report calls for automatically applying arbitrary model output.
