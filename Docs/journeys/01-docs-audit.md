**What the original bet (`architecture.md`, `implementation-guide.md`) promised**, five to ten bullets with file:line, judged rather than restored per the architect's framing:

1. A strict LLM/Mangle role split with the LLM barred from planning/memory/self-correction — `.codex/skills/codenerd-builder/references/architecture.md:7-22` ("Current AI agents make a fundamental mistake... codeNERD separates concerns"). This premise is intact in the live `CLAUDE.md` North Star almost verbatim.
2. A "Hollow Kernel" that treats a 10-million-row vector DB and a local variable identically via Virtual Predicates — `architecture.md:46-55`. The live corpus (`Docs/architecture/mcp/`, `Docs/architecture/store/`) still uses "virtual predicate" language, so this survived as a name but the doc never specifies the contract of one (see Section 4).
3. A four-phase OODA loop with named fact shapes at each phase (`observation/3`, `next_action`, `abductive_hypothesis`, `delegate_task`, `execution_result`) — `architecture.md:59-91`. The live Working Map (`CLAUDE.md`) keeps "Observe -> Orient -> Decide -> Act" as a Quick Reference bullet but the specific fact names in the original doc are not the ones the live schemas use (see Section 3 sample #1).
4. Context-Directed Spreading Activation as the explicit alternative to vector RAG, with a stated formula and provenance requirement — `architecture.md:93-125`. The live `Docs/architecture/context/` corpus documents a "9-component scoring/ranking" system (`INDEX.md:12`) — a different mechanism under the same "spreading activation" name; whether the formula in `architecture.md:108` corresponds to any live function is unverified (candidate for Section 3).
5. A steganographic "Piggyback Protocol" with a fixed JSON envelope (`surface_response` / `control_packet` / `mangle_updates` / `memory_operations` / `abductive_hypothesis`) — `architecture.md:182-212`, and a target compression ratio of >100:1. `Docs/architecture/articulation/` is described as owning exactly this ("Piggyback envelope & prompt assembly" — `INDEX.md:5`), so this promise has a direct current-day address; the 100:1 ratio claim is unverified.
6. Autopoiesis via Inductive Logic Programming with a named Grey-Goo-prevention sandboxing step — `architecture.md:163-181`. Now `internal/autopoiesis/` (Ouroboros), one of the largest live corpora (28 files) — heavily built out relative to the original two paragraphs.
7. A project layout with single files per concern — `internal/core/kernel.go`, `internal/core/virtual_store.go`, `internal/core/shard_manager.go`, `internal/mangle/{schemas,policy,coder,tester,reviewer}.gl` — `implementation-guide.md:5-57`. None of this survives structurally: live `internal/core/kernel.go` is "a package marker; implementation is split across `kernel_*.go`" (root `CLAUDE.md` Working Map), Mangle files use `.mg` not `.gl`, and policy lives in a "modular Mangle policy corpus" (`internal/core/defaults/policy/`) rather than one `policy.gl`. The original bet's file-level structure was never a durable contract — it was rewritten wholesale, and nothing in the corpus marks that as an intentional break versus drift.
8. A single `RealKernel` struct owning facts + a Mangle `factstore.FactStore` directly, with an `evaluate()` method rebuilding the store from a Go slice every cycle — `implementation-guide.md:82-124`. This concrete mechanism (rebuild-from-slice each eval) is exactly the kind of seam-relevant behavioral claim that Section 3 checks against current `internal/core/kernel_*.go`.
9. `internal/store/local.go` (SQLite) and `internal/store/learning.go` (Autopoiesis storage) as the entire persistence layer — `implementation-guide.md:43-45`. Live `internal/store/` has 26 files across vector/graph/cold/session/world/atoms/traces/learnings/tools/corpora tiers (`INDEX.md:47`) — the two-file sketch never described a `prompt_atoms` table, its writers, or its column set, because at design time there was no such table to describe.

None of the nine promises above states a cross-component contract (a shared name with an agreed shape on both sides). Every one is a single mechanism described from one vantage point — which is the pattern Section 4 tests directly.

### Pattern across all four

Every seam has the same shape: each side is a single package's concern, documented once, by the corpus that owns that package, using only that package's symbols. The corpus-authoring rule itself (`Docs/architecture/AGENTS.md`) never asks a writer to also describe the *other* endpoint of a name a package exposes to a caller in a different package — "one writer owns a corpus" (`AGENTS.md:28`) is enforced as a non-overlap rule, not paired with any rule that a relationship crossing that boundary gets written down somewhere third. There is no third place. A seam has no home by construction, not by neglect on any one writer's part.

## 5. Verdict

The architect's question was whether the codebase "was tore up from the floor up" because of an absence of good architectural documents. The evidence above answers: **not absence — orientation.** There are 972 files across 43 corpora, a canonical 18-document-per-package standard, claim-labeling rules, a validator script, and a rebuild journal. Measured against "do good architectural documents exist," the honest answer is yes, extensively, for exactly one shape of question: "what does package X do." Measured against "would any existing document have prevented the eleven 2026-09-17/18 defects," the answer is no, and Section 4 shows why for all four sampled seams, not just plausibly but with the exact grep run and the exact zero-result count.

Three candidate explanations were in play; the evidence discriminates between them:

1. **"Docs were absent."** False. The corpus is large, recent (newest architecture file 2026-09-17, same day as the boot-guard bug it failed to prevent), and structurally rigorous by its own standard (claim labels, path#symbol citations, a validator). Absence is not the failure mode.
2. **"Docs were vertical — one package at a time — so seams had no home."** True, and this is the dominant explanation. Every one of the four seams traced in Section 4 is a case of two packages each documenting their own half of a shared name, with zero cross-references. This is not an accident of any one writer's diligence: the production process (Section 2 — 37 subagents, one per `internal/<pkg>`, dispatched in parallel batches, each told to overwrite its own directory) *structurally cannot* produce a document describing a relationship between two packages, because no agent in that wave ever held both sides in context at once, and the authoring rule that resulted (`AGENTS.md:28`, "one writer owns a corpus... serialize shared portfolio, index, validator, and ledger edits") formalizes non-overlap as a virtue with no paired rule for where a cross-cutting relationship goes. The `INDEX.md:3` claim "1:1 with every `internal/*` package" is the tell: a corpus assigned to match the package tree inherits the package tree's blindness to the edges between packages — and even inherits gaps in the tree itself (Sample #11: a nested package, `internal/core/shards`, fell into neither its outer package's corpus nor its logical sibling's).
3. **"Docs existed but were wrong."** Also true, as a secondary finding, and worse than simple staleness in one case: Section 3 sample #1 (`store/00-ALIGNMENT-VISION-REVIEW.md:41`) didn't just fail to document the `prompt_atoms` seam — it explicitly claimed the seam's gap was "fixed in this rebuild," which was false at the time it was written and stayed false for two months until a live re-embed run surfaced 914 NULL rows. A document that asserts a cross-package contract is settled, without stating what the contract is, is worse than silence: it tells the next reader not to look.

The mechanism is now specific enough to name without hedging: **the documentation process is isomorphic to the package tree, and seams are not packages.** A boot guard shared by two structs in two packages, a table written by five files in two packages, a task string built one way in `cmd/` and forwarded another way in `internal/system`, and a result struct whose meaning is decided by a `strings.Contains` call three packages away from its declaration — none of these has an address in a corpus keyed one-to-one on `internal/<pkg>`. They were never going to. The fix is not "write more docs" or "review the docs harder" — the fix is a document *type* that is keyed on the seam, not the package, so that the question "what must be true on both sides of this name" has somewhere to be answered once, checked mechanically, and updated by whichever side changes.

## 6. What the journey corpus must contain

The package-keyed corpus (`Docs/architecture/`) is not wrong to keep — it answers "what does this package do" well and should stay the front door for that question. What's missing is a second axis, keyed on the seam rather than the package, plus mechanical checks that make a seam document fail loudly when the code drifts from it (the way a stale package doc currently does not).

### New artifact types (concrete)

1. **A contract registry, one file per seam, keyed by the shared name — not the package.** Format: `Docs/architecture/_contracts/<name>.md`, one file per shared symbol/table/string-format that crosses a package boundary, containing: the exact identifier (`DisableBootGuard`, `prompt_atoms`, `TaskRequest.Task`, `ShardResult.Result`), every struct/table/function on both sides with `path:line`, the invariant that must hold across the boundary (e.g. "a database opened by either `internal/prompt` or `internal/store` must have exactly these N columns, in this order, checked by `TestPromptAtomsSchemaMatchesAcrossPackages`"), and a **required "who changes this" list** naming every file that must be touched together. This directly replaces the failed attempt in `store/00-ALIGNMENT-VISION-REVIEW.md:41`, which named a seam but not its contract. First four entries, seeded from this audit: `boot-guard.md` (VirtualStore vs ExecutivePolicyShard vs ShardManager bridge), `prompt-atoms-schema.md` (internal/prompt vs internal/store column sets and writers), `task-string-shape.md` (delegation.go vs factory.go vs work_steps.go), `shard-result-status.md` (types.ShardResult vs process_continuation.go's substring inference vs internal/session's unrelated same-named "hollow success").
2. **A predicate/writer map generated from the running kernel, not hand-maintained prose.** `nerd world predicates` (or an equivalent introspection command against `internal/core`) can enumerate every Mangle predicate and, cross-referenced with a grep-generated writer list per Go package, produce a table of `predicate/table/struct -> [writer file:line, …]`. Where a name has writers in more than one top-level package, that row *is* a seam and gets a contract-registry entry automatically flagged as required. This is the concrete mechanism for "the harness decides, not the model's discretion" (root `CLAUDE.md`, The Vision) applied to documentation itself: the kernel's own fact space tells you where the corpus has a gap, instead of a subagent's package-scoped guess.
3. **Per-journey-stage tables** (what this `01-docs-audit.md` and its sibling `00-journey-map.md` are already doing) — kept as the narrative layer that explains *why* a seam matters to a user-visible outcome, with the contract registry as the normative layer underneath it that a test can check.
4. **Invariant tests, one per contract-registry entry, run in CI, named for the seam.** The four defects fixed 2026-09-17/18 already show the pattern in miniature (`c1c50cf9`'s three tests replacing one that "asserted the buggy behaviour by name"; `94e8f7ae`'s and `71748955`'s schema tests). The missing piece is that these tests currently exist *after* a bug is found, per-fix, not *before*, per-contract. A contract-registry entry without a linked test is incomplete by definition — the registry format should require a test file:line or say explicitly "no test yet, see TODO.md#<n>."
