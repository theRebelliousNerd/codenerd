## 1. The window, assembled

### The compile pipeline (`internal/prompt/compiler.go`)

`JITPromptCompiler.compile` (`internal/prompt/compiler.go:582-922`) is the single entry point for both the interactive chat turn and a delegated shard turn — both go through the same `Compile(ctx, cc *CompilationContext)` (`compiler.go:574-580`); the caller distinguishes itself only via fields on `CompilationContext` (`ShardID`, `ShardType`, `IntentVerb`, `OperationalMode`). Steps, in order:

1. **Cache check** (`compiler.go:622-634`) — keyed by `cc.Hash()`; a hit returns a shallow copy (`privateResult`, `compiler.go:325-336`) with no re-compilation. A `singleflight.Group` (`compiler.go:636`) collapses concurrent identical compiles.
2. **Step 1 — assert context facts to kernel** (`compiler.go:670-683`): `cc.ToContextFacts()` is asserted via `AssertBatch` so `jit_compiler.mg` / `policy/jit_selection.mg` rules can boost atoms matching the live turn. This is the one point where the *user's current turn* becomes Mangle-queryable before selection.
3. **Step 1.5 — collect candidate atoms, concurrently, from 4+1 sources** (`compiler.go:685-756`, `sourceBreakdown` struct at `1159-1165`, `collectAtomsWithStats` at `1167-1255`):
   - `embedded` — compiled-in corpus, canonical; wins ID collisions over every later source (`compiler.go:1185-1222`).
   - `project` — `.nerd/prompts/corpus.db` (per field comment `compiler.go:348`).
   - `shard` — per-shard-type DB (`compiler.go:351-352`, keyed by `shardDBKey(cc.ShardID)`).
   - `evolved` — System Prompt Learning (`collectEvolvedAtoms`, referenced `compiler.go:1246`).
   - `strategy` — learned-strategy provider (`collectStrategyAtoms`, `compiler.go:1252`), added last so it never shadows a built-in ID.
   - Plus two more collected in parallel via `errgroup`: **kernel-injected atoms** (`collectKernelInjectedAtoms`, `compiler.go:1053-1156` — see below) and **semantic knowledge atoms** / **learning atoms** (`collectKnowledgeAtoms`, `collectLearningAtoms`, `compiler.go:718-727`).
   - The exact debug log line is `"Collected %d candidate atoms (embedded=%d, project=%d, shard=%d, evolved=%d, strategy=%d) in %dms"` (`compiler.go:760-764`) — this is the literal source of the "project=0 shard=0 evolved=0" figures referenced in the assignment; see Section 2 for why they read zero.
4. **Step 2 — select** (`compiler.go:766-784`): `c.selector.selectAtomsWithTimingKernel` — Mangle rules + vector search combined (detailed in Section 2).
5. **Step 3 — resolve** (`compiler.go:786-797`): `c.resolver.Resolve(scored)` — dependency-aware topological ordering (Go code, detailed below).
6. **Step 4 — fit token budget** (`compiler.go:799-822`): `budgetMgr.Fit(ordered, budget)`; budget = `cc.AvailableTokens()` or `config.DefaultTokenBudget` (200000 default, `compiler.go:491`) if unset.
7. **Step 5 — assemble** (`compiler.go:824-829`): `c.assembler.Assemble(fitted, cc)` (detailed below).
8. **Step 5b — enforce assembled budget** (`compiler.go:831-843`): a *second*, post-hoc token check, because template placeholders like `{{available_specialists}}` can expand past what `Fit` charged per-atom — the code comment states this overshoot used to be "detected in `logCompilationStats` and then shipped anyway" (`compiler.go:836-839`), i.e. a real historical seam, now closed by `enforceAssembledBudget`.
9. Result cached (LRU, `cacheLimit=1000`, `compiler.go:514`, evicted from the back on overflow `887-899`).

### Ordering — decided by a Go constant, not the kernel

`internal/prompt/assembler.go`'s `FinalAssembler.Assemble` (`assembler.go:120-236`) determines the **macro-order** (which category block comes first) via `defaultCategoryOrder()` (`assembler.go:50-95`) — a **hardcoded Go slice literal**, explicitly commented: *"Order is extremely important for Prefix Caching: static categories first (Head), highly dynamic JIT context last (Tail)"* (`assembler.go:51-52`). The four tiers, verbatim from the comment structure:
- Level 0 "Core Identity" (identity, safety, protocol, hallucination, methodology, capability)
- Level 1 "Stack & Knowledge" (language, framework, domain, knowledge)
- Level 2 "Goal Context" (campaign, northstar, init, build_layer, ouroboros, autopoiesis)
- Level 3 "Mode Context" (reviewer, eval, exemplar)
- Level 4 "JIT Working Memory" — **the tail** — intent, world_state, system, context (`assembler.go:82-94`)

`CategoryContext` is deliberately last — comment: *"Context stays last: the tail position is pinned by `TestDefaultCategoryOrder`"* (`assembler.go:89-90`). This is a **Go-constant decision enforced by a Go unit test**, not a Mangle predicate or config value — nothing in `.mg` policy chooses category placement.

Within a category, **micro-order** comes from `internal/prompt/resolver.go`'s `DependencyResolver.Resolve` (`resolver.go:48-135`): a Kahn's-algorithm topological sort (`topologicalSort`, `resolver.go:166-272`) that respects `Atom.DependsOn` edges, tie-broken by `scoredPeerLess` (`resolver.go:143-162`): mandatory-first, then `Combined` score (NaN-safe), then declared `Priority`, then atom ID alphabetically. The score itself comes from the selector (Mangle + vector, Section 2), but the sort/placement logic executing on that score is plain Go, not a kernel query. Conflict handling, by contrast, **was** moved into Mangle: resolver.go's own comment says conflict detection "is now Mangle's: atoms carry `ConflictsWith`, `selector.go` feeds it to `atom_conflicts()` in `jit_compiler.mg`, and the kernel resolves conflicts during selection rather than after" (`resolver.go:325-330`) — leaving `DependencyError{Type: DependencyErrorConflict}` and `CycleIDs` as unreachable/dead branches (`resolver.go:319-336`, confirmed by comment "which is why the dark-field gate reports both fields").

Inside a category, atoms join with `atomSeparator` ("\n\n" default, `assembler.go:44-45`); categories join with `sectionSeparator` ("\n\n"); section headers are **off by default** (`addSectionHeaders: false`, `assembler.go:43`) "for cleaner prompts". `{{...}}` template placeholders (`{{available_specialists}}`, `{{available_tools}}`, `{{token_budget}}`, `{{world_states}}`, etc. — `assembler.go:340-443`) are expanded as a final pass over the joined string, which is exactly the mechanism that can blow the per-atom budget noted in Step 5b above.

### Kernel-injected context atoms (the spreading-activation seam)

`collectKernelInjectedAtoms` (`compiler.go:1053-1156`) queries two live Mangle predicates directly — `injectable_context` and `specialist_knowledge` — and turns matching rows (filtered by shard-ID match, `matchesShard`, `compiler.go:1058-1071`) into two synthetic, **always-mandatory** atoms:
- `kernel/context/<hash>` (Category `Context`, `Priority=95`) — rendered by `renderKernelContextBlock` (`compiler.go:1034-1051`), header literally `"// KERNEL-INJECTED CONTEXT (from spreading activation)"` (`compiler.go:1036`) — i.e., the compiler's own naming confirms this is where spreading-activation output (Section 3) surfaces in the prompt, if anything asserts `injectable_context` facts.
- `kernel/knowledge/<hash>` (Category `Knowledge`, `Priority=90`) — specialist-knowledge blocks.

Both are hard-capped rather than left to the budget manager, because — per the code comment (`compiler.go:984-999`) — being `IsMandatory=true` means `budget.Fit` never sheds them incrementally, only rejects the *entire* merged atom if it alone exceeds the whole budget, which previously caused the northstar block to vanish silently on growth. Caps: `maxKernelContextRows=60`, `maxKernelContextRowChars=1024`, `maxKernelInjectedAtomChars=16384` (~4k tokens), `maxSpecialistKnowledgeBlocks=12`, `maxSpecialistTopicChars=200`, `maxSpecialistBlockChars=4096` (`compiler.go:1000-1029`). Truncation is never silent: `TruncationNotice(shown, len(rows), "...")` (`compiler.go:1046-1048`, `1141-1143`) appends an explicit "N of M shown" marker — this is the one place in the pipeline confirmed to honor the repo's "never silently truncate" rule end-to-end (see Section 5 for where that rule is *not* honored).

**Partial answer to "which subsystem asserts `injectable_context`", found independently of the background agent**: `internal/core/defaults/policy/prompt_context.mg` ("Section 41 of Cortex Executive Policy") is a substantial, genuinely-derived producer. It defines `shard_context_atom(ShardID, Content, Relevance)` from multiple weighted sources — intent match (90), specialist knowledge (80), high-scoring reflection trace recall (85, or 90 for past failures), learned preferences (75), campaign constraints (70), learned exemplars (60), tool descriptions (65), successful trace patterns (50) — each a real join against a distinct EDB predicate (`prompt_context.mg:25-76`), then derives `injectable_context(ShardID, Atom) :- shard_context_atom(ShardID, Atom, Relevance), Relevance > 50` (`prompt_context.mg:80-83`). This is a genuine, non-trivial instance of the vision's "kernel decides what enters the window": a relevance-scored fusion of five-plus distinct evidence sources into one predicate, computed entirely in Mangle. Full trace, including a significant wiring gap found in the same file, in Section 3 (dispatched agent's territory) and Section 8.

### A second, entirely unwired activation channel: `CompilationContext.ActivatedFacts`

Separate from the `injectable_context`/`specialist_knowledge` route above, `CompilationContext` itself carries a field that was clearly built to be the direct bridge from spreading-activation scores to atom selection — and is, by its own code comment, **inert**: `ActivatedFacts map[string]float64` (`internal/prompt/context.go:225-255`, "maps fact string representation to activation score (0.0-1.0), intended to boost atoms related to highly-activated facts") and its companion `ActivationThreshold float64` (`context.go:257-260`, default `0.5`, `DefaultCompilationContext` at `context.go:295`). The comment states, in full precision, why:

1. **No schema relates facts to atoms.** Every selector dimension on `PromptAtom` is a *context* dimension (operational mode, campaign phase, intent verb, shard type, language, framework, model, provider, world state) — none is fact-shaped, so "boost atoms related to hot facts" has no defined meaning in the corpus schema today. The comment is explicit that inventing one (e.g., text-matching a fact's predicate name against atom content) "is a design decision, not a wiring task" (`context.go:240-243`).
2. **It would silently defeat the prompt cache.** `ActivatedFacts` is part of `CompilationContext.Hash()` (the prompt-cache key); since activation scores are intent-dependent and move every turn, populating this map with live scores would give every compile a unique cache key, turning the LRU cache in `compiler.go` (Section 1) permanently cold — described as a regression that "would show up weeks later as 'the agent got slow' rather than as anything traceable to this field" (`context.go:245-250`). A real test, `TestActivatedFactsWouldDefeatThePromptCache`, pins this so whoever wires the field hits the cost immediately rather than in production.

Both fields exist, are typed correctly, are covered by tests protecting *against* their own naive use — and are simply never written to by any production code path. This is the sharpest concrete illustration in the whole compiler of the gap between the vision ("the kernel has the math to hand the LLM what it needs") and the shipped mechanism: the field the architecture clearly anticipated for exactly that purpose is present, empty, and intentionally so pending a design decision that has not yet been made. See Section 7/8.

### The chat-turn entry point (`internal/articulation/prompt_assembler.go`)

`PromptAssembler.AssembleSystemPrompt` (`prompt_assembler.go:367-519`) is the top-level function that decides JIT vs. legacy for the **system-prompt half** of the window:

1. If `useJIT && compiler != nil` (`prompt_assembler.go:401`): calls `compiler.Compile` (the full pipeline above) and returns its `.Prompt` (plus a `PiggybackProtocolSuffix` appended if the shard type needs the control-packet protocol and the compiled prompt lacks it, `421-424`).
2. **On JIT failure** (`prompt_assembler.go:429-440`): asserts a `jit_fallback(ShardType, "reason")` fact into the kernel for telemetry, logs a Warn, and falls through to a **separate, hand-written legacy assembler** (`442-519`) that is a distinct code path, not a degraded JIT run:
   - baseline template: kernel `shard_prompt_base` predicate (`queryShardTemplate`, `537-...`) → else embedded-baseline atoms (`prompt.AssembleEmbeddedBaselinePrompt`) → else a **hardcoded Go string constant** per shard type (`coderFallbackTemplate`, `testerFallbackTemplate`, etc., `prompt_assembler.go:1060-1141`).
   - kernel-injected context atoms — a **second, independent** query against the *same* `injectable_context` predicate (`queryContextAtoms`/`getInjectableContextFacts`, `574-635`), capped at `maxInjectedContextAtoms=60` / `maxInjectedContextAtomChars=1024` (`906-911`) — deliberately mirroring the JIT path's `maxKernelContextRows` cap so "the fallback does not admit what the primary path rejects" (comment, `907-908`).
   - session context ("blackboard": diagnostics, shard outputs, recent actions, domain knowledge, tools, safety, **compressed history if <1500 chars**) — `buildSessionContext`, `prompt_assembler.go:636-885`, capped at `maxSessionContextChars = 32KB` (`902-903`) with a head+tail-preserving clamp (comment `878-884`: "the head carries diagnostics and failing tests..., the tail carries safety constraints and compressed history... Cutting either end blind loses one of those").
   - user intent block.
   - Piggyback suffix if a hardcoded template was used.

   **This is a fully separate ordering scheme from the JIT `defaultCategoryOrder()`** — a second, independently-maintained sequence decision, hand-written in Go rather than even the same constant. This is a **seam**: two different code paths each decide "what goes where in the window," and they can drift (see Section 8).

3. **After either path returns**, `internal/session/executor.go` (`executor.go:1058-1070`) does two more unconditional appends that bypass JIT/legacy scoring entirely:
   - `withProjectInstructions(compileResult.Prompt)` — the user's per-workspace `nerd.md`, appended raw, **not** modeled as a scorable prompt atom. Comment explains why: *"the atom selector has no way to score a document it has never seen, and budget-driven eviction could silently drop the project's own rules"* (`executor.go:1060-1063`). This is knowledge injected outside the entire JIT selection/budget system by design.
   - `withFileContext(ctx, systemPrompt, intent.Target)` — **only when `e.workingWorld == nil`** (`executor.go:1066-1070`), i.e. this is itself a fallback for when the World Model isn't wired; when the World Model *is* present, file context is expected to arrive through it instead (mechanism not yet confirmed — open item for Section 4).

### The full LLM request window (`internal/session/executor.go` + `executor_tools.go`)

The actual API call assembled by `generateResponse` (`executor.go:1407-1469`) and `runToolLoopPass`/`runToolLoop` (`executor_tools.go:52-160`) has this final shape, for a client with native multi-turn tool calling:

```
[system prompt: JIT/legacy-assembled string, see above]
+ messages: [ ...prior turns (chronological) ..., current user message ]
+ tool definitions (from EffectiveAgentRuntimeConfig.AllowedTools)
→ client.CompleteWithTools(...) / completeWithWorkingContext(...)
```

- **Prior turns**: `priorTurnMessages()` (`executor.go:2053-2099`) reads `e.GetHistory()` (the full `conversationHistory` slice) and applies **two purely mechanical, recency-based limits, in Go, with no Mangle/kernel involvement**: (1) keep only the last `cfg.HistoryTurnWindow` turns (`2082-2084`); (2) while the remaining total character count exceeds `cfg.HistoryCharBudget` (default `DefaultHistoryCharBudget = 24000`, `executor.go:399`), drop turns from the **front, two at a time** (a user+assistant pair) until it fits (`2085-2094`). **No truncation notice, no marker, no summarization — turns are silently and permanently dropped from the message array** if they fall outside the window/budget. This is the sharpest contrast in the whole pipeline against the atom-truncation pattern in Section 1 above (which always emits a "N of M" notice): here, older conversation is dropped with **zero signal to the model or to any log the model could act on** (a debug log line exists for the operator: `"history window: %d prior messages (%d chars)"`, `executor.go:1419`, but nothing reaches the prompt itself).
- **Degraded history for non-native clients**: if the client doesn't implement `types.ToolResultsProvider`, prior messages are flattened into a plain-text transcript and **prepended to the current user message** via `renderHistoryTranscript` (`executor.go:2110-2125`) rather than sent as separate role-tagged messages — still under the same silent recency truncation above.
- **Tool loop**: once the model requests tools, `runToolLoopPass` executes them and feeds results back via the native multi-turn channel (`completeWithWorkingContext`) for as many rounds as `MaxToolIterations` allows — default `8` (`executor.go:383,411`), `0` meaning open-ended when the loop is otherwise progress-driven (`executor_tools.go:183`), separately bounded by a wall-clock deadline (`executor_tools.go:222`).

**Key structural finding**: `CompilationContext` (`internal/prompt/context.go:20-...`) — the struct that drives all JIT atom selection — carries only *categorical/state dimensions* (operational mode, campaign phase, build layer, intent verb/target, shard type, world-model counts like `FailingTestCount`/`DiagnosticCount`, etc.). It has **no field for conversation history, the raw task text, or tool-call results**. This confirms a clean separation: the JIT/Mangle-driven half of the window (the system prompt) is a function of *state*, never of the literal transcript; the transcript itself is carried by a completely separate, conventionally-coded (non-Mangle) path in `executor.go`. Whether that is the right split, or a gap the vision wants closed, is taken up in Section 7.

## 2. The JIT selector

### Mandatory atoms — three independent paths to "always included"

`mandatory_atom/1` in `internal/core/defaults/policy/jit_selection.mg:196-211` derives mandatory status from **three disjoint rules** (a union, per Mangle semantics — any one firing is enough):

1. **Skeleton category + shard match**: `prompt_atom(AtomID, Category, _, _, _), skeleton_category(Category), atom_tag(AtomID, /shard, ShardType), compile_shard(_, ShardType), !prohibited_atom(AtomID)` (`jit_selection.mg:196-201`). Skeleton categories are `identity, protocol, safety, methodology` — but this list is **not itself Mangle-derived**; it is a Go map literal, `skeletonCategories` (`internal/prompt/selector.go:34-39`), read by `isSkeletonCategory` (`selector.go:44-46`), doc-commented "These MUST always be included and failure to load them is CRITICAL." `filterSkeletonAtoms` (`selector.go:956-965`) is a Go pre-filter gating this same category list before Mangle ever sees it — the category boundary is fixed at compile time in Go, only per-atom eligibility within it is derived.
2. **Explicit author flag**: `prompt_atom(AtomID, _, _, _, /true)` (`jit_selection.mg:204-206`) — the atom's own `IsMandatory` field, set by whoever authored the atom YAML/DB row.
3. **`is_mandatory(AtomID)` fact** (`jit_selection.mg:209-211`) — one of the ephemeral predicates asserted per-compile (`promptEphemeralPredicates`, `compiler.go:61-77`); this is essentially the same Go-side `IsMandatory` flag round-tripped through the kernel as a fact so Mangle rules can reference it, not an independently-derived signal.

So "mandatory" is a **union of a fixed Go category allowlist and an author-set boolean**, surfaced through Mangle for join convenience — not a property the kernel computes from anything dynamic like usage history or measured importance. This is consistent with the assignment's cited 2026-09-17 measurement that ~36% of the atom library is mandatory: that number is a property of how the corpus was *authored* (how many atoms got tagged mandatory or fall in one of 4 fixed categories), not of a runtime relevance judgment. (Exact corpus counts pending the atom-census background agent.)

### The vector tier — `topKEligibleVectorScores` (`internal/prompt/selector.go:209-318`)

- **Eligibility** (`selector.go:258-271`): an atom qualifies for a vector slot only if it is in the flesh set, `!atom.IsMandatory` (mandatory atoms don't need a vector slot — they're in regardless), `!atom.RetrievedContext` (retrieved-context atoms reach selection through their own fact, not `vector_hit`), and `atom.MatchesContext(cc)` passes (fail-closed context matcher).
- **Relative floor**: computed only when `len(eligible) >= 8` — `floor = mean + 1.5 * stddev` (population variance, `selector.go:274-287`) over the eligible scores; below 8 eligible atoms the relative floor is skipped and only the absolute floor (`s.minScoreThreshold`) applies. Comment explains why a relative floor is needed at all: *"embedding models differ in range (nomic-embed-text: median ~0.52, best ~0.70), which makes any fixed absolute threshold meaningless on its own"* (`selector.go:222-224`).
- Survivors must clear **both** `absoluteFloor` and the relative `floor` (`selector.go:291`), sorted score-desc/ID-asc, capped at `k` (default 10, `selector.go:246-248`).
- Exact log line: `"Vector tier: %d scored, %d eligible, floor=%.3f, kept %d"` (`selector.go:305-308`) — this is the literal wire format referenced in the assignment.
- **A degenerate but load-bearing edge case**: when `len(scores)==0 || len(fleshAtoms)==0`, the function logs `"Vector tier: nothing to rank..."` and returns nil (`selector.go:233-244`); the comment states this is exactly what happens "with every stored vector unstamped (the state before `nerd embedding reembed` runs)" — i.e., an **embedding-model mismatch silently zeroes the entire vector channel** for every compile until a re-embed is run, and the *only* signal is this debug log line, never surfaced to the model or a health check (cross-ref project memory `project_jit_selector_state_2026-09.md`).

### Score combination — the "logic score" is a constant, not a graded signal

For atoms that Mangle's flesh query actually selected (`loadFleshAtoms`, `selector.go:~1230-1288`), the combination is:
```go
logicScore := 1.0  // selector.go:1266 — always 1.0 for any Mangle-selected atom
weight := s.vectorWeight  // default 0.3 (70% logic / 30% vector), selector.go:572; overridable per-CompilationContext via cc.VectorWeight
combined := (1.0-weight)*logicScore + weight*vScore  // selector.go:1271
```
i.e., **Mangle's contribution to the blended score is binary** (selected → 1.0, not selected → absent) — all continuous variation in `Combined`, and therefore in resolver-stage tie-breaking/ordering (Section 1), comes from the vector score alone. There is no graded "how strongly does logic prefer this atom" signal feeding the sort. A `fallbackFleshSelection` path (`selector.go:1305-1355`, used when Mangle is unavailable) uses `LogicScore: 0.5` and direct Go context-matching instead of any kernel query at all.

### Token budget & reserved tokens

- `jit.token_budget` (config) flows into `CompilationContext.TokenBudget`; `cc.AvailableTokens()` is what `compiler.go:801-804` uses, falling back to `CompilerConfig.DefaultTokenBudget = 200000` (`compiler.go:491`) only if the context left it unset.
- A separate **Mangle-mandatory cap** exists specifically for `/legislator` and `/mangle_repair` shards writing Mangle code (`isMangleMandatoryContext`, `selector.go:487-496`): `mangleMandatoryTokenCap = 900000`, `mangleMandatoryAtomCap = 600`, `mangleMandatoryBudgetRatio = 0.90` (`selector.go:48-52`) — i.e. atoms tagged for the Mangle language can consume up to 90% of the turn's budget before the rest of the corpus is even considered, gated by `mangleMandatoryLimits` (`selector.go:396-419`).
- Reserved tokens: `cc.ReservedTokens`, defaulting from `JITConfig.ReservedTokens = 8000` (`internal/config/jit.go:18-19,68`). `PromptAssembler.SetJITBudgets` (`prompt_assembler.go:1255-1281`) is a **safety clamp, not a primary computation**: it only engages when `reservedTokens >= tokenBudget` (an invalid combination), in which case it recomputes `reservedTokens = tokenBudget / reservedTokensFallbackRatio` (default ratio `10`, i.e. 10% of budget, from `JITConfig.ReservedTokensFallbackRatio = 10`, `jit.go:22,69`), and zeroes it entirely if that's still `>= tokenBudget`. So in the normal case the configured `reserved_tokens` value is used as-is; the fallback ratio only exists to prevent a misconfigured budget from producing a negative or nonsensical available-token count.

### Mandatory-atom conflict resolution: a fixed mechanism, currently inert on the shipped corpus

`internal/core/defaults/jit_compiler.mg` (this is the file most `jit_selection.mg`/`jit_logic.mg` comments refer to by that name; it lives directly under `internal/core/defaults/`, not under `defaults/policy/`) documents a real, previously-measured bug and its fix:
- **The bug** (`jit_compiler.mg:153-174`): the naive rule `prohibited(B) :- atom_conflicts(A, B), mandatory_selection(A)` had **no effect**, because a mandatory atom reaches `selected_result` via `mandatory_selection → tentative → final_valid`, and nothing on that path reads `prohibited`. Measured against a real kernel: *"a mandatory atom and a mandatory atom conflicting with it were BOTH returned in `selected_result`. The conflict was computed and discarded."* (`jit_compiler.mg:165-167`) — i.e., two atoms that explicitly contradict each other could both land in the same compiled prompt.
- **Why the obvious fix doesn't work**: adding `!prohibited(Atom)` to `mandatory_selection` closes a negation cycle (`prohibited` already depends on `mandatory_selection`) and breaks stratification (`jit_compiler.mg:169-171`).
- **The actual fix**: a separate predicate, `mandatory_superseded(B) :- atom_conflicts(A, B), is_mandatory(A), !blocked_by_context(A)` (`jit_compiler.mg:190-193`), feeding `mandatory_selection(Atom) :- is_mandatory(Atom), !blocked_by_context(Atom), !mandatory_superseded(Atom)` (`jit_compiler.mg:196-199`) — derived only from EDB plus `blocked_by_context`, avoiding the cycle. The relation is deliberately **directional** (`A` supersedes `B`, not mutual incompatibility) specifically so a conflicting pair can't "cancel both atoms and silently delete the guidance entirely — the worst outcome available" (`jit_compiler.mg:175-178`).
- **Current status, stated in the same file**: *"Inert on the shipped corpus: no atom under `internal/prompt/atoms` declares `conflicts_with`, so this derives nothing until a producer opts in"* (`jit_compiler.mg:188-189`). The mechanism is correctly built and stratified, but as of this reading, no atom in the actual corpus exercises it — mandatory-atom conflict resolution is a proven-correct no-op today.

The **fail-closed `regime_dimension` gate** that makes a selector dimension binding (referenced throughout Section 1/8) is an explicit, small, enumerable list: `/shard, /mode, /phase, /layer, /init_phase, /northstar_phase, /ouroboros_stage, /provider, /model` (`jit_compiler.mg:133-141`) — **nine dimensions**. `/shard_type` is conspicuously absent (the historical bug in Section 8 below), and so are `/verb`, `/language`, `/framework`, `/world_state`, meaning a `compile_context` fact asserted under any of those does not participate in `blocked_by_context` filtering at all unless routed through one of the nine gated dimensions.

## 3. Context management

Most of this section (scoring components in `internal/context`, `working_set.mg`, eviction/recoverability, the `predicate_corpus.db` serializer) is pending the dispatched background Explore agent. What follows was found independently while tracing memory/reflection config (`internal/config/reflection.go`), and answers part of the brief directly: **the derivation chain from reflection-based memory recall to `injectable_context`, and a significant, precisely-located wiring gap in it.**

### The derived chain: reflection recall → relevance fusion → `injectable_context`

`internal/core/defaults/policy/prompt_context.mg` is the policy file (labeled "Section 41 of Cortex Executive Policy" in its own header comment) implementing this. The full chain, traced end to end:

1. **Recall**: `cmd/nerd/chat/reflection.go`'s `performReflection` (`reflection.go:35`) runs a vector-similarity search over trace and learning stores (`store.TraceRecallHit`, `store.LearningRecallHit`), ranks hits with `rankTraceHits`/`rankLearningHits` against `config.ReflectionConfig` (`TopK=5`, `MinScore=0.70`, `RecencyHalfLifeDays=14` — `internal/config/reflection.go:52-60`), applying **recency-decay weighting** (`applyRecencyWeight`, `reflection.go:409`) — a genuinely relevance-and-recency-aware scoring, unlike the flat FIFO history truncation in Section 1/5.
2. **Assertion**: `assertReflectionFacts` (`reflection.go:368-396`) asserts the ranked hits as `trace_recall_result(TraceID, Score, Outcome, Summary)` and `learning_recall_result(LearningID, Score, Predicate, Description)` facts (`Decl`s in `internal/core/defaults/schemas_memory.mg:26-32`) directly into the kernel.
3. **Fusion**: `prompt_context.mg:5-76` derives `shard_context_atom(ShardID, Content, Relevance)` — a **numeric relevance score fused from at least eight distinct evidence sources**: intent-match (90), specialist knowledge (80), high-scoring trace recall ≥85 score (85; past-failure recall specifically, 90), high-scoring learning recall ≥80 score (75), active campaign constraints (70), learned exemplars matching intent category (60), relevant tool descriptions (65), and historically-successful trace patterns from high-quality traces (50).
4. **Threshold selection**: `injectable_context(ShardID, Atom) :- shard_context_atom(ShardID, Atom, Relevance), Relevance > 50` (`prompt_context.mg:80-83`) — everything above the flat cutoff qualifies. This is the predicate `internal/prompt/compiler.go:1076` (`collectKernelInjectedAtoms`, Section 1) actually queries.
5. **A learning loop closes over it**: `context_injection_effective(ShardID, Atom) :- final_injectable(ShardID, Atom), shard_success(ShardID)` feeds `learning_signal(/effective_context, Atom)` and `promote_to_long_term(/context_pattern, Atom) :- context_effective_count(Atom, N), N >= 3` (`prompt_context.mg:183-199`) — context that repeatedly correlates with a successful shard outcome is promoted toward long-term memory. Whether `promote_to_long_term` itself is consumed anywhere is unchecked in this pass (flag: unverified).

### The gap: the budget-awareness layer this same file builds is never reached

`prompt_context.mg:102-138` ("Context Budget Awareness" / "Spreading Activation Integration") builds exactly the derived-budget mechanism Section 7 argues is missing elsewhere — `context_budget_constrained(ShardID) :- context_budget(ShardID, Budget), Budget < 5000`, `context_budget_sufficient` for the complement, and `final_injectable(ShardID, Atom)` selecting *all* `injectable_context` when budget is sufficient but **only high-priority (`Relevance >= 80`) items when constrained** — a real, derived, budget-sensitive pruning decision, plus `activation(Atom, 95) :- final_injectable(_, Atom)` explicitly feeding back into spreading activation. **This layer is disconnected from the running system on both ends, independently confirmed:**
- **`context_budget(ShardID, Budget)`** is asserted only as a **campaign-scoped concept** — `internal/campaign/recurse_plan.go:87-91` (`ContextBudget int \`json:"context_budget"\`` on a campaign-recursion config struct) — not by `internal/session/executor.go` or `internal/core/shards/manager_spawn.go` (which *does* assert `active_shard` on every shard spawn, confirmed live at `manager_spawn.go:316-321`, but nothing budget-related alongside it). So for an ordinary chat turn or a shard delegated outside an active `/campaign`, `context_budget/2` is simply never asserted for that `ShardID`. **[REFUTED — see Verification]**
- **`final_injectable/2` has no production Go consumer at all** — grepping the entire `internal/` tree for `final_injectable` returns exactly one hit, a generic Mangle-wiring test (`internal/core/mg_decl_body_literal_wiring_test.go`) that almost certainly just asserts every declared predicate has a `Decl`, not a real consumer. **[REFUTED — see Verification]** The Go side (`compiler.go:1076`, Section 1) reads `injectable_context` **directly**, bypassing the budget gate entirely.

**Net effect**: every `injectable_context` row scoring above the flat 50-point threshold reaches the prompt (subject only to the unrelated, hardcoded Go caps `maxKernelContextRows=60` etc. from Section 1) regardless of how tight the turn's actual token budget is. The one piece of this document's evidence that most closely matches the vision's "compression as a derived decision" — a Mangle rule that shrinks what's injected under budget pressure — is fully built, stratified, and commented as intentional, and is not on the path anything reads. This is a stronger, more specific version of the general claim in Section 7.

### `internal/context`: the rest of the picture, from the background agent (spot-checked: 2/2 checks passed)

**Compression: some drops are marked, several are not — a direct addition to Section 5.** The kernel-driven case is marked: `generateObservationMaskedSummary` (`compressor_turns.go:452-497`) drops only observation atoms the kernel's `should_mask_observation(TurnID)` (`context_compilation.mg:135-140`) names `/old`/`/ancient`, and explicitly annotates it in-band (`"# turn %d observations masked by should_mask_observation (%d atoms)"`, `:483-484`); reasoning atoms are protected by `should_preserve_reasoning` and the Go code honors it. **`predicate_corpus.db` and ordering — a three-way hybrid, precisely:**

## 4. CodeDOM, world model, memory, vector search

### CodeDOM — parsed, stored as Mangle facts, never rendered into a prompt

CodeDOM is not one package; it spans three: `internal/world/` (the parser/scope engine — `cartographer.go:33`'s `Cartographer` struct, Go via `go/ast`, others via tree-sitter; `code_elements.go:52`'s `CodeElement` — the DOM node itself: ref, type, file, line range, signature, body, parent, visibility; `scope.go:809/923` for fact emission/accessors), `internal/core/virtual_store_codedom.go` (tool handlers: `handleOpenFile`, `handleGetElements`, `handleGetElement`, `handleEditElement`, `handleRefreshScope`, `handleEditLines`/`handleInsertLines`/`handleDeleteLines`), and `internal/tools/codedom/` (`apply_edits.go`, `run_impacted_tests.go`).

- **What it stores**: `CodeElement.ToFacts()` (`world/code_elements.go:91`) emits Mangle facts — `code_element(Ref, Type, File, Start, End)`, `code_defines`, `code_calls`, `code_implements`, dataflow facts (`assigns`, `guards_return`, `function_scope`) — into the VirtualStore's fact base, not a document/string store.
- **Refresh**: on-demand only, tool-call-driven — `open_file` populates scope initially; every mutating action (`edit_element`, `edit_lines`, `insert_lines`, `delete_lines`) calls `scope.RefreshWithRetry(3)` plus `clearCodeDOMFacts()`; an explicit `refresh_scope` action exists. No timer, no session-start scan.
- **Does it reach the prompt? No.** The only CodeDOM-related prompt content found is static YAML *instructions for calling the tools* (`internal/prompt/atoms/capability/codedom_first.yaml`, `codedom_selection.yaml`, `codedom_core.yaml`, `codedom_tools.yaml`) — no function in `internal/prompt` or `internal/articulation` reads `code_element`/signature facts and injects their content into a compiled prompt. Parsed elements live only in the Mangle fact store for the model to pull back out via `get_elements`/`get_element`/`read_file` tool calls, and for `internal/core/defaults/policy/codedom_safety.mg` to validate edits against. **This is a confirmed, clean instance of "the model must grep around" for exactly the content a north-star bullet says it shouldn't have to.**

### World model — reaches the prompt only as booleans, not content

Scanner: `internal/world/cartographer.go` (Go AST + tree-sitter for Python/TS/JS/Rust), configured by `internal/config/world.go` (`WorldConfig` — worker counts, ignore patterns, size caps, Section 1/4 cross-ref). Facts flow into the kernel, then get read back **as booleans/counts, not raw fact dumps** — confirmed on both turn types:
- **Chat path**: `internal/session/executor.go:1155` (`buildCompilationContext`) — `e.kernel.Query("test_state(/failing)")` → `cc.FailingTestCount` (`:1284-1285`), `e.kernel.Query("diagnostic")` → `cc.DiagnosticCount` (`:1289-1290`), then `types.GetSessionContext(ctx)` for the rest (`:1296-1297`). Runs every turn (`executor.go:991`).
- **Shard path**: `internal/articulation/prompt_assembler.go:101` (`toCompilationContext`) — reads `pc.SessionCtx` fields (`FailingTests`, `CurrentDiagnostics`, `ImpactedFiles` → `IsLargeRefactor`; `GitUnstagedCount` → `IsHighChurn`; `SafetyWarnings`/`BlockedActions` → `HasSecurityIssues`; `ReflectionHits`, `:260-262`) — same field set as `internal/types/types.go:462-535`. Both `toCompilationContext` (generic, any shard type) and `buildCompilationContext` (interactive-specific) are live, confirmed reached.

The model learns *that* tests are failing or *that* a diagnostic exists, and must still call a tool to see which test or what the diagnostic says, unless that detail happens to also be threaded through `injectable_context` (Section 3).

### Memory — a live fact-based path and a dead raw-text path, side by side

Confirmed as a genuinely separate persistent store: `internal/store/` (SQLite — `reflection_search.go`, `reflection_worker.go`, `reflection_reembed.go`, `learning_reflection.go`, `trace_reflection.go`), configured by `ReflectionConfig` (Section 3: `TopK=5`, `MinScore=0.70`, `RecencyHalfLifeDays=14`).

Reconciling this agent's finding with Section 3's independent trace: **reflection recall has two parallel downstream paths from the same recall step** (`cmd/nerd/chat/reflection.go:35`, triggered every chat turn from `process.go:316`):
1. **The live path** (Section 3): recall hits are asserted as kernel facts (`trace_recall_result`/`learning_recall_result`), which `prompt_context.mg` fuses into `shard_context_atom`/`injectable_context` — read by the JIT compiler (`compiler.go:1076`). This path works, modulo the `final_injectable` budget-gate disconnection already documented in Section 3/8.
2. **The dead path**, newly found here: the same recall results are *also* formatted into `state.ContextHits` (`reflection.go:121`) and copied into `sessionCtx.ReflectionHits`/`ExtraContext["reflection_hits"]` (`cmd/nerd/chat/model_session_context.go:196-198`). `toCompilationContext` only turns this into a boolean, `cc.HasReflectionHits = true` (`prompt_assembler.go:248-261`) — the raw recalled text itself is carried on `CompilationContext.SessionContext`, which **is confirmed write-only by its own doc comment**: *"Write-only baggage: the articulation adapter sets these for downstream consumers that do not exist yet. Nothing reads them, so they are correctly excluded from Hash"* (`internal/prompt/context.go:204-211`, independently re-read and confirmed verbatim in this pass). The raw text only gets rendered — under a `"REFLECTION HITS:"` heading — by `buildSessionContext` (`prompt_assembler.go:636,692-703`), which is part of the **legacy fallback assembler** (Section 1) that runs only when JIT is disabled or fails.

**Net effect, stated precisely**: in the default (JIT-enabled) configuration, the *fact-shaped* summary of a memory hit reaches the prompt via `injectable_context` (subject to the Section 3 budget-gate gap), but the *verbatim recalled text* on `SessionContext` never does — only a boolean that selects a generic static guidance atom. Two somewhat-redundant channels were built for the same recall step; one is live-but-capped, the other is a documented dead end.

### Vector search / embeddings

- **Floor formula**, independently re-confirmed against Section 2's own direct read: `internal/prompt/selector.go:279,285-286` — population-variance `floor = mean + 1.5*stddev`, relative floor applied only when `len(eligible) >= 8` (`:274`), else the absolute `minScoreThreshold` alone (`:249-251,273`). Matches Section 2 exactly.

## 5. Compression and pruning

### Where the "never silently truncate" rule holds

`internal/prompt/limits.go` is the single, shared implementation the repo's own memory rule (`feedback_never_truncate_send_back.md`: "a cut answer goes back to the model to be restated... count caps are suspect") is actually implemented against for **prompt-atom content**:
- `ClampText(text, maxChars, label)` (`limits.go:70-90`) — head+tail preserving (keeps a head portion and a tail portion, snapped to line boundaries via `snapHeadToLine`/`snapTailToLine`), inserts a marker `"[…clamped N of M chars from <label>] …"` (exact prefix `clampMarkerPrefix`, format string `limits.go:78-79`) in the middle. **[REFUTED — see Verification]**
- `ClampHead(text, maxChars, label)` (`limits.go:121-131`) — head-only variant with a trailing marker.
- `ClampLines(text, maxLines, label)` (`limits.go:136-...`) — line-oriented variant for compiler diagnostics / test output specifically so a cut mid-line doesn't "produce a fragment the model may misread as a complete record" (comment `133-135`).
- `TruncationNotice(shown, total, unit)` (`limits.go:157-162`) — the "N of M shown" suffix used when a *list* (not raw text) is capped (e.g. `injectable_context` rows, `specialist_knowledge` blocks — Section 1).
- `IsClamped(text)` (`limits.go:166-168`) — lets tests assert a marker is present without pinning exact wording.

**Confirmed call sites** (grep for `ClampText(`/`ClampHead(`/`ClampLines(` unqualified, since `compiler.go` is in the same package and calls them bare): `internal/prompt/compiler.go` (kernel-injected context/specialist-knowledge blocks, Section 1), `internal/articulation/prompt_assembler.go` (legacy session-context blackboard, `sessionContextLine`/`maxSessionContextChars`, Section 1), `internal/context/serializer.go` (own investigation pending — Section 3), `internal/perception/transducer_llm.go`. Every one of these paths marks what it cuts.

### Where it does not hold

- **Conversation-history eviction is silent.** `priorTurnMessages()` (`internal/session/executor.go:2053-2099`, documented in Section 1) drops the oldest user+assistant turn pairs once `HistoryCharBudget` (default 24000 chars) or `HistoryTurnWindow` is exceeded, with **no marker inserted into the message stream** — only an operator-facing debug log (`"history window: %d prior messages (%d chars)"`, `executor.go:1419`). The model that receives a shortened history has no way to know earlier turns existed and were cut, which is exactly the "cut answer" scenario the memory rule targets, just applied to the conversation channel rather than tool/LLM output.
- **Shell/tool-output truncation is structured but its visibility to the model is unconfirmed.** `internal/tactile` (the shell-execution backend used across `direct.go`, `docker.go`, `platform_windows.go`, `platform_linux.go`, `platform_linux_firejail.go`) caps captured stdout+stderr at `MaxOutputBytes` (default 10 MiB, `internal/tactile/types.go:362-363,381`) and sets `Result.Truncated = true` / `Result.TruncatedBytes = N` (`types.go:197-201`, set at each platform backend, e.g. `direct.go:194-196`) plus an operator-facing `logging.TactileWarn` — but tracing forward from `tactile.Result` to the actual `types.ToolResult.Content` string returned to the LLM (in `internal/session/executor_tools.go`) was not completed in this pass; **unverified** whether `Truncated`/`TruncatedBytes` ever become a visible marker in the model-facing text the way `ClampText`'s marker does, or whether the model just sees a silently shorter blob. Flagged as a concrete follow-up (see Section 8 candidate seam).
- **`withProjectInstructions`** (`executor.go:1064`, Section 1) injects the user's `nerd.md` **uncompressed and unbudgeted** — no clamp, no notice, and explicitly outside the token-budget-aware JIT pipeline. A large `nerd.md` has no documented ceiling in the code read so far.

Pending confirmation from the background context-management agent: whether `internal/context`'s working-set eviction (Section 3) leaves evicted facts recoverable, and whether the serializer's use of `ClampText`/`ClampHead` (found via grep above) covers its own outputs the same way.

## 7. Gaps against the vision

The two north-star bullets under test: (3) *"it never has to grep around... the kernel has the math to hand the LLM what it needs"*; (4) *"lost-in-the-middle is eliminated by context compression, pruning and ordering... where a fact sits in the window is a decision."* `Docs/journeys/M2-mangle-programming-model.md` does not exist yet, so this section states requirements directly rather than deferring to it.

### Bullet 3 — delivered vs. grepped

**Delivered without a tool call, confirmed by direct read:**
- The entire compiled system prompt (mandatory + selected atoms, Sections 1-2).
- `injectable_context` / `specialist_knowledge` kernel facts, when something has asserted them (mechanism of assertion still pending Section 3's agent).
- Per-workspace `nerd.md` project instructions (`executor.go:1064`) — though delivered *outside* any selection/scoring, which is its own gap (below).
- Recency-windowed conversation history (`priorTurnMessages`).

**What still sends the model to a tool instead of the kernel handing it over**, now confirmed by Sections 3-6:
- **Symbol/AST-level knowledge (CodeDOM) — confirmed grep-around, cleanly.** Section 4: CodeDOM is fully parsed into Mangle facts (`code_element`, `code_defines`, `code_calls`, `code_implements`, dataflow facts) by `internal/world`, but **no code anywhere reads those facts back into a prompt** — the only CodeDOM-related prompt content is static YAML telling the model *how to call the tools*. Every turn that needs symbol-level detail pays for it with a `get_elements`/`get_element`/`read_file` round trip, which is precisely the "grep around" bullet 3 says shouldn't be necessary, for exactly the kind of structured, already-parsed knowledge the vision names as the kernel's to hand over.
- **World-model facts reach the prompt only as booleans, never content.** Section 4: `FailingTestCount`, `DiagnosticCount`, `IsLargeRefactor`, `HasSecurityIssues`, etc. select *which static guidance atom* is included (`WorldStates()` → `world_state/*.yaml`), never the underlying content (which test, what diagnostic). The model knows *that* something is wrong and must still fetch *what*.
- **Recalled memory text is asserted twice, and only one copy is live.** Section 4: the same reflection-recall step populates both a live path (kernel facts → `injectable_context`, capped by Section 3's disconnected budget gate) and a dead path (`CompilationContext.SessionContext`, confirmed write-only by its own code comment — rendered only by the legacy fallback assembler, which the default JIT-enabled configuration never runs). The raw recalled text a memory hit was scored on is not what reaches the model in the default configuration; a coarser, re-derived summary is.
- **File contents for the current intent target**: `withFileContext` (`executor.go:1069`) is explicitly a **fallback that only runs when `e.workingWorld == nil`** — and Section 4 confirms the "real" path (`buildCompilationContext`/`toCompilationContext`) never delivers file content either, only booleans. So this fallback is, in practice, not really a fallback from a richer alternative — neither path delivers raw file content proactively; `read_file` is the only route either way.
- **Anything not captured by the fixed 10-tier `CompilationContext`** (Section 1): if a fact about the current turn doesn't fit one of operational mode / campaign phase / build layer / init phase / northstar phase / ouroboros stage / intent verb-target / shard type / world-model counts / (implicitly) provider-model, there is no channel for it to influence atom selection at all except by being asserted as an ad hoc `injectable_context` row — a much coarser, unscored, string-based channel than the rest of the JIT machinery.
- **Measured, not just inferred**: Section 6's log analysis of one real Reviewer-shard turn found **3 files read 2-3 times each in a single turn** — content the model had already fetched once, re-fetched again, with no mechanism (confirmed in Section 6) that would have caught or prevented it.

### Bullet 4 — ordering and compression as *decisions*, not defaults

The vision's claim is that "where a fact sits in the window is a decision" — implying a decision that can be reasoned about, changed by policy, and audited. What was actually found:

- **Macro-ordering (category order) is a Go constant**, `defaultCategoryOrder()` (`assembler.go:53-95`), pinned by a Go unit test (`TestDefaultCategoryOrder`). This is a *good* engineering decision (prefix-cache stability wants a stable head) but it is **not a decision the kernel makes or could change per-turn** — it is identical for every compile, every shard type, every operational mode. The vision's "where a fact sits is a decision" is true only in the coarse sense that someone, in Go, decided once. It is not re-derived from any Mangle predicate about, say, "this turn most needs safety context up front because a destructive action is pending" — the position of `CategorySafety` (always Level 0, always near-top) doesn't change based on live risk signals the kernel already computes elsewhere (e.g. `HasSecurityIssues` on `CompilationContext` selects *whether* safety atoms are mandatory, not *where* they sit).
- **Micro-ordering (within a category) is Kahn's-algorithm topological sort in Go** (`resolver.go`), tie-broken by a score that is itself half-constant (Section 2's "logic score is always 1.0" finding) — so the *only* graded signal actually moving an atom's position within its category is the vector-similarity score, when one exists at all (mandatory and mangle-mandatory atoms have none).
- **Conflict resolution *is* Mangle-derived** (`atom_conflicts`/`prohibited_atom`/`conflict_loser` in `jit_selection.mg`, wired as vetoes into `jit_compiler.mg`) — this is the one clear instance of the vision actually realized: a two-atom disagreement is resolved by kernel logic, not a Go heuristic. It is, notably, restricted to *whether* an atom is in the window at all, never *where*.
- **Compression is a mix of derived-adjacent and purely mechanical — and where it IS derived, it's disconnected.** The atom-truncation/notice pattern (Section 5) is deterministic Go code (`ClampText`/`TruncationNotice`) operating on Go-side caps (`maxKernelContextRows=60`, etc.) that are themselves **hardcoded constants, not Mangle-derived budgets**. Conversation-history pruning (`priorTurnMessages`) is plain FIFO-by-recency with **no relevance signal at all**, Mangle or otherwise — the exact "lost in the middle" failure mode the vision names, applied to the one channel (turn-to-turn memory) that arguably needs relevance-aware retention the most. Notably, this is **not** for want of a derived alternative existing anywhere in the corpus: Section 3 traces a real, stratified, budget-sensitive selection rule (`context_budget_constrained/sufficient` → `final_injectable` in `prompt_context.mg`) that does exactly what's missing — narrows injection to high-priority content under a tight budget — and it has **zero production Go consumers**, while its gating fact (`context_budget`) is asserted only inside campaigns. The gap here is not "no one has designed derived compression" — it's that a working design exists and was never connected to the read path.

### What would have to become facts and rules for the kernel to decide injection

**The architecture already anticipated this and left the socket empty.** `CompilationContext.ActivatedFacts`/`ActivationThreshold` (Section 1) is precisely a "let the kernel's activation math hand the LLM what it needs" channel, fully typed, cache-safety-tested, and populated by nothing. Closing this gap is priority zero and does not require inventing a new mechanism — it requires the two design decisions its own code comment names: (1) a fact-to-atom relevance relation (schema for "this fact is about that atom"), and (2) a cache-safe encoding of activation (quantized buckets or a hot-fact-set rather than exact floating scores, so `Hash()` stays stable across turns with similar-but-not-identical activation). Everything else below is secondary to this.

Concretely, closing the rest of the gap would require at minimum:
1. **A `window_position(AtomOrFactID, Slot)` or equivalent derivable predicate** replacing (or overriding) `defaultCategoryOrder()`, so placement can respond to live risk/urgency signals already sitting in the kernel (e.g., a pending destructive action promotes `CategorySafety` content nearer the tail, which is the position models attend to most under recency bias) rather than being fixed at compile time in Go.
2. **A relevance-scored history/working-set predicate** analogous to `topKEligibleVectorScores` but for conversation turns — replacing `priorTurnMessages`'s pure FIFO cutoff with something that can keep an old-but-load-bearing turn (e.g., a stated constraint) over a recent-but-irrelevant one, plus a **mandatory visible marker** (matching the atom-truncation pattern) whenever a turn is dropped, so the omission itself becomes an observable fact rather than a silent one.
3. **Wiring, not building, a budget-aware injection predicate**: `prompt_context.mg`'s `final_injectable` (Section 3) already computes exactly this — falling back to high-priority-only content when `context_budget` is tight — and is a strictly cheaper fix than inventing a new mechanism. Closing it needs two things: (a) `internal/session/executor.go` or `internal/core/shards/manager_spawn.go` asserting `context_budget(ShardID, Budget)` from `cc.AvailableTokens()`/`jit.token_budget` on every turn, not just campaign waves, and (b) `compiler.go:1076` querying `final_injectable` instead of (or in addition to, unioned) `injectable_context`. Only once that's done would it be worth asking whether `final_injectable`'s own fixed 80-point high-priority cutoff and the still-independent Go-side character caps (`maxKernelContextRows`, `maxSessionContextChars`, `HistoryCharBudget`) should also be unified into one derived ceiling.
4. **A generalized `read_before_ask/1`-style predicate** the executor could consult before falling into `withFileContext` or a `read_file` tool call — i.e., an explicit derivable fact for "the kernel already holds current content for this target" vs. "this must be fetched" — which today is only implicit in the `e.workingWorld == nil` branch condition, not a queryable fact itself.
5. **A cross-check between tool calls and delivered context.** Section 6 confirms `tool_budget_controller.go`'s per-turn signature tracking already has half of this built (it can tell a repeated tool call from a novel one within a turn) but only uses it to gate loop-iteration budget, never to compare against what the compiled prompt already contained. A derivable `tool_call_was_redundant(Call, AtomID)` — joining a tool call's target (file path, symbol) against the turn's `IncludedAtoms`/`injectable_context` rows — would convert Section 6's hand-diffed finding (3 files read 2-3 times in one real turn) into something the kernel or a lint pass catches on every turn, not just when someone audits a log by hand.
6. **A shared vocabulary/gate-list contract check** — the `regime_dimension` gate list (Section 8) and the Go selector's fact-emission vocabulary are two independently maintained lists that have already drifted once (the `/shard_type` incident). A rule or test deriving "every dimension `selector.go` emits is present in `regime_dimension`" (or vice versa) would convert a category of bug the corpus's own comments show has already happened into something the kernel — or at least CI — catches structurally.

Pending Sections 3/4/6 findings for further gap material (spreading-activation reach, CodeDOM/world-model/memory wiring, and what measurement tooling would need to add to observe lost-in-the-middle directly).

## 8. Seams found

### Two turn types derive context relevance from different rule sets, not just different data

Section 3: the interactive chat kernel loads every file under `defaults/policy/*.mg` at boot (`internal/core/kernel_init.go:310-329`), including `activation.mg`. The tool-loop/shard-delegation path's `WorkingSet` builds its own **private** Mangle engine that loads only schemas, `context_compilation.mg`, and `working_set.mg` (`internal/context/working_set.go:47,51,61`) — `activation.mg` is absent, confirmed by direct re-read. `context_compilation.mg`'s own fallback tier (`context_relevant(Fact,/p60) :- context_atom(Fact)`) depends on `activation.mg`'s `context_atom/1`, so that fallback tier is live for chat and structurally inert for the delegated path. Two turn types this document otherwise found to share one pipeline (Section 1's `Executor`/JIT-compiler path) diverge here at the policy-corpus level.

### `ActivationEngine.SpreadFromSeeds` — a second dead implementation of the same design goal

Section 3, independently spot-checked (2 references repo-wide: its own definition and its test). `internal/context/activation.go`'s own package header names multi-hop spreading activation as a design goal; the Go implementation of it has never had a production caller. Distinct from, and should not be confused with, the earlier-documented `atom_selector`/`atom_has_*_match` dead design in `jit_logic.mg` (both are real, both are dead, in different subsystems) — the repo has more than one instance of "designed, built, tested, never wired" for closely related purposes (relevance-weighted context propagation).

### A third unconditional, non-JIT prompt append: `stevenMoorePersona`

Section 3, via cross-reference to `00-journey-map.md`: `cmd/nerd/chat/process.go:832` appends a hardcoded persona string to the kernel-relayed JIT prompt, unconditionally, after JIT compilation — the same shape as `executor.go`'s `withProjectInstructions`/`withFileContext` (Section 1), a third independent instance of content reaching the window outside the atom-selection/budget system entirely.

### CodeDOM is fully parsed and never read back into a prompt

Section 4: `internal/world`/`internal/core/virtual_store_codedom.go` parse every element the model edits into rich Mangle facts (`code_element`, `code_defines`, `code_calls`, `code_implements`, dataflow facts) specifically so the system has structured knowledge of the code — and no consumer in `internal/prompt` or `internal/articulation` ever queries those facts back into a compiled prompt. The only bridge is a handful of static YAML atoms teaching the model to call the CodeDOM tools itself. Two systems (the parser and the prompt compiler) were built to the same fact schema, and only one side of the potential connection was ever written.

### Reflection recall is asserted to two places; only the coarser one is live by default

Section 4: `cmd/nerd/chat/reflection.go`'s recall step writes to both a kernel-fact path (live, feeds `injectable_context` via `prompt_context.mg`) and `CompilationContext.SessionContext` (dead by its own doc comment, rendered only by the legacy fallback assembler). The two paths disagree about whether the model ever sees the verbatim recalled text — the JIT-enabled default answers "boolean flag only," the disabled/failed-JIT fallback answers "yes, full text under a heading" — and there is no single place documenting that these produce meaningfully different outputs for the same recall.

### A redundancy detector exists but doesn't know about delivered context

Section 6: `internal/session/tool_budget_controller.go` can already tell a repeated tool call from a novel one within a turn (SHA-256 signature tracking) but uses that signal only to throttle loop iterations, never to check whether the repeated call's target was already sitting in the compiled prompt.
