## Subsystem Analyzed: internal/session (Executor Safety Boundary)
The `internal/session` module, specifically `executor_boundary_test.go` and `executor_tools.go`, acts as the critical Constitutional Gate for codeNERD's execution engine. It governs the transition from the LLM's non-deterministic output to the Mangle kernel's deterministic state modifications. This boundary is paramount because any bypass, corruption, or resource exhaustion here directly compromises the integrity of the VirtualStore and the wider workspace.

Our analysis focuses heavily on Boundary Value Analysis and Negative Testing vectors, moving beyond "Happy Path" scenarios to identify systemic gaps in the executor's resilience.

## Vector 1: Null / Undefined / Empty States
When examining `checkSafety` and `extractTarget`, we must consider how the system responds to missing or uninitialized data. Go's type system handles `nil` pointers well, but logical extraction from `map[string]any` is vulnerable to missing keys or unexpected zero-values.

Currently, the executor normalizes `nil` arguments to an empty map (`{}`) to align with permitted facts. However, there are notable gaps in testing:
- **Explicit `nil` values**: If a candidate key (like `path` or `url`) is explicitly present in the map but its value is `nil` (e.g., `map[string]any{"path": nil}`), does `extractTarget` panic, or does it correctly fall back to `"unknown"`? A type assertion like `val.(string)` would panic if `val` is `nil`.
- **Deeply Nested Empty Objects**: If a tool payload contains a deeply nested map or an uninitialized slice (e.g., `map[string]any{"data": []any{}}`), how does the JSON marshaling interact with the `maxPayloadBytes` limit, and more critically, how does Mangle evaluate these structures when asserted?
- **Empty Action Names**: While `validMangleActionAtom` rejects malformed strings, what happens if the `ToolCall.Name` is entirely empty or consists solely of whitespace? We need strict tests ensuring categorical rejection before any kernel interaction occurs.
- **Empty String Targets**: If `extractTarget` encounters an empty string for a valid key, does it correctly skip it and check the next candidate key, or does it return an empty target, potentially causing malformed Mangle facts like `permitted(/action, , {})`?

### Mangle Engine Performance Considerations (Null/Empty)
Mangle's engine uses a Clean Slate Fact Store for evaluation. Inserting facts with missing or `"unknown"` targets is generally safe, provided the schema permits it. Mangle's type system (Level 5 prevention) should theoretically reject atoms with incorrect arity or invalid types (e.g., if a string was expected but null/empty was provided). However, if an atom is successfully asserted, the performance impact is negligible. The main risk is schema drift or silent failures (empty results) where a rule fails to join due to missing target strings.

## Vector 2: Type Coercion
The transducer layer maps JSON from the LLM into Go structures, but the conversion from `map[string]any` to string representations for Mangle facts is a frequent source of "Atom/String Dissonance". Mangle treats `/active` (Atom) and `"active"` (String) as disjoint types.

- **Complex Types as Strings**: If an LLM incorrectly passes a map or slice as the value for a target key (e.g., `"path": {"nested": "file.txt"}`), `extractTarget` might stringify the entire complex type using `%v` or JSON, resulting in a target string like `map[nested:file.txt]`. This would pollute the Mangle fact store with malformed targets. We need tests to ensure graceful rejection or safe coercion.
- **Numeric Extraction**: When an LLM passes an integer or float for a target (e.g., `"session_id": 12345`), JSON unmarshaling often converts this to a `float64`. If `extractTarget` doesn't explicitly format this (e.g., `fmt.Sprintf("%v", val)` vs type asserting), it might result in unexpected strings like `"12345.0"`.
- **Atom vs String Confusion**: When asserting `pending_action`, does the system correctly map strings from the tool arguments into Mangle strings, or does it accidentally coerce them into atoms? A test is needed to verify the exact type asserted.

### Mangle Engine Performance Considerations (Type Coercion)
Mangle's performance is highly dependent on type safety. If malformed strings or complex types are asserted into the kernel, they consume memory in the EDB (Extensional Database). While a few such facts won't degrade performance, they will cause rules to fail to fire (resulting in zero results). Since Mangle relies on fixpoint evaluation, an inability to join on a coerced type means the derivation halts early for that branch. It is highly performant in failing closed, but the memory pressure of the bad facts remains until retracted.

## Vector 3: User Request Extremes
The coding agent must withstand extreme constraints and brownfield complexity (e.g., 50-million-line monorepos).

- **Massive Atom Names**: While `maxPayloadBytes` guards the overall JSON payload, what if the `target` string extracted by `extractTarget` is just under the limit (e.g., 90KB)? Does the Mangle engine support 90KB atom names or strings in its fact store? We must test if `kernel.Assert` panics or degrades significantly when handling massive individual arguments.
- **Garbage Collection Pressure**: If a user request spawns a massive parallel plan executing 10,000 rapid concurrent `checkSafety` calls, the allocation of JSON marshaling, string formatting, and `pending_action` facts will thrash the garbage collector. We must stress-test the `Executor`'s lock contention and memory footprint under extreme concurrency.
- **Frontier Coding Benchmarks**: In complex environments, tool calls might contain deeply recursive ASTs or massive source code blocks inline. The system must truncate or reject these cleanly before hitting Mangle, as asserting a 100KB string into a monotonic logic store can cause significant performance degradation when joining.

### Mangle Engine Performance Considerations (Request Extremes)
Mangle is a declarative, monotonic engine designed for deterministic planning, not bulk data storage. Asserting massive strings or millions of concurrent facts violates its design assumptions. Under extreme load, the in-memory SimpleStore will suffer from elevated memory usage, and join operations (which involve set intersections) will slow down linearly or quadratically depending on the rule complexity. The executor's `maxPayloadBytes` is a vital defense, but Mangle itself might require stricter constraints on the maximum length of any single string argument within a fact to maintain sub-millisecond evaluation times.

## Vector 4: State Conflicts and Race Conditions
The `Executor` operates in a concurrent environment where the user context, agent configuration, and underlying workspace state are highly mutable.

- **Hot-Reloading Configurations**: We have a test `TestExecutorConfigSnapshotConcurrentSet` for configuration snapshots, but what if the `ToolRegistry` itself is mutated (e.g., a tool is added or removed by `generate_tool`) exactly while `checkSafety` is validating a call? We need a test for race conditions during `e.isToolAllowed` combined with safety validation.
- **Deleted Resources**: If a user attempts to act on a deleted resource (e.g., modifying a file that was just removed by another tool call), `checkSafety` itself won't fail (as it only validates policy), but the subsequent execution will. We need to verify that `pending_action` facts are correctly retracted even if the target resource causes the execution to panic or hang indefinitely.
- **Context Cancellation**: If the parent `context.Context` is violently canceled (e.g., user hits Ctrl+C) right after `kernel.Assert(pendingFact)` but before `kernel.Query`, does the deferred retraction reliably clean up the fact? A leaked `pending_action` fact could permanently brick subsequent actions in that session.

### Mangle Engine Performance Considerations (State Conflicts)
Mangle is stateful across a session. If a `pending_action` fact leaks due to a race condition or an incomplete `defer` block, it remains in the monotonic store. If the same action is attempted again, Mangle deduplicates identical facts (idempotency). However, if the leaky facts vary slightly (e.g., different timestamps or payload shapes), they will accumulate, causing a "memory leak" in the fact store. Over a long-running campaign, this will slow down all queries. The Mangle engine is performant enough to handle race conditions safely (assuming the store uses appropriate read/write locks), but the logical correctness of the program degrades if state is not meticulously managed.

## Extended Architectural Review: Boundary Value Integration with the OODA Loop

The executor sits at the heart of codeNERD's OODA (Observe, Orient, Decide, Act) loop. Its primary function is to transduce the non-deterministic output of the LLM into a deterministic action that the Mangle kernel can authorize and execute. The integrity of this transduction is tested across the boundary conditions we've identified.

### The Observation Phase: Handling Unknowns
During the "Observe" phase, the system ingests user inputs and environmental state. A critical boundary value here is the introduction of entirely novel or unrecognized data formats. For example, if a user uploads a binary file or a file with an unsupported encoding, how does the system represent this in Mangle?
- **Edge Case**: A file containing null bytes (\x00) or malformed UTF-8.
- **System Impact**: If this data is passed through a tool call (e.g., reading the file), the JSON marshaller might fail, or worse, the Mangle engine might fail to parse the string atom.
- **Testing Strategy**: We must introduce tests that inject malformed UTF-8 into `ToolCall.Args` and verify that `checkSafety` rejects it cleanly with a well-formed security violation fact, rather than crashing the transducer.

### The Orientation Phase: Mangle Schema Adherence
Orientation involves mapping observed facts to the internal schema (`schemas.mg`). The Mangle engine relies on strict type checking (Level 5 prevention in our Healing Hierarchy).
- **Edge Case**: Schema Drift. If an LLM generates a tool call that implies a new argument or a different data type for an existing argument, the orientation phase must reject it.
- **System Impact**: If a schema expects a `User.Type<Atom>` but the LLM provides a string literal, Mangle will fail to join (producing empty results).
- **Testing Strategy**: We need tests that deliberately mismatch Mangle types (passing raw strings where atoms are expected) and assert that the `Executor`'s validation layer catches this *before* asserting it to the engine, saving valuable compute cycles.

### The Decision Phase: Policy Evaluation Limits
The Mangle kernel evaluates the `pending_action` against the policy corpus. This evaluation must complete within a strict budget to prevent denial of service.
- **Edge Case**: Algorithmic Complexity Attacks. If a user requests an action that triggers a deeply recursive Mangle rule (e.g., a complex ACL check with transitive dependencies).
- **System Impact**: The Mangle engine could exceed its derivation limits or enter an infinite loop if cycle detection is flawed.
- **Testing Strategy**: We must introduce cyclic dependencies into the mock environment during a `checkSafety` test and ensure that the context timeout correctly terminates the Mangle query, returning a safe default-deny without leaking goroutines.

### The Action Phase: Execution Boundaries
The final step is executing the tool via the VirtualStore. The boundary here involves the transition from the deterministic Mangle environment back to the non-deterministic OS environment.
- **Edge Case**: Path Traversal and Option Injection. If an LLM attempts to execute a shell command or read a file using relative paths (`../../etc/passwd`) or injected flags (`--rm`).
- **System Impact**: A sandbox escape or unauthorized data access.
- **Testing Strategy**: `executor_boundary_test.go` must verify that `checkSafety` correctly identifies and blocks path traversal attempts by querying the Mangle kernel's `permitted` facts against an absolute path resolution, not just the raw string provided by the LLM.

## Deep Dive: Memory Pressure and Mangle's EDB

The Mangle Extensional Database (EDB) is the in-memory store for all facts during a session. Its performance characteristics are crucial for understanding the system's resilience.

1. **Monotonicity and Garbage Collection**: Mangle is monotonic within a single evaluation. Facts are added, never removed, until the evaluation completes. If `checkSafety` is called 10,000 times in a long-running session, and each call asserts temporary facts, those facts must be explicitly retracted or scoped to a fresh `FactStore`. The current design appears to use a session-scoped kernel, meaning deferred retractions are the only defense against memory leaks.
2. **Join Ordering**: When evaluating a rule like `permitted(Action, Target) :- pending_action(Action, Target, Payload), policy_allow(Action, Target).`, Mangle's query planner must decide the join order. If the `pending_action` relation grows massive (due to leaked facts), the join complexity increases.
3. **Atom Interning**: Mangle likely interns atoms (converting strings to integer IDs) to optimize joins. If an attacker can force the system to generate millions of unique atom strings (e.g., by randomizing the `Target` string in a loop), the interning table will grow unbounded, leading to an Out-Of-Memory (OOM) panic.

### Proposed Mitigations
- **Scoped Fact Stores**: Instead of relying on `defer kernel.Retract()`, `checkSafety` should ideally operate on a temporary, request-scoped `FactStore` that overlays the main session store. This guarantees that temporary facts are destroyed when the request completes, eliminating the risk of leaks from context cancellation.
- **Atom Generation Limits**: Implement a strict rate limit on the generation of novel atoms within a given timeframe to mitigate interning table exhaustion.

## The Interplay of Go's Garbage Collector and Mangle Evaluation

A significant area of concern for high-performance, long-horizon coding agents is the interaction between Go's Garbage Collector (GC) and the Mangle evaluation engine, particularly under sustained load.

### Allocation Profiles in `checkSafety`
Every call to `checkSafety` involves several allocations:
1. `json.Marshal(call.Args)`: Allocates a new byte slice. For a 90KB payload, this is a significant heap allocation.
2. `types.MangleAtom(actionName)`: If atoms are interned, this might involve a map lookup. If not, it's a string allocation.
3. `fmt.Sprintf("pending_action(%s, %s, %s)", ...)`: String concatenation allocates memory.
4. `kernel.Assert(pendingFact)`: The fact must be stored in the Mangle EDB, involving struct allocations and potentially slice appends.

Under a scenario where a complex plan requires hundreds of tool calls, these allocations add up rapidly. Go's GC is optimized for low latency, but high allocation rates will inevitably trigger frequent GC cycles, consuming CPU cycles that could otherwise be used for Mangle evaluation or LLM inference.

### GC Spikes and Latency Jitter
When the GC runs, it introduces latency jitter. In a tight OODA loop, unpredictable latency can disrupt the flow of execution, especially if the agent is interacting with time-sensitive external systems (e.g., live preview servers or network sockets).
- **The Threshold Effect**: The `maxPayloadBytes` limit (100KB) is a blunt instrument. While it prevents single massive allocations, it does not prevent 1,000 concurrent 99KB allocations.
- **Stress Test Design**: We need a stress test that explicitly measures GC pause times while firing concurrent `checkSafety` calls. If pause times exceed a predefined threshold (e.g., 50ms), the test should fail. This enforces a performance contract on the boundary layer.

### Memory Fragmentation
As temporary facts are asserted and retracted, the Mangle EDB's underlying memory structures (slices, maps) may become fragmented. Go handles fragmentation reasonably well, but over a multi-hour coding session, fragmented memory can lead to increased heap sizes and inefficient cache utilization.
- **Compaction Strategy**: The system might need a periodic "compaction" phase where the Mangle EDB is paused, reachable facts are copied to a contiguous memory block, and the old fragmented block is discarded.
- **Testing for Fragmentation**: This is notoriously difficult to test in a unit test environment. It requires long-running integration tests (campaigns) combined with continuous memory profiling (`pprof`) to detect long-term degradation.

## Transduction Interface Resilience

The transducer interface is the bridge between the natural language/code domain and the formal logic domain. It is inherently lossy.

### The Lossy Nature of Extraction
When `extractTarget` reduces a complex `map[string]any` down to a single string `target`, information is lost.
- **Ambiguity**: If a tool call contains both a `path` and a `url`, which one is the true target? The current implementation uses a hardcoded precedence list.
- **Security Implications**: An attacker (or a hallucinating LLM) could craft a payload with a benign `path` (which satisfies the policy) and a malicious `url` (which is executed by the tool but ignored by `checkSafety`).
- **Testing Mitigation**: We must write tests that intentionally provide multiple conflicting candidate keys (e.g., `{"path": "safe.txt", "url": "malicious.com"}`) and assert that the executor either rejects the ambiguity or that the Mangle policy explicitly validates *all* relevant keys, not just the primary target.

### Structural vs. Semantic Validation
`checkSafety` primarily performs structural validation (does it fit the schema? is it too large?). Semantic validation (is this action safe in this context?) is offloaded to Mangle.
- **The Gap**: If the structural validation successfully parses a structurally sound but semantically malicious payload (e.g., a well-formed JSON object containing a path traversal), the burden falls entirely on Mangle.
- **Defense in Depth**: The Go layer should implement cheap, heuristic semantic checks (e.g., `filepath.IsLocal()`) before asserting to Mangle. This saves Mangle from evaluating trivially malicious actions.

## Advanced Scenario Analysis: Mangle Evaluator Under Adversarial Conditions
A core assumption of the Executor boundary is that structural checks (e.g., `maxPayloadBytes`) are sufficient to protect the Mangle kernel from denial-of-service (DoS). However, this ignores the nature of logic programming evaluation.

### Adversarial Payload Shaping
An attacker could shape a payload that is small in bytes but computationally explosive for Mangle to evaluate.
- **The "Billion Laughs" Equivalent in Datalog**: If the LLM generates a payload that exploits recursive rules in the policy corpus, it could trigger an exponential number of derivations. For example, if a policy has rules like `p(X, Y) :- q(X, Z), q(Z, Y)` and the payload injects facts that form a dense graph, Mangle's fixpoint evaluation could hang.
- **Boundary Responsibility**: The Executor is currently blind to the *semantic density* of the payload. It only checks byte length.
- **Testing Approach**: We must create a test corpus of "explosive" JSON payloads (e.g., deeply nested but short strings that map to complex graph structures in Mangle) and verify that the `Executor`'s timeout wrapper correctly intercepts and kills the evaluation thread before it starves other goroutines.

### The Problem of Silent Failures in Logic Resolution
In traditional imperative boundaries, a malformed request usually results in an exception (e.g., `400 Bad Request`). In the Mangle boundary, a malformed request often results in *zero derivations* (empty set).
- **False Negatives in Safety**: If the LLM requests an action that *should* be allowed, but typos the action name (`/read_fil` instead of `/read_file`), Mangle will return an empty set. The Executor interprets this as "denied by policy" rather than "invalid request format".
- **Impact on OODA**: The LLM receives a generic "action denied" message and gets stuck in a loop trying to guess why it was denied, wasting token budget.
- **Testing Mitigations**: The Executor must differentiate between "Evaluation succeeded and returned zero results (Denied)" and "Evaluation failed due to unbound variables or type mismatches (Error)". We need tests asserting that type mismatch errors from Mangle are surfaced correctly to the LLM, not swallowed as generic denials.

## Architectural Bottlenecks: The FactStore Mutex
The current implementation appears to use a session-level `FactStore`. This means that all concurrent tool executions within a session share the same Mangle EDB.
- **Lock Contention**: `kernel.Assert` and `kernel.Retract` must acquire write locks on the EDB. If multiple tools are executing concurrently (e.g., via a parallel test runner or an advanced agent strategy), these locks will contend heavily.
- **Test Gap**: There are no tests in `executor_boundary_test.go` that simulate high-concurrency read/write operations against the shared `kernel`.
- **Recommendation**: We should implement a `TestExecutor_ConcurrentAssertRetract` that spawns 100 goroutines, each simulating an LLM tool call, and asserts that no deadlocks occur and that the final state of the EDB is completely clean (all pending facts retracted).

## Type Coercion: The Subtleties of JSON Number parsing
JSON does not differentiate between integers and floats. Go's `encoding/json` decodes numbers to `float64` by default when decoding into an `any` interface.
- **The Mangle Impact**: If a tool expects an integer ID (e.g., `123`), the JSON unmarshaler produces `float64(123)`. If `extractTarget` stringifies this blindly using `%v`, it might produce `"123"` or it might produce `"123.0"` depending on internal formatting.
- **Type Mismatch in Rules**: If the policy rule expects an integer atom `/123`, but the asserted fact contains the string `"123"`, the join fails.
- **Testing Strategy**: We need a dedicated test `TestExecutor_NumericExtraction` that explicitly passes integers, large integers (exceeding int32 bounds), and floats to `checkSafety`, and verifies that the resulting Mangle fact contains the exact, correctly typed primitive expected by the schema.

## Extreme State Conflicts: The "Zombie Fact" Scenario
A critical edge case involves the failure of the `defer kernel.Retract()` mechanism.
- **The Scenario**: `checkSafety` asserts `pending_action`. The policy evaluation begins. Before evaluation finishes, the underlying network connection is closed, triggering a context cancellation. The `defer` block executes, but if the `Retract` function itself respects the now-canceled context, it might return early without actually deleting the fact from the EDB.
- **The Result**: A "Zombie Fact" is left in the store. Subsequent runs of the agent in the same session will now evaluate against this stale fact, potentially granting unauthorized access if a new rule suddenly makes that action permissible.
- **Testing Approach**: We must write a test that forcefully injects a canceled context *during* the evaluation phase, waits for the goroutine to unwind, and then performs a bare query on the `FactStore` to verify it is absolutely empty. This ensures the retraction logic uses a detached or background context, guaranteeing cleanup.

## Integration Guide: Writing High-Leverage Mangle Tests for the Executor

Based on the analysis of common AI failure modes in this codebase, the following architectural patterns must be employed when implementing the newly identified `TEST_GAP` items in `executor_boundary_test.go`.

### 1. The "Clean Slate" Fact Store Requirement
When writing tests for State Conflicts and Context Cancellation, we must never reuse a Mangle store across test iterations.
- **The Pitfall**: Mangle’s evaluation is monotonic and stateful. Reusing a store leads to "ghost facts" from previous runs contaminating the current fixpoint. A test checking for "empty results" will fail if the store retains facts from a prior "success" test.
- **The Pattern**: Always instantiate a fresh `factstore.NewSimpleInMemoryStore()` (or the mock equivalent) inside every `t.Run` loop. This ensures idempotency and guarantees that state conflicts are tested in isolation.

### 2. The Analysis Phase (`analysis.Analyze`) vs Raw Execution
When testing adversarial payloads, do not just run `kernel.Query` directly if testing raw rule evaluation.
- **The Pitfall**: Running unanalyzed rules can lead to Stratification Errors (negation cycles like `p :- not p`) or Safety Errors (unbound variables) that manifest as silent runtime failures or infinite loops depending on the engine's strictness.
- **The Pattern**: For deep boundary testing, the test should explicitly parse the rules and run `analysis.Analyze(program)` before evaluation. This proves the rules are safe and stratifiable. A test that skips this might pass on a permissive engine configuration but fail in strict production environments.

### 3. Enforcing Type-Strict AST Helpers
When testing the Type Coercion gaps, we must use precise AST constructors.
- **The Pitfall**: The most common AI failure is the "Atom/String Dissonance". Mangle treats `/active` (Atom) and `"active"` (String) as disjoint types. Passing raw Go strings often defaults to Mangle strings, causing joins to fail silently.
- **The Pattern**: Use helpers that force you to choose the type. `ast.Name("active")` corresponds to `/active`. `ast.String("active")` corresponds to `"active"`. Tests must explicitly verify which type the `Executor` is asserting.

### 4. Avoiding "Stringly Typed" Assertions
When validating the output of `checkSafety` or the contents of the Mangle store, avoid converting results to strings for comparison (e.g., `res.String() == "p(/a)"`).
- **The Pitfall**: Datalog sets are unordered. `[A, B]` is logically identical to `[B, A]`, but their string representations differ. String matching leads to flaky tests.
- **The Pattern**: Use set membership checks (e.g., `store.Read(...)`) to verify specific facts exist within the kernel, regardless of ordering.

### 5. Managing the "Forgotten Sender" (Goroutine Leaks)
When testing Context Cancellation scenarios, we must be vigilant about goroutine leaks.
- **The Pitfall**: If a test fails an assertion early and returns, and the Mangle engine's goroutine is trying to send the next result to an unbuffered channel, it will block forever, leaking memory.
- **The Pattern**: Always use `context.WithCancel` and `defer cancel()` at the top of the test function to ensure the engine stops immediately when the test finishes, even on failure.
