# QA Journal: Articulation Layer Boundary Value Analysis
## Date: 2026-09-27 00:12:22 EST

### Subsystem Studied: `internal/articulation/emitter.go` (ResponseProcessor)

The Articulation layer (`emitter.go`) is responsible for parsing the 'Piggyback Protocol' responses from the LLM, separating the `surface_response` intended for the user from the `control_packet` intended for the kernel. This acts as the critical barrier preventing LLM output from hallucinating kernel commands directly or leaking raw internal states to the user. The primary worker is `ResponseProcessor.Process`, which attempts JSON parsing, fallback regex parsing (`extractEmbeddedJSON`), and finally plain text fallback.

While the current test suites (`emitter_test.go`, `emitter_boundary_test.go`) cover structural robustness, massive strings, and decoy injections, there are significant edge cases related to input handling, type coercion limits, and state conflicts that are missing.

### Architectural Considerations & Performance Metrics

The current `ResponseProcessor` is designed to be resilient, favoring the recovery of user-facing text over strict protocol adherence. This is a sound product decision, but it opens the door to performance vulnerabilities in the fallback layer.

1.  **String Scanning Overhead**: The `extractEmbeddedJSON` and `salvageSurfaceFromPartial` functions use iterative string scanning. In the worst case (e.g., highly fragmented, nested decoy JSON), this can degrade. We should measure the latency of parsing a 100KB malformed JSON string. If it exceeds 10ms, we might need a more optimized parser (e.g., a hand-rolled state machine).
2.  **Memory Allocation**: `Process` allocates multiple strings and structs. For large payloads, this causes GC pressure. We could investigate using `sync.Pool` for byte buffers if profiling shows `ResponseProcessor` as a memory hotspot.
3.  **Security boundaries**: The articulation layer is the final guard before executing kernel commands. Any bug that allows user input to masquerade as a `control_packet` is a critical vulnerability. The 'decoy injection' tests are good, but we must continually expand the arsenal of evasion techniques tested against `extractEmbeddedJSON`.
4.  **Hardware Constraints**: The prompt specifies running on an 8GB RAM laptop. The Mangle engine itself is memory intensive. The `ResponseProcessor` must operate within a strict memory budget, meaning we cannot afford to load 50MB strings into memory multiple times. Streaming parsers might be necessary for extremely large responses in the future.
5.  **Telemetry and Alerting**: The `stats` struct tracks parsing failures. We need specific alerting if the `FallbackParses` ratio exceeds 5%. This indicates the LLM is consistently failing to generate valid JSON, which might signal a prompt degradation or model drift.

### Conclusion

The `emitter.go` subsystem is robust against standard failures, but the boundary value analysis reveals gaps in handling explicitly null values, complex type coercions, extreme user request evasion tactics, and high-concurrency contention on the statistics mutex. Implementing the TODOs added to `emitter_test.go` will significantly harden the articulation layer against these edge cases.
