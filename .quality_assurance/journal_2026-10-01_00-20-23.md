# QA Journal - Boundary Value Analysis & Negative Testing
## Date: 2026-10-01 00:20:23 EDT
## Target Subsystem: `internal/mangle/schema_validator.go`

### 1. Introduction and Scope

This journal entry documents a deep-dive Boundary Value Analysis (BVA) and Negative Testing review of the Mangle
engine's Schema Validator subsystem within the codeNERD framework. As a QA Automation Engineer specializing in edge case
discovery and system resilience, my objective is to evaluate the robustness of `SchemaValidator`, specifically focusing
on how it handles unexpected, malformed, malicious, or extreme inputs. The `SchemaValidator` acts as a crucial
gatekeeper in the neuro-symbolic loop. It ensures that rules generated by the LLM (the 'learner') conform strictly to
the declared schemas, preventing hallucinated predicates, arity mismatches, and schema drift from polluting the
deterministic fact store.
The evaluation explores four primary vectors:

1. **Null/Undefined/Empty**: Handling of absent or semantically void inputs.

2. **Type Coercion**: Handling of structural mismatches and syntax violations.

3. **User Request Extremes**: System behavior under massive scale, ReDoS attacks, and frontier-level loads.

4. **State Conflicts**: Concurrency issues and temporal race conditions.


### 2. Architectural Context of Mangle Schema Validation

The `internal/mangle` package is a deterministic rule engine that parses, evaluates, and validates rules over an
in-memory fact store. The `SchemaValidator` is responsible for parsing `Decl` schemas and enforcing them on both
hand-written and LLM-generated rules. The engine's integrity depends entirely on the validator correctly identifying and
rejecting invalid rules before they can be added to the program. The validator uses regular expressions extensively
(e.g., `declHeadPattern`, `predicatePattern`, `learnedHeadPattern`) to extract predicate names and arguments. This
regex-heavy approach introduces significant vulnerabilities regarding state transitions, parser desynchronization, and
performance under extreme conditions.

### 3. Vector Analysis: Null, Undefined, and Empty States

The first category of boundary values involves the absence of expected data. How does the validator behave when inputs
are theoretically valid but semantically empty?
#### 3.1 Empty Strings and Whitespace Variations

The `ValidateRule` method relies on `splitRuleBody` to separate the head from the body. If a rule consists solely of
whitespace, or whitespace followed by a period (` .`), `splitRuleBody` returns `isRule=false`. However, what happens if
the input is `:- .`? The `splitRuleBody` function identifies `:-` and returns ` .` as the body. The `predicatePattern`
regex (`([a-z_][a-z0-9_]*)\s*\(`) will not match anything in ` .`. Consequently, the loop checking for undefined
predicates will execute zero times, and the function will return `nil` (success). This means a completely invalid, empty
rule body can bypass validation. To mitigate this, the engine needs explicit checks for syntactically complete rules,
not just the absence of undefined predicates. The test suite lacks coverage for `:-` with no subsequent predicates.

#### 3.2 Null Bytes and Binary Payloads

A common negative testing vector is injecting null bytes (`\x00`) into string inputs. Since Go strings can contain
arbitrary bytes, a rule text like `candidate_action(/test\x00) :- user_intent(...)` might be parsed by the regexes in
unexpected ways. If the underlying `analysis.AnalyzeOneUnit` fails gracefully, the system is safe. However, regex
engines often exhibit anomalous behavior when encountering null bytes mid-string. If the null byte truncates the string
during a CGO call or regex evaluation, the validator might greenlight a rule that later crashes the parser or engine. We
must test rules containing embedded nulls.

#### 3.3 The 'Undefined' Fact Store State

The validator assumes that `schemasText` and `learnedText` represent the totality of the schema. What if an LLM is
prompted to define rules but no schema has been loaded yet? The `declaredPredicates` map will be empty. Any rule with a
body will be rejected. This is the correct fail-closed behavior. However, the tests do not explicitly verify this
'zero-schema' state. We need tests that initialize the validator with empty schemas and assert that *every* body
predicate is rejected, preventing the engine from bootstrapping with hallucinated schemas.

### 4. Vector Analysis: Type Coercion and Structural Mismatches

Type coercion in this context refers to situations where the LLM produces output that resembles Mangle syntax but
violates the structural grammar, forcing the regex parser to make incorrect assumptions.
#### 4.1 String/Atom Confusion in Rule Bodies

Mangle differentiates between atoms (e.g., `/active`) and strings (`"active"`). The regex `predicatePattern` looks for
`([a-z_][a-z0-9_]*)\s*\(`. What happens if the LLM generates a rule where a string literal happens to contain a
predicate-like structure? For example: `log_message("error: undefined_predicate(X) occurred")`. The `splitRuleBody`
function attempts to handle strings, but its implementation is naive: it just toggles an `inString` boolean. If
`ValidateRule` extracts the body, does the regex match inside the string? Looking at `ValidateRule` (lines 173-195), it
searches the *entire* body using `predicatePattern`. It does not strip strings first. Therefore, the string `"error:
undefined_predicate(X) occurred"` will cause `undefined_predicate` to be flagged as an undefined predicate, falsely
rejecting a valid rule. This is a critical false positive.

#### 4.2 Malformed Declarations and Arity Coercion

The `extractDeclsFromText` function parses `Decl` statements. It relies on `countTopLevelArgs` which, presumably, counts
commas. If a schema defines a complex type bound with commas, e.g., `Decl my_pred(A) bound [fn(/a, /b)]`, the comma
inside the bound list might be counted as an argument separator if `countTopLevelArgs` isn't robust. This leads to an
incorrect expected arity. If the schema has an incorrect arity, `CheckArity` will falsely reject perfectly valid rules
or accept invalid ones. The test suite needs to explicitly test schema declarations with nested parentheses, brackets,
and commas to ensure the regex/parsing logic correctly identifies top-level arguments only.
#### 4.3 Numeric Predicates and Identifiers

What happens if a predicate name starts with a number? Mangle grammar might forbid it, but what does the validator do?
The regex `[a-z_][a-z0-9_]*` explicitly requires a letter or underscore first. If a rule is `123bad(X) :- valid(X).`,
the regex will completely ignore `123bad` when scanning for predicates. If it's in the body, it won't be flagged as
undefined, meaning an invalid syntax could slip past the schema validator. While the parser might catch it later, the
*schema validator* is failing its specific contract. We must test identifiers that violate the regex constraints but are
passed to the validator.

### 5. Vector Analysis: User Request Extremes and Performance

The system must remain performant and stable even when handling extreme edge cases, such as massive monorepos or
maliciously crafted inputs designed to cause Resource Exhaustion (ReDoS).
#### 5.1 ReDoS (Regular Expression Denial of Service)

The `predicatePattern` is `([a-z_][a-z0-9_]*)\s*\(`. The `\s*` quantifier can be problematic if applied to extremely
long strings of spaces. A more concerning regex is likely `declHeadPattern` or `headPattern`. If an LLM generates a rule
with 50,000 spaces between the predicate name and the opening parenthesis, e.g., `candidate_action (...)`, the regex
engine has to process this. While Go's `regexp` package guarantees linear time complexity (`O(N)`) and is generally
immune to catastrophic backtracking (unlike PCRE), it still requires memory proportional to the input size. Passing a
100MB string to the regex engine will cause a massive allocation. The system needs bounds checking on the size of the
rule text *before* regex processing begins. The tests should include a 'megabyte-sized rule' test to measure performance
and memory allocation.

#### 5.2 Extreme Arity and Recursive Depth

What if an LLM is asked to generate a schema for a database table with 10,000 columns? The `countTopLevelArgs` function
will have to iterate through a massive string. If it's a recursive parser, it could hit a stack overflow. If it's
iterative, it might just be slow. A test should dynamically generate a `Decl` with 10,000 arguments and verify that
`extractDeclsFromText` can parse it within an acceptable time threshold (e.g., < 100ms). This tests the system's ability
to handle frontier-level database schemas.
#### 5.3 Massive Rule Sets

The `ValidateRules` function takes a slice of strings. If an LLM campaign generates 500,000 candidate rules,
`ValidateRules` iterates through all of them. The `sv.declaredPredicates` map is accessed concurrently if multiple
goroutines call `ValidateRules` (though the current signature doesn't imply concurrency). However, the sequential
processing of 500k rules using regexes will be a significant bottleneck. The performance test should benchmark
`ValidateRules` with 100,000 valid and invalid rules to determine the throughput (rules/second) and ensure it meets
real-time requirements for the JIT loop.

### 6. Vector Analysis: State Conflicts and Concurrency

State conflicts arise when the system's internal state is mutated while it is being read, or when sequence dependencies
are violated.
#### 6.1 Concurrent Map Reads and Writes

The `SchemaValidator` uses `sv.declaredPredicates` and `sv.predicateArities` maps. The `HotLoadRule` method (line 272)
exists. If `HotLoadRule` parses a new declaration and mutates the maps, what happens if `ValidateRule` is running
concurrently in another goroutine? Go's map implementation is not safe for concurrent read/write. If `HotLoadRule`
updates the map while `ValidateRule` is checking `sv.declaredPredicates[predicate]`, the program will `panic` with a
concurrent map read and map write error, taking down the entire codeNERD process. The `SchemaValidator` lacks a
`sync.RWMutex`. The test suite *must* include a concurrency test: a goroutine loop calling `ValidateRule` while another
loop calls `HotLoadRule` or `SetPredicateArity`.
#### 6.2 Temporal Inconsistency in Schema Loading

If `LoadDeclaredPredicates` is called twice, it overwrites existing maps. If an error occurs during the second load
(e.g., malformed syntax), the maps might be left in a partially updated, inconsistent state. The function should parse
everything into temporary maps and atomically swap them, or return an error without modifying the validator's state. The
tests need to verify that a failed `LoadDeclaredPredicates` call does not corrupt the previously loaded, valid schema
state.

### 7. Proposed Test Improvements and Action Items

Based on the Boundary Value Analysis, the following explicit tests must be added to `schema_validator_test.go`:

1. **Concurrency Panic Test**: Create a test with `go` routines that simultaneously call `ValidateRule` and
`SetPredicateArity`. This will almost certainly trigger a race detector failure or panic, proving the need for a mutex.
2. **String Literal Regex False Positive**: Test `ValidateRule` with a body containing `some_pred("fake_pred(X)")`.
Verify that `fake_pred` is *not* flagged as undefined.
3. **Empty Rule Body Validation**: Test `ValidateRule(":- .")` and `ValidateRule("head(X) :-")`. These should be
rejected, but currently might pass due to regex misses.
4. **Extreme Arity Benchmark**: Test a `Decl` with 10,000 arguments to ensure O(N) parsing complexity without stack
overflow.
5. **Null Byte Injection**: Test `ValidateRule` with embedded `\x00` characters to ensure the regex engine and string
boundary logic handle it gracefully.
6. **Malformed Identifiers**: Test rules where predicates start with numbers (e.g., `123_invalid(X)`) to verify that the
schema validator correctly identifies the syntax error or delegates it appropriately without silently passing.
7.  **State Preservation on Failure**: Test that a failed schema load does not destroy previously declared predicates.


### 8. Conclusion on Performance and Resilience

The `SchemaValidator` is currently highly reliant on regular expressions for parsing, which is a known anti-pattern for
complex grammars, leading to vulnerabilities with strings containing parenthesis (Vector 4.1). While performant for
typical inputs, the lack of concurrency control (Vector 6.1) makes it entirely unsuitable for a multi-threaded JIT loop
where schemas might be hot-reloaded dynamically. The system is performant enough to handle normal loads, but extreme
lengths or ReDoS vectors will linearly degrade performance. To be production-ready for codeNERD's rigorous demands, the
validator must replace naive regexes with a proper AST traversal for rule validation and introduce `sync.RWMutex` for
state management. The identified gaps highlight the necessity of negative testing in ensuring the neuro-symbolic
engine's reliability against LLM hallucinations.

### 9. Deep Dive: The Parse vs Validation Dichotomy

A fundamental architectural issue discovered during this BVA is the separation between parsing (ast/analysis) and
regex-based schema validation. Mangle has a robust `analysis.AnalyzeOneUnit` function which builds a proper AST and
performs stratification and safety checks. However, `SchemaValidator.ValidateRule` attempts to bypass this by acting as
a fast-path regex filter.
This dual-path architecture means the parser and the validator can disagree on what a rule actually means. If the
validator's regex is more permissive than the parser, an invalid rule is caught later. But if the validator's regex is
*less* permissive or misinterprets structure (like the string confusion issue), it falsely rejects valid logic.
Testing must target the delta between these two systems. Generate inputs where the regex state machine desynchronizes
from the AST tree state.
For example, nested comments: `# comment
 head :- body.` vs inline comments `head :- #comment
 body.`
The `splitRuleBody` and regex filters must perfectly emulate the whitespace and comment swallowing logic of the true
parser.

### 10. Deep Dive: Unicode and Multi-byte Character Boundaries

Mangle predicates are defined as `[a-z_][a-z0-9_]*`. This explicitly restricts to ASCII. However, Go strings are UTF-8.
If an LLM hallucinates a predicate with a visually similar unicode character (e.g., a Cyrillic 'а' instead of an ASCII
'a'), the regex `[a-z_]` will fail to match it.
If `а_bad_pred(X)` is in the body, the regex engine skips it. It won't be collected in the `matches`, and therefore
won't be checked against `declaredPredicates`. The rule passes validation.
Later, if the true parser accepts unicode (or fails in a different way), the schema validator has failed its gatekeeping
role. We must inject a comprehensive suite of homoglyph and multi-byte boundary tests to ensure the system fails closed
on non-ASCII identifiers, rather than silently ignoring them.

### 11. Deep Dive: Memory Profiling Under Duress

In a long-running campaign, the codeNERD agent might generate tens of thousands of candidate rules. `SchemaValidator` is
instantiated and used heavily.
The `FindAllStringSubmatch` calls allocate slices of strings for every match. If a rule has 50 predicates in its body (a
complex join), the regex engine allocates heavily.
A dedicated `BenchmarkSchemaValidator` must be written that feeds it a synthetic file containing 10,000 rules, each with
20 body predicates. We must run this with `-benchmem` to track allocations.
If `SchemaValidator` allocates excessively, it will trigger frequent Garbage Collection (GC) pauses, destroying the JIT
loop's low-latency guarantees.
The fix would likely involve `sync.Pool` for regex match buffers or abandoning regex entirely for a zero-allocation byte
scanner.

### 12. Deep Dive: Mangle Built-in Predicates Masking

The `isBuiltin` function hardcodes a list of internal predicates. What happens if a `Decl` attempts to redefine a
built-in? E.g., `Decl :lt(A, B) bound [/number, /number].`
If the system loads this, `sv.declaredPredicates[":lt"] = true`. If an LLM then generates a rule using `:lt` with wrong
arity or types, the validator might be confused between the built-in semantics and the declared semantics.
The test suite must explicitly assert that loading a schema containing built-in redefinitions either returns a hard
error or properly namespaces them (which Mangle likely doesn't support). This is a critical security boundary to prevent
LLMs from overriding core arithmetic or structural operators.

### 13. Deep Dive: The Threat of `LoadDeclaredPredicates`

This function reads schemas from text. If the text source is partially user-controlled (e.g., reading a schema file from
a cloned, untrusted repository), a malicious repository could include a massive, malformed `schemas.mg`.
If the regex parsing of the schema is vulnerable to ReDoS or extreme memory allocation, simply *loading* the schema file
acts as an attack vector against the codeNERD agent, before any LLM inference even occurs.
We must write a fuzzer specifically for `schemas.mg` input to `LoadDeclaredPredicates` to ensure it bounds execution
time and memory regardless of input garbage.

### 14. Further Exploration on Arity State

The arity tracking (`predicateArities`) is currently just an integer count. Mangle supports polymorphic predicates or
varargs in some contexts? If not, the integer count is sufficient.
However, what if a schema declares the same predicate twice with *different* arities? `Decl foo(A). Decl foo(A, B).`
The current regex loop simply overwrites `sv.predicateArities[predicate]` with the last one seen.
This means the earlier declaration is silently shadowed. An LLM using `foo(A)` will be flagged for an arity mismatch,
even though it was technically declared. The validator should either reject duplicate declarations or support
multi-arity lookup.
A test must be written to inject conflicting schema declarations and verify the system's conflict resolution policy
(preferably a strict error).

### 15. The `LearnedHeadProtection` Context

The `LearnedHeadProtection` struct is passed dynamically. It includes `HostOnly` maps.
If the host-only map is large, and validation runs per-rule, the overhead of checking `p.protectedHead(h)` for every
learned rule might dominate CPU time.
We should profile the performance of `ValidateLearnedRuleProtected` when `HostOnly` contains 1000+ entries, a realistic
scenario for a complex operating environment with extensive host bindings.

### 16. Syntactic Sugar and Desugaring Failures

Mangle supports syntactic sugar. If an LLM generates a rule using sugar that expands into multiple internal predicates,
does the `SchemaValidator` see the sugar or the desugared AST?
Since it operates on raw strings, it sees the sugar. If the sugar implies the use of a predicate that isn't explicitly
declared, the validator might falsely accept it (if the regex misses it) or falsely reject it (if it doesn't understand
the sugar syntax).
This further reinforces the need to move validation to the AST level, post-desugaring, rather than relying on brittle
string matching at the perimeter.

### 17. Final Synthesis

The `SchemaValidator` is a critical component that currently relies on an architectural shortcut (Regex) to perform
semantic validation. While it works for the 'Happy Path', this Boundary Value Analysis has demonstrated numerous vectors
where Type Coercion, Unicode boundaries, String confusion, and State Conflicts can either bypass the validator entirely
or crash the agent.
The immediate next steps are to implement the 7 proposed test improvements to definitively prove these gaps exist in CI,
and subsequently refactor the validation logic to rely on the robust `analysis` package AST rather than regular
expressions.
