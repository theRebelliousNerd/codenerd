## 1. Executive Summary & Context

I have conducted a deep review of the `delegation_decision` module and its accompanying test suite. The system is responsible for critical Mangle-driven routing decisions regarding shard delegation, particularly how findings are ranked to determine target files and how intent verbs are mapped to execution modes (`/parallel`, `/advisory`, `/advisory_with_critique`).

The test suite provides basic coverage of tie-breaking mechanics and default fallback behavior. However, they are strictly "happy path" or mildly constrained scenarios (e.g., standard severity labels, normal strings). As a high-performance neuro-symbolic system, the boundaries must be tested against adversarial inputs, extreme load, and malformed facts generated by stochastic LLM operations.

This analysis evaluates the current test posture against four major Boundary Value vectors: Null/Undefined/Empty states, Type Coercion boundaries, Request Extremes (e.g., memory bounds, non-standard payloads), and State Conflicts (e.g., concurrency races on the shared kernel).

## 2. Null/Undefined/Empty Vector Analysis

The system handles JSON outputs from upstream LLMs, which are inherently untrustworthy.

### Current Coverage:
The tests verify that a finding containing a generic empty string for a file name (e.g., `{"file": "   ", "severity": "high"}`) is gracefully ignored. This prevents the system from delegating a shard to a non-existent blank file.

### Gaps Identified:
*   **Nil Findings Array:** What happens if the `findings` payload isn't an empty array, but actually `nil`? The Go map decoding might yield `nil`. Passing a `nil` slice to `delegatedFile` might cause a panic if not explicitly guarded.
*   **Nil Value Injection:** An LLM might generate a finding where the key exists, but the value is explicitly `null` in JSON (e.g., `{"file": "a.go", "severity": null}`). The current Go extraction logic might attempt a blind type assertion `f["severity"].(string)`, leading to a runtime panic.
*   **Empty Verb String:** The `derivedExecutionMode` function maps intent verbs to Mangle-defined execution modes. If the verb string is perfectly empty `""`, the system must handle it. While `TestNilKernelKeepsTheGenericTarget` briefly touches on this without a kernel, we need a parameterized test evaluating an empty verb string against the *real* Mangle kernel to ensure it doesn't cause a syntax error during dynamic query generation.

## 3. Type Coercion Vector Analysis

The `cmd/nerd/chat` package expects strings for both the `file` and `severity` fields to properly rank delegation targets and construct the `delegation_target_file` fact.

### Current Coverage:
The tests completely lack type coercion edge cases. They assume the `extractFindings` logic or JSON unmarshaler has guaranteed string types.

### Gaps Identified:
*   **Numeric Coercion on Severity:** If an LLM decides to rank severity numerically (e.g., `{"file": "a.go", "severity": 1}`), the system will likely fail to match the string-based Mangle taxonomy (like `/high`, `/critical`). Worse, if the Go code attempts a string type assertion, it panics. We need tests to ensure numeric types are safely cast to strings or rejected without crashing the system.
*   **Complex Object Coercion:** An adversarial LLM output might nest objects: `{"file": ["a.go", "b.go"], "severity": {"level": "low"}}`. Passing these arrays or nested maps into the `delegation_target_file` logic will break the `ExtractString` assumptions. The test suite must simulate these complex payloads to verify the extraction layer drops them safely rather than escalating a panic to the main orchestrator loop.
*   **Type Confusion in Mangle:** Mangle distinguishes between Atoms (e.g., `/fix`) and Strings (e.g., `"fix"`). The tests must verify that passing a raw string where an Atom is expected (or vice versa) during fact assertion fails gracefully and defaults to the `/parallel` mode, rather than failing silently or hanging the engine.

## 4. User Request Extremes Vector Analysis

The `codeNERD` framework is designed to work on large monorepos (e.g., 50 million lines) on consumer hardware (e.g., 8GB RAM).

### Current Coverage:
The tests handle a maximum of 4 concurrent findings in their tie-breaking scenarios. There is no stress testing or boundary validation on the size of the inputs.

### Gaps Identified:
*   **Extreme Path Lengths:** What if a file path is 100,000 characters long? When the system generates the task string via `formatShardTaskWithContext`, allocating such a massive string could cause memory spikes. The Mangle fact store might also struggle to intern a 100k character Atom. Tests must verify the system truncates or rejects absurdly long file paths.
*   **Extreme Findings Volume:** A "review everything" request on a massive monorepo might generate 1,000,000 findings. The current `delegatedFile` logic uses an $O(N)$ loop to find the worst severity. While fast in Go, generating 1,000,000 maps and passing them through the Mangle translation layer might exhaust available RAM. We need a test simulating 1M findings to verify memory consumption remains under a strict threshold (e.g., 50MB).
*   **Non-UTF8 / Malicious Payloads:** The `file` field is passed down to other shards. If the LLM generates a path containing null bytes (`\x00`), directory traversal strings (`../../etc/passwd`), or invalid UTF-8 sequences, the `delegationTargetFile` might accept it, but downstream tools will fail. We need tests to verify that these extreme strings are sanitized before being used as delegation targets.

## 5. State Conflicts & Concurrency Vector Analysis

The `delegation_decision_test.go` suite utilizes a globally shared kernel, initialized once via `sync.Once`.

### Current Coverage:
The tests execute serially. They mutate the kernel state (e.g., `_ = k.Retract("asked_delegation_verb")`) to test specific fallback rules.

### Gaps Identified:
*   **Mangle Engine Race Conditions:** Mangle's `Query` is generally thread-safe, but interleaving `Retract` and `LoadFacts` across concurrent goroutines leads to non-deterministic fixpoints. We need a test using `sync.WaitGroup` to launch 100 concurrent calls to `derivedExecutionMode` with different verbs to ensure the underlying kernel interactions (if any state is mutated) do not trigger the Go Race Detector.
*   **Shared State Pollution in Tests:** The `TestExecutionModeMatchesTheVerbTable` test modifies the shared kernel state to test the fallback behavior for `/no_such_verb`. Because there is no `t.Cleanup` to restore the state, any subsequent test added to this file might fail unpredictably. We must refactor the test suite to use isolated kernel clones or implement strict teardown mechanics.

## 6. Subsystem Performance Profile & Bottleneck Analysis

Is the system performant enough to handle these edge cases?

The core delegation logic relies heavily on the Mangle engine. Based on the `TestExecutionModeMatchesTheVerbTable` test, querying the `execution_mode` involves evaluating Datalog rules against the active fact store.

1.  **Atom Interning Overhead:** Mangle heavily interns strings to Atoms to optimize join performance. If we process 100,000 findings with unique file names, we will generate 100,000 unique Atoms. Go maps (which Mangle uses for interning) do not shrink. A sustained burst of unique file names across many chat turns could cause a permanent memory leak. The system *must* implement a bounded LRU cache for dynamic Atom interning or strictly sanitize file names against a known repository index *before* they reach the Mangle boundary.
2.  **Sort Stability & Performance:** The Go implementation of the tie-breaking logic (earliest index wins on tied severity and count) is currently $O(N)$, which is excellent. However, the translation of the resulting Go structures back into Mangle facts (e.g., `delegation_target_file`) adds serialization overhead.
3.  **Panic Resilience:** The current Go extraction code is fragile. If the LLM produces a non-string type that somehow bypasses the initial `json.Unmarshal` (e.g., via a weak `map[string]any` structure), the subsequent type assertions `types.ExtractString(fact.Args[1])` will panic. In a multi-tenant or long-running CLI session, a single panic in the delegation logic will crash the entire orchestrator, losing all active context. The system must replace blind type assertions with the comma-ok idiom (`val, ok := f["severity"].(string)`) everywhere in this critical path.

## 7. Strategic Testing Roadmap

To address these vulnerabilities, the following testing strategies must be implemented.

### Phase 1: Harden the Extraction Layer (Type Coercion)
We must replace the `map[string]any` structure with a strictly typed Go struct for Findings. The tests should then intentionally feed malformed JSON (e.g., integers for strings, arrays for objects) into the unmarshaler to ensure it fails gracefully, defaults the severity to `/unknown`, or drops the invalid finding entirely.

### Phase 2: Bounded Contexts (Resource Limits)
We must implement a hard limit on the number of findings processed per delegation decision (e.g., top 500). We will write a benchmark test `BenchmarkExtremeFindingsVolume` that generates 1,000,000 simulated findings and asserts that memory allocation does not exceed 10MB during the delegation resolution phase.

### Phase 3: Concurrency Hardening (Race Conditions)
We will introduce `t.Parallel()` to the entire test suite. To support this, we must eliminate the shared `delegationKernel` singleton and instead use `Clone()` or instantiate a fresh, lightweight kernel for each test. We will then add a specific `TestConcurrentDelegationDecisions` to fuzz the `derivedExecutionMode` function simultaneously across 50 goroutines.

### Phase 4: Path Sanitization (Malicious Payloads)
We will add a table-driven test suite specifically for the `file` field, injecting null bytes, Unicode normalization traps (e.g., combining characters), and path traversal strings. The test will verify that `delegatedFile` either sanitizes these paths or rejects the finding entirely before it is passed to downstream execution shards.

## 8. Deep Dive: Mangle Rule Evaluation Edge Cases

When evaluating the `derivedExecutionMode` under extreme load, we must consider how Mangle handles evaluation cycles.

### Scenario A: The Hallucinated Verb Flood
In this scenario, we simulate a burst of 10,000 unique, un-configured intent verbs generated by a rogue LLM loop. Each novel verb string passed to `m.derivedExecutionMode(verb)` is eventually translated into a Mangle query.
If the system dynamically generates Atoms for each of these novel strings, the Atom intern pool will grow linearly. Since Go maps do not shrink their allocated bucket arrays even after elements are deleted, this poses a permanent memory leak risk. Over the lifecycle of a long-running codeNERD daemon session, a sustained assault of novel verbs could cause the process to bloat.
**Test Mitigation:**
We need a test that injects 100,000 unique verbs into `derivedExecutionMode` and measures the heap profile (`runtime.ReadMemStats`). If the heap growth exceeds a strict baseline threshold, the test should fail. This forces the engineering team to implement a bounded LRU cache for dynamic Atom interning.

### Scenario B: Stratification Attacks
Adversarial atoms might attempt to construct a rule that depends on its own negation. If the LLM somehow injects a fact that alters the dependency graph, the kernel's `analysis.Analyze` must catch this before evaluation. If it does not, Mangle will either crash or loop infinitely trying to reach a fixpoint that doesn't exist.
**Test Mitigation:**
We must test that dynamic fact injection (e.g., via the findings payload) cannot bypass stratification validation or introduce new rules, ensuring the system strictly separates data from logic.

### Scenario C: The Null Byte Injection
The LLM injects `\x00` into a target string. Go strings allow null bytes, so the Kernel parses it fine. But when passed to downstream C-bindings or system calls, the string is truncated.
**Test Mitigation:**
We must inject `{"file": "config.yaml\x00.txt"}` and verify the delegation logic explicitly rejects strings containing null bytes.

## 9. Conclusion

The `delegation_decision` subsystem is logically sound for the "happy path" but structurally vulnerable to the stochastic nature of its inputs. The neuro-symbolic architecture shines when the facts are pristine, but it is fragile when the facts are malformed.

## 10. Extended Subsystem Interface Verification

### 10.1 The JSON Boundary
The system's reliance on `encoding/json` standard library for untyped maps requires rigorous boundary checks. We must fuzz the JSON decoder with deeply nested structures that exceed the stack limit.
If an adversarial LLM outputs a JSON payload with 10,000 levels of nesting, `json.Unmarshal` will panic with a stack overflow, crashing the daemon. We need tests that cap the recursion depth or use a streaming decoder with strict limits.

### 10.2 The Logging Interface Constraints
When findings are dropped due to invalid severities or empty file paths, the system logs these events. We must ensure the logging subsystem itself is bounded.
If 1,000,000 findings are rejected in a single burst, the logging system might block the main execution thread or overwhelm the disk I/O. We need tests verifying that high-volume rejection events are properly rate-limited or aggregated (e.g., "Dropped 10,000 findings due to invalid format").

### 10.3 The Memory Alignment Edge Case
Go's garbage collector efficiency depends heavily on struct alignment and pointer tracking. By using `map[string]any`, we force the GC to track countless interface pointers. If we switch to strict structs, we reduce GC pressure. We must benchmark the difference in GC pause times between the two approaches under extreme load (e.g., 50,000 findings).

### 10.4 The Time Skew Anomaly
While the delegation decision doesn't explicitly rely on time, the overarching session metrics might. If a finding is logged with a timestamp that is radically skewed (e.g., year 2099 due to a malformed payload), it might corrupt the telemetry downstream. We must verify timestamp sanitization at the boundary.

### 10.5 The Empty Struct Anomaly
In Go, an empty struct `struct{}` consumes zero memory. We must verify if the Mangle engine leverages this optimization for facts without arguments. If it doesn't, we are wasting memory representing boolean facts (like `/flag_active`).

### 10.6 The Panic Recovery Layer
Every boundary where untrusted data interacts with the Mangle kernel should be wrapped in a `defer func() { recover() }()` block. We must inject intentional panics (e.g., via type coercion failures) into the `delegationTargetFile` function and verify the caller successfully recovers and returns a sane error, rather than crashing the process.

### 10.7 The Unicode Normalization Attack
If a finding targets `M̄ain.go` (M + combining macron) instead of `Main.go`, the string equality checks might fail, leading to duplicated file entries in the aggregation phase. The test suite must normalize strings to NFC before processing.

### 10.8 The Symlink Resolution
The file paths provided in the findings might be symlinks. We must verify if the delegation logic resolves symlinks to their canonical paths before grouping. Otherwise, findings for `path/to/symlink.go` and `actual/file.go` will be treated as distinct targets, diluting the severity ranking.

### 10.9 The Virtual Store Injection
If the delegated file path contains shell metacharacters (e.g., `$(rm -rf /)`), and this string is eventually passed to a shell-based tool, it constitutes a remote code execution vulnerability. The tests must strictly sanitize and escape all file paths.

### 10.10 The Dependency Injection Edge
The `delegationKernelOnce` singleton makes dependency injection for tests difficult. We should refactor the code to accept a `Kernel` interface, allowing tests to inject mock kernels that return specific error states (e.g., `ErrEngineTimeout`) to verify the system handles kernel failures gracefully.

### 10.11 The Mangle Atom Collision Attack
Mangle uses strings as the primary identifier for Atoms. If an attacker can control the strings being generated, they could potentially cause hash collisions in the Go map used for Atom interning, leading to degraded performance (O(N) lookup instead of O(1)). We need a test that intentionally generates known colliding strings to verify performance degradation is within acceptable bounds.

### 10.12 The Fact Store Cardinality Limits
What happens if the number of facts in the kernel exceeds a predefined limit? Does the engine start ejecting old facts (LRU cache behavior) or does it return an error? The delegation logic must be robust against `ErrFactStoreFull`.

### 10.13 The Multi-Step Intent Resolution
If a user intent implies multiple delegation actions (e.g., "fix the auth bug and then review the tests"), the current logic maps one intent to one execution mode. ### 11. Cross-Boundary Data Contamination Vectors

When Mangle resolves delegation decisions, the inputs originated from unstructured LLM responses and the outputs dictate the actions of heavily-privileged Go execution shards.

#### 11.1 The Cross-Site Scripting (XSS) Equivalent
If the LLM output contains control characters designed to break terminal emulators (e.g., ANSI escape sequences hidden in a file name finding: `{"file": "[2J[Hmalicious.go"}`), the delegation logic will likely pass this through intact. When the terminal UI renders the "Task: fix malicious.go" string, it might clear the user's screen or worse, inject input back into the terminal. We must test that terminal control characters are stripped from findings *before* they are assigned as delegation targets.

#### 11.2 The Markdown Injection Attack
The downstream systems often format task execution summaries into Markdown for subsequent LLM context windows. If an LLM hallucinates a finding containing raw Markdown syntax (e.g., `{"file": "```go
func Malicious() {}
```"}`), it could break the parser of the next LLM in the chain, causing it to misinterpret instructions. The boundary between the Go map and the string formatter must escape Markdown specifically.

#### 11.3 The Environment Variable Exfiltration
If the LLM outputs a finding targeting an environment variable string (e.g., `{"file": "$AWS_SECRET_ACCESS_KEY"}`), the delegation logic itself won't evaluate it. But if the downstream coder shard uses a shell (e.g., `run_in_bash_session`) and interpolates this target unsafely (e.g., `cat $TARGET_FILE`), the secret could be exfiltrated into the log stream. The tests must verify that `delegatedFile` either rejects variables or that we enforce strict interpolation boundaries.

#### 11.4 The Command Injection via Filename
Similar to environment variables, a filename like `{"file": "a.go; rm -rf /"}` is technically a valid string in Go. If a downstream tool executes `git diff "a.go; rm -rf /"` via an unsafe `exec.Command` construction, the system is compromised. The test suite for delegation targeting *must* include payloads with bash metacharacters and assert they are structurally sanitized.

#### 11.5 The JSON Schema Poisoning
If the LLM outputs `{"$schema": "http://malicious.com/schema.json", "file": "a.go"}`, the system's JSON parser might (if misconfigured) attempt to fetch the remote schema, causing a Server-Side Request Forgery (SSRF) or a hang. While Go's standard `encoding/json` doesn't do this natively, third-party libraries might. We must ensure the unmarshaling boundary is hardened against schema poisoning.

#### 11.6 The Over-Permissioned Execution Mode
If an intent is subtly misclassified (e.g., a simple "how does X work?" is misclassified as `/refactor`), the delegation logic maps it to `/advisory_with_critique`. This grants the shard permission to mutate files (refactor), which is a violation of the principle of least privilege for a read-only query. We need boundary tests that ensure `wants_direct_answer()` strictly overrides the `execution_mode` topology, preventing read-only queries from escalating to write-capable execution modes.

### 12. Conclusion & Next Steps
The sheer number of boundary conditions identified in this document highlights the fragility of relying on untyped `map[string]any` structures when bridging the gap between stochastic LLM output and deterministic Go/Mangle execution. The recommended action is a complete refactoring of the `extractFindings` pipeline to use strongly typed Go structs, combined with rigorous input fuzzing across all the identified vectors.

### 13. System Resilience under Malformed Fact Injection

The `codeNERD` framework relies on the integrity of the Mangle fact store. When the `delegation_decision` subsystem injects facts derived from LLM output, it must ensure these facts do not destabilize the kernel.

#### 13.1 Fact Store Pollution over Long Sessions
If a user maintains a long-running session, the LLM might generate hundreds of findings across dozens of turns. The current tests assume a fresh kernel (`delegationTestKernel`) or manually retract specific facts. In production, if `Retract` logic is buggy, the kernel will accumulate orphaned facts (e.g., `delegation_target_file("old_file.go")`). When a new task requires a delegation decision, the query might return multiple target files, causing the orchestrator to fail or branch unexpectedly. We need longitudinal tests that simulate 100 consecutive turns to verify the fact store size remains stable and orphaned facts are aggressively pruned.

#### 13.2 The Circular Dependency Trap in Task Strings
When `formatShardTaskWithContext` formats the findings for the subagent, it passes the target file and the severity. If the file name itself contains the string representation of a severity (e.g., a file literally named `critical_error.go`), the string matching logic in downstream tools might get confused. We need tests that inject keywords (like `[CRITICAL]`, `/high`, `file:`) directly into the file names and verify the parser doesn't break.

#### 13.3 Fact Grounding Failures
Mangle rules depend on grounded facts. If the extraction layer yields an empty string for the file, and it is injected into the kernel as `delegation_target_file("")`, the rules that join on the file name might fail to ground if the other side of the join expects a valid file path from the workspace schema. The test suite must ensure that partially invalid findings (e.g., a severity with an empty file) are entirely discarded rather than partially asserted.

#### 13.4 The Topology Fallback Cascades
If `execution_mode` defaults to `/parallel` for an unknown verb, this decision cascades. A `/parallel` execution mode might spawn three shards simultaneously (Reviewer, Security, Tester). If the underlying intent was actually a simple read-only question that slipped past the `wants_direct_answer()` guard, we have just amplified the token cost by 3x. Boundary tests must explicitly check the cost impact of fallback modes under adversarial conditions.

#### 13.5 The "Ghost" Fact Phenomenon
In neuro-symbolic systems, a "ghost fact" occurs when a rule derives a conclusion based on a premise that was temporarily true but later retracted. Because Mangle is monotonic within a single evaluation cycle, but stateful across cycles, a finding injected at $T_1$ might derive a permanent categorization fact. Even if the finding is retracted at $T_2$, the categorization might remain. We must test the full lifecycle of facts derived from findings to ensure no "ghost" state persists between turns.

### 14. Observability and Debugging Boundaries

When boundary conditions are hit, the system's ability to log the failure cleanly is paramount.

#### 14.1 The Truncated Log Edge Case
If a finding contains a 1MB base64 string in the `message` field, and the validation logic rejects it, the logging system might attempt to print the entire finding: `logging.Warn("Rejected finding: %v", finding)`. This will spam the log file, rotate it prematurely, and obscure actual errors. The logging boundary must truncate large maps before rendering them to the console or disk.

#### 14.2 The Silent Drop Condition
Conversely, if an entire finding is dropped because the `line` number couldn't be parsed, and there is no log emitted, the developer has no visibility into why the LLM's output was ignored. The tests must verify that every rejected finding emits a specific, traceable telemetry event.

#### 14.3 Traceability of Delegation Logic
When `delegatedFile` breaks a tie, it does so silently. If file A and file B both have one critical finding, A wins because it appeared first. In a complex debugging scenario, a developer needs to know *why* A was chosen over B. The system must emit the exact tie-breaking rationale (e.g., "resolved tie between A and B via earliest index rule") into the debug trace. The test suite should assert this trace exists.

### 15. Final Thoughts on Boundary Value Analysis

This deep dive into the `delegation_decision` subsystem reveals a critical truth about neuro-symbolic agent architecture: the boundaries between neural outputs (LLM strings) and symbolic execution (Mangle logic) are the most fragile points in the system.
While the current tests validate the core rules of the game (tie-breakers, fallbacks), they do not validate the boundaries of the board itself. By implementing the robust, type-safe, and bounds-checked architectures described in this journal, we can elevate `codeNERD` from an experimental tool to a hardened, enterprise-grade engineering asset.

### 16. The Mangle AST Integration Vulnerabilities

The most complex boundary in the system is where Go code interfaces directly with the Mangle AST.

#### 16.1 Atom vs. String Confusion Edge Case
In Mangle, `ast.Name("active")` creates the Atom `/active`, whereas `ast.String("active")` creates the string `"active"`. These are disjoint types. A common failure mode in AI logic programming is the "Stringly Typed" assertion, where raw strings are passed when the schema expects Atoms.
If `delegationTargetFile` translates the severity string `"critical"` into an AST node, it must explicitly use the Atom constructor. If it uses the String constructor, the downstream joins against the `severity_ladder` (which defines `/critical` as an Atom) will silently fail, yielding zero results. We need tests that explicitly verify the exact AST node types generated from the findings payload.

#### 16.2 The Unbuffered Channel Leak in Mangle Streaming
When `derivedExecutionMode` queries the Mangle engine, it typically receives results over a channel or iterator. If the Go logic finds a match and `return`s early without fully draining the result set, the Mangle background goroutine attempting to send the next result will block forever. This is a classic "Forgotten Sender" goroutine leak. We must ensure the `derivedExecutionMode` logic uses `context.WithCancel` and `defer cancel()` to tear down the query execution immediately after the first match is found. Tests must verify no goroutines are leaked during early returns.

#### 16.3 The Empty Result Set Fallacy
In logic programming, bugs often manifest as an empty result set rather than a runtime exception. If a join fails (due to type confusion as described above), the query returns nothing. The Go code might interpret this empty set as "use the fallback `/parallel` mode". The test suite must differentiate between a legitimate missing verb (where `/parallel` is correct) and a structural logic failure where the query *should* have returned a result but didn't. We need assertion helpers that enforce strict presence checks.

#### 16.4 Golden File Testing for Derived Logic
Testing complex recursive rules or transitive dependencies using hardcoded Go structs is brittle. For the `execution_mode` derivations, we should transition to "Golden File" testing. The test should serialize the entire expected IDB (derived facts) after evaluating a specific set of findings and compare it against a `.golden` file. This approach detects subtle regressions in join ordering or derivation limits that manual struct assertions might miss.

#### 16.5 Verification of Evaluation Halting
If the LLM manages to inject facts that trigger recursive rules involving arithmetic or cyclic constructors, the engine must halt. We need a test that feeds a deliberately cyclic graph into the fact store and verifies that the Mangle engine reaches a fixpoint (or halts via timeout) rather than infinite generation looping (e.g., `p(X+1) :- p(X)`).

### 17. The Memory Profile of String Allocation

When `formatShardTaskWithContext` formats the findings, it uses standard string concatenation or `fmt.Sprintf`.

#### 17.1 The Allocation Storm
If there are 1,000 findings, calling `fmt.Sprintf` 1,000 times inside a loop creates a massive amount of short-lived string allocations, triggering frequent Garbage Collection pauses.
**Test Mitigation:** We need to test the performance of the string formatting logic. The tests should enforce the use of `strings.Builder` with a pre-allocated capacity based on the number of findings, avoiding the allocation storm entirely.

#### 17.2 Null Byte Padding in Output
If the formatting logic accidentally appends padding that includes null bytes (` `), Git might misclassify the resulting text files as binary data. This prevents text diffs and breaks automated code reviews. We must write tests that explicitly scan the output of `formatShardTaskWithContext` for null bytes and ensure proper line wrapping is used instead of arbitrary buffer padding.

### 18. Interaction with the API Scheduler and Queue Saturation

The delegation decisions dictate how many shards are spawned, which directly impacts the `api-scheduler-stress.md` vectors.

#### 18.1 Queue Saturation via Parallel Mode
If an unknown verb defaults to `/parallel`, and the system is under heavy load, the sudden spawning of multiple background shards (e.g., Reviewer, Tester, Security) might saturate the API scheduler's queue. If the orchestrator doesn't apply backpressure, the queue will explode, leading to `429 Too Many Requests` from upstream LLM providers.
**Test Mitigation:** The test suite for delegation must simulate a burst of unknown verbs and assert that the resulting `/parallel` mode derivations include proper rate-limiting metadata or priority flags to ensure the API scheduler can throttle them effectively.

#### 18.2 Priority Inversion in Advisory Mode
When the system selects `/advisory_with_critique`, it sequences the execution: advise, execute, critique. If the "critique" phase is queued with low priority while new interactive turns are queued with high priority, the critique might never execute, leaving the task functionally incomplete.
**Test Mitigation:** We need tests verifying that the execution mode topologies correctly propagate priority context down to the individual spawned shards, preventing priority inversion.

### 19. The CGO Boundary and SQLite Context

The tests must be executed with CGO enabled and the correct SQLite headers, otherwise they time out or fail.

#### 19.1 Unmanaged CGO Allocations
If the delegation logic stores facts in a Mangle store backed by SQLite (via CGO), we must ensure that any temporary tables or in-memory databases used for the delegation evaluation are properly garbage collected. Go's GC cannot clean up memory allocated in C land. We must test that closing the kernel context reliably frees all associated CGO memory.

### 20. Summary of Architectural Technical Debt

This boundary value analysis reveals that the `delegation_decision` subsystem, while functional, relies on several brittle assumptions:
1.  **Trust in LLM Types:** The use of `map[string]any` is a critical vulnerability.
2.  **Unbounded Operations:** The lack of strict limits on input sizes (strings, arrays) exposes the system to resource exhaustion.
3.  **Shared Global State:** The `delegationKernelOnce` singleton in the test suite masks concurrency bugs and prevents parallel testing.
4.  **Implicit Fallbacks:** The silent fallback to `/parallel` for unknown verbs obscures prompt drift and intent misclassification.

Addressing these issues through the proposed boundary tests is essential for the long-term stability of the codeNERD framework.
