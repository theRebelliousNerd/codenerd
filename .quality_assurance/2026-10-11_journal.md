# QA Engineering Journal: Boundary Value Analysis and Negative Testing
## Date: 2026-10-11 00:17:34 EDT
## Subsystem Analyzed: Perception Transducer (internal/perception/transducer.go)
## Test Suite: tests/e2e/perception_adversarial_e2e_test.go

### 1. Executive Summary

As a QA Automation Engineer specializing in Boundary Value Analysis and Negative Testing, I conducted a deep dive into the Perception Transducer subsystem, specifically focusing on its parsing of user intent via the UnderstandingTransducer and the corresponding adversarial test suite. This subsystem is a critical boundary layer because it bridges natural language (LLM output) into the formal, deductive rules of the Mangle engine. If the perception layer is poisoned or fails to handle edge cases, the entire neuro-symbolic safety contract is compromised.

After reviewing the code and the `perception_adversarial_e2e_test.go` suite, I identified several critical gaps in negative testing and boundary condition handling. While the existing tests cover basic decoy JSON injections, OOV (Out of Vocabulary) action types, and basic Mangle injection, they miss several critical edge case vectors around null/empty inputs, type coercion, extreme user requests, and state conflicts within the transducer's internal processing logic.

### 2. Analysis of the Transducer and its Test Suite

The transducer (`internal/perception/transducer.go`) is responsible for parsing JSON responses from the LLM, sanitizing strings intended for Mangle facts (`sanitizeFactArg`), and managing the mapping of semantic intents to Mangle categories.

The test suite (`tests/e2e/perception_adversarial_e2e_test.go`) is quite robust in specific areas:
- `TestE2E_Perception_Adversarial_Decoy`: Tests that the parser picks the last valid JSON, avoiding early decoy payloads.
- `TestE2E_Perception_Adversarial_OutOfVocabulary`: Tests fallback to `/explain` when unknown semantic types are encountered.
- `TestE2E_Perception_Adversarial_MangleInjection`: Tests that `sanitizeFactArg` stops some Mangle injections, although it explicitly documents a known security flaw where `( ) . :- ;` characters are preserved, allowing constraint injection.
- `TestE2E_Perception_Adversarial_InputTruncation`: Tests that inputs over 100KB are truncated before hitting the LLM and the fact arguments.

However, the following boundary value and negative testing vectors are completely missing:

### 3. Missing Edge Case Vectors

#### A. Null/Undefined/Empty Vectors
- **Empty JSON / Empty Strings:** What happens if the LLM returns `{"understanding": {"primary_intent": "", "semantic_type": "", "action_type": ""}}`? Does the system fallback correctly, or does it try to route an empty verb?
- **Null Values:** What if the LLM returns `{"understanding": {"primary_intent": null}}`? In Go, depending on the unmarshaling logic, this might cause a panic if not handled correctly or default to an empty string.
- **Empty Arrays for Tools/Constraints:** If `tools_needed` or `user_constraints` is `null` instead of `[]`, does the system panic during iteration?

#### B. Type Coercion Vectors
The LLM response is inherently untyped until unmarshaled into Go structs.
- **Number as String / String as Number:** The `confidence` field is a float. What if the LLM returns `"confidence": "high"` or `"confidence": "0.99"` (string instead of number)? Does `json.Unmarshal` fail entirely, dropping the whole intent, or is there a fallback?
- **Boolean as String:** What if `is_question` is `"true"` instead of `true`?

#### C. User Request Extremes (Frontier Cases)
- **Deeply Nested JSON:** A malicious LLM response could contain heavily nested JSON in the `target` or `constraint` fields, aiming to cause a stack overflow during unmarshaling.
- **Unicode/Control Character Extremes:** The `sanitizeFactArg` function strips some control characters. But what about massive payloads of zero-width spaces, RTL overrides, or invalid UTF-8 sequences? Do these cause the Mangle engine to fail during parsing?
- **Extreme Length Campaigns:** The truncation test only checks a 100KB string of "X"s. What if the input is exactly at the boundary (e.g., 60000 chars)? What if the input is a massive single word with no spaces, defeating some tokenization/truncation strategies?

#### D. State Conflicts and Race Conditions
- **Concurrent Perception:** The `UnderstandingTransducer` holds state (e.g., `lastUnderstanding`). If two requests are processed concurrently using the same transducer instance (which shouldn't happen by design, but might in a bug), does `GetLastUnderstanding()` return the wrong state?
- **Transient Failure State Conflict:** The `TransientFailure` boolean on the `Intent` struct. What happens if the system is rapidly oscillating between available and unavailable? Does the fallback logic correctly handle a transient failure followed immediately by a malformed response?

### 4. Performance and System Capability Evaluation

Is the Perception subsystem performant enough to handle these edge cases?

- **Regex Performance:** The `getRegexCandidates` function explicitly limits input to 2000 characters to avoid linear-time amplification on massive inputs. This is a good defense against ReDoS (Regular Expression Denial of Service).
- **JSON Unmarshaling:** Go's standard `encoding/json` is generally robust against deeply nested JSON (it has recursion limits), but massive payloads could still cause memory spikes. The fact that the test suite truncates inputs to ~50000 characters before sending to the LLM helps, but we must also protect against massive *responses* from a compromised LLM.
- **Sanitization Performance:** `sanitizeFactArg` iterates rune by rune using a `strings.Builder`. This is `O(N)` and very fast. However, it's currently flawed (as noted in the test suite) because it preserves Mangle syntactic characters. Fixing this by adding more complex escaping or stripping might marginally increase CPU cost but is absolutely necessary for safety.
- **Mangle Engine Overhead:** Asserting facts to the Mangle engine is stateful. If we allow massive strings (even if sanitized) into the engine, it increases memory pressure in the `VirtualStore`. The current truncation caps args at 2048 chars, which is acceptable.

### 5. Proposed Test Improvements

To address these gaps, I will add the following TODO comments to `tests/e2e/perception_adversarial_e2e_test.go`:

1.  **Test Null/Empty/Missing Fields:** Ensure the system degrades gracefully to `/explain` and `dream` mode when critical JSON fields are missing or null.
2.  **Test Type Coercion:** Verify behavior when LLM hallucinates string values for boolean or float fields.
3.  **Test Extreme Encoding/Unicode:** Verify `sanitizeFactArg` and intent parsing against null bytes, invalid UTF-8, and zero-width spaces.
4.  **Test Concurrent Access:** Verify that `GetLastUnderstanding()` is thread-safe or that the transducer is explicitly documented/tested as not thread-safe and panic-protected.

These additions will significantly harden the boundary between the non-deterministic LLM output and the deterministic Mangle execution environment.
