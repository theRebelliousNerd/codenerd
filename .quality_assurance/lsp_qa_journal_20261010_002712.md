**Date & Time:** 2026-10-10 00:27:12 EDT

## 1. Executive Summary

This journal entry documents a deep dive into the Mangle Language Server Protocol (LSP) subsystem and its associated test suite. The Mangle LSP component (`internal/mangle/lsp.go`) is critical for providing intelligent code completion, navigation (GoToDefinition, FindReferences), diagnostics, and hover capabilities to developers interacting with Mangle logic via IDEs. Because codeNERD relies heavily on accurate neuro-symbolic logic execution, the developer experience and correctness of the tooling that authors this logic are paramount. A flawed LSP can mislead developers, resulting in unstratified logic, unbounded variables, or syntax errors slipping into production campaigns.

Upon reviewing the current test suite in `internal/mangle/lsp_test.go`, it is evident that the testing surface is severely lacking. It currently spans fewer than 90 lines and only verifies the initialization of the `LSPServer` struct and the basic functionality of `OpenDocument` and `CloseDocument` on a "Happy Path" level. There is zero coverage for the core LSP features (`GoToDefinition`, `FindReferences`, `GetHover`, `GetCompletions`, `IndexWorkspace`, `ServeStdio`, or `handleRequest`). Furthermore, there is absolutely no Boundary Value Analysis (BVA) or Negative Testing applied to the state transitions, concurrent operations, or edge-case payloads that an LSP server typically encounters in the wild.

This document outlines a comprehensive QA strategy, enumerating specific missing edge cases across multiple vectors (Null/Empty, Type/Data bounds, Extremes, and State Conflicts) and evaluates whether the current implementation in `internal/mangle/lsp.go` is robust enough to handle them.

## 2. Evaluation of System Robustness and Test Gaps

### Vector 1: Null, Undefined, and Empty Inputs

**Observation:** IDEs frequently send edge-case requests during intermediate typing states, network latency, or due to plugin bugs. The LSP server must gracefully handle null, empty, or malformed URIs, contents, and positions.

*   **Empty Document Initialization:**
    *   *Scenario:* What happens when `OpenDocument` is called with an empty string for `content`?
    *   *System Assessment:* `lsp.go` creates a `Document` with `Lines: strings.Split("", "
")`, resulting in `Lines` containing one empty string. Subsequent calls to `indexDocumentLocked` will iterate over this empty string. The regex matches will yield no results. This seems safe, but it's completely untested.
    *   *Test Gap:* Missing test for `OpenDocument` with empty content.
*   **Empty/Null URIs:**
    *   *Scenario:* `GetDiagnostics`, `GoToDefinition`, or `CloseDocument` are invoked with an empty `uri` or a malformed URI scheme (e.g., `file://`).
    *   *System Assessment:* The maps in `LSPServer` (`documents`, `definitions`, `diagnostics`) are keyed by string URIs. An empty string is a valid map key in Go, meaning the server might silently track state under the `""` key. While not an immediate crash, this can cause state leakage or memory consumption over time.
    *   *Test Gap:* Missing test verifying operations on empty URIs fail gracefully or are rejected outright.
*   **Zero or Negative Positional Arguments (Line/Col):**
    *   *Scenario:* `GoToDefinition` or `GetHover` is queried with negative line numbers, or column numbers less than zero.
    *   *System Assessment:* Looking at `getWordAtPosition(line string, col int)`, there is a safety check: `if col < 0 || col > len(line) { return "" }`. This is a good guard. However, what about `line`? If `line < 0` or `line >= len(doc.Lines)`, looking up `doc.Lines[line]` in `GoToDefinition` will cause a slice bounds out-of-range panic.
    *   *System Risk:* High. A simple out-of-bounds request from a malfunctioning client can crash the entire LSP server process.
    *   *Test Gap:* Missing negative tests for out-of-bounds `line` and `col` arguments.
*   **Empty Schema/Engine References:**
    *   *Scenario:* `GetHover` relies on `s.engine` to fetch schema documentation. What if `s.engine` is nil?
    *   *System Assessment:* `NewLSPServer(nil)` is permitted, but calling features that traverse `s.engine.schemas` will lead to a nil pointer dereference.
    *   *Test Gap:* Missing tests that ensure LSP gracefully returns empty results or errors when the underlying engine is uninitialized.

### Vector 2: Type Coercion and Boundary Data Extremes

**Observation:** While Go is statically typed, the LSP operates on strings received over JSON-RPC. Boundaries involving character encodings, very large numbers, and unusual symbol characters must be verified.

*   **Multibyte Character / Unicode Boundaries:**
    *   *Scenario:* A document contains complex Unicode characters, emojis, or RTL text (e.g., `foo("こんにちは").`). The LSP client sends character offsets based on UTF-16 code units, but Go strings are UTF-8 bytes.
    *   *System Assessment:* `lsp.go` uses `col` directly as a byte index in `getWordAtPosition`: `line[start-1]`. If `col` happens to land in the middle of a multibyte UTF-8 sequence, `isWordChar` might incorrectly evaluate individual bytes of the rune, leading to broken symbol extraction or slice panics.
    *   *System Risk:* Medium. Slicing strings at arbitrary byte indices can produce invalid UTF-8 and fail to resolve definitions.
    *   *Test Gap:* Missing boundary value tests for symbol resolution involving multibyte characters and multi-plane emojis.
*   **Extreme Line Lengths (Minification/Generated Code):**
    *   *Scenario:* A developer pastes a generated Mangle ruleset where the entire logic is on a single 500,000-character line.
    *   *System Assessment:* `indexDocumentLocked` uses `bufio.Scanner` or regex on the entire content. Deep regex execution on a 500k-character line can lead to catastrophic backtracking or memory exhaustion. Furthermore, `countArity` iterates character by character.
    *   *System Risk:* Medium. Performance degradation, possible ReDoS (Regular Expression Denial of Service).
    *   *Test Gap:* Missing performance and boundary tests for extreme line lengths.
*   **Type Mismatches in JSON-RPC (Simulated):**
    *   *Scenario:* The underlying `handleRequest` receives fractional line numbers or extremely large integers (e.g., `line: 1e15`) that exceed standard integer bounds.
    *   *Test Gap:* Missing negative tests for JSON payload deserialization boundaries in `handleRequest`.

### Vector 3: User Request Extremes and "Frontier" Workloads

**Observation:** As codeNERD is designed to scale across brownfield environments and massive monorepos, the LSP must handle frontier-level workloads without degrading IDE responsiveness.

*   **Massive Workspace Indexing:**
    *   *Scenario:* `IndexWorkspace` is pointed at a root directory containing 50,000 `.mg` files across deeply nested folders.
    *   *System Assessment:* `IndexWorkspace` likely traverses the filesystem. Without proper concurrency controls (e.g., worker pools) or context cancellation checks, this can block the LSP server entirely or exceed file descriptor limits (ulimit).
    *   *System Risk:* High in enterprise environments.
    *   *Test Gap:* Missing tests simulating `IndexWorkspace` on thousands of synthetic files, checking for timeouts and context cancellation compliance.
*   **Infinite Recursion / Deep Nesting in Arity Parsing:**
    *   *Scenario:* A user creates a deeply nested set of parentheses in a rule: `foo(((((((...)))))))`.
    *   *System Assessment:* The `countArity` function loops and increments `depth`. If the nesting is extreme, it handles it iteratively, which is safe from stack overflows, but what if the parentheses are unbalanced? It falls back to `countTopLevelArgs`, which might behave unpredictably.
    *   *Test Gap:* Missing stress tests for `countArity` with deeply nested, unbalanced, or bizarrely formatted logic (e.g., alternating string quotes and parentheses).
*   **Invention of Unknown Syntax (Graceful Degradation):**
    *   *Scenario:* The user inputs completely invalid Mangle syntax, or attempts to write Python code in a `.mg` file.
    *   *System Assessment:* The regexes in `indexDocumentLocked` will simply fail to match, resulting in no definitions. This is the correct behavior.
    *   *Test Gap:* Missing tests proving that entirely foreign syntax does not crash the indexer and gracefully yields zero diagnostics/definitions.

### Vector 4: State Conflicts and Race Conditions

**Observation:** The LSP Server runs asynchronously, processing requests concurrently. State conflicts are the most common source of intermittent failures in language servers.

*   **Concurrent Document Modification (Read/Write Data Races):**
    *   *Scenario:* A client sends a rapidly successive series of `OpenDocument` (which is effectively a full sync update in some LSP models) while a background goroutine is servicing a `FindReferences` request.
    *   *System Assessment:* `LSPServer` has a `sync.RWMutex`. `OpenDocument` takes a write lock (`s.mu.Lock()`). `FindReferences` takes a read lock (`s.mu.RLock()`). This is structurally sound, provided all access points correctly use the mutex. However, we must ensure that the inner slices (e.g., `doc.Lines`) are not modified in place if references are leaked outside the lock.
    *   *Test Gap:* Missing concurrent stress tests using `go test -race` simulating heavy read/write contention.
*   **Acting on Deleted or Closed Resources:**
    *   *Scenario:* `CloseDocument` is called, followed immediately by `GoToDefinition` for the same URI before the client state syncs.
    *   *System Assessment:* If `s.documents[uri]` is removed, `GoToDefinition` must safely return an empty response instead of assuming the document exists.
    *   *Test Gap:* Missing state conflict tests for requests on closed/non-existent documents.
*   **Stale Versioning Conflicts:**
    *   *Scenario:* `OpenDocument` is called with `version: 5`, then due to network reordering, `OpenDocument` is called with `version: 4`.
    *   *System Assessment:* Most LSPs track versions to reject stale updates. Does `lsp.go` check `if version < doc.Version`? Likely not, meaning an older packet could overwrite newer state.
    *   *Test Gap:* Missing tests verifying version increment monotonicity and handling of out-of-order state updates.

## 3. Recommended Remediation and Testing Strategy

To elevate the quality of the Mangle LSP subsystem to a tier-1 IDE experience, the following architectural and testing improvements are mandated:

### 3.1. Architectural Hardening
1.  **Context-Aware Timeouts:** All LSP request handlers must enforce timeouts via `context.Context` to prevent slow filesystem reads (`IndexWorkspace`) or massive regex evaluations from blocking the main event loop.
2.  **Rune-Aware Positional Mapping:** Refactor `getWordAtPosition` to use `[]rune` instead of `[]byte` (or utilize a dedicated UTF-16 offset mapping utility) to guarantee multi-lingual safety and compliance with the official LSP specification on character offsets.
3.  **Strict Bounds Checking:** Add explicit, defensive bounds checks for `line` parameters across all query functions (`GetHover`, `GoToDefinition`, etc.) before slicing `doc.Lines`.

### 3.2. Concrete Test Plan Expansion

The `internal/mangle/lsp_test.go` file must be expanded to include the following distinct suites:

1.  **TestLSPServer_BoundsAndSafety:**
    *   Test `GoToDefinition` with `line = -1`, `line = 999999`.
    *   Test `GetHover` with `col = -1`, `col = 999999`.
    *   Test `OpenDocument` with `content = ""`.
2.  **TestLSPServer_Concurrency:**
    *   Spin up 100 goroutines continuously calling `GetHover` and `FindReferences`.
    *   Concurrently spin up 10 goroutines calling `OpenDocument` and `CloseDocument` with changing contents.
    *   Run with `-race` to prove the `sync.RWMutex` fully covers all state paths.
3.  **TestLSPServer_UTF8Compliance:**
    *   Test symbol extraction where the line contains emojis and multibyte sequences. Assert that byte-indexing does not panic and correctly identifies the symbol.
4.  **TestLSPServer_ExtremePayloads:**
    *   Generate a document with a 100,000 character single line.
    *   Validate that `OpenDocument` (and its internal `indexDocumentLocked`) completes within a reasonable threshold (e.g., < 100ms) without triggering ReDoS.
5.  **TestLSPServer_ArityEdgeCases:**
    *   Test `countArity` with strings like `foo("()()", bar)`, ensuring string bounds are respected.
    *   Test deeply unbalanced parentheses.

## 5. Deeper Analysis of Edge Cases and Performance Profiles

### 5.1 Deep Dive: String Indexing and UTF-8 Boundaries
The implementation of `getWordAtPosition` and `getWordPrefixAtPosition` relies heavily on single-byte indexing: `isWordChar(line[start-1])`. Go strings are read-only slices of bytes. When an IDE sends an LSP request (like Hover or GoToDefinition), the `line` and `col` values are provided. According to the LSP specification, character offsets are measured in UTF-16 code units (not bytes, and not runes).

If a document contains a string like:
`description("This is a 🌟 test").`
The star emoji (🌟) is represented by 4 bytes in UTF-8 (`F0 9F 8C 9F`). In UTF-16, it is represented by 2 code units (a surrogate pair).
1. If the IDE sends a column index of 20 (based on UTF-16), it might point to the middle of the UTF-8 byte sequence if the server blindly uses it as a byte index.
2. The `isWordChar` function evaluates `c >= 'a' && c <= 'z'` etc. If given a continuation byte (e.g., `9F`), it will evaluate to false.
3. More critically, if `start` or `end` manipulation splits a multibyte sequence, extracting `line[start:end]` will result in a malformed UTF-8 string containing partial runes.

**Remediation:** The system must convert the incoming UTF-16 column offset into a byte offset before indexing into the Go string. Alternatively, it could cast the string to `[]rune`, map the UTF-16 offset to a rune offset, and perform the logic on runes.

### 5.2 Deep Dive: ReDoS (Regular Expression Denial of Service)
In `internal/mangle/lsp.go` (and presumably `indexDocumentLocked`), regular expressions are used to extract definitions and references.
Consider a generated Mangle file with an extremely long argument list or complex nesting.
If a regex like `\w+\s*\([^)]*\)` is used to find predicates, an input like `foo( ` followed by 100,000 spaces, but no closing parenthesis, might cause the regex engine to backtrack catastrophically. Go's `regexp` package guarantees linear time complexity `O(N)` and is generally immune to ReDoS, unlike PCRE or JavaScript's regex engines. This is a strong point for the system's robustness!

However, *memory exhaustion* is still a risk if `IndexWorkspace` reads a 500MB generated `.mg` file into memory (e.g., as a single string for `content`). `strings.Split(content, "
")` would allocate a massive slice of strings.
**Recommendation:** Implement a file size limit in `IndexWorkspace`. If a file exceeds e.g., 2MB, the LSP should skip indexing it or provide a degraded experience (only index top-level declarations) to protect the server's memory footprint.

### 5.3 Deep Dive: Type Coercion in JSON-RPC
The LSP server operates by reading JSON-RPC messages from `stdin` and writing to `stdout`. The `handleRequest` function likely unmarshals the JSON into a Go struct.
What happens if the client sends:
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "textDocument/definition",
  "params": {
    "textDocument": { "uri": "file:///doc.mg" },
    "position": { "line": 999999999999999999999999999, "character": 5 }
  }
}
```
If the Go struct defines `line` as `int`, standard `encoding/json` might fail to unmarshal this extremely large number, returning an error. If the error is not handled gracefully (e.g., by returning an LSP Error response), the server might crash or silently ignore the request.
Furthermore, what if `line` is sent as a string `"5"` instead of an integer? Type coercion rules in Go's JSON unmarshaler are strict unless a custom unmarshaler or `string` struct tag is used.
**Recommendation:** Negative tests must explicitly send malformed JSON and structurally valid JSON with incorrect types to ensure the `ServeStdio` loop does not crash.

### 5.4 State Conflicts: Race Conditions on Shared Maps
The `LSPServer` uses a `sync.RWMutex` to protect `documents`, `definitions`, `references`, etc.
Consider the following interleaving of operations:
1. Goroutine A processes `FindReferences` for `uri_1`. It acquires a read lock `mu.RLock()`.
2. Goroutine B processes `OpenDocument` for `uri_2`. It blocks waiting for a write lock `mu.Lock()`.
3. Goroutine C processes `GetHover` for `uri_1`. It blocks waiting for a read lock (because there's a pending writer).
This standard RWMutex behavior is fine.

But consider what happens inside `indexDocumentLocked(uri, content)`.
```go
s.clearFileEntriesLocked(uri)
// ... regex matching ...
s.addDefinition(symbol, uri, line, col, kind, arity)
```
If `indexDocumentLocked` takes 500ms for a massive file, it holds the `mu.Lock()` for the entire duration. This completely stalls all read requests (`Hover`, `Completion`, etc.) for ALL documents, not just the one being indexed.
**Remediation for High Performance:** The server should build the new index maps locally (shadow maps) without a lock. Once the new index is fully computed, it should acquire the write lock only to swap the pointers / merge the updates, reducing lock contention from `O(DocumentSize)` to `O(1)`.

### 5.5 Conclusion on Performance Profile
Is the system performant enough? The current implementation uses global maps keyed by URI and a single global RWMutex. For small to medium workspaces (100-500 files), this architecture is performant and simple.
For "Frontier" workloads involving a 50 million line monorepo, a single global lock around `IndexWorkspace` or `OpenDocument` will lead to severe IDE stuttering. The indexing phase must be decoupled from the query phase, utilizing background worker pools and immutable data structures (like persistent trees or copy-on-write maps) for lock-free querying.

**Recommendation:** Negative tests must explicitly send malformed JSON and structurally valid JSON with incorrect types to ensure the `ServeStdio` loop does not crash.

### 5.4 State Conflicts: Race Conditions on Shared Maps
The `LSPServer` uses a `sync.RWMutex` to protect `documents`, `definitions`, `references`, etc.
Consider the following interleaving of operations:
1. Goroutine A processes `FindReferences` for `uri_1`. It acquires a read lock `mu.RLock()`.
2. Goroutine B processes `OpenDocument` for `uri_2`. It blocks waiting for a write lock `mu.Lock()`.
3. Goroutine C processes `GetHover` for `uri_1`. It blocks waiting for a read lock (because there's a pending writer).
This standard RWMutex behavior is fine.

But consider what happens inside `indexDocumentLocked(uri, content)`.
```go
s.clearFileEntriesLocked(uri)
// ... regex matching ...
s.addDefinition(symbol, uri, line, col, kind, arity)
```
If `indexDocumentLocked` takes 500ms for a massive file, it holds the `mu.Lock()` for the entire duration. This completely stalls all read requests (`Hover`, `Completion`, etc.) for ALL documents, not just the one being indexed.
**Remediation for High Performance:** The server should build the new index maps locally (shadow maps) without a lock. Once the new index is fully computed, it should acquire the write lock only to swap the pointers / merge the updates, reducing lock contention from `O(DocumentSize)` to `O(1)`.

### 5.5 Conclusion on Performance Profile
Is the system performant enough? The current implementation uses global maps keyed by URI and a single global RWMutex. For small to medium workspaces (100-500 files), this architecture is performant and simple.
For "Frontier" workloads involving a 50 million line monorepo, a single global lock around `IndexWorkspace` or `OpenDocument` will lead to severe IDE stuttering. The indexing phase must be decoupled from the query phase, utilizing background worker pools and immutable data structures (like persistent trees or copy-on-write maps) for lock-free querying.
