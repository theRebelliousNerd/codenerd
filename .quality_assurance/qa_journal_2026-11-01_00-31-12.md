# QA Journal - Boundary Value Analysis & Negative Testing
Date: 2026-11-01 00:31:12 EST
Subsystem: `cmd/nerd/cmd_mangle_check.go`

## Subsystem Overview
The `cmd_mangle_check.go` subsystem provides the `check-mangle` CLI command. It serves as an offline validator and evaluator for Mangle (`.mg`) source files. It handles file resolution (including globbing), loads the shared system schemas by default, instantiates a `mangle.Engine`, parses the files, and optionally runs evaluation to derive facts. The core logic relies on `codenerd/internal/mangle` for execution.

## 1. Null/Undefined/Empty Vectors
*   **Empty Argument Slice:** While `cobra.MinimumNArgs(1)` guards the CLI entry point, `checkMangleFiles(w, []string{}, opts)` is syntactically valid Go. If invoked programmatically, it will iterate 0 times and return `true`. This is technically correct but lacks an explicit test asserting this behavior, leaving it vulnerable to regressions if initialization logic is added that assumes at least one file.
*   **Empty File Content:** `os.ReadFile(path)` can successfully read a zero-byte file. The Mangle engine (`LoadSchemaString("")`) should conceptually handle an empty string gracefully (resulting in an empty AST). However, there is no explicit test verifying that checking an empty file doesn't crash the parser or return an unexpected EOF error.
*   **Empty Evaluation Slice:** Passing `--eval ""` or invoking `evalMangleFile` with `[]string{}`. The function iterates over the empty slice and returns `true`. An explicit test should guarantee it doesn't attempt to evaluate a nil/empty predicate name.
*   **Empty/Missing Shared Schemas:** If the codeNERD runtime environment is corrupted and `internal/core/defaults` is missing, `preloadSharedSchemas` swallows errors quietly. It iterates through search paths, and if none exist, it just returns. This silently downgrades the environment, which could cause confusing validation failures for valid policy files.

## 2. Type Coercion / Invalid Data Vectors
*   **Directory as a File:** If a user passes a directory path (e.g., `nerd check-mangle .`), `os.Stat` succeeds (it exists), so it bypasses the glob failure check. It then passes the directory path to `os.ReadFile`. On Linux/Unix, reading a directory returns an `EISDIR` error. The CLI currently handles this by printing the error and continuing, but this error path is completely untested.
*   **Non-UTF8 / Binary Data:** Passing a binary file (e.g., an image or compiled executable) to `check-mangle`. `os.ReadFile` reads the bytes, and `string(data)` coerces it into a Go string (which may contain invalid UTF-8 sequences). The Mangle lexer/parser must handle this garbage data without panicking. The current test suite only feeds well-formed ASCII/UTF-8 strings.
*   **Malformed Predicate Names:** Passing invalid strings to `--eval` (e.g., `--eval "pred!name"`, `--eval "123"`). The engine's `AtomStrings` method is invoked. Does the engine safely reject malformed predicate requests, or does it cause a runtime panic down the stack?
*   **Broken Symlinks:** A path that exists as a symlink but points to a deleted file. `os.Stat` (if not using `os.Lstat` depending on glob implementation) or `os.ReadFile` will fail with `ENOENT`. This needs explicit test coverage.

## 3. User Request Extremes Vectors
*   **Extreme File Size (Memory Exhaustion):** `checkFile` uses `os.ReadFile(path)`, which loads the entire file contents into RAM simultaneously. If a user maliciously or accidentally passes a massive file (e.g., a 10GB log file named `huge.mg`), the process will likely OOM (Out of Memory) panic before the Mangle parser even starts. The system lacks a file size limit check before reading.
*   **Infinite Recursion / Halting Problem:** If `--eval` is used on a Mangle file with non-terminating recursive rules (e.g., generating new constants infinitely), `engine.Evaluate()` will run forever. The CLI lacks any `context.Context` integration with a timeout. A malicious user could trivially hang the `nerd` process indefinitely, requiring a hard `SIGKILL`.
*   **Massive Glob Expansion:** A pattern like `**/*.mg` in a massive monorepo might expand to millions of files. `filepath.Glob` reads directories into memory. Furthermore, `checkMangleFiles` iterates and processes them sequentially. This could take hours without any progress indication to the user.
*   **Extreme Path Lengths:** File paths exceeding OS maximums (e.g., > 255 characters or MAX_PATH on Windows) during glob expansion or explicit argument passing.

## 4. State Conflicts Vectors
*   **File Permissions (Unreadable):** Passing a file that exists but lacks read permissions (`chmod 000`). The current code will correctly fail at `os.ReadFile` and print an error, but this critical error path lacks explicit automated test coverage.
*   **Race Conditions / Ephemeral Files:** A file is identified by `filepath.Glob`, but is deleted by another process milliseconds before `os.ReadFile` is called. This classic TOCTOU (Time-of-Check to Time-of-Use) race condition will result in a "file not found" error during the read phase. The code appears to handle errors per-file gracefully, but it's an edge case worth testing.
*   **Environment Drift for Preloads:** `preloadSharedSchemas` uses relative paths (`.`, `..`, etc.). If the CLI is executed from an unexpected working directory structure (e.g., deeply nested in a temp folder during a CI run), it might fail to find the schemas, drastically altering the validation context without explicit warning to the user.

## Performance & Scalability Conclusion
The `cmd_mangle_check.go` subsystem is currently designed as a simple, synchronous CLI utility. It is performant enough for its primary use case: validating small, human-authored Mangle policy files (typically < 1000 lines).

However, it is **not performant or resilient enough** to handle the extreme vectors identified.
1.  **Memory:** The reliance on `os.ReadFile` makes it fundamentally vulnerable to OOM when processing large files. It cannot handle "brownfield requests" involving massive auto-generated logic files without architectural changes (e.g., streaming parsers, though Mangle likely requires the full AST in memory anyway, so file size caps are needed).
2.  **Compute/Halting:** The lack of execution timeouts during `engine.Evaluate()` is a critical vulnerability. The Mangle engine must be wrapped in a context-aware execution model to prevent infinite loops from locking up the system.
3.  **Concurrency:** Processing multiple files sequentially is inefficient. For checking thousands of files, it should utilize Go routines (e.g., an `errgroup`) to parallelize parsing and analysis, significantly reducing wall-clock time.

To safely operate in high-stress, frontier-level environments, the subsystem needs strict bounds checking (file sizes, evaluation timeouts) and better resilience against invalid or hostile inputs.
