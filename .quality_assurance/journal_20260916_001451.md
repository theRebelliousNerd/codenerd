# QA Automation Journal - Boundary Value Analysis & Negative Testing
**Date/Time:** 2026-09-16 00:14:51 EST
**Target Subsystem:** Mangle Schema Validator (`internal/mangle/schema_validator.go`)

## Overview
This journal documents an in-depth review of the `SchemaValidator` component within the Mangle integration subsystem of codeNERD.
The focus is on identifying missing edge cases, negative test scenarios, and boundary value testing gaps that could compromise system stability, correctness, or security.
The `SchemaValidator` is critical as it enforces schema boundaries, prevents hallucinated predicates from polluting the fact store (Bug #18 fix), and safeguards core logic from rogue learned rules.

## Subsystem Analysis: `SchemaValidator`
The `SchemaValidator` relies heavily on regular expressions (`declHeadPattern`, `headPattern`, `predicatePattern`, `learnedHeadPattern`) to extract predicate names and arities from string representations of Mangle rules.
It also implements manual parsing logic to count arguments (arity) by tracking parenthesis depth, ignoring commas within string literals.
This combination of regex and manual character-by-character parsing is a prime target for boundary value and negative testing, as edge cases in rule syntax can easily bypass these checks if not handled correctly.

### Edge Case Vectors & Identified Gaps

#### 1. Null/Undefined/Empty Inputs
- **Gap:** `LoadDeclaredPredicates` and `NewSchemaValidator` handle empty strings (`""`) gracefully by checking `sv.schemasText != ""`, but what happens if the input is entirely whitespace (`"   \n  \t  "`)? The regex might not trigger, but the manual parsing might still try to execute or it might silently fail to load any schemas without reporting an error, leading to a state where *everything* is rejected.
- **Gap:** `CheckArity` with a predicate that exists but has an empty argument list `()` vs no parentheses. The `countArity` function starts with `count = 1`. If `argsStr` is empty, it returns `0`. But if it's spaces `( )`, does it return `1`? Yes, because `depth==0` is true inside the parens, but no comma is encountered, so `count` remains `1`. This means `foo()` and `foo( )` might be parsed as having arity `1` instead of `0`.
- **Actionable Test:** Test `countArity(" ")` and `countArity("")` directly. Test `CheckArity` on predicates defined with zero arguments.

#### 2. Type Coercion & Format Mismatches
- **Gap:** The validator expects valid Mangle syntax. If a user/agent passes non-Mangle strings (e.g., JSON, YAML, or plain text) into `ValidateLearnedRule` or `ValidateProgram`, how does it fail? The regex `learnedHeadPattern` (`^([a-z_][a-z0-9_]*)\s*\(`) is very specific. If the input is `{ "rule": "foo(X)" }`, it won't match, and might silently pass the forbidden head check, falling through to the AST parsing.
- **Gap:** What if `CheckArity` receives negative arities from external callers? The function checks `if expectedArity < 0` to skip validation (unknown arity), but if `actualArity` is negative, it will just fail the equality check. This is mostly safe but should be verified.

#### 3. User Request Extremes (Performance & Resource Exhaustion)
- **Gap (ReDoS - Regular Expression Denial of Service):** The regexes like `(?m)^([a-z_][a-z0-9_]*)\s*\(` use `\s*`. If an attacker or a runaway LLM generates a rule with 10 megabytes of spaces between the predicate name and the opening parenthesis, the regex engine might stall or consume excessive CPU. Go's `regexp` package guarantees linear time (`O(N)`), so it's generally safe from catastrophic backtracking, but extremely large inputs still consume memory and processing time.
- **Gap (Extreme Arity/Nesting):** The `countArity` function iterates byte-by-byte. If an agent generates a rule with 1,000,000 arguments or 100,000 nested parentheses, this will consume significant CPU cycles. More importantly, deeply nested structures might blow the call stack later in the AST parsing phase (`ValidateProgram`), even if `countArity` handles it iterativley.
- **Gap (Massive String Literals):** A string literal spanning megabytes inside a rule `foo("...")` will force `splitRuleBody` and `headText` to iterate over millions of characters. This tests the performance limits of the `SchemaValidator`.
- **Actionable Test:** Generate a 5MB string literal and time `ValidateRule`. Generate a rule with 10,000 arguments and time `CheckArity`.

#### 4. State Conflicts & Concurrency
- **Gap:** `SchemaValidator` uses Go maps (`declaredPredicates`, `predicateArities`). Go maps are not safe for concurrent use. If the system hot-loads schemas (e.g., via `SetPredicateArity` or a hypothetical `ReloadSchemas`) while another goroutine is concurrently validating rules (`ValidateRule`), the application will panic with `fatal error: concurrent map read and map write`.
- **Gap:** Phantom State. If `LoadDeclaredPredicates` is called multiple times, it appends to the maps. It does not clear them first. If schemas change and a predicate is removed or its arity changes, the old arity/declaration might persist in the map, leading to incorrect validation results.
- **Actionable Test:** Write a test that spawns 100 goroutines calling `ValidateRule` and 10 goroutines calling `SetPredicateArity` simultaneously.

#### 5. Logic & Parsing Evasion (Syntax Tricks)
- **Gap (String Literal Evasion):** The `countArity` function toggles `inQuote` when it sees `"`. However, it doesn't handle escaped quotes `\"` inside strings. A rule like `foo("bar\"baz", X)` would toggle `inQuote` on the escaped quote, thinking it's outside a string, and then see a comma, miscounting the arity.
- **Gap (Rule Separator Evasion):** `splitRuleBody` and `headText` *do* handle escaped quotes correctly (`if c == '\\' { escaped = true }`). But what if the rule separator `:-` is broken by whitespace? Mangle syntax might allow `: -`. The manual parser strictly looks for `if c == ':' && ruleText[i+1] == '-'`. If whitespace is injected, it might fail to split the rule.
- **Gap (Whitespace Bypass on Forbidden Heads):** `learnedHeadPattern` uses `^` (start of string). `ValidateLearnedRule` calls `strings.TrimSpace(ruleText)` before applying the regex, which mitigates this. However, multiline inputs where the forbidden head is on the second line (e.g., `\npermitted(/dangerous)`) might bypass it because `strings.TrimSpace` won't remove the newline if there are other characters before it. Wait, `(?m)^` is used in `declHeadPattern` but `learnedHeadPattern` is `^([a-z_][a-z0-9_]*)\s*\(`. If the input is `foo()\npermitted(...)`, it will only check `foo()` against the forbidden list.

## System Performance & Resilience
Is the `SchemaValidator` performant enough to handle these edge cases?
1. **Time Complexity:** The manual string parsing routines (`countArity`, `splitRuleBody`, `headText`) are `O(N)` where `N` is the length of the string. Go's string indexing is fast, but on megabyte-sized inputs, this will cause noticeable latency (milliseconds to tens of milliseconds per rule). In a high-throughput loop, this could be a bottleneck.
2. **Space Complexity:** The regex match operations allocate strings. Large matches mean large allocations, causing garbage collection pressure.
3. **Concurrency:** As noted, the maps are a critical vulnerability. The system *must* synchronize access if dynamic schema updates are supported, otherwise panics are guaranteed under load.

## Recommendations for Improvement
1. **Fix Escaped Quote Handling in `countArity`:** Replicate the `escaped` logic from `splitRuleBody` into `countArity` to prevent attackers from using `\"` to confuse the arity counter.
2. **Add Mutex for Maps:** If `SetPredicateArity` or `LoadDeclaredPredicates` are ever called after initialization (e.g., in a JIT context), wrap map accesses in a `sync.RWMutex`.
3. **Fix 0-Arity Counting:** Update `countArity` to return `0` if `strings.TrimSpace(argsStr) == ""` before entering the counting loop.
4. **Harden Forbidden Head Check:** Instead of regex matching only the first line of the string, the forbidden head check should ideally use the AST parser, or at least apply a regex that searches for forbidden heads anywhere in the head fragment, not just anchored to the start of the string.
