# QA Engineering Journal: Boundary Value Analysis & Negative Testing
## Subsystem: Mangle Schema Validator (internal/mangle/schema_validator.go)
## Date/Time: 2026-08-23 00:11:29 EST

### Overview
This journal entry documents a deep-dive QA analysis of the codeNERD Mangle Schema Validator subsystem, specifically focusing on Boundary Value Analysis (BVA) and Negative Testing.
The Schema Validator is a critical security and stability boundary that prevents AI agents from hallucinating predicates or injecting unauthorized facts into the Mangle engine.

### Why Mangle Schema Validator?
Based on code output quality and architectural importance, the Schema Validator is paramount. It bridges the gap between the untrusted generative AI output (which often hallucinate predicate names or arguments) and the strict, monotonic Mangle logic engine. A failure here could lead to ghost facts, corrupted fact stores, or unauthorized state transitions (e.g., granting `permitted(/dangerous)`).

### Analysis Vectors & Edge Cases Identified

#### 1. Null/Undefined/Empty Handling
*   **Empty Schema/Learned Texts:** The system handles empty texts, but what if `LoadDeclaredPredicates` is called when `learnedText` is empty but `schemasText` is populated? The tests don't explicitly verify that the absence of learned rules doesn't break schema extraction.
*   **Empty Arguments in `CheckArity`:** If a predicate is called with zero arguments `pred()`, the current parsing logic `strings.Count(argsStr, ",") + 1` might incorrectly calculate the arity if `argsStr` is empty.
*   **Empty Lines and Whitespace Variations:** The regex `(?m)^([a-z_][a-z0-9_]*)\s*\(` requires the predicate to be at the start of the line. What if an AI generates an indented learned rule like `  permitted(/dangerous) :- user_intent(...).`? The regex would miss it, allowing a forbidden head to bypass validation!

#### 2. Type Coercion & Formatting Anomalies
*   **Comma Injection in Generic Types:** The arity calculator uses `strings.Count(argsStr, ",") + 1`. If an AI hallucinates a complex nested type with commas, e.g., `Decl generic_map(Map.Type<string, string>)`, the arity will be miscalculated as 2 instead of 1.
*   **Unbalanced Parentheses:** The `validateHeadArity` depth loop tracks parentheses. What if the input is malformed, e.g., `candidate_action(/test`. The loop might terminate early or handle the `-1` state incorrectly, potentially allowing invalid schemas to pass through silently.
*   **Missing Dots:** While `HotLoadRule` tests missing dots, the overarching `ValidateProgram` might behave unpredictably with massive blocks of text lacking standard Datalog punctuation.

#### 3. User Request Extremes (Adversarial/Stress)
*   **Massive Arity:** What if a predicate is declared with 10,000 arguments? Can `validateHeadArity` and `extractDeclsFromText` handle massive string parsing without panicking or triggering regex catastrophic backtracking?
*   **Extreme Rule Length:** An AI might generate a deeply nested, recursive rule spanning thousands of characters on a single line. The string splitting and memory allocation during validation must remain performant.
*   **Built-in Redefinition Attempts:** The validator checks `isBuiltin` for missing declarations, but what if an AI explicitly tries to redefine a built-in in a learned rule? e.g., `count(X) :- ...`. This must be strictly forbidden to prevent core logic corruption.

#### 4. State Conflicts & Concurrency
*   **Concurrent Map Access:** The validator uses native Go maps (`declaredPredicates`, `predicateArities`). During a highly concurrent workflow (e.g., stress testing the API scheduler), multiple goroutines might attempt to call `HotLoadRule` or `LoadDeclaredPredicates` simultaneously. Go maps are NOT thread-safe for concurrent read/writes. This is a massive panic vector!
*   **Phantom State Across Evaluations:** If a single `SchemaValidator` instance is reused and `LoadDeclaredPredicates` is called multiple times with different corpus data, the maps are never cleared. Stale schemas could persist (ghost schemas), allowing predicates that were removed from the latest corpus version.

### Specific Gaps to Address in `schema_validator_test.go`

1.  **Concurrency Safety:** We must add tests that spawn multiple goroutines validating and loading rules simultaneously to expose map panics.
2.  **Whitespace Bypass:** Test indented forbidden predicates to ensure the regex `(?m)^([a-z_][a-z0-9_]*)\s*\(` doesn't leak.
3.  **Generic Type Commas:** Test `Decl` parsing with complex generic types containing commas.
4.  **Unbalanced Syntax Coercion:** Test arity validation with missing closing parentheses.
5.  **State Contamination:** Test sequential calls to `LoadDeclaredPredicates` with contradictory schemas.

### Performance & Capability Assessment
Currently, the subsystem is heavily reliant on regex (`regexp.MustCompile`) and manual string manipulation (`strings.Index`, `strings.Count`). While performant for typical workloads, regex parsing of untrusted AI output is inherently risky due to ReDoS (Regular Expression Denial of Service) vulnerabilities.
Furthermore, the lack of a sync mutex around the maps makes the current implementation incapable of handling true concurrent load safely. The system is performant enough for single-threaded edge cases but structurally vulnerable to state conflicts.

### Action Plan
1. Inject `// TODO:` comments into `internal/mangle/schema_validator_test.go` to highlight these specific gaps for the engineering team.
2. Recommend refactoring the maps to use `sync.RWMutex` or `sync.Map`.
3. Recommend replacing simple regex matching with the robust ANTLR Mangle parser (`parse.Unit`) for all validation steps, moving away from string heuristics.
