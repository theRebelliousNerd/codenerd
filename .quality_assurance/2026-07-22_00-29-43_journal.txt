Subsystem Reviewed: internal/campaign (Orchestrator Execution Module)

I have deeply reviewed the Orchestrator Execution module (`internal/campaign/orchestrator_execution.go` and `internal/campaign/orchestrator_execution_test.go`). The orchestrator is the central coordinator for running multi-phase, multi-task campaigns in codeNERD, utilizing a Mangle logic kernel to maintain state.

The current test file (`orchestrator_execution_test.go`) is practically empty, containing only a single dummy test function (`TestOrchestratorExecution_Placeholder`) and several TODO comments highlighting critical gaps in testing for edge cases.

To bring the testing of this module to a QA Automation Engineer level specializing in Boundary Value Analysis and Negative Testing, the test suite must be aggressively expanded to cover the following edge case vectors, which are currently unhandled or untested:

1. Null/Undefined/Empty Input Vectors
- Orchestrator state nulls: The `Run` method immediately checks for `o.campaign == nil`, but it assumes that if it exists, its fields are valid. Tests must verify behavior when `o.campaign.ID` is an empty string, or `o.campaign.Title` is empty. The kernel uses `o.campaign.ID` to assert facts (like `campaign_heartbeat`); an empty ID string could lead to malformed Mangle facts (`campaign_heartbeat("", 123456789)`), which might violate schema expectations or cause unintended fact collisions.
- Partial Initialization: If `o.config` is partially uninitialized, such as `o.config.CampaignTimeout` being negative, `context.WithTimeout` will instantly expire the context. Tests need to ensure this doesn't cause a panic but gracefully exits the run loop.
- Channel state: If `o.pauseCh` is nil but `o.isPaused` is true, the `Run` method defensively initializes it, but the test suite does not verify this self-healing behavior under stress.
- Context Pager state: If `o.contextPager` is completely uninitialized (nil) and the campaign transitions to a new phase, how does the system recover or crash?
- Zero length tasks array: What happens when the active phase has zero tasks? Does the orchestrator immediately complete the phase, or does it hang waiting for a task that will never be scheduled?

2. Type Coercion & Invalid State from Mangle
- Mangle is a logic programming language, and its facts are returned to Go code which must parse them. The `Run` method calls `o.getCurrentPhase()`. Tests must simulate the Mangle kernel returning a phase ID that does not exist in `o.campaign.Phases`. The execution loop expects `currentPhase` to be valid. If Mangle returns a ghost phase or a phase ID of a different type (e.g., an integer coerced to a string), the orchestrator must not crash.
- Block Reason Coercion: The `getCampaignBlockReason()` relies on Mangle facts. If the block reason contains non-printable characters or enormous strings, the Go logging layer may fail or truncate in unexpected ways.
- Heartbeat Timestamp Coercion: The `runHeartbeatLoop` pushes `time.Now().Unix()` to Mangle. Does the Mangle schema for `campaign_heartbeat` enforce `int64`? Can float precision errors happen during round-tripping?

3. User Request Extremes & System Stress
- Massive Campaigns: Testing must evaluate the orchestrator's behavior when a campaign contains 1,000,000 phases or tasks. Context cancellations or timeouts occurring during the processing of such massive lists must not cause OOM errors or block forever.
- High-frequency context switching: The context pager (`o.contextPager.ActivatePhase`) is invoked on phase transitions. If phases complete instantly (e.g., empty phases), the rapid switching must not overwhelm the LLM client or cause a memory leak.
- Massive file path deduplication: If a phase has millions of artifact files, the orchestrator must deduplicate them efficiently without O(N^2) latency spikes.
- Extremely long phase names: Can the logging subsystem gracefully handle phase names that are 10MB strings?
- Deeply nested directories: If the workspace config points to a repository with extremely deep nesting, will the orchestrator's file monitoring or loading crash with path too long errors?

4. State Conflicts & Race Conditions (Concurrency)
- The orchestrator employs a `runHeartbeatLoop` goroutine alongside the main `Run` loop.
- TOC/TOU (Time of Check / Time of Use) in Heartbeat: In `runHeartbeatLoop`, `o.campaign.ID` is read while holding `o.mu.RLock()`. The lock is released, and then `o.kernel.RetractFact` and `Assert` are called using that ID. If the campaign is reset or changed concurrently between the lock release and the Mangle assertion, the system might assert a heartbeat for a campaign that is no longer active, corrupting the Mangle state.
- Concurrent Cancellation & Autosave: If `ctx.Done()` fires in the main `Run` loop, the orchestrator immediately locks, updates status, and calls `saveCampaign()`. If the `autosaveTicker` in `runHeartbeatLoop` fires at the exact same millisecond, there could be lock contention or redundant file I/O operations. Tests must intentionally induce these exact timing collisions using mock tickers or synchronized channels.
- State Desynchronization: If the Mangle kernel's transaction commit fails, but the orchestrator's internal Go state has already advanced, how is the mismatch reconciled?
- Parallel Phase Execution: If multiple phases are forced active simultaneously via corrupted logic, does `runPhase` cause race conditions on shared orchestrator maps?

Performance Considerations:
The orchestrator heavily relies on `o.mu.Lock()` and `o.mu.RLock()` for synchronization. While read locks allow concurrency, the frequent writes (status updates, progress emits, autosaves) will cause lock contention under heavy stress (e.g., thousands of micro-tasks completing rapidly). The `runHeartbeatLoop` uses `time.NewTicker`, which is generally efficient, but the I/O cost of `saveCampaign` during every autosave tick could become a bottleneck if the campaign struct grows to tens of megabytes (Extreme Length Campaigns). The system must implement debouncing or delta-saves to remain performant.

Detailed Execution Profiles & Mangle Assertions:
To truly prove these edge cases, tests must implement custom `core.Kernel` mocks that simulate specific logic states that Mangle might enter, rather than just returning standard values.

- Simulation 1: The Infinite Loop State. The Mangle program fails to stratify or enters an infinite loop. The orchestrator's `kernel.Query` calls must have explicit timeouts to prevent the entire campaign from freezing.
- Simulation 2: The Silent Failure State. Mangle returns zero facts when it should return exactly one (e.g., no active phases, but the campaign isn't marked complete). The orchestrator must gracefully fail or auto-heal rather than busy-looping at 100% CPU.
- Simulation 3: Fact Type Mismatch. A fact is asserted as an Atom but retrieved as a String. Mangle treats these as distinct types, which will cause join failures. The orchestrator test must verify type strictness in its assertions.
