# QA Automation Engineering Journal
## Date: 2026-09-26_00-59-12
## Subsystem: Holographic Context Provider (`internal/world/holographic.go` & `holographic_test.go`)

### Overview
This journal entry focuses on a deep-dive QA analysis of the **Holographic Context Provider**, specifically targeting Boundary Value Analysis (BVA) and Negative Testing. CodeNERD's holographic subsystem is critical; it is the "X-Ray Vision" layer that aggregates multi-dimensional code context (AST signatures, package siblings, architectural constraints) before piping it into the prompt assembler for the LLM.

Failures here have cascading effects. If the Holographic Context truncates or hallucinates package imports, the AI agent will confidently write broken code.

### Evaluated Vectors & Missing Edge Cases

During our review of `internal/world/holographic.go` and `internal/world/holographic_test.go`, we evaluated the system against the following core negative testing vectors:

#### 1. Null / Undefined / Empty Scenarios
*   **Empty Structs/Interfaces (Already tested, but let's look deeper):** The test `TestExtractTypeDefinition_EmptyStructAndInterface` exists, which is good. However, what if a file contains *only* a package declaration and literally zero bytes of content after it? The `parser.ParseFile` behavior on zero-byte files (or files containing just `package main` followed by EOF) is tested loosely via `TestHolographicContext_EmptyFile`, but there's a missed edge case:
    *   **The Unnamed Package:** What happens if `package ` is declared with no name (e.g., just `package
`) due to an incomplete LLM generation? The AST parser might panic or return a nil tree.
*   **Empty PackageSiblings List:** If a file is completely isolated (no siblings, not even itself due to a weird symlink issue), does `buildGoContextWithContext` gracefully handle the empty array during JSON marshaling for the LLM prompt? (We need a test for `nil` slices in the context struct).
*   **Missing Imports:** What if a Go file uses a package (e.g., `fmt.Println`) but the `import` block is completely missing? The `narrowLocalRefs` function relies on `PackageImports` to determine external vs local refs. If the import is missing, it might falsely attribute the missing symbol to an unresolved local package symbol.
*   **Empty Function Body with Valid Signature:** A function may have a valid signature but an entirely empty body (`func doSomething() {}`). Does the `fetchFunctionBody` gracefully handle this, or does it attempt to index lines that don't exist?
*   **Null Receiver on Methods:** What happens if a method is declared on a type, but the pointer receiver is inexplicably missing (e.g., `func ( *MyType) Method()`) due to generated code errors? The `extractFuncSignature` might fail when extracting `fn.Recv.List[0].Type`.
*   **Empty File Path Queries:** If the Holographic Provider is invoked with an empty string for the file path, does the path resolution logic safely return an error, or does it resolve to the current working directory and attempt to parse the entire monorepo root?

#### 2. Type Coercion / Format Mangling
*   **Mangled Binary in Text Files:** We have a test `TestHolographicContext_BinaryFileFallback`, but it relies on `.bin` extensions. What if a `.go` file is actually a binary artifact (e.g., an LLM hallucinated a compiled binary and wrote it as `main.go`)? If `parser.ParseFile` is invoked on a 2MB binary blob disguised as a `.go` file, it will fail, but does it fail *fast* and without allocating massive amounts of memory for error strings?
*   **C-Go Interop Coercion:** If a Go file contains massive C-Go comments (`/* #cgo CFLAGS: ... */`), does `extractFuncSignature` accidentally truncate the signature or consume the C code as a function docstring?
*   **JSON-in-Go Hallucinations:** A common AI failure mode is wrapping JSON configurations inside a Go file without proper backticks. Does the parser recover, or does it abort the entire package analysis?
*   **Unicode/RTL Override Characters:** If an adversarial user input includes Right-to-Left (RTL) override characters in a variable name or string literal, does the AST parser handle it, and more importantly, does the `SymbolSignature` JSON serialization correctly encode it without breaking downstream LLM logic?
*   **Excessively Long Variable Names:** An LLM might generate a variable name that is 10,000 characters long to fulfill a bizarre prompt. Does the `extractTypeDefinition` truncate this, or does it pass the massive string into the context, eventually breaking token limits?

#### 3. User Request Extremes (The "Frontier" Edge Cases)
*   **Extreme File Density:** The test `TestBuildGoContext_SiblingFilesCap` tests 110 sibling files and ensures the cap of 100 is respected. However, what if a user asks CodeNERD to analyze a generated `models` directory containing **100,000** sibling `.go` files?
    *   *The Performance Bottleneck:* The `os.ReadDir(dir)` call in `buildBasicContextWithContext` will load 100,000 `DirEntry` objects into memory at once. Furthermore, `extractGoSignatures` parses up to the cap, but `buildBasicContext` might iterate over all of them. Is the system performant enough to handle 100k files in a single directory?
    *   *Conclusion:* No, it likely isn't. The `DirEntry` slice alone will consume significant RAM, and if multiple concurrent Shards are querying this directory, we hit OOM panics (Panic Catalog P11/P12).
*   **Infinite AST Nesting:** What if a generated tool outputs a Go file with 5,000 nested closures or deeply nested `struct` definitions (e.g., `struct { A struct { B struct { ... } } }`)? `extractTypeDefinition` uses AST recursion. A deeply nested struct might trigger a stack overflow in the Go runtime (Panic Catalog P6: Stack Overflow in Recursion).
*   **Polyglot Confusion:** If a user requests analysis on a monorepo where `.go` files are actually symlinks to Python scripts (bizarre, but happens in extreme chaos scenarios), the Go parser will fail.
*   **Extreme Line Lengths:** A generated file might contain a single line of code that is 50 megabytes long (e.g., a massive base64 encoded string literal). The `scanner` inside the AST parser might struggle to allocate memory for the token. We need to verify the `max size` bounds on individual token extraction.
*   **Monolithic Files:** A user might provide a 50 Million Line monorepo concatenated into a single `everything.go` file. The `fetchFunctionBody` has a 5MB limit, but what happens to the AST parser when it tries to build the `PackageSignatures` array?

#### 4. State Conflicts & Race Conditions
*   **The "Deleted File Mid-Flight" Race:** As noted in the existing TODOs (`TestHolographicContext_DeletedFileMidFlight`), there is a critical race condition. `os.ReadDir` gets the file list. Then, before `parser.ParseFile` opens the file, an external process (like `go generate` or another CoderShard) deletes it. The current implementation might throw an unhandled `os.ErrNotExist` that bubbles up and aborts the entire Holographic context generation, starving the LLM of context for the *remaining* valid files.
*   **Regex Cache Contention:** The regex cache (if used in the holographic parser, though it seems more AST-driven now) or any shared maps across Holographic instances are prone to concurrent map read/write panics (Panic Catalog P4). The TODO `TestHolographicContext_ConcurrentReadWrite` explicitly calls this out.
*   **Concurrent Sibling Modifications:** While `buildGoContextWithContext` is running, what if a different Shard is actively appending to one of the sibling files? The `parser.ParseFile` might catch a partially written function declaration, resulting in an unexpected EOF error.
*   **Directory Permissions Race:** What if the directory permissions change from readable to unreadable exactly between the `os.Stat` check and the `os.ReadDir` execution?

5.  **TestHolographicContext_ExtremeSiblingCount:** Add a benchmark/stress test that generates 10,000 empty `.go` files and ensures the provider parses them within an acceptable time limit (e.g., < 2 seconds) and memory budget, proving resilience against the "Extreme File Density" vector.
6.  **TestHolographicContext_DeeplyNestedAST:** Add a test with an AST depth of 500 to ensure `extractTypeDefinition` doesn't stack overflow.

By implementing these negative tests, we ensure the Holographic Context Provider remains a robust foundation for CodeNERD's intelligence, rather than a fragile dependency that panics under adversarial monorepo conditions.

### Architectural Performance Review
Regarding the prompt's question: "if the system the test is written for is performant enough to handle each edge case vector."
- **For Null/Undefined/Empty:** Yes, the Go parser is robust against small, malformed files, but edge cases like `package ` (with trailing spaces) could be unhandled.
- **For Type Coercion:** Handing large binary files is risky. The 5MB cap (`fetchFunctionBody`) is good, but `parser.ParseFile` should not be fed un-validated 4.9MB blobs.
- **For User Request Extremes:** The system is **NOT** performant enough for 100,000 sibling files or 10,000 deep AST trees. We need hard caps, not just logic caps.
- **For State Conflicts:** The system requires better isolation or retry logic for "Deleted File Mid-Flight" scenarios. The performance penalty of an aborted context generation is too high.

### Extended Analysis of Code Context Aggregation
The HolographicContext struct represents a multi-dimensional view of the code. This includes PackageScope, Architectural Layer, Dependency Context, and Symbol Graph. When we consider boundary values for these dimensions, we must look at the combinatorial explosion. For example, if a file has 100 siblings, and each sibling imports 100 packages, the PackageImports map becomes enormous. This stresses not just the parsing layer, but the LLM Prompt Assembler which must serialize this to JSON. Negative testing should attempt to overflow the JSON encoder by supplying gigabytes of valid AST data. Furthermore, the `narrowLocalRefs` function is an optimization. If the initial parse is too large, the optimization itself becomes a bottleneck. We must ensure that the 'cap' applies before the expensive AST traversals.

#### Mangle Validation and Healing Context
We must also consider how Holographic context interacts with Mangle. The `holographic` package provides facts to the kernel. If it provides a corrupted or extremely large fact (e.g., a function signature with a 10MB string), the Mangle `engine` might exhaust memory during `Analyze`. Testing must include creating Go files that intentionally generate massive Mangle facts to see if the validation layer or self-healing mechanisms catch it before memory exhaustion. The `internal/world/holographic.go` provides a bridge between unstructured Go code and structured facts, making it a critical boundary for validation.

### Advanced Negative Testing Matrix: Go Type System Boundaries

The following sections define explicit boundary test cases for the Go type system as evaluated by the holographic parser. These vectors are critical because LLMs frequently invent synthetic types that violate Go's strict specifications but appear superficially valid.

#### Interface Implementation Constraints
A common hallucination is an interface implementation that relies on unexported methods from a different package.
When `narrowLocalRefs` evaluates this, does it correctly identify the missing symbols, or does it silently drop the interface?
Negative Test: Generate a file implementing an interface `error` with a method `error() string` (lowercase, wrong signature).
Expected Result: The holographic context should serialize this exactly as parsed, passing the malformed signature to the AI.
Performance Impact: Low. The AST parser natively handles malformed signatures.

#### Generic Type Instantiation
The introduction of Go 1.18 generics introduced significant complexity to `TypeSpec` parsing.
Boundary Value: What happens if an AI generates a struct with a type parameter list that is thousands of parameters long?
Negative Test: `type Massive[T1 any, T2 any, ..., T10000 any] struct{}`
Expected Result: The `formatNode` function must not allocate unbounded strings when formatting the generic type parameters.
Performance Impact: High. A string builder without a capacity limit could cause massive GC pressure.

#### Channel Directionality Edge Cases
Channels can be unidirectional or bidirectional.
Boundary Value: An AI agent mistakenly declares a channel that sends and receives on the wrong side of the arrow.
Negative Test: `func Process(c <-chan<- int)` (syntactically invalid).
Expected Result: The Go AST parser will likely reject this during `parser.ParseFile`. We need to ensure that one rejected file doesn't crash the entire package context building process.
Performance Impact: Medium. Error propagation must be isolated.

#### Goroutine Closure Capture Leaks
When an LLM writes concurrent code, it often forgets to copy loop variables (prior to Go 1.22).
Boundary Value: Does the holographic context detect variables captured in closures for `localRefs`?
Negative Test: A massive `for` loop with 50 nested closures capturing the same `i` variable.
Expected Result: The `narrowLocalRefs` function must accurately trace the reference count without causing a stack overflow in the AST visitor.
Performance Impact: Medium. Recursion depth must be capped.

#### Struct Tag Reflection Parsing
Struct tags are a major source of AI hallucination, often mixing JSON, YAML, and GORM syntax arbitrarily.
Boundary Value: A struct field with a 50KB struct tag string.
Negative Test: `type Config struct { Field string ` + "`json:"field"" * 1000 + "`}`
Expected Result: The `extractTypeDefinition` logic must parse the field, but should it truncate the tag? Currently, it does not.
Performance Impact: High. Massive string allocations during context serialization.

#### CGO Header Resolution
The AI might attempt to import C headers that don't exist.
Boundary Value: Importing a C library with an incredibly long path.
Negative Test: `import "C/very/long/path/..."`
Expected Result: The system shouldn't attempt to resolve C headers dynamically during context building.
Performance Impact: Low, assuming the AST parser skips deep resolution.

#### Build Tag Exclusions
Build tags (`//go:build`) dictate which files belong to a package.
Boundary Value: A file with a build tag that explicitly conflicts with another file in the same directory.
Negative Test: `//go:build linux` and `//go:build windows` in siblings.
Expected Result: The `buildBasicContextWithContext` currently includes *all* files with the same extension, ignoring build tags. This is a known limitation.
Performance Impact: Low, but context quality impact is high.

#### Vendor Directory Isolation
Boundary Value: The user asks to analyze code inside a deep `vendor/` directory.
Negative Test: Path traversal into `vendor/github.com/google/mangle/...`
Expected Result: The `fetchFunctionBody` must enforce workspace containment rules, even if the directory exists locally.
Performance Impact: Medium. Security checks must be fast.

#### Alias Type Resolution
Boundary Value: Deeply chained type aliases.
Negative Test: `type A = B; type B = C; type C = D; ... type Z = int`.
Expected Result: The holographic context does not resolve aliases, it just reports them.
Performance Impact: Low.

#### Cyclomatic Complexity Limits
While the holographic provider doesn't explicitly calculate complexity, the `PrioritizedCallers` logic implies ranking.
Boundary Value: A single function with 10,000 `switch` cases.
Negative Test: `func MassiveSwitch() { switch x { case 1: ... case 10000: } }`
Expected Result: The AST parser must navigate the case list without OOM.
Performance Impact: High.

### Resilience and Recovery
The final aspect of our QA analysis involves system resilience. When the Holographic Context Provider encounters a critical failure (e.g., an OOM during AST parsing or an I/O timeout during file reads), how does the surrounding CodeNERD infrastructure recover?
Currently, many methods return an `error` interface, which is a standard Go practice. However, `queryRelationshipsWithContext` simply returns early on error without logging the failure vector.
If `h.kernel.Query("code_defines")` fails due to a malformed Mangle fact, the context is silently degraded.
This "fail-open" behavior is dangerous in an AI context. The LLM will assume the file has no dependencies, rather than realizing the dependency check failed.
A proper QA approach dictates that degraded context MUST be explicitly flagged to the prompt assembler.
We propose adding a `ContextDegradation` field to the `HolographicContext` struct to track partial failures.
