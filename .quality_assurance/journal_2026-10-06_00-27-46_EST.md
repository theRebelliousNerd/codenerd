# Quality Assurance Journal Entry: Boundary Value Analysis and Negative Testing
**Date:** 2026-10-06 00:27:46 EDT

## 1. Executive Summary and Subsystem Selection

For this deep-dive Quality Assurance review, I selected the `internal/persist/factsnap` module. This subsystem is fundamentally responsible for serializing, compressing, persisting, and deserializing 'facts'—the core atomic units of data operated upon by the Mangle logic programming engine within codeNERD. Its correctness and performance are paramount. If fact snapshotting fails, corrupts, or halts due to edge-case inputs, the entire system's state is compromised, potentially leading to catastrophic failure across dependent subsystems (e.g., `corpus-builder`, `stress-tester`, and system self-healing components).

The current test suite (`factsnap_test.go`) primarily verifies 'Happy Path' scenarios. It uses a `sampleFacts` generator that yields neatly structured, modestly sized strings and integers. While it covers various codecs (JSON, Gzip, Zstd) and sidecar validation, it notably lacks rigorous Boundary Value Analysis (BVA) and Negative Testing. This journal details a comprehensive strategy to augment the test suite, assessing whether the underlying implementation can robustly withstand adversarial, extreme, and malformed inputs.

## 2. Null, Undefined, and Empty Vectors

### 2.1 Empty Facts and Nil Slices
The current tests initialize a specific number of facts (e.g., `sampleFacts(1000)`). What happens if `facts` is `nil` or an empty slice (`[]types.Fact{}`)?
- **Scenario:** A campaign initialization process creates a snapshot before any facts have been derived. The input slice to `Write` or `WriteCodec` is `nil`.
- **Expected Behavior:** The system should cleanly write an empty snapshot (e.g., a minimal valid Gzip stream or empty JSON array) without panicking. The `Read` function should subsequently return an empty slice (or `nil`), but crucially, it must not return an `io.ErrUnexpectedEOF`.
- **System Readiness:** Looking at `factsnap.go`, `WriteCodec` loops over the facts. If `facts` is empty, it skips the loop and writes the schema. This should perform well, but a specific test must assert that `Read` correctly infers an empty state.

### 2.2 Empty Predicates and Arguments
- **Scenario:** A fact is created with an empty string predicate `""`, or an empty array of arguments (`[]any{}`).
- **Expected Behavior:** Mangle typically requires valid atom shapes. If a predicate is empty, the encoder should either reject it early with a clear validation error, or encode it safely if empty predicates are technically permitted.
- **System Readiness:** Mangle uses `Symbol` for predicates. A zero-length symbol might cause issues in the `SimpleColumnStore`. If `factsnap` delegates directly to Mangle without validating `Predicate != ""`, the crash might occur deep in the CGO or Mangle engine. We must test this to ensure the system gracefully rejects or handles it without crashing the process.

### 2.3 Null Bytes in Strings
- **Scenario:** An LLM or external data source injects a null byte (`\x00`) within a string argument: `types.Fact{Predicate: "code_defines", Args: []any{"func\x00main"}}`.
- **Expected Behavior:** The serialization format must correctly escape or binary-encode the null byte. JSON will escape it as `\u0000`, but what about the `SimpleColumnStore` custom binary codec?
- **System Readiness:** The Mangle string types handles bytes, but if the string is passed through C-strings or unescaped ASCII formats, it could truncate the string or corrupt the subsequent column data. This needs an explicit negative test.

## 3. Type Coercion and Data Shape Vectors

### 3.1 Unmapped Go Types
- **Scenario:** Go's `any` interface allows passing arbitrary structs, channels, or functions into `types.Fact.Args`. What happens if `Args: []any{make(chan int)}` is passed to `Write`?
- **Expected Behavior:** The system should return a serialization error (e.g., "unsupported type chan int") instead of panicking via `reflect` or silently dropping the argument.
- **System Readiness:** The `normalizeArg` and `atomToFact` functions in `factsnap.go` use type switches. For unknown types, `baseTermToValue` uses `fmt.Sprintf("%v", term)`. This means a channel might be serialized as `"<chan int Value>"`. This silent coercion might lead to downstream logical errors in Mangle queries. A strict schema validation is preferable.

### 3.2 Floating Point Edge Cases
- **Scenario:** A fact argument is a `float64` containing `math.NaN()` or `math.Inf(1)`.
- **Expected Behavior:** Standard JSON does not support NaN or Infinity. The legacy JSON path will fail to marshal it. The Gzip/Zstd custom paths need to be evaluated. Does `SimpleColumnStore` support IEEE 754 infinity?
- **System Readiness:** If `json.Marshal` is the fallback, it will throw `json: unsupported value: NaN`. The system must normalize or strictly reject NaNs before reaching the persistence layer to avoid failed saves leading to lost progress.

### 3.3 Numeric Overflow
- **Scenario:** A fact argument receives an `int64` at the absolute maximum value (`math.MaxInt64`), or a `uint64` that exceeds `math.MaxInt64`.
- **Expected Behavior:** The value must round-trip exactly without truncation or sign-flipping. Mangle might treat numbers as 64-bit signed integers; passing a `uint64` could cause it to wrap to a negative number.
- **System Readiness:** Since `factsnap.go` normalizes `int` to `int64`, an overflow check or type strictness for `uint64` is required. The test suite needs bounds-checking scenarios.

## 4. User Request Extremes (Volume and Length)

### 4.1 Extreme Campaign Lengths and Arity
- **Scenario:** A fact contains an incredibly long array of arguments, e.g., `types.Fact{Predicate: "mega_fact", Args: make([]any, 100000)}`.
- **Expected Behavior:** `SimpleColumnStore` represents data in columns. An arity of 100,000 might exhaust column descriptor limits or memory during allocation. The system should enforce a maximum arity (e.g., 255) and reject facts exceeding it.
- **System Readiness:** `factsnap` loops over `a.Args`. If the Mangle AST allows large arities, the memory footprint will grow linearly, but could cause a stack overflow or OOM if recursive processing is used deep in the engine.

### 4.2 Massive Monolithic Monorepo Filenames
- **Scenario:** In an enterprise brownfield request, an LLM extracts a file path that is 50 Megabytes long (due to a glitch in text extraction or a malformed URL payload).
- **Expected Behavior:** The string should be written and read correctly, though realistically, a string of that size in a fact is anomalous.
- **System Readiness:** The `SimpleColumnStore` might buffer strings in memory. A 50MB string could cause a large contiguous allocation. This is a severe stress test vector. Given modern 8GB RAM laptops, multiple such strings could induce GC pauses or swap thrashing. The system might need string-length sanitization.

### 4.3 High Volume Fact Insertion
- **Scenario:** The user triggers a "frontier coding benchmark" request requiring the ingestion of 50 million discrete facts into a single snapshot.
- **Expected Behavior:** `WriteCodec` must stream the facts or batch them to avoid allocating a 50M-element slice in memory at once.
- **System Readiness:** Currently, `WriteCodec` takes `facts []types.Fact`. This requires the entire slice to reside in memory before persistence begins. For 50 million facts, this could easily consume 5-10GB of RAM just for the slice and underlying interfaces. The system is NOT performant enough to handle this edge case without a streaming API design (e.g., `WriteIter(iter FactIterator)`).

## 5. State Conflicts and Race Conditions

### 5.1 Concurrent Writes to the Same Snapshot Path
- **Scenario:** 10,000 goroutines attempt to write a snapshot to the exact same file path `/workspace/.nerd/snapshot.sc.gz` simultaneously.
- **Expected Behavior:** The `pathLocks` `sync.Map` should serialize the access, ensuring that no file corruption occurs.
- **System Readiness:** The code uses `v, _ := pathLocks.LoadOrStore(key, &sync.Mutex{})` and then locks it. This effectively serializes the writers. However, with 10,000 writers, this will cause immense lock contention and starvation. Furthermore, `writeFileAtomic` creates a new temp file per write. 10,000 concurrent temporary files will exhaust the OS file descriptor limit (`EMFILE`), causing cascading crashes. The system is currently vulnerable to FD exhaustion under extreme concurrency.

### 5.2 File Deletion Mid-Read
- **Scenario:** A user or another agent aggressively deletes the snapshot file or the `<path>.sha256` sidecar right after `os.ReadFile` but before parsing finishes.
- **Expected Behavior:** Since `os.ReadFile` loads the entire file into memory, deletion after read is fine. However, what if the sidecar is deleted between reading the file and reading the sidecar?
- **System Readiness:** The code reads the main file, then calls `verifyChecksum` which reads the sidecar. If the sidecar is missing (`os.IsNotExist`), it returns `nil` (skips verification). This is structurally safe from panics but introduces a Time-Of-Check to Time-Of-Use (TOCTOU) race condition where a malicious actor or errant process could strip the checksum to bypass integrity validation.

### 5.3 Partial Overwrites from External Processes
- **Scenario:** An external process (e.g., a buggy script written by the agent) opens the snapshot file and writes garbage data into the middle of the zstd stream while `Read` is executing.
- **Expected Behavior:** The `verifyChecksum` step should detect the alteration and reject the file with `ErrIntegrity`. If the checksum is bypassed, the Zstd or Gzip decoder should error out safely rather than panicking on malformed data.
- **System Readiness:** `verifyChecksum` protects against this, assuming the sidecar is intact. We must explicitly test feeding corrupted Gzip bytes to `factstore.NewSimpleColumnStoreFromGzipBytes` to ensure the CGO/Mangle layer doesn't segfault and properly returns a Go error.

## 6. Detailed Test Improvement Strategy

To achieve production-grade robustness against these vectors, the following specific test categories must be implemented:

### A. The Nullity Matrix
We will create a table-driven test `TestFactsnap_Nullity Matrix` that iterates through:
1. `nil` slice of facts.
2. Slice containing a zero-value fact `types.Fact{}`.
3. Facts with `nil` `Args`.
4. Facts with `[1]any{nil}` arguments.
We will assert that `WriteCodec` and `Read` symmetrically handle these without panic.

### B. The Adversarial Payload Suite
A fuzz-like suite `TestFactsnap_AdversarialPayloads` will inject:
1. 50MB predicate strings.
2. Extremely deep recursive arguments (if supported by `types.Fact`).
3. Embedded null bytes and non-UTF8 sequences.
4. Type coercion vectors (passing maps, channels, structs where scalars are expected).

### C. The Concurrency Crucible
We will design `TestFactsnap_ConcurrencyCrucible` to launch thousands of goroutines attempting to write and read from the same path. We will monitor for:
1. File descriptor leaks or limits.
2. Deadlocks in `pathLocks`.
3. Temporary file orphaned on disk (checking the temp directory post-test).

### D. Codec Fuzzing and Desync
Tests will deliberately write a Zstd file, rename it to `.sc.gz`, and verify `resolveReadCodec` successfully recovers. Furthermore, we will inject random byte mutations into the compressed payload to ensure `collectFacts` and the underlying Mangle store gracefully return errors instead of hanging in infinite loops or panicking.

## 7. Conclusion on Performance and Scalability

While the current `factsnap` implementation is highly optimized for size (as demonstrated by `TestSizeComparison`), its memory and concurrency models are built for 'Happy Path' workloads. The reliance on fully materializing slices (`[]types.Fact`) in memory limits its ability to handle extreme user requests (like the 50M fact frontier benchmark) on constrained hardware.
Additionally, the atomic write pattern, while safe from corruption, creates file descriptor pressure under high concurrency.
Implementing these boundary value and negative tests will not only expose these architectural boundaries but also serve as the regression baseline necessary to refactor `factsnap` towards a more robust, streaming-oriented architecture.
