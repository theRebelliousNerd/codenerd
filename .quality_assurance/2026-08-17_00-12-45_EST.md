# QA Automation Engineering Journal: Boundary Value Analysis and Negative Testing
## Target Subsystem: `internal/tools/core/file_ops.go`
## Date: 2026-08-17 00:12:45 EST

### Executive Summary
After an extensive review of the codeNERD ecosystem, including its underlying Mangle-based reasoning engine (`.claude/skills/codenerd-builder/SKILL.md`), neuro-symbolic intent classification, autopoiesis system, and the stress-tester methodology (`.claude/skills/stress-tester/SKILL.md`), I am directing my QA analysis towards the core filesystem manipulation toolset: `internal/tools/core/file_ops.go` and its test suite `file_ops_test.go`.

**Why this module?**
As detailed in the `codenerd-builder` documentation, the agent's OODA loop explicitly connects the *Observe* phase to an *Act* phase facilitated by the `VirtualStore`, which relies on modular tools. The `file_ops` package (providing `read_file`, `write_file`, `edit_file`, and `delete_file`) acts as the primary tactile interface between the reasoning engine and the physical file system.

It ranks highest in terms of *material code quality output impact*:
1.  **Durable State Modification**: Unlike ephemeral internal facts, actions here permanently alter the user's workspace.
2.  **Security Boundary**: It is the enforcement point against directory traversal and malicious containment escapes (`workspaceRoot` usage).
3.  **Self-Healing Feedback Loop**: When the LLM makes a mistake (e.g., hallucinating a file name like `campaign_observer.go` instead of `observer.go`), the specific text returned by these tools (see `file_ops_notfound_test.go`) is fed back into the transducer. A misleading error string can derail an entire task.
4.  **Autopoiesis Target**: This is the very toolset codeNERD uses to modify its own generated tools.

While the existing tests are robust (handling explicit type checking, confirming `replace_all` logic, and mitigating "F-TOOL-2" guess loops), a rigorous Boundary Value Analysis (BVA) and Negative Testing audit reveals critical gaps in handling edge cases, specifically around null/undefined inputs, type coercion vulnerabilities, extreme state conflicts, and bizarre user requests that push the performance boundaries of the Mangle engine.

### Detailed Vector Analysis & Identified Gaps

#### 1. Null / Undefined / Empty Input Vectors

The current tests verify that missing keys (like `path` or `new_text`) return errors. They also explicitly test that `new_text: ""` correctly acts as a deletion in `edit_file`. However, they fail to address the boundary between explicit zero-values and implicit type defaults in JSON payloads unmarshaled into `map[string]any`.

**Gap 1.1: `write_file` - The Null / Empty Content Boundary**
*   **Scenario:** What happens if the `content` argument is present but is explicitly JSON `null`? The code uses `rawContent, ok := args["content"]` and then `content, ok := rawContent.(string)`. If it is `nil`, the type assertion fails, returning an error. *However*, what if `content` is exactly `""` (empty string)?
*   **Impact:** Is it a bug to `write_file` with an empty string? Does this just create an empty file, or truncate an existing file to 0 bytes? The current test suite doesn't explicitly verify the behavior of `write_file` creating an empty file (0 bytes). This is critical because some tools or compilers might fail unexpectedly on completely empty source files.
*   **Required Test:** `TestWriteFileTool_Execute_EmptyContent`

**Gap 1.2: `list_files` - The Empty Path Boundary**
*   **Scenario:** `list_files` defaults to `.` if `path` is empty (`""`). But what if the user passes `path: null`? The `rawPath, _ := args["path"].(string)` will evaluate to `""` (the zero value for string) when the assertion fails on `nil`. This implicitly defaults to `.`.
*   **Impact:** This implicit fallback on `nil` (from a potentially malformed LLM JSON output where the key was meant to be populated but wasn't) means a hallucinated request to list a non-existent directory might silently list the root directory, polluting the context window with the root's contents instead of erroring out.
*   **Required Test:** `TestListFilesTool_Execute_NullPath_ImplicitDefault`

**Gap 1.3: `edit_file` - Empty `old_text`**
*   **Scenario:** What happens if `old_text` is `""` (empty string) in `edit_file`? The code says `if oldText == "" { return "", fmt.Errorf("old_text is required") }`. This is handled. But what if it's whitespace `old_text: " "` or a zero-width space `​`?
*   **Impact:** `strings.Contains(contentStr, " ")` will almost certainly be true. Without `replace_all`, it replaces the *first* space. This is highly ambiguous and likely destructive. The non-unique check `strings.Count(contentStr, oldText) > 1` might catch it, but if a file only has one space, it proceeds.
*   **Required Test:** `TestEditFileTool_Execute_WhitespaceOldText_Ambiguity`

#### 2. Type Coercion Vectors

The Go map `map[string]any` is notorious for type coercion issues, especially when populated by `encoding/json` where numbers are `float64`.

**Gap 2.1: `list_files` - Boolean Coercion from Strings**
*   **Scenario:** The LLM outputs `{"recursive": "true"}` instead of `{"recursive": true}`.
*   **Impact:** The code `if r, ok := args["recursive"].(bool); ok` will fail (it's a string, not a bool). The `ok` is false, so `recursive` remains `false`. The tool silently ignores the user's intent to recurse.
*   **Required Test:** `TestListFilesTool_Execute_StringBoolean_CoercionFailure`

**Gap 2.2: `delete_file` - Confirmed Coercion**
*   **Scenario:** The LLM outputs `{"confirmed": "yes"}` or `{"confirmed": 1}`.
*   **Impact:** The type assertion `confirmed, _ := args["confirmed"].(bool)` fails, yielding `false`. The tool rejects the deletion safely, but does it provide a clear error message explaining *why* it failed (type mismatch vs not confirmed)? The current error is `"delete_file requires confirmed=true"`, which doesn't specify the type error.
*   **Required Test:** `TestDeleteFileTool_Execute_ConfirmedTypeMismatch`

#### 3. User Request Extremes (Performance & Limitations)

These tests evaluate how the physical limitations of the host interact with the logical constraints of the `file_ops` tools, simulating "Brownfield requests on a laptop with 8GB RAM."

**Gap 3.1: `list_files` - The Node Modules / Deep Tree Attack**
*   **Scenario:** The user asks to list a massive, deeply nested directory (e.g., `node_modules` with 150,000 files) using `recursive: true`.
*   **Impact:** The `filepath.Walk` will build a `files []string` slice containing 150,000 paths, then `strings.Join(files, "
")` it. This string could easily exceed 10MB. When this string is returned to the `JITPromptCompiler`, it will obliterate the `TokenBudgetManager` allocations (40% working memory budget), likely causing an immediate token limit crash or forcing catastrophic eviction of the context window.
*   **Required Test:** `TestListFilesTool_Execute_MassiveDirectory_TokenBudgetDoS` (Testing if `list_files` implements internal truncation or limits).

**Gap 3.2: `edit_file` - Multi-Megabyte Files & `ReplaceAll`**
*   **Scenario:** A 50 million line monorepo. The user targets a 500MB CSV or log file and executes `edit_file` with `replace_all: true` to change commas to semicolons.
*   **Impact:** `projectdoc.ReadFileForTool(path)` loads the entire 500MB into memory. `strings.ReplaceAll` creates a *new* 500MB string. Peak memory spikes to >1GB just for string manipulation. On an 8GB RAM machine running Docker containers and a local LLM, this causes an Out-Of-Memory (OOM) kill. The tool lacks streaming edits or size caps.
*   **Required Test:** `TestEditFileTool_Execute_LargeFileOOM_Protection`

**Gap 3.3: Extreme Path Lengths (Windows Limitations)**
*   **Scenario:** Running the tactile shard on Windows (`internal/tactile/platform_windows.go`), an LLM generates a nested directory structure exceeding `MAX_PATH` (260 characters).
*   **Impact:** `os.MkdirAll` (via `write_file`) or `os.Stat` (via `read_file`) may panic or return cryptic OS-level errors instead of clean tool errors, breaking the Mangle reasoning loop.
*   **Required Test:** `TestWriteFileTool_Execute_MaxPathLength_Violation`

#### 4. State Conflicts & Race Conditions

Mangle's stateful, monotonic evaluation requires atomic, idempotent actions. The filesystem is intrinsically mutable and concurrent.

**Gap 4.1: `write_file` - The Symlink / Hardlink Overwrite**
*   **Scenario:** The file at `path` is actually a symlink pointing *outside* the workspace (e.g., `/etc/passwd`). The `workspace_guard.go` checks if the *resolved* path is safe. But what if a concurrent process changes the symlink between the `resolveWorkspacePath` check and the `os.WriteFile` execution (Time-of-Check to Time-of-Use / TOCTOU vulnerability)?
*   **Impact:** Privilege escalation or critical system file corruption.
*   **Required Test:** `TestWriteFileTool_Execute_Symlink_TOCTOU`

**Gap 4.2: `edit_file` - The Concurrent Modification Race**
*   **Scenario:** Two ephemeral SubAgents (or a user and an agent) try to edit the same file simultaneously. Agent A reads the file, finds `old_text`. Agent B modifies the file, changing or removing `old_text`. Agent A then writes its modified version, overwriting Agent B's changes completely.
*   **Impact:** Silent data loss. `edit_file` does not use file locking (e.g., `flock`) or compare-and-swap semantics (like an ETag or checking file mod time before write).
*   **Required Test:** `TestEditFileTool_Execute_ConcurrentModification_RaceCondition`

**Gap 4.3: `delete_file` - Deleting an Open/Locked File**
*   **Scenario:** The agent attempts to delete a file that is currently locked by a long-running background process (e.g., a test server the agent itself spun up via `run_in_bash_session`).
*   **Impact:** On Linux, the file is unlinked but the inode remains (ghost file consuming disk). On Windows, `os.Remove` fails with a "file in use" error. Does the LLM understand this error, or does it repeatedly retry the deletion in a tight Mangle loop?
*   **Required Test:** `TestDeleteFileTool_Execute_LockedFile_Behavior`

**Gap 4.4: `edit_file` - Line Ending Corruption (CRLF vs LF)**
*   **Scenario:** A Windows user edits a file with `
`. The LLM outputs `old_text` with just `
` or the Go runtime normalizes it internally.
*   **Impact:** While `tactile.NormalizeLineEnding` is used, if `old_text` spans multiple lines and the LLM slightly hallucinated the indentation or line endings in the payload, the `strings.Contains` fails. The agent gets "not found" and spins.
*   **Required Test:** `TestEditFileTool_Execute_MixedLineEndings_Boundary`

---

### Conclusion and Recommendations

The `internal/tools/core/file_ops.go` module is functionally sound for happy-path operations but lacks critical defensive mechanisms against non-deterministic LLM behavior and hostile or resource-constrained environments.

**Performance Verdict:**
Is the system performant enough? **No.** The complete reliance on in-memory string manipulation (`os.ReadFile`, `strings.ReplaceAll`) limits the tool to small source files. Monorepo scaling (Gap 3.2) will fail catastrophically.

**Actionable Steps:**
1.  **Inject TODO Comments:** I will immediately inject mapping `// TODO:` comments into `internal/tools/core/file_ops_test.go` to flag these exact missing tests.
2.  **Implement Size Caps:** `read_file` and `edit_file` must enforce a maximum byte limit (e.g., 2MB) and return a soft error instructing the LLM to use `grep` or `sed` for larger files.
3.  **Implement Truncation:** `list_files` must aggressively truncate outputs > 1000 lines to protect the context window.
4.  **Strict Type Enforcement:** `args["key"].(type)` should be replaced with a robust decoding layer that handles type coercion (string "true" -> bool true) gracefully or fails with explicit schema errors.
