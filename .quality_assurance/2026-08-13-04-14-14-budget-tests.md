## Analysis Context

I conducted a deep dive into the `TokenBudgetManager` implementation in the `internal/prompt` module, alongside its test suite `budget_test.go`. The subsystem is responsible for allocating token budgets across different prompt atom categories (like Identity, Capability, Context, etc.) based on a defined strategy (Proportional, Balanced) and priority levels (Mandatory, High, Medium, Low).

It implements essential safeguards against pathological allocation requests (e.g., `maxAtomsInput`) and modifies state by optionally truncating string contents of prompt atoms if they don't fit into the available budget (`truncateAtomToBudget`).

This component acts as a critical choke point between intent gathering and LLM execution. If it fails, either prompts exceed context windows (causing LLM API errors) or critical data is discarded.

## Missing Edge Cases Identified

### 1. State Conflicts / Race Conditions (Critical)

**Gap:** `TokenBudgetManager.Fit` modifies `OrderedAtom` elements in place and mutates the underlying `PromptAtom` instances directly via `truncateAtomToBudget` and by adjusting `TokenCount` and `RenderMode`. Concurrent operations sharing these `PromptAtom` pointers will result in data races.
**Performance/Handling Evaluation:** The system currently deep-copies the `PromptAtom` object during execution (`clonedAtom := *atom.Atom`), which attempts to solve this issue, but we still need negative testing to prove that multiple concurrent calls don't leak or race against external consumers. The Go garbage collector handles the temporary deep copies performantly, but allocating up to 100k temporary structures on heavily threaded operations might lead to thrashing.

### 2. Null/Undefined/Empty Strings

**Gap 2.1:** Atoms with empty `Content` but a manually set, non-zero `TokenCount`.
**Performance/Handling Evaluation:** The `Fit` method uses `getTokenCount` which relies on `TokenCount` if present, skipping recalculation. However, if truncation triggers (`truncateUTF8Safe`), it will operate on the empty string and update `TokenCount` to 0. This behavior needs explicit negative testing to ensure it doesn't cause logic errors downstream that expect the original manual `TokenCount`.

**Gap 2.2:** Atoms with `Content` that is only whitespace or unprintable characters.
**Performance/Handling Evaluation:** The underlying `EstimateTokens` handles whitespace, but boundary tests must verify that large blocks of whitespace don't consume unnecessary budget priorities, preventing meaningful context from being included.

**Gap 2.3:** Missing Categories in Budget Map.
**Performance/Handling Evaluation:** The system handles missing categories gracefully by assigning them a priority lower than `PriorityConditional`. However, the test suite lacks specific tests to assert this fallback behavior doesn't break proportional or balanced allocation math when mixed with configured categories.

### 3. Type Coercion / Formatting

**Gap:** Invalid UTF-8 sequences in `Content`.
**Performance/Handling Evaluation:** `truncateUTF8Safe` attempts to trim back invalid trailing bytes when slicing, but a string completely composed of invalid bytes or malformed Unicode might cause unexpected behaviors in token estimation or UI rendering later. Testing how `truncateUTF8Safe` performs with aggressive malformed data is required.

### 4. User Request Extremes

**Gap 4.1:** Extreme `totalBudget` (`math.MaxInt`).
**Performance/Handling Evaluation:** While Go handles `int` math safely, `calculateAllocations` does float multiplication (`float64(totalBudget) * b.BasePercent`). Very large ints converted to `float64` lose precision. This might cause the sum of allocations to deviate from the total budget, leading to unused tokens or negative remaining allocations.

**Gap 4.2:** Massive string content exceeding memory limits.
**Performance/Handling Evaluation:** A single atom with gigabytes of string data. The `Fit` function loops through atoms and does string slicing. Go's string slices are O(1) and performant, but generating the initial slice or deep-copying it inside the `Fit` loop will cause massive allocations and immediate OOM errors. The `maxAtomsInput` protects against many items, but not against single, excessively large items.

**Gap 4.3:** Mandatory Item Overflow.
**Performance/Handling Evaluation:** If mandatory items far exceed `totalBudget`, the system will truncate them. The performance is fine, but the exact truncation logic (which item gets truncated first?) is not fully bounded by tests when all items share the `PriorityMandatory` tier.

## Conclusion

The `TokenBudgetManager` is highly performant for standard usage and correctly utilizes Go's slice mechanics for fast manipulation. However, it relies heavily on the caller not abusing pointer sharing (mitigated by deep copies, but untested concurrently) and doesn't fully guard against single-item memory bombs. The provided `TODO`s in the test suite map out the precise negative tests needed to solidify this component against adversarial or malformed inputs.

### Deep Dive: `truncateUTF8Safe` Edge Cases

func truncateUTF8Safe(content string, maxChars int) string {

3.  **Performance:** If `maxChars` is very large (e.g., 100MB of continuation bytes), this backward scan becomes an O(N) operation on a massive string, potentially causing a CPU spike.
4.  **Assertion:** Test `truncateUTF8Safe` with a large string of invalid continuation bytes and enforce a strict timeout (e.g., `< 5ms`) to ensure it doesn't create a Denial of Service (DoS) vulnerability.

## Final Thoughts on System Performance

The system relies on `sort.SliceStable`. The Go implementation of `sort.Slice` is `pdqsort` (Pattern-Defeating Quicksort), which is generally $O(N \log N)$ but degrades to $O(N^2)$ in the absolute worst (though highly unlikely) adversarial cases, and is $O(N)$ for already sorted or reverse-sorted data.

Given the `maxAtomsInput` cap of 100,000, $N \log N$ operations are well within acceptable bounds for a single request (taking milliseconds). However, if multiple SubAgents are spawned simultaneously and each triggers a `Fit` operation with 100,000 atoms, the CPU contention for sorting could become a bottleneck.

**Recommendation:** While the current performance is likely sufficient, if profiling indicates `TokenBudgetManager.Fit` is a hotspot, consider optimizing the sorting step. Since we primarily care about the *top* N items that fit within the budget, a Max-Heap or partial sort (e.g., Quickselect) could potentially reduce the sorting overhead from $O(N \log N)$ to $O(N + K \log K)$, where K is the number of items that actually fit in the budget. This is a future optimization, but worth noting in a comprehensive QA review.

## Expanding on Token Count Estimations

The `EstimateTokens` function represents another significant area for boundary value analysis.
The implementation of `EstimateTokens` could range from a simple length-based heuristic (e.g., `len(content) / 4`)
to a complex dictionary-based approach, or even calling an external tokenizer.

### Scenario: The "Token Bomb"

If `EstimateTokens` is a simple heuristic, it can be bypassed.
Consider a string like `aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa`.
A simple heuristic might estimate this as `50 / 4 = 12` tokens.
However, an actual BPE tokenizer might process this as 50 distinct tokens if 'a' is not a common repeating sequence,
or as 1 token if it is. The discrepancy between the heuristic and reality can be weaponized.

**Testing Strategy:**
1. Generate "Token Bombs": strings that are heavily compressed by the heuristic but explode when tokenized by the real LLM.
2. Generate "Anti-Bombs": strings that are heavily overestimated by the heuristic.
3. Call `TokenBudgetManager.Fit` with these strings.
4. Verify that the `truncateAtomToBudget` correctly bounds the string based on the heuristic.
5. (Crucial Step): Pass the resulting truncated string to a reference tokenizer (e.g., Tiktoken if testing an OpenAI model).
6. Assert that the *actual* token count of the truncated string is within a safe margin (e.g., +10%/-10%) of the *requested* budget. If the heuristic allows a string through that actually consumes 300% of the budget when tokenized, the system will fail at runtime.

### Scenario: The Null Byte and Control Characters

What happens when the `Content` string contains null bytes (`\x00`) or other ASCII control characters?

**Testing Strategy:**

3. Does `EstimateTokens` panic? Does it return 0? Does it return a massive number?

## Exploring Edge Cases: The Deleted Resource & State Conflicts

*   **Current Architecture Check:** Based on `budget.go`, `PromptAtom.Content` is a concrete string. However, if the architecture evolves to use lazy loading (as seen in `internal/mangle/torture_test.go` with `FactStoreProxy`), the `Fit` method becomes the point of failure.
*   **Testing Strategy:**

    2. Pass an atom representing a deleted file to `Fit`.
