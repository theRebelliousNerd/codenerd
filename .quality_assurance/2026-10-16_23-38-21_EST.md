# Quality Assurance Journal: validate_prompt_atoms (Boundary Value Analysis & Negative Testing)
Date: 2026-10-16 23:38:21 EST

## System Under Test
Subsystem: `validate_prompt_atoms` (`cmd/tools/validate_prompt_atoms`)
This subsystem is a CLI tool that validates the prompt atoms YAML corpus used by the JIT prompt compiler in codeNERD. The corpus dictates the modular components of system prompts, defining tool access, priorities, constraints, and dependencies.

The current test suite verifies basic correctness, ensuring that simple issues like missing IDs, incorrect categories, white-space in names, and unknown tools in `requires_tools` are flagged properly. However, these tests mostly orbit the "Happy Path" or shallow, anticipated failure states.

## Identified Gaps (Negative Testing & Boundary Values)

### 1. Null/Undefined/Empty Fields (Deep Inspection)
- The test suite handles `""` for an ID or Category. But what about properties that are pointers? For instance, `Priority` and `IsMandatory`.
- In YAML parsing, if a key exists but the value is empty, how does it parse? A pointer could be explicitly provided as a pointer to the zero-value, or left entirely absent (nil pointer). The existing tests verify `missing required field: priority` when it is entirely omitted, but what if the user explicitly writes `priority: null` in the YAML? What if an empty list `[]` is given for `RequiresTools`, as opposed to an uninitialized nil slice?
- What happens if the file contains no valid YAML documents, or is completely empty (`""`)? `parseAtomYAMLFile` is invoked, but the test suite for `validateAtomDef` doesn't test the boundary of zero-length inputs interacting with the validation pipeline.
- For lists like `RequiresTools`, what if the list contains a mix of null, empty strings, and valid values?

### 2. Type Coercion and YAML injection
- The tests directly construct `atomDefinition` structs. They bypass the YAML parser for validation logic. This is a massive gap in negative testing. What if a string is provided for `Priority` (an `*int`) in the YAML? Does the parser panic, or does it silently fail, leaving a nil pointer, or does it coerce the value?
- What happens if an integer is provided for the `ID` (e.g., `id: 123`)? Does `atomID` become `"123"`, or does the parser fail?
- What if a boolean is passed to `DependsOn`?

### 3. User Request Extremes (Extreme Payloads & Depth)
- **Extreme Length / Payload:** A malicious or extreme scenario could involve an atom with a `Content` string that is 50MB in size. Is the validator performant enough to handle this without OOM (Out Of Memory) crashing? What if `RequiresTools` contains 100,000 duplicated tool names?
- **YAML Bomb:** A user could easily craft a YAML file with aliases that expand infinitely (YAML bomb / Billion Laughs attack), which would exhaust memory before validation even begins.
- **Deep Dependencies:** What if an atom has a circular dependency that involves 10,000 steps? The validator checks if `depends_on contains self`, but does it perform a deep cycle check (A -> B -> C -> A)? If it doesn't, the JIT compiler later might hang or stack overflow.

### 4. State Conflicts and Edge Interactions
- The test `TestValidateRequiresToolsList_DuplicateOfUnknownReportsDuplicateOnce` is good, but what about conflicts in `DependsOn` and `ConflictsWith` simultaneously referencing the same atom?
- What if `Content` and `ContentFile` are both defined but the `ContentFile` is a broken symlink or a directory instead of a file? The test suite mocks this lightly but doesn't check for file system boundaries like broken permissions, named pipes, or device files (e.g., `/dev/urandom` mapped via a relative path traversal like `../../../dev/zero`).

## Evaluation of Performance and Robustness
The system reads the YAML file and processes validations. The current tests execute rapidly.
However, because the `validateAtomDef` tests use mock Go structs rather than actual YAML unmarshaling, they fail to exercise the `yaml.Unmarshal` surface against hostile inputs.

Additionally, if `ContentFile` points to a file that is 10GB, `os.ReadFile(full)` is used entirely in memory. This is not performant or safe for extreme brownfield/adversarial edge cases, and it will immediately OOM crash a laptop with 8GB RAM.

To improve performance and safety for extreme edge cases, `validate_prompt_atoms` should:
1. Impose a strict file-size limit before `os.ReadFile` via `os.Stat`.
2. Disable YAML alias expansion or limit expansion depth during parsing to prevent YAML bombs.
3. Validate circular dependency graphs explicitly via Topological Sort during validation.

By implementing these strict boundary and negative tests, we elevate the robustness of the prompt atom corpus validation, ensuring that CodeNERD does not choke on malformed inputs from automated generators or adversarial manipulations.

## In-Depth Analysis and Remediation Details

### Architectural Considerations for Validation Robustness

1. **Memory Bounds via Custom Readers:**
   Replacing `os.ReadFile` with `io.LimitReader` wrapped around an `os.File` descriptor would enforce an absolute maximum on the memory consumed by a single `ContentFile` read. This limits our exposure to artificially large files or misconfigured directories containing huge logs.

2. **Parsing Limits via yaml.Node Unmarshaling:**
   Instead of unmarshaling directly into an `atomDefinition` struct, we could first unmarshal the raw YAML into a `yaml.Node`. This tree structure allows us to measure the depth of the document before struct mapping. A recursive walk of the AST could fail fast if the depth exceeds an arbitrary threshold (e.g., 20 levels deep), defending against recursive expansion attacks.

3. **Dependency Graph Traversal Strategies:**
   To solve the deep dependency cycle gap, implementing Tarjan's strongly connected components algorithm or Kahn's algorithm for topological sorting is required. This transforms a potential infinite recursion into a predictable $O(V+E)$ operation during the validation step.

4. **Regex Constraints for String Lengths:**
   The `ID` and `Category` fields must have strict regex constraints and maximum length caps defined. We must validate these *before* string processing logic, preventing downstream systems from truncating IDs unexpectedly and breaking database primary keys.

5. **Type Coercion Audits:**
   We need negative tests that actively attempt to force the `yaml.v3` unmarshaler to incorrectly cast an object or an array into a string slice. If an atom defines `requires_tools` as a nested dictionary, does the unmarshaler error out immediately, or does it attempt partial deserialization? The suite needs boundary tests that feed purely invalid data types to struct fields.

6. **File Descriptor Leaks in ContentFile Reads:**
   Currently, the system might not explicitly close file descriptors if reading fails mid-way, although `os.ReadFile` manages this. However, if we shift to streams for memory safety, we must rigorously test `defer file.Close()` behaviors under panic conditions to ensure we do not exhaust the host's file descriptor limits when processing 100,000 atom files.

### Detailed Fuzz Testing Strategy Proposal
To bridge these identified gaps, implementing Go's native Fuzzing (`go test -fuzz`) is highly recommended for the validation layer.

1. **Fuzzing `validateAtomDef`:**
   Generate pseudo-random byte arrays that approximate YAML but contain intentional syntax errors, null bytes (`\x00`), and unexpected Unicode code points. Pass this to the underlying parsing function and assert that it correctly bubbles up predictable error types, without entering an infinite loop.

2. **Fuzzing Graph Cycles:**
   Generate pseudo-random arrays of strings for `DependsOn` and `ConflictsWith` across thousands of generated `atomDefinition` structs. Map them into a graph structure and fuzz the validation cycle checker. This will ensure our cycle detection algorithms perform linearly and never stack overflow.

3. **Fuzzing String Constraints:**
   Generate pseudo-random strings of varying lengths (0 to 1GB) and inject them into the `Content` field. This fuzzing validates that the memory allocation limits of the validation process hold steady.

### Comprehensive Vulnerability Matrix for Prompt Atom Validation
The following section categorizes potential test vectors and the likelihood of exploitation.

**Vector 1: YAML Bomb / Billion Laughs Attack**
*   **Description:** Utilizing YAML anchors and aliases to create exponentially expanding structures.
*   **Impact:** Denial of Service (OOM crash) for the compiler process.
*   **Mitigation:** Configure the YAML unmarshaler to reject unknown aliases, or strictly bound alias resolution depth.

**Vector 2: Symlink Directory Traversal**
*   **Description:** Utilizing `ContentFile` paths that contain `../` sequences or point to sensitive system files.
*   **Impact:** Information Disclosure (system file contents loaded into prompt generation).
*   **Mitigation:** Require `filepath.Clean` output to exist strictly within the expected atom definition directory sub-tree. Reject absolute paths completely.

**Vector 3: Memory Exhaustion via Long Fields**
*   **Description:** Providing gigabyte-sized strings for standard fields like `ID` or `Category`.
*   **Impact:** Denial of Service (memory exhaustion).
*   **Mitigation:** Enforce strict field-level string length maximums during the validation routine.

**Vector 4: Cyclic Dependency Hangs**
*   **Description:** A malicious corpus introduces A -> B -> C -> A dependencies.
*   **Impact:** Denial of Service (CPU starvation and hang) during compilation.
*   **Mitigation:** A fast DAG (Directed Acyclic Graph) validation phase before prompt execution.

**Vector 5: Tool Capability Over-Privilege via Injection**
*   **Description:** Injecting unexpected characters or bypassing the regex validator in `requires_tools` to access unapproved Mangle actions.
*   **Impact:** Privilege Escalation / Unintended Execution.
*   **Mitigation:** The regex validation for tool names must be bulletproof, ensuring no newline, null-byte, or shell-injection vectors exist within the parsed string representation.

### Specific Negative Testing Implementation Details

To fully realize the boundary tests required, the following specific test structures must be constructed within `validate_test.go`:

#### 1. Fuzzing Target Structure

```go
func FuzzValidateAtomDef(f *testing.F) {
    // Seed the corpus with known-good YAML permutations
    f.Add([]byte(`id: valid_atom\ncategory: core\npriority: 10\nis_mandatory: true\ncontent: "hello"`))
    f.Add([]byte(`id: another_atom\ncategory: core\npriority: 99\nis_mandatory: false\ncontent: "world"`))

    f.Fuzz(func(t *testing.T, data []byte) {
        var def atomDefinition
        // The goal here isn't to test the unmarshaler's core functionality, but how OUR system reacts to its outputs or errors
        err := yaml.Unmarshal(data, &def)
        if err != nil {
            // It's expected that garbage input will fail to unmarshal. We just want to make sure it doesn't panic.
            return
        }

        // If it DOES unmarshal (maybe it generated perfectly valid YAML by chance, or type coercion succeeded),
        // we feed it to our validator.
        validCategories := map[string]struct{}{"core": {}}
        opts := validationOptions{}

        // The key assertion is that validateAtomDef never panics, regardless of the input it receives.
        defer func() {
            if r := recover(); r != nil {
                t.Fatalf("Validation panicked on input %q: %v", string(data), r)
            }
        }()

        _ = validateAtomDef("fuzz.yaml", "fuzz.yaml", def, validCategories, opts)
    })
}
```

### Expanding on Symlink Traversal and File System Interactions

The `ContentFile` property is uniquely vulnerable because it dictates how the validator interacts with the host OS. The current test logic simply joins the paths and reads the file:

`full := filepath.Join(filepath.Dir(path), contentFile)`

This is insufficient. The test suite must mock a file system environment where `contentFile` contains arbitrary relative paths.

**Test Case: Symlink Loop**
1. Create a temporary directory.
2. Create a symlink `loop1` pointing to `loop2`.
3. Create a symlink `loop2` pointing to `loop1`.
4. Construct an `atomDefinition` where `ContentFile: "loop1"`.
5. Assert that the validator returns a clear error (e.g., "too many levels of symbolic links") rather than hanging.

**Test Case: Directory Traversal Escape**
1. Create a root directory `/tmp/validator_test_root/atoms/`.
2. Place a valid `atom.yaml` inside.
3. In `atom.yaml`, define `content_file: "../../../../etc/passwd"`.
4. Assert that the validator rejects the path because it resolves outside the intended `atoms/` directory tree.

### Type Coercion Edge Cases in Detail

YAML's flexibility is its downfall in strict systems. The `requires_tools` field is defined as a `[]string`.

What happens when the YAML provides:

```yaml
requires_tools:
  - tool_a
  - 123
  - true
```

The `yaml.v3` parser might coerce `123` into `"123"` and `true` into `"true"`. The validator's regex `[a-z0-9_]+` will catch `"123"`, but it will also catch `"true"`. Does `"true"` represent a valid tool? If a tool named "true" is registered, this type coercion would silently grant access to it based on a boolean input.

The test suite must explicitly inject these varied types into the unmarshaler and verify the final behavior of the validator pipeline.

### Addressing the "Pointer to Zero Value" Ambiguity

The distinction between an omitted key and an explicitly null key is vital when using pointers to primitives (like `*int` for `Priority`).

Go's standard library `encoding/json` distinguishes these. `yaml.v3` also behaves specifically.

If the YAML is:
```yaml
priority: null
```
`def.Priority` will be `nil`.

If the YAML is:
```yaml
priority: 0
```
`def.Priority` will be a pointer to `0`.

The test suite must ensure that the validation logic treats an explicitly missing key (`nil`) as an error, but correctly handles `0` as a valid boundary value for Priority. The current tests cover `Priority out of range`, but the boundary tests for exactly `0` and exactly `100` are implicit. Explicit tests for these exact values must be added to guarantee stability.

### The Role of Mangle in Tool Access Validation

The prompt atoms define the capabilities available to the JIT prompt. The `requires_tools` field ties directly into the Mangle rule engine.

If an atom requests a tool, that tool name must correspond to a valid, registered capability within the catalog. The test `TestValidateRequiresToolsList_UsesProductionCatalog` verifies this linkage.

However, an edge case exists: what if a tool name is excessively long, potentially causing issues when converted into a Mangle atom string (e.g., `/read_file_extremely_long_name...`)?

Mangle atoms have length constraints. The validator must ensure that tool names do not exceed these constraints *before* they are passed to the Mangle engine.

Negative testing must include injecting tool names that are 10,000 characters long to ensure they are rejected gracefully.

### Validation of `DependsOn` Depth and Complexity
The current system checks if an atom depends on itself, or depends on a non-existent atom.
What it does *not* do is evaluate the total size of the transitive closure of dependencies.

If an atom depends on 100 other atoms, and each of those depends on 100 others, the resulting resolution tree has $100^{100}$ nodes if not properly memoized.
The test suite needs a test that asserts `validateAtomTree` runs in bounded time (e.g., <1 second) even when presented with a heavily interconnected (but acyclic) graph of 1,000 atoms.

### Evaluating Edge Cases With `reflect` Mocks
While testing the YAML unmarshaler is critical, the validator itself (`validateAtomDef`) receives a struct. There are states a struct can enter via manual assignment or reflection that the unmarshaler might naturally protect against, but the validator must still handle defensively in case it's used as an internal API library.

For instance, what if `def.DependsOn` is pre-populated with a slice containing 1,000,000 nil pointers (if the underlying type was changed to a slice of pointers)?
Currently it is `[]string`. What if it is populated with strings containing ANSI escape codes? These strings will pass regex checks if not strictly bound, and could cause command-injection vulnerabilities later in the `codeNERD` pipeline when rendered to a terminal.

### Concurrency Verification
The validation tool runs linearly through the directory tree. However, if this package is imported by the JIT Prompt Compiler, it might be executed in parallel during multi-threaded prompt generation.
The internal `productionToolNames()` function utilizes `sync.Once` for thread safety, which is good. But are there other shared variables?
`validCategories` is passed around as a map map[string]struct{}. In Go, reading a map concurrently is safe, but any accidental write during validation could panic the server. A test case must verify this map is never modified after initialization.

### Further Negative Testing Considerations: Null Byte Injection
In Go, strings are UTF-8, but file paths passed to the underlying OS API must be valid for the host platform (e.g., C strings which are null-terminated).
If a `ContentFile` string contains a null byte (` `), the `os.ReadFile` call will typically fail with an `invalid argument` error.
However, depending on where the validation layer splits or joins strings, a null byte could be used to truncate a file path maliciously (e.g. `path/to/expected_file /../../etc/passwd`).

The test suite must explicitly inject null bytes into `ContentFile`, `ID`, and `Category` and ensure the validator catches these cleanly as invalid formatting BEFORE they hit system APIs.

### Conclusion
The prompt atom validation subsystem (`validate_prompt_atoms`) represents a critical security and stability boundary within the codeNERD architecture. As it sits directly on the boundary between configuration data and prompt compilation, it must be hardened against both accidental misconfigurations (e.g., massive log files incorrectly referenced) and intentional adversarial manipulation (e.g., YAML bombs, symlink traversals).

The current test suite is inadequate for this level of assurance. It mocks the struct inputs rather than exercising the full parser and file system integration layers.

By implementing the negative testing vectors outlined in this journal—specifically memory bounds on file reads, YAML alias defenses, deep cycle detection, and strict type checking—we can ensure the robust compilation of prompts even when operating under extreme user requests, brownfield conditions, or adversarial interference.
