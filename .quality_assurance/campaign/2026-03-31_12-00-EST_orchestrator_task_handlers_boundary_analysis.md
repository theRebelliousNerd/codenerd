## 1. Executive Summary

This journal details a deep-dive Boundary Value Analysis (BVA) and negative testing assessment of the `orchestrator_task_handlers.go` module within the `internal/campaign` subsystem of the codeNERD architecture. The orchestrator is the engine that drives multi-step campaigns, delegating work to JIT-configured SubAgents via `spawnTask()`.

The analysis specifically eschews "happy path" validation. Instead, it systematically interrogates the system's resilience against four distinct failure vectors:
1.  **Null/Undefined/Empty Inputs:** How the system behaves when required structures, fields, or configurations are unexpectedly absent.
2.  **Type Coercion & Payload Mismatches:** How the system handles improperly formatted data, especially JSON payloads derived from LLM articulation layers.
3.  **User Request Extremes:** The system's stability under pathological loads, such as massive files, infinite test loops, or massive task dependency graphs.
4.  **State Conflicts:** Race conditions, concurrent file access, and kernel state desynchronization.

The `orchestrator_task_handlers.go` subsystem is critical. If a task handler panics or fails silently, the entire campaign halts, potentially leaving the user's workspace in a corrupted state or leaving zombie SubAgents running in the background.

---

## 2. Architectural Context & Mangle Integration

The orchestrator relies heavily on the `TaskExecutor` interface (often a JIT Clean Loop executor) to spawn SubAgents.
The control flow is generally:
`executeTask` -> `switch on Task.Type` -> `execute<Specific>Task` -> `spawnTask` -> `taskExecutor.Execute`.

Crucially, the orchestrator also handles *fallbacks*. For instance, if `executeFileTask` calls a SubAgent and the SubAgent fails to write the file, `executeFileTaskFallback` uses a direct LLM call. This multi-layered execution strategy requires rigorous testing to ensure state is properly cleaned up between attempts.

## 3. Vector Analysis: Null/Undefined/Empty Inputs

### 3.1 Task Input Starvation

**Scenario:** The `Task` struct passed to `executeTask` is minimally populated.
*   **Gap:** `Task.Type` is empty string (`""`).
    *   *Current Behavior:* The `switch` statement falls through to the `default` case, calling `executeGenericTask(ctx, task)`.
    *   *Risk:* `executeGenericTask` relies on `task.Description`. If `task.Description` is also empty, the underlying LLM/SubAgent receives a blank prompt, likely generating a hallucinated response or failing.
*   **Gap:** `Task.Shard` is explicitly set, but `Task.Description` is empty.
    *   *Current Behavior:* `executeWithExplicitShard` builds input via `buildTaskInputWithSpecialistKnowledge`. If the intent is empty, the JIT compiler might fail to select appropriate tools.
*   **Gap:** `Task.Artifacts` is `nil` or empty for a `TaskTypeFileCreate`.
    *   *Current Behavior:* The code attempts to extract the path from the description via `extractPathFromDescription`. If that also fails, it returns an error.
    *   *Risk:* Is the error handled gracefully by the parent campaign orchestrator? Does it halt the entire campaign, or just retry?

### 3.2 Context & Infrastructure Nullification

**Scenario:** Essential infrastructure components are missing.
*   **Gap:** `o.taskExecutor` is `nil` during `spawnTask`.
    *   *Current Behavior:* Returns an error `fmt.Errorf("taskExecutor not initialized")`.
    *   *Risk:* This is a fatal configuration error. Tests should explicitly verify that initializing an orchestrator without an executor correctly fast-fails rather than panicking later.
*   **Gap:** `ctx` (Context) is already cancelled when `executeTask` begins.
    *   *Current Behavior:* The cancelled context is passed down.
    *   *Risk:* Do the underlying LLM clients and file system operations properly respect `ctx.Err()` immediately, or do they attempt work and discard the result?

### Proposed Empty Input Tests:
1.  `TestExecuteTask_EmptyType_EmptyDescription`: Assert generic handler fails gracefully without panics.
2.  `TestExecuteFileTask_NoArtifacts_NoPathInDescription`: Assert explicit error return when target path cannot be resolved.
3.  `TestExecuteTask_NilTaskExecutor`: Assert orchestrator catches uninitialized state safely.

## 4. Vector Analysis: Type Coercion & Payload Mismatches

### 4.1 Artifact Schema Mismatches

**Scenario:** The artifacts slice contains poorly structured data.
*   **Gap:** A task is generated by an LLM (e.g., via the decomposer) with an artifact path that is not a string, or contains invalid characters (e.g., null bytes `\x00`).
    *   *Current Behavior:* `os.WriteFile` in the fallback mechanism will fail if the path contains null bytes.
    *   *Risk:* Path traversal vulnerabilities. What if `targetPath` is `../../../../etc/passwd`? The code uses `filepath.Join(o.workspace, targetPath)`, which might resolve outside the workspace if `targetPath` is not properly sanitized. (Security/Type coercion).

### 4.2 LLM Output Coercion (The Fallback Mechanism)

**Scenario:** The primary SubAgent fails, and `executeFileTaskFallback` takes over, requesting direct code from the LLM.
*   **Gap:** The LLM returns markdown fences, but with the wrong language tag (e.g., asked for `.go`, returned ` ```javascript `).
    *   *Current Behavior:* `extractCodeBlock` attempts to match the specific language. If it fails, it might return the raw string *with* fences.
    *   *Risk:* Writing ````javascript...```` to a `.go` file breaks the build for subsequent tasks.
*   **Gap:** The LLM returns valid JSON when code was expected.
    *   *Risk:* The code writes raw JSON to a source file.

### Proposed Type Coercion Tests:
1.  `TestExecuteFileTask_PathTraversal_Sanitization`: Ensure paths like `../foo.go` are trapped and rejected before disk writing.
2.  `TestExecuteFileTaskFallback_LanguageMismatch`: Force LLM mock to return ````python` for a `.go` file and verify `extractCodeBlock` behavior.
3.  `TestExtractCodeBlock_MalformedFences`: Test inputs like ````go\ncode\n```\n``` ` (nested fences).

## 5. Vector Analysis: User Request Extremes

### 5.1 The Monorepo Brownfield Scenario

**Scenario:** The user asks codeNERD to operate on a 50-million line monorepo.
*   **Gap:** `executeTestRunTask` executes a test suite. What if the test suite outputs 10GB of logs to stdout/stderr?
    *   *Current Behavior:* The code likely reads the entire output into memory to return it as a string result.
    *   *Risk:* OOM (Out Of Memory) crash of the codeNERD agent itself. `exec.Cmd.Output()` or similar functions will buffer endlessly.

### 5.2 The Infinite Loop / Hang

**Scenario:** A generated tool or test enters an infinite loop.
*   **Gap:** `executeTestRunTask` or `executeToolCreateTask` spawns a process or SubAgent.
    *   *Current Behavior:* Relies on the provided `ctx`. If `ctx` does not have a timeout, the orchestrator hangs forever.
    *   *Risk:* Campaign stalling. The user perceives codeNERD as "frozen."

### 5.3 Massive Code Generation (The 100k LoC Class)

**Scenario:** The user requests the creation of an entirely new framework in one file.
*   **Gap:** The LLM in `executeFileTaskFallback` streams back 50MB of text.
    *   *Current Behavior:* The string is held in memory, regex operations (like `extractCodeBlock`) are run against it.
    *   *Risk:* Catastrophic backtracking in regex. If `extractCodeBlock` uses complex regex on a 50MB string, CPU spikes to 100% and blocks the goroutine indefinitely.

### Proposed Extreme Request Tests:
1.  `TestExecuteTestRunTask_MassiveStdout_OOMProtection`: Mock a test runner that streams 1GB of data and ensure codeNERD truncates it rather than crashing.
2.  `TestExecuteTestRunTask_TimeoutEnforcement`: Verify that long-running tests are killed gracefully.
3.  `TestExtractCodeBlock_CatastrophicBacktracking`: Feed a massive 50MB string with near-matching code fences to ensure regex/parsing is O(N).

## 6. Vector Analysis: State Conflicts

### 6.1 The "Schrödinger's File" Race Condition

**Scenario:** Multiple tasks attempt to modify the same file concurrently, or a task assumes a file exists when it was deleted.
*   **Gap:** `executeFileTask` checks if the file exists *after* the shard completes:
    ```go
    if _, statErr := os.Stat(fullPath); os.IsNotExist(statErr) {
        // Fallback
    }
    ```
    *   *Risk:* What if the file is created by another goroutine *just* as `os.Stat` is called? Or what if it's created, but empty because the write is still flushing?

### 6.2 Tool Creation vs. Tool Registration (Autopoiesis)

**Scenario:** `executeToolCreateTask` triggers the Ouroboros loop.
*   **Gap:** The orchestrator needs to know when the tool is actually ready for use by subsequent tasks.
    *   *Risk:* If the tool is compiled but the `tool_registered` fact hasn't propagated to the Mangle kernel yet, the next task in the campaign that requires this tool will fail. There must be synchronization between tool compilation and kernel state.

### 6.3 Zombie SubAgents

**Scenario:** A campaign is cancelled (`ctx` cancelled) while a SubAgent is running.
*   **Gap:** `spawnTask` returns immediately upon context cancellation.
    *   *Risk:* Does the underlying JIT Clean Loop cleanly terminate the LLM request and release resources? If not, the application leaks goroutines and memory.

### Proposed State Conflict Tests:
1.  `TestExecuteFileTask_ConcurrentModification`: Run multiple `executeFileTask` calls targeting the same file and assert safe locking/failure.
2.  `TestExecuteToolCreateTask_KernelSynchronization`: Verify that the task does not return success until the Mangle kernel explicitly confirms tool availability.
3.  `TestExecuteTask_ContextCancellation_ResourceLeak`: Cancel the context mid-execution and verify no goroutines are left hanging (using `goleak`).

## 7. Performance & Optimization Review

The subsystem relies heavily on `os.ReadFile` and `os.WriteFile` in fallbacks. For extreme scenarios (e.g., the 50M line monorepo), reading entire files into memory just to append a line is highly inefficient.
**Optimization Recommendation:** The modular tool registry (`internal/tools/codedom/edit_lines`) should be prioritized over `executeFileTaskFallback` whenever possible. The fallback should be an absolute last resort, as it bypasses the neuro-symbolic safety checks and AST-aware editing.

Furthermore, string concatenation in logging (`logging.CampaignDebug("Built shard input (%d bytes) for task %s", len(input), task.ID)`) is safe here as it uses formatting, but building large prompts dynamically using `fmt.Sprintf` can create significant memory pressure and garbage collection overhead. Using `strings.Builder` for assembling large LLM prompts would improve throughput in heavy campaigns.

## 8. Conclusion

The `orchestrator_task_handlers.go` module is robust in its happy path, particularly with its multi-layered fallback design. However, it exhibits vulnerabilities to pathological inputs, specifically regarding bounded resource constraints (OOM from massive test outputs or huge files) and race conditions during file verification.

Addressing the gaps identified in this BVA will elevate codeNERD from a fragile prototype to a production-grade, high-assurance coding partner capable of handling frontier-level software engineering tasks.

## 10. Risk Scoring Breakdown

*   **Risk Area:** Subsystem `internal/campaign/orchestrator_task_handlers.go`.
*   **Overall Risk Profile:** **High.** The orchestrator is the campaign orchestrator. Failures here disrupt the entire user-requested workflow.
*   **Most Critical Gap:** Unbounded resource consumption during test execution (`executeTestRunTask`). A poorly written test or an adversarial script can cause codeNERD to crash with an Out-of-Memory error by dumping gigabytes of logs to stdout. This must be wrapped in an `io.LimitReader` or similar bounded buffer.
*   **Second Most Critical Gap:** Path Traversal in File creation (`executeFileTask`). Because the LLM dictates the path (or it's extracted from description), a hallucinated path like `../../../.ssh/id_rsa` could potentially be written to if not properly sanitized relative to the workspace.

## 11. Final Remarks

The architectural decision to transition to a JIT Clean Loop (`spawnTask()`) simplifies the routing logic considerably, replacing hundreds of lines of type-specific shard spawning logic. However, this unification makes `spawnTask()` a single point of failure. The fallbacks (like `executeFileTaskFallback`) are essential safety nets but must be hardened against the boundary values and extreme edge cases outlined above to prevent the system from failing into an insecure or broken state.

## 12. Advanced Performance Benchmarking & Thresholds

The following performance thresholds should be codified in the automated testing suite for `orchestrator_task_handlers.go`. The orchestrator must handle these without degradation.

### 12.1 Throughput and Latency

*   **Task Dispatch Latency:** The overhead of `executeTask` routing and invoking `spawnTask` must remain under 100 microseconds per task.
*   **Fallback Transition:** If `spawnTask` fails, the transition to `executeFileTaskFallback` must not block the main orchestrator goroutine for more than 5 milliseconds.
*   **Regex Processing:** `extractCodeBlock` must process a 5MB response from the LLM in under 50 milliseconds. Processing times above 100ms indicate catastrophic backtracking or inefficient string allocation.

### 12.2 Memory Footprint Limits

*   **Task Allocation:** A single `Task` struct and its associated `executeTask` stack frame must not allocate more than 1KB of memory (excluding the payload strings).
*   **LLM Response Buffering:** During `executeFileTaskFallback`, the orchestrator must enforce a hard memory limit of 50MB per file generation request. If the LLM returns more than 50MB, the stream must be truncated and an error returned to prevent OOM.
*   **Test Runner Buffering:** `executeTestRunTask` must enforce a 10MB limit on `stdout`/`stderr` buffering. Anything beyond 10MB should be discarded, with a warning prepended to the final log output.

### 12.3 Concurrency Capacity

*   **Parallel Tasks:** The orchestrator should be capable of handling 100 concurrent `TaskTypeResearch` operations without thrashing the JIT prompt compiler or locking the Mangle kernel excessively.
*   **Kernel Lock Contention:** The `o.mu.RLock()` in `spawnTask` for accessing `taskExecutor` must not become a bottleneck when hundreds of tasks are scheduled simultaneously.

## 13. Deep Dive into `executeFileTaskFallback` Failure Modes

The `executeFileTaskFallback` function is the safety net when the primary SubAgent fails to write a file. It uses a direct LLM call. This section analyzes its specific failure modes.

### 13.1 The "Path Extraction" Heuristic Failure

If `targetPath` is empty, the function attempts to extract the path from `task.Description` using `extractPathFromDescription`.

*   **Failure Vector:** The description contains multiple valid paths (e.g., "Move logic from `src/old.go` to `src/new.go`").
*   **Result:** `extractPathFromDescription` might return the first path it finds (`src/old.go`), causing the LLM to overwrite the wrong file.
*   **Testing Requirement:** Create a test case where `task.Description` contains complex language and multiple paths. The regex or heuristic must either fail explicitly (requiring user clarification) or consistently select the correct target based on context.

### 13.2 Directory Creation Race Conditions

The fallback uses `os.MkdirAll` before writing the file.

*   **Failure Vector:** Two fallback tasks concurrently attempt to write different files in the same new directory (`src/newdir/file1.go` and `src/newdir/file2.go`).
*   **Result:** `os.MkdirAll` is generally safe against concurrent calls, but file permissions might be applied inconsistently if the OS intercepts the calls in a specific interleaved order.
*   **Testing Requirement:** A stress test spawning 50 goroutines, all calling `executeFileTaskFallback` into the same non-existent directory tree.

### 13.3 Partial Writes and Corruption

The fallback uses `os.WriteFile`.

*   **Failure Vector:** The disk is full, or the process is killed halfway through the `WriteFile` operation.
*   **Result:** The file exists but is truncated or corrupted. The orchestrator records a success (if killed) or a messy failure (if disk full).
*   **Testing Requirement:** Simulate an `ENOSPC` (No space left on device) error during the `os.WriteFile` call using a mocked filesystem interface or a loopback device with zero capacity. Ensure the task fails cleanly and reports the exact error to the campaign manager.

## 14. Deep Dive into `executeCampaignRefTask` Failure Modes

This handler delegates execution to a nested sub-campaign.

### 14.1 Infinite Recursion

*   **Failure Vector:** Campaign A delegates to Campaign B, which delegates back to Campaign A.
*   **Result:** Stack overflow or complete exhaustion of available goroutines and memory.
*   **Testing Requirement:** `TestExecuteCampaignRefTask_InfiniteRecursionPrevention`. Ensure the orchestrator tracks the call stack of sub-campaigns and enforces a maximum depth (e.g., 5 levels).

### 14.2 Fact Leakage and Contamination

*   **Failure Vector:** A sub-campaign generates temporary facts (e.g., `user_intent(/explore)`) that leak into the parent campaign's Mangle kernel state.
*   **Result:** The parent campaign behaves erratically because its state is polluted by the sub-campaign's temporary logic.
*   **Testing Requirement:** Verify that the Mangle kernel provides strict isolation or scoping for sub-campaign execution. Only explicitly returned or `learned_fact` atoms should propagate back to the parent.

### 14.3 Priority Inversion

*   **Failure Vector:** A high-priority parent task spawns a low-priority sub-campaign task.
*   **Result:** The sub-campaign task starves in the scheduler queue while the parent waits indefinitely, blocking the primary campaign thread.
*   **Testing Requirement:** Ensure priority inheritance or explicit priority mapping between parent and child campaigns.

## 15. The Autopoiesis Vector: `executeToolCreateTask`

This is perhaps the most dangerous task type, as it involves the system writing and compiling its own executable code.

### 15.1 The "Poisoned Tool" Scenario

*   **Failure Vector:** The orchestrator successfully executes a `TaskTypeToolCreate`, but the tool contains a syntax error or logic bomb that crashes the JIT compiler later.
*   **Result:** The tool is registered in the Mangle kernel (`tool_registered`), but any subsequent task attempting to use it panics the agent.
*   **Testing Requirement:** `TestExecuteToolCreateTask_RejectsSyntaxErrors`. The `executeToolCreateTask` must internally run `go build` (or invoke the Thunderdome validation) *before* asserting the `tool_registered` fact.

### 15.2 The "Name Collision" Scenario

*   **Failure Vector:** The task attempts to create a tool named `read_file`, overwriting the core system tool.
*   **Result:** Catastrophic failure of standard SubAgent capabilities.
*   **Testing Requirement:** Ensure `executeToolCreateTask` checks a protected namespace list before writing tool files or updating the registry.

### 15.3 Dependency Hell

*   **Failure Vector:** The LLM generates a tool that imports a massive, un-vendored third-party library (`github.com/aws/aws-sdk-go-v2/...`).
*   **Result:** `go mod tidy` and `go build` during tool compilation take 10 minutes, timing out the campaign step.
*   **Testing Requirement:** Enforce a strict allowlist of imports for generated tools, or place a hard 30-second timeout on tool compilation.

## 16. Actionable QA Recommendations for the codeNERD Team

1.  **Implement the `io.LimitReader` pattern globally:** Any interaction with `exec.Cmd.Stdout` or external LLM streams must be wrapped in a size-limiting reader. This is the #1 defense against OOM failures.
2.  **Harden `extractPathFromDescription`:** This regex/heuristic is too fragile for a high-assurance system. If `Task.Artifacts` is empty, the LLM prompt generating the task should be fixed to guarantee structured output, rather than relying on regex scraping of a description string.
3.  **Implement Path Sanitization Middleware:** Before any `os.*` function is called, the path must be passed through a `SecureJoin(workspace, path)` function that guarantees the resulting absolute path is a child of `workspace`.
4.  **Enforce Strict Context Lifetimes:** Every single `execute*Task` function must enforce a timeout. `executeTask` should wrap the incoming context with `context.WithTimeout(ctx, 5 * time.Minute)` to guarantee no task can hang the orchestrator indefinitely.

## 18. Extended Vector Analysis: Orchestrator Subtask Interactions

The `orchestrator_task_handlers.go` system doesn't operate in a vacuum. It interacts with `Task` structs generated by the `Decomposer` and executed by the `TaskExecutor`. This section analyzes boundary conditions across these boundaries.

### 18.1 Malformed Task Identifiers (ID)

*   **Scenario:** A `Task.ID` is missing, contains invalid characters (like spaces or newlines), or is excessively long (e.g., 10,000 characters).
*   **Gap:** The orchestrator logs `task.ID` extensively (`logging.CampaignDebug("Executing task %s...", task.ID)`). If the ID is a massive string, the logging subsystem will consume excessive memory and disk space. If the ID contains control characters, it could corrupt log files or terminal output.
*   **Testing Requirement:**
    *   `TestExecuteTask_MassiveTaskID_LoggingSafety`: Ensure logging truncates massive task IDs.
    *   `TestExecuteTask_InvalidTaskID_Rejection`: Verify that tasks with empty or maliciously formatted IDs are rejected before execution.

### 18.2 SubCampaign Loop Resolution (Cyclic Dependencies)

*   **Scenario:** `executeCampaignRefTask` executes a sub-campaign that, through the `Ouroboros` loop or a flawed `Decomposer` plan, schedules another `TaskTypeCampaignRef` pointing back to the original campaign ID.
*   **Gap:** The orchestrator relies on the `CampaignManager` to handle the execution. If there is no cycle detection in the orchestrator's task handling, this leads to an infinite loop of task scheduling and execution.
*   **Testing Requirement:**
    *   `TestExecuteCampaignRefTask_CycleDetection`: Mock a `CampaignManager` that immediately returns a cyclic task. The orchestrator must detect the cycle (e.g., by tracking active campaign IDs in the context) and fail the task with a `CyclicDependencyError`.

### 18.3 Task Artifact Payload Corruption

*   **Scenario:** `Task.Artifacts` contains entries where `Path` is valid, but the associated `Content` (if any is pre-populated by a planner) is a massive blob (e.g., a 1GB core dump).
*   **Gap:** If the orchestrator or the fallback mechanism attempts to log or process this artifact content before writing, it could trigger an OOM.
*   **Testing Requirement:**
    *   `TestExecuteFileTask_MassiveArtifactContent_OOMProtection`: Provide a `Task` with a 1GB artifact. Ensure the handler streams the write to disk rather than loading the entire string into memory, or rejects artifacts over a certain size threshold (e.g., 50MB).

### 18.4 The "File Modify" vs. "File Create" Ambiguity

*   **Scenario:** `TaskTypeFileModify` is executed on a file that does not exist.
*   **Gap:** The coder shard might attempt to read the file to modify it and fail. The fallback mechanism (`executeFileTaskFallback`) currently just uses `os.WriteFile`, which will *create* the file if it doesn't exist. This masks the underlying error (the file was supposed to exist for modification).
*   **Testing Requirement:**
    *   `TestExecuteFileTask_ModifyNonExistentFile`: Verify that a modify task explicitly fails if the target file is missing, rather than silently falling back to creation, which could lead to disjointed codebase states.

### 18.5 "Verify" Task Edge Cases

*   **Scenario:** `TaskTypeVerify` is executed to check if a fix was applied correctly. The verification script or command (contained in `task.Description`) is malicious or unbounded (e.g., `while true; do echo "checking..."; done`).
*   **Gap:** `executeVerifyTask` might spawn a shell command that runs indefinitely.
*   **Testing Requirement:**
    *   `TestExecuteVerifyTask_TimeoutEnforcement`: Ensure verification tasks are strictly bounded by a context timeout (e.g., 30 seconds).

## 19. Extended Vector Analysis: Context and Intent Propagation

The orchestrator relies on Mangle facts (like `user_intent`) to inform task execution.

### 19.1 Stale Intent Propagation

*   **Scenario:** The user changes their intent mid-campaign (e.g., via a UI interrupt), but the `executeTask` loop is already processing a task based on the old intent.
*   **Gap:** The `spawnTask` function uses the `intent` string passed to it. If this string is not dynamically refreshed from the Mangle kernel before each task execution, the SubAgents will operate on stale instructions.
*   **Testing Requirement:**
    *   `TestExecuteTask_IntentRefresh`: Verify that `executeTask` queries the kernel for the *latest* `user_intent` before spawning a shard, rather than relying on a static string passed down from the campaign start.

### 19.2 Conflicting Intents

*   **Scenario:** The Mangle kernel contains multiple, conflicting `user_intent` facts (e.g., `user_intent(/refactor)` and `user_intent(/revert_changes)`).
*   **Gap:** The JIT prompt compiler might build a schizophrenic persona, or the orchestrator might pick the wrong intent to pass to `spawnTask`.
*   **Testing Requirement:**
    *   `TestSpawnTask_ConflictingIntents`: Assert multiple intents and verify the orchestrator correctly resolves the conflict (e.g., by taking the most recent fact or failing safely).

## 22. Additional Boundary Analysis: Type Coercion Resilience

The orchestrator interacts with dynamically typed data structures (e.g., JSON unmarshaled into `interface{}` or `map[string]interface{}`) originating from LLM tool calls. This introduces significant type coercion vulnerabilities.

### 22.1 Arbitrary Payload Coercion in JIT Tools

*   **Scenario:** A dynamically generated tool (via Ouroboros) expects a string parameter `filename`, but the LLM provides an array `["file1.txt", "file2.txt"]` or a boolean `true`.
*   **Gap:** If the JIT Tool Registry or the orchestrator's `TaskExecutor` attempts to blindly cast `payload["filename"].(string)`, the system will panic.
*   **Testing Requirement:**
    *   `TestExecuteTool_TypeCoercion_PanicPrevention`: Inject malformed JSON payloads into the `Task.Artifacts` or `Task.Description` (if parsed as JSON) and ensure the orchestrator gracefully returns a type error instead of a runtime panic.

### 22.2 Integer Overflow in Configuration Tasks

*   **Scenario:** A task instructs the system to modify a configuration file, setting a timeout value or a retry limit. The LLM provides `9999999999999999999999` (exceeding `int64` bounds).
*   **Gap:** When the orchestrator parses or applies this value (e.g., in a specialized configuration task handler), it might trigger an overflow panic or wrap around to a negative number, causing immediate, silent failure loops.
*   **Testing Requirement:**
    *   `TestExecuteConfigTask_IntegerOverflow`: Verify that large numerical inputs are caught by schema validation or boundary checks before being applied to internal state or written to disk.

The `orchestrator_task_handlers.go` module serves as the central hub connecting multiple systems. Any BVA must consider the interactions at these boundaries:

1.  **Orchestrator <-> Mangle Kernel:** Safe fact assertion/retraction during task execution.
2.  **Orchestrator <-> TaskExecutor (Clean Loop):** Context propagation and timeout handling.
3.  **Orchestrator <-> File System:** Safe, concurrent file I/O operations.
4.  **Orchestrator <-> LLM Client:** Handling rate limits, context window exhaustion, and malformed responses during fallback.
5.  **Orchestrator <-> Campaign Manager:** Updating task status (`updateTaskStatus`) accurately, especially during partial failures.

By systematically addressing these vectors, the orchestrator will achieve the stability required for complex, multi-agent workflows.
