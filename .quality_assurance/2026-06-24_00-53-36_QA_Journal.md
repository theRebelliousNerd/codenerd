# QA Automation Journal: Boundary Value Analysis & Negative Testing
## Date & Time: 2026-06-24 00:53:36 EDT
## Subsystem Reviewed: Orchestrator Failure (internal/campaign/orchestrator_failure.go)

### 1. Introduction and Architectural Context
The codeNERD `internal/campaign` package orchestrates multi-phase goal execution via a JIT-driven Campaign Orchestrator. The subsystem under review (`orchestrator_failure.go` and its associated test suite) manages task failure states, retry logic, error taxonomy, backoff computation, logic failure escalation, and deterministic diagnostic task insertion (e.g., repro tests).

This review targets the robustness of the system using Boundary Value Analysis and Negative Testing, deliberately eschewing happy paths to explore how the system reacts to extreme, edge, or malformed states. The test suite currently has high-level gap implementations (e.g., `TestOrchestratorFailure_MassiveErrorString`, `TestOrchestratorFailure_StateConflicts_Concurrency`) but misses nuanced boundary assertions, specifically in type coercion, extreme state manipulation, and bizarre user requests.

### 2. Edge Case Vectors Identified

#### 2.1 Null/Undefined/Empty Strings and Arrays
* **Vector A: Nil Pointer Dereferences in Nested Types.** While `handleTaskFailure` checks if `task == nil` or `phase == nil`, what happens if `o.campaign` is nil but `o` is not? Or if `o.kernel` is nil when attempting to assert facts (`_ = o.kernel.Assert(...)`)? The current implementation avoids a panic inside `insertReproDiagnosticTaskLocked` via `if o.kernel != nil`, but `handleTaskFailure` directly calls `o.kernel.Assert` without checking `o.kernel != nil` in multiple places. If `o.kernel` is completely uninitialized, it will cause a panic.
* **Vector B: Empty Array Mutations.** What if `attempts` array in `shouldEscalateLogicFailure` is nil? It correctly handles `len(attempts) == 0`. What if the `Tasks` array within a `Phase` is initialized to a 0-capacity array and `insertReproDiagnosticTaskLocked` tries to `append`? Go handles this, but does the orchestrator state sync correctly to the VirtualStore?
* **Vector C: Empty Error Strings.** If `err.Error()` returns an empty string or just whitespaces, `classifyTaskError` correctly defaults to `/logic`. However, `handleTaskFailure` uses `errStr = err.Error()`. Later, `errStr` is appended to facts. Empty strings as fact arguments in Mangle are valid, but how do they serialize during JIT planning?

#### 2.2 Type Coercion and Fact Serialization
* **Vector D: Extreme Timestamps.** `attempt.Timestamp` is used in `shouldEscalateLogicFailure`. What if the system clock returns an extremely old time (e.g., Unix Epoch) or an extremely future time (e.g., Year 9999)? The loop age check uses `now.Sub(oldestLoopFailure)`. If `oldestLoopFailure` is year 9999, `now.Sub` yields a negative duration, which is less than `logicFailureEscalationMaxLoopAge`. The logic skips escalation.
* **Vector E: Integer Overflows in Retry Count.** What if `attemptNum` passed to `computeRetryBackoff` is negative due to integer overflow somewhere else? The logic `shift := min(max(attemptNum-1, 0), 10)` handles negative values safely, bounding them to 0. However, if `maxRetries` is extremely large (e.g., `math.MaxInt`), the retry logic will persist forever, potentially locking the orchestrator in a zombie loop.

#### 2.3 User Request Extremes
* **Vector F: Massive Error Strings.** A user executing a frontier coding benchmark might trigger a `panic` in the target compiler that outputs a 500MB stack trace. The orchestrator captures this as `err`. In `insertReproDiagnosticTaskLocked`, there is a substring truncation: `errSummary = errSummary[:220] + "..."`. However, in `handleTaskFailure`, `errStr` is passed wholly to `o.kernel.Assert` for `task_error`. Serializing a 500MB string into a Mangle fact will bloat the in-memory Datalog store, potentially OOMing the process.
* **Vector G: Pathological Dependency Graphs.** If a task failure dynamically inserts a repro diagnostic task, and the user request creates an environment where *every* task fails identically, the orchestrator might spawn hundreds of dependent repro tasks, maxing out the `TotalTasks` counter. Does `TotalTasks` have an upper bound limit?

#### 2.4 State Conflicts & Race Conditions
* **Vector H: Concurrent Task Failures for the SAME Task.** If two goroutines somehow report failure for the same task simultaneously, `handleTaskFailure` acquires `o.mu.Lock()`. The first one marks the task as failed and increments attempts. The second one will also increment attempts, potentially jumping the attempt count from 1 to 3 instantly, triggering logic failure escalation prematurely.
* **Vector I: Context Cancellation during Transaction Validation.** If the overarching `ctx` is canceled right as `handleTaskFailure` attempts to run `runPhaseCheckpoint` or `replanner.Replan`, the error is swallowed and logged, but does it leave the campaign in an inconsistent state?

### 3. Deep Dive: Performance Analysis under Edge Cases

Is the system performant enough to handle these edge vectors?

* **Massive Error Strings:** The `VirtualStore` and `Mangle` integration are NOT performant enough to handle 500MB error strings as fact arguments. `ast.String(errStr)` will allocate another copy of the 500MB string. The JIT clean loop architecture passes the facts context to LLMs. A 500MB prompt payload will violate LLM token limits and crash the HTTP transport. This requires immediate truncation BEFORE asserting the fact.
* **Concurrency:** The `o.mu.Lock()` prevents data races on the `Campaign` struct, but lock contention during a high-concurrency "Assault Campaign" (where 50 tasks might fail in parallel due to a broken environment) will serialize orchestrator throughput.
* **Mangle Re-evaluation:** Repeatedly retracting and asserting facts (`_ = o.kernel.RetractFact(core.Fact{...})`) inside `handleTaskFailure` forces the Mangle store to invalidate caches. This is an expensive operation inside the JIT Transducer.

6.  **TestHandleTaskFailure_ContextCancellationPropagation:** Provide a canceled context, trigger replan, and ensure state remains cleanly aborted.

### 5. Further Vector Elaboration: Type Coercion in Datalog Fact Assertion

The core of the JIT architecture relies on the Mangle Kernel (`o.kernel`). When `handleTaskFailure` captures a task failure, it emits `task_error` facts. The `task_error` predicate takes `[task.ID, errorType, errStr]`.
* Mangle separates `/atom` types from `"string"` types. `errorType` is often an atom like `"/logic"`.
* If `err.Error()` somehow produces a string that strictly maps to a datalog atom literal (e.g., parsing a string input that explicitly outputs `"/transient"` instead of `"network down"`), does the internal assertion system coerce it?
* If `fmt.Sprintf("max_retries_%d", maxRetries)` is emitted as the secondary argument for `task_error` upon maximum retry limit reached, the schema for `task_error` expects a specific argument type. If maxRetries is injected from user config (e.g., an environment variable read as a string but not validated), it might corrupt the fact. We need a test mapping malformed config values to Datalog assertion validation.

### 6. Further Vector Elaboration: User Request Extremes and Campaign Serialization

What happens if a user submits a massive prompt detailing a 50-file modification, resulting in a campaign with hundreds of logic loop failures?
* As `handleTaskFailure` repeatedly fails tasks, it mutates `o.campaign.Phases`.
* `o.saveCampaign()` is called under `o.mu.Lock()`.
* If the user request spawned 5,000 tasks, `saveCampaign` will serialize the entire JSON state for *each discrete failure event*. This is O(N) where N is campaign size. During a mass failure event, this generates O(N * F) disk writes where F is the number of failures.
* A boundary value test must be created: `TestHandleTaskFailure_O_N_DiskSpike`. Simulate 500 task failures sequentially, mocking the persistence layer to assert that I/O operations are batched or that the orchestrator does not block on disk fsync synchronously during high-throughput failures.

### 7. State Conflicting: The "Zombie" Replan Loop

When `facts, _ := o.kernel.Query("replan_needed")` matches, the orchestrator triggers `o.replanner.Replan(...)`.
* Suppose the replanner fails internally due to a disconnected Codex exec engine (SK-015 scenario). `handleTaskFailure` emits an event, but `task` remains in a failed state.
* The transducer might invoke `handleTaskFailure` *again* for a subsequent dependent task. This re-triggers the `replan_needed` check.
* If replan is repeatedly failing, the orchestrator might get stuck in an infinite replan-failure loop. A state conflict test is required to ensure replan failures increment a backoff specifically for replanning, not just task retries.

### 8. System Performance Implications: Memory Fragmentation

In `shouldEscalateLogicFailure`, a window slice is created: `window := attempts[start:]`.
* While Go slices are efficient, if `TaskAttempt` structs grow large (e.g., containing full AST deltas or deep error traces), slicing and retaining references to large underlying arrays might cause memory fragmentation or garbage collection pressure.
* `TestShouldEscalateLogicFailure_MemoryProfile` should be implemented to benchmark 100,000 attempts within a single task loop to ensure the GC is not overloaded by persistent references in the orchestrator log.

### 9. Edge Case Vectors Continued: Null/Undefined Artifacts

* Task artifacts are not directly evaluated in `handleTaskFailure`, but what if a failing task *did* produce artifacts (e.g., partial compile logs) before failing?
* The orchestrator marks the task as failed but leaves the artifacts array in an indeterminate state. If a repro task is spawned, it depends on the failed task. The repro task might attempt to ingest the partial, corrupt artifacts.
* Boundary Test required: `TestHandleTaskFailure_CorruptArtifactsPropagation`. Inject a failing task with 5 artifacts (some nil pointer representations, some empty) and assert that `insertReproDiagnosticTaskLocked` sanitizes or isolates the task dependency chain to avoid crashing downstream tasks.

### 10. Expanding Type Coercion Vectors: String Interception

* In `classifyTaskError`, error types are deduced by checking hints like "timeout", "network", etc., within `err.Error()`.
* **Negative Test Vector:** What if a developer intentionally names a function `TestConnectionReset`? If the task fails and the compiler error mentions "TestConnectionReset", `classifyTaskError` intercepts "connection reset" and classifies it as `/transient` even though it was a pure syntax/logic `/logic` failure.
* This is a critical edge case! The string matching is too greedy. We must test strings that contain keywords as substrings of legitimate legitimate identifiers.

### 11. Edge Cases in Checkpoint Verification

* If `checkpointOnFail` is true, a checkpoint is triggered. Checkpoints interact with the VirtualStore.
* If a state conflict exists where the file has been deleted in `VirtualStore` but still referenced in the task `write_set`, the checkpoint failure will cascade.
* What if `checkpoint` encounters an `syscall.ENOTSUPP` during fsync (as noted in system memories)? The orchestrator might propagate this as a critical task failure instead of a warning. The `orchestrator_failure_test.go` should assert behavior when `fsync` fails on unsupported volumes.

### 12. Negative Testing with Malformed Mangle Code DOM Payloads

* In `orchestrator_failure.go`, facts are serialized. The `task_error` strings could contain malformed string interpolations (e.g., unescaped quotes `" `).
* If `errStr` contains quotes, it might break Mangle's string parser during JIT payload extraction.
* Test required: Inject `err.Error()` outputting JSON payloads and verify Mangle's AST builder correctly escapes it before assertion.

### 13. Edge Case: Transducer Token Starvation

* If an assault campaign creates hundreds of transient errors, the `task_error` facts accumulate.
* The orchestrator only retracts `task_retry_at`, not `task_error`.
* This means the fact base monotonically grows with every failure. A long-running campaign with transient network issues will accumulate thousands of `task_error` facts.
* This is a memory leak vector and token starvation vector for the LLM context.
* We must write a boundary test that asserts `task_error` facts are pruned or bounded to the last N failures.

### 14. Extreme State Manipulations: Priority Inversion

* When a repro task is inserted, it's given `PriorityCritical`.
* What if the original task had an invalid priority (e.g., `-100` or `PriorityUnknown`)? Does the repro task inherit broken metadata?
* And what if the queue sorting logic fails because of integer overflow on task priorities? We need a boundary test that spawns a task with max int priority and verifies queue ordering stability.

### 15. Race Condition: Task Dependency Resolution

* In `ensureTaskDependsOn`, the `DependsOn` array is updated.
* If a replan occurs concurrently, reading `DependsOn` might panic or read partial states.
* Test required: Concurrent task dependency injection vs. context graph generation.
