
# QA Automation Engineer Journal
## Module: Mangle Repair Shard (`internal/shards/system/mangle_repair_test.go`)
## Methodology: Boundary Value Analysis and Negative Testing

### 1. Executive Summary
This document serves as an exhaustive QA analysis of the Mangle Repair Shard, focusing on negative
testing vectors, edge
cases, and boundary conditions. The current test suite (`internal/shards/system/mangle_repair_test.go`) provides solid
"happy path" coverage and structural checks (e.g., verifying the presence of specific keywords in
generated prompts, and
ensuring basic mock interactions work correctly). However, it lacks deep verification against real-world chaos,
malicious inputs, systemic resource limits, and extreme boundary cases.

In the logic-first architecture of codeNERD, the Mangle kernel is the source of truth for planning, constraints, and
execution routing. The Repair Shard acts as a critical immune system—when rules fail to parse or
evaluate (e.g., missing
predicates, unstratified logic), this shard attempts an LLM-assisted repair. If this shard fails catastrophically or
enters an invalid state, it could lead to unbounded loop execution, system panic, or arbitrary code execution through
prompt injection.

The following sections detail specific vulnerabilities, untested boundaries, and structural gaps in the current test
suite, categorized by the standard QA vectors: Null/Empty, Type Coercion, Extremes, and State Conflicts.

### 2. Vector: Null/Undefined/Empty Input Handling

The current tests verify the structure of a successfully generated repair prompt (e.g.,
`TestMangleRepairShard_BuildRepairPromptWithoutCorpus`), but they do not sufficiently test how the system handles
degenerate inputs.

**2.1 Empty Rule String (`rule == ""`)**
- *Scenario:* The `ValidateAndRepair` function is called with an empty string, whitespace-only string, or a null-byte
payload ``.
- *Expected Behavior:* The system should immediately short-circuit, reject the request with a specific "Empty Rule"
error, and bypass any LLM API calls.
- *Current Coverage Gap:* There is no test verifying that an empty rule is caught early. If it falls through, it might
generate a generic LLM prompt containing `""` as the target rule, wasting API budget and potentially confusing the LLM
into generating hallucinatory Mangle constraints.
- *Performance Impact:* Fast failure is O(1). Allowing it to reach the LLM is O(Network) and wastes tokens.

**2.2 Empty Error Slice (`errors == []string{}`)**
- *Scenario:* The repair shard is triggered, but the slice of Mangle parse/evaluation errors is completely empty or
`nil`.
- *Expected Behavior:* The system should not attempt a repair if there are no stated errors, or it
should treat it as an
anomaly ("Why was a repair requested if there are no errors?").
- *Current Coverage Gap:* `TestMangleRepairShard_BuildRepairPromptWithoutCorpus` passes a hardcoded `errors` array. If
an empty array is passed, the string concatenation in `extractErrorTypes` or `buildRepairPrompt`
might fail silently, or
the LLM might be told "Fix this rule with these errors: []", leading to non-deterministic repair attempts.

**2.3 Empty/Degenerate LLM Responses**
- *Scenario:* The schema-capable LLM returns a completely empty response `""`, a whitespace string, or an empty JSON
object `{}`.
- *Expected Behavior:* The JSON parsing in the repair pipeline must handle `EOF` or `Unexpected end of JSON input`
gracefully. It should trigger the retry logic (up to `maxRetries`) rather than panicking.
- *Current Coverage Gap:* `TestMangleRepairShard_UsesSchemaCapableClient` mocks a perfect JSON response. There is no
test simulating an LLM that returns garbage, partial JSON, or empty responses.

### 3. Vector: Type Coercion and JSON Structure Malformations

The Repair Shard relies on the LLM to output a strictly structured `MangleSynth` JSON object. While a schema is
provided, LLMs are known to occasionally hallucinate the schema or wrap the JSON in Markdown backticks.

**3.1 Markdown Code Block Wrapping**
- *Scenario:* The LLM returns ```json
{ "format": "mangle_synth_v1", ... }
``` instead of raw JSON.
- *Expected Behavior:* The parser (`ExtractPiggyback` equivalent or local unmarshaler) must strip the Markdown blocks
before attempting `json.Unmarshal`.
- *Current Coverage Gap:* There is no test verifying that code blocks are correctly sanitized before parsing.
- *Performance Impact:* If it fails to parse, it triggers a retry. If it consistently fails to parse, it exhausts the
retry budget (O(MaxRetries * Network_Latency)).

**3.2 Invalid JSON Types (The "Stringly Typed" AI Failure Mode)**
- *Scenario:* The LLM returns a JSON object where the `program` field is a raw string instead of a nested object
representing the AST, or where boolean flags are strings (`"rejected": "true"`).
- *Expected Behavior:* `json.Unmarshal` will return a type error. The system must catch this error, log it specifically
as a schema violation, and retry.
- *Current Coverage Gap:* No tests verify that type coercion failures during Unmarshal are handled safely without
causing a panic.

**3.3 The "Atom/String Dissonance" in Repaired Rules**
- *Scenario:* The LLM repairs a Mangle rule but uses string literals `"active"` instead of Mangle Atoms `/active`.
- *Expected Behavior:* The repaired rule should be analyzed via `analysis.Analyze(parsed)` to ensure it is safe and
stratified before being accepted.
- *Current Coverage Gap:* The tests only verify that the repair process completes, but they do not execute a test loop
that instantiates a `factstore`, parses the repaired rule, and runs `analysis.Analyze()`. As
detailed in the "AI Failure
Modes" memory, skipping `analysis.Analyze` can lead to unstratified logic entering the system.

### 4. Vector: Extremes (Boundary Pushing)

Stress testing requires pushing the system to its physical and logical limits. The current tests handle small, well-
formed rules (e.g., `next_action(/start) :- undefined_predicate(X).`).

**4.1 Extreme Rule Length (The 50MB Monorepo Request)**
- *Scenario:* A user attempts to run codeNERD on a massive codebase, and a generated Mangle constraint contains
thousands of literals (e.g., an exhaustive list of all 50,000 files in an `IN` clause or a massive disjunction). The
rule fails to parse, and the 5MB string is passed to the Repair Shard.
- *Expected Behavior:* The system must impose a reasonable length limit on the `rule` string before attempting repair.
If a rule exceeds 100KB, it is likely too large for the LLM context window anyway.
- *Current Coverage Gap:* There is no truncation or rejection test for excessively large rules. Passing a 5MB string
into `buildRepairPrompt` might lead to an OOM or exceed the LLM provider's token limit, causing an unhandled 400 Bad
Request error.
- *Performance Assessment:* String concatenation in Go is relatively fast, but copying a 5MB string multiple times to
build a prompt, then marshaling it into a JSON payload for the LLM client, will create significant GC pressure and
memory spikes. The system is likely performant enough to survive a single instance, but under concurrent stress tests
(e.g., `nerd spawn coder "refactor all 500 Go files"`), this could trigger the OOM killer.

**4.2 Extreme Error Count (The Parsing Bomb)**
- *Scenario:* A syntax error at the top of a large Mangle file causes the parser to emit 10,000 cascading "undefined
predicate" errors.
- *Expected Behavior:* `extractErrorTypes` should cap the number of errors it processes (e.g., top 10). The prompt
should summarize the errors rather than dumping 10,000 lines into the context window.
- *Current Coverage Gap:* `extractErrorTypes` iterates over the entire `errors` slice. If `len(errors) == 10000`, it
processes all of them. The string builder for the prompt will also append all 10,000 errors. This is a vulnerability.
- *Performance Assessment:* O(N) over 10,000 elements is fast in CPU time, but the resulting prompt string will be
massive, blowing out the token budget and increasing API latency.

**4.3 Deep Recursion / Retry Exhaustion (The TDD Infinite Loop)**
- *Scenario:* The LLM consistently returns un-parseable JSON or continuously proposes an unstratified rule (e.g., `p :-
not p.`).
- *Expected Behavior:* The `maxRetries` limit must be strictly enforced. After `maxRetries` attempts, it must return a
clean failure object without leaking goroutines.
- *Current Coverage Gap:* `TestMangleRepairShard_UsesSchemaCapableClient` sets `maxRetries = 1` and succeeds on the
first try. There is no test that forces the loop to iterate multiple times and verifies that it eventually halts
correctly.

### 5. Vector: State Conflicts and Concurrency (Race Conditions)

The codeNERD CLI operates concurrently. Sub-agents run in separate goroutines, and multiple agents might hit Mangle
parse errors simultaneously.

**5.1 Concurrent Corpus Updates**
- *Scenario:* Agent A triggers a repair, reading `shard.predicateSelector`. Simultaneously, a
background task or another
agent updates the schema, calling `SetPredicateSelector()`.
- *Expected Behavior:* The `sync.RWMutex` (`shard.mu`) must protect `predicateSelector` against concurrent reads and
writes.
- *Current Coverage Gap:* While the lock is present in the code, there are no parallel tests (`t.Parallel()`) or
goroutine fuzzing tests to verify that `ValidateAndRepair` doesn't experience a race condition if the corpus is swapped
mid-execution.

**5.2 Context Cancellation (The "Forgotten Sender" Leak)**
- *Scenario:* A user hits `Ctrl+C` or a parent campaign times out exactly while `ValidateAndRepair` is waiting on the
`CompleteWithSchema` network call.
- *Expected Behavior:* The system must respect `ctx.Done()`, cancel the network request, and return immediately.
- *Current Coverage Gap:* There are no tests using `context.WithCancel` or `context.WithTimeout` to verify that the
repair loop respects context boundaries. As noted in the memory constraints, failing to handle context cancellation
properly can lead to goroutine leaks.

### 6. Architectural and Performance Assessment

**Is the system performant enough to handle these edge cases?**
In its current implementation, the Mangle Repair Shard is a synchronous, blocking operation that waits on an external
LLM call.
- *Memory:* The lack of bounds checking on `rule` length and `errors` slice length means it is vulnerable to memory
spikes. A single massive request could allocate 50-100MB of temporary strings.
- *CPU:* Go's string manipulation is fast, but JSON marshaling/unmarshaling of large payloads is CPU intensive.
- *Network/Latency:* This is the real bottleneck. If the shard gets stuck in a retry loop (e.g., 5 retries taking 10
seconds each), it blocks the execution pipeline for 50 seconds.
- *Conclusion:* To be truly robust, the shard needs defensive programming: bounded inputs, truncated error logs, strict
context timeouts, and robust parsing of LLM markdown wrappers.

### 7. Recommendations for Test Enhancements

The `internal/shards/system/mangle_repair_test.go` file should be expanded with the following tests:
1.  `TestMangleRepairShard_EmptyRule` - Assert immediate rejection.
2.  `TestMangleRepairShard_TruncatesMassiveErrors` - Assert only the top N errors are sent to the prompt.
3.  `TestMangleRepairShard_HandlesMarkdownJSON` - Assert markdown codeblocks are stripped.
4.  `TestMangleRepairShard_RetryExhaustion` - Mock an LLM that always fails, assert it halts at `maxRetries`.
5.  `TestMangleRepairShard_ContextCancellation` - Assert the function returns immediately when the context is cancelled
mid-execution.
6.  `TestMangleRepairShard_ConcurrentAccess` - Use `t.Parallel()` and spin up 100 goroutines calling
`ValidateAndRepair`
while another updates the corpus.

### 8. Conclusion
By addressing these boundary values and negative testing vectors, the codeNERD Mangle Repair Shard will transition from
a brittle "happy path" implementation to a robust, self-healing component capable of surviving the
chaotic edge cases of
autonomous agent execution.

func TestMangleRepairShard_ContextCancellation(t *testing.T) {
    shard := NewMangleRepairShard()

    // We need a mock that blocks until context is cancelled
    blockingMock := &BlockingLLMMock{}
    shard.SetLLMClient(blockingMock)

    ctx, cancel := context.WithCancel(context.Background())

    // Start repair in a goroutine
    errChan := make(chan error)
    go func() {
        _, err := shard.ValidateAndRepair(ctx, "rule.")
        errChan <- err
    }()

    // Give it a moment to start
    time.Sleep(10 * time.Millisecond)

    // Cancel the context
    cancel()

    // Wait for result
    select {
    case err := <-errChan:
        if !errors.Is(err, context.Canceled) {
            t.Errorf("Expected context.Canceled error, got: %v", err)
        }
    case <-time.After(1 * time.Second):
        t.Error("Timeout waiting for ValidateAndRepair to return after context cancellation")
    }
}

type BlockingLLMMock struct {
    schemaCapableLLMMock
}

func (m *BlockingLLMMock) CompleteWithSchema(ctx context.Context, systemPrompt, userPrompt,
jsonSchema string) (string, error) {
    // Block until context is done
    <-ctx.Done()
    return "", ctx.Err()
}

### 10. Architectural Implications of Missing Coverage

The missing test coverage identified in this document highlights several architectural risks within
the logic-first agent framework:

1.  **Trust in LLM Outputs:** The `MangleRepairShard` inherently trusts that the LLM will obey the
JSON schema. While modern LLMs are good at this, they are not perfect. In a neuro-symbolic system,
the symbolic engine (Mangle) must be protected by strict boundary checks. The transducer layer must
not pass unvalidated or incorrectly typed data into the kernel.
2.  **Resource Exhaustion Vectors:** The lack of bounds checking on error slice length and rule
string length provides a vector for resource exhaustion. An autonomous agent exploring a large
codebase could easily generate a 10MB Mangle rule dynamically. When it fails to parse, passing 10MB
to the repair shard will cause a memory spike and likely an LLM context window overflow.
3.  **Goroutine Lifecycles:** In codeNERD, shards are spawned and managed by the `Spawner` and
`Session`. If a shard operation like `ValidateAndRepair` blocks indefinitely because it ignores
`context.Canceled`, it will leak goroutines. In a long-running campaign, these leaks accumulate,
eventually leading to application crash.

### 11. Final Recommendations

1.  Implement the missing boundary checks directly in `internal/shards/system/mangle_repair.go`
(e.g., `if strings.TrimSpace(rule) == "" { return ... }`).
2.  Add the test cases outlined in Section 9 to `internal/shards/system/mangle_repair_test.go`.
3.  Ensure the CI/CD pipeline runs `go test -race ./...` to catch the concurrency issues highlighted in Section 5.1.
4.  Implement a strict markdown stripper in the JSON unmarshaling path.
5.  Set maximum bounds on the `errors` slice and `rule` string length before building the repair prompt.

### 12. Synthetic Audit Summary
The Mangle Repair Shard is structurally critical to codeNERD's Logic-First architecture. When the
engine encounters unstratified logic or missing predicates, this shard attempts to heal the system.
However, the current test coverage is overly optimistic. It tests the "Happy Path" where the LLM is
compliant, network requests complete instantly, inputs are reasonably sized, and no concurrent
operations modify the shared state.

Negative testing and boundary value analysis reveal significant gaps:
- **Null/Empty Handling:** Missing checks for empty rules or degenerate LLM responses.
- **Type Coercion:** Assumes LLMs will perfectly adhere to JSON schema without hallucinating types
or adding markdown wrappers.
- **Extremes:** Vulnerable to OOM/Memory spikes if passed massive rules or thousands of parse errors.
- **State Conflicts:** Missing context cancellation checks and concurrent read/write tests for
shared state (`predicateSelector`).

Addressing these gaps will elevate the codeNERD architecture from a prototype to a high-assurance,
production-ready system.

### 13. Future Considerations
As codeNERD evolves, the Mangle Repair Shard might need to handle even more complex scenarios:
