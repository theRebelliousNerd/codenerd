## 1. Executive Summary

This journal details a deep, comprehensive QA analysis of the Campaign Orchestrator's failure handling mechanism in the codeNERD architecture. The `Orchestrator` is a central piece of the Neuro-Symbolic Agent Framework, acting as the primary loop controller (the "Executive" in the Creative-Executive Partnership). Specifically, `handleTaskFailure` is the critical path for TDD loops, error recovery, and failure escalation.

Given its placement, failures in this module don't just stop a task; they can corrupt the shared Mangle kernel state, lock up the entire system (due to orchestrator-wide mutexes), or cause runaway loops that drain API budgets and compute resources.

The current test suite (`internal/campaign/orchestrator_failure_test.go`) covers deterministic escalation and basic gap coverage (nil pointers, negative backoffs). However, it fundamentally lacks rigorous testing against extreme boundary values, state conflicts, adversarial inputs, and type coercion anomalies that manifest in logic programming integrations (Atom vs. String dissonance).

This document outlines extensive strategies to harden the Orchestrator via missing test cases, categorized by four primary vectors: Null/Undefined/Empty, Type Coercion, User Request Extremes, and State Conflicts.

## 2. System Architecture & Performance Context

Before diving into the edge cases, it is critical to understand the operational context of `handleTaskFailure`:

*   **Concurrency**: The function acquires `o.mu.Lock()` to modify the task state and drops it before emitting events or triggering a replan. However, it also calls `o.saveCampaign()` while holding the lock.
*   **Kernel Integration**: The function heavily interacts with `o.kernel.Assert` and `o.kernel.RetractFact`. The Orchestrator expects the kernel to act as a highly available, synchronous FactStore.
*   **Timeouts & Backoffs**: It calculates exponential backoffs to prevent tight failure loops, shifting based on `attemptNum`.
*   **Escalation Logic**: It analyzes the history of task attempts (`shouldEscalateLogicFailure`) to decide if a repro-diagnostic task should be inserted.
*   **Performance Requirements**: codeNERD may run on resource-constrained laptops (e.g., 8GB RAM). The Orchestrator must process failures rapidly without causing memory bloat (e.g., from massive error strings or attempt histories) and without stalling the JIT Clean Loop.

## 3. Vector Analysis: Null, Undefined, and Empty States

The current tests verify `nil` task and `nil` error inputs, but they miss several nuanced "empty" states that occur in distributed or highly dynamic environments.

### 3.1 Empty Task ID
*   **Scenario**: What if `task.ID` is an empty string `""` due to a deserialization error or a malformed dynamic task generated by an Ouroboros loop?
*   **Impact**: The system iterates over phases looking for the task. If it finds a task with an empty ID, it processes the failure. It then attempts to assert facts into Mangle: `o.kernel.Assert(core.Fact{Predicate: "task_error", Args: []any{"", errorType, errStr}})`.
*   **Mangle Implication**: In Mangle, an empty string might be treated as a valid string value, but if the schema expects a strictly formatted Atom identifier (e.g., `/task_123`), passing an empty string can cause silent type-mismatch rejections during logic derivation, leaving ghost tasks in the system.
*   **Test Improvement**: Create a test where `task.ID` is `""`. Verify that the orchestrator either rejects the failure gracefully or that the kernel mock safely handles the empty string without panicking or creating unjoinable facts.

### 3.2 Empty Error Type / Classification
*   **Scenario**: The function `classifyTaskError` currently hardcodes returns to `"/logic"` or `"/transient"`. If a future update introduces a bug returning `""`, or if a third-party extension injects an empty error type, how does the system react?
*   **Impact**: The `computeRetryBackoff` might apply default logic. However, the kernel assertion `Args: []any{task.ID, "", errStr}` will inject an empty string into the error taxonomy.
*   **Test Improvement**: Force the classifier to return an empty string (via dependency injection or overriding) and ensure the Orchestrator falls back to a safe default (e.g., `"/unknown"`) rather than poisoning the logic kernel.

### 3.3 Empty Phase List / Corrupt Campaign State
*   **Scenario**: The orchestrator is active (`o.isRunning`), but `o.campaign.Phases` is an empty array `[]Phase{}` due to a checkpoint corruption or an aggressive `RetractFact` bug.
*   **Impact**: `handleTaskFailure` iterates over the empty array and immediately exits the loop. It then proceeds to call `o.updateTaskStatus(task, newStatus)` and asserts facts based on variables that might not have been initialized properly within the loop (e.g., `attemptNum` defaulting to 0).
*   **Test Improvement**: Initialize the orchestrator with a campaign that has zero phases. Pass a dummy task. Ensure that the system logs the discrepancy and exits safely without mutating the kernel with invalid retry states.

## 4. Vector Analysis: Type Coercion & Data Integrity

The boundary between Go's imperative typed system and Mangle's logic-based Datalog system is the most frequent source of AI failure modes (The "Atom/String Dissonance").

### 4.1 The Attempt Number Overflow
*   **Scenario**: The logic calculates backoff using `attemptNum := len(o.campaign.Phases[i].Tasks[j].Attempts) + 1`. What if a logic error causes the attempt slice to grow unboundedly because `maxRetries` is dynamically changed, or transient errors force continuous retries over days?
*   **Impact**: While `computeRetryBackoff` has a safety clamp (`shift := min(max(attemptNum-1, 0), 10)`), it assumes `attemptNum` fits within standard integer bounds. If `attemptNum` somehow reaches extremely high numbers (e.g., generated by a synthetic test or corrupted state), it could overflow.
*   **Test Improvement**: Artificially inject `MaxInt` attempts into a task's history. Verify that the shift calculation caps correctly and that `backoff` does not calculate to a negative duration or zero duration, which would cause an infinite tight loop.

### 4.2 Adversarial Error Strings & Mangle Injection
*   **Scenario**: An LLM-generated script or a parsed log file returns an error string that contains Mangle syntax, such as `Error: syntax error :- true. //`.
*   **Impact**: `handleTaskFailure` asserts this directly into the kernel: `o.kernel.Assert(core.Fact{... Args: []any{task.ID, errorType, errStr}})`. If the `VirtualStore` or kernel implementation uses string formatting instead of parameterized AST construction, this could result in a Mangle injection attack.
*   **Test Improvement**: Inject adversarial payload strings (e.g., `"foo), injected_fact(/bad). //"`, `"\x00"`, `"\\u0000"`) as the error message. Ensure the MockKernel validates that the argument is treated strictly as a string literal (`ast.String`) and not evaluated as an Atom (`ast.Name`) or parsed as rules.

### 4.3 Type Mismatch in Kernel Feedback
*   **Scenario**: `handleTaskFailure` calls `o.kernel.Query("replan_needed")`. What if the kernel derives a fact but the arguments are of the wrong type (e.g., an Integer instead of a String, or a nested struct)?
*   **Impact**: If the orchestrator code (elsewhere) attempts to `types.ExtractString()` on a non-string argument, it could panic.
*   **Test Improvement**: Though `handleTaskFailure` only checks `len(facts) > 0`, future-proof the tests by mocking the kernel to return badly typed facts for `"replan_needed"` and ensure it doesn't cause cascading panics.

## 5. Vector Analysis: User Request Extremes & Boundary Values

Users push systems to their limits. A brownfield repo with 50 million lines of code processed on a laptop with 8GB RAM requires high performance and extreme resilience.

### 5.1 The Fail-Fast Configuration (MaxRetries = 0)
*   **Scenario**: A user configures a campaign with `config.MaxRetries = 0` because they want strict fail-fast behavior (e.g., in a CI environment).
*   **Impact**: The code says:
    ```go
    maxRetries := o.config.MaxRetries
    if maxRetries <= 0 {
        maxRetries = 3
    }
    ```
    This completely prevents fail-fast behavior. If a user asks for 0 retries, they get 3. This is a severe logic bug for negative testing boundaries.
*   **Test Improvement**: Write a test verifying `config.MaxRetries = 0`. Expectation: The system currently forces 3, so the test will prove the bug. The proposed fix would be to distinguish between "uninitialized" (maybe use a pointer or a distinct default flag) and explicitly "0".

### 5.2 Extreme Backoff Configurations
*   **Scenario**: A user sets `RetryBackoffBase = time.Duration(math.MaxInt64)` and `RetryBackoffMax = time.Duration(math.MaxInt64)`.
*   **Impact**: `backoff := base * time.Duration(1<<shift)` will overflow an `int64`, wrapping around to a negative number.
*   **Test Improvement**: Inject `math.MaxInt64` for the backoff configs. Call `computeRetryBackoff`. Assert that the result does not wrap to a negative duration. (The current implementation will likely fail this test).

### 5.3 Massive Attempt History & Memory Pressure
*   **Scenario**: In a long-running system, a task might accumulate thousands of transient attempts.
*   **Impact**: `shouldEscalateLogicFailure` copies slices: `window := attempts[start:]`. It also iterates over this window. While `logicFailureEscalationWindowAttempts` limits the window to 3, the slice `attempts` itself could be massive. More concerning is that `o.campaign.Phases[i].Tasks[j].Attempts = append(...)` will continually reallocate and copy memory for a massive slice. If a user runs a campaign for 4 days with a 1-second transient loop, the array grows to 345,600 items. This causes massive memory pressure on an 8GB laptop, leading to OOM kills.
*   **Test Improvement**: Create a task with 100,000 dummy attempts. Call `handleTaskFailure`. Measure the execution time and memory allocations (using Go benchmarks). The system should cap the history size (e.g., keeping only the last 100 attempts) to prevent unbounded memory growth.

### 5.4 Time Travel & Epoch Edge Cases
*   **Scenario**: NTP sync shifts the clock backward, or a bug causes `attempt.Timestamp` to be recorded as the Unix Epoch (1970-01-01) or a time far in the future.
*   **Impact**: `shouldEscalateLogicFailure` calculates loop age: `now.Sub(oldestLoopFailure) >= logicFailureEscalationMaxLoopAge`. If `oldestLoopFailure` is the epoch, the loop age will be ~50 years, instantly triggering an escalation on the first failure.
*   **Test Improvement**: Test `shouldEscalateLogicFailure` where one of the attempts has a timestamp of `time.Unix(0, 0)`. Verify if the system handles time anomalies gracefully (e.g., rejecting timestamps older than the campaign start time).

## 6. Vector Analysis: State Conflicts & Race Conditions

Distributed logic systems are highly prone to race conditions, especially when bridging Go's concurrency with Mangle's fixpoint evaluation.

### 6.1 The I/O Blocking Mutex (Context Cancellation)
*   **Scenario**: At the end of `handleTaskFailure`, the code does:
    ```go
    o.mu.Lock()
    _ = o.saveCampaign()
    o.mu.Unlock()
    ```
*   **Impact**: `saveCampaign` performs disk I/O (writing to SQLite or JSON). If the disk is slow (e.g., a heavily loaded 8GB laptop), this blocks `o.mu` for hundreds of milliseconds. Meanwhile, the `ctx` passed to `handleTaskFailure` might have been canceled (e.g., the user hit Ctrl+C). Because the code doesn't check `ctx.Err()` before attempting the save, it forces the user to wait for the I/O to complete, causing a sluggish CLI experience.
*   **Test Improvement**: Pass a canceled context to `handleTaskFailure`. Use a mocked `saveCampaign` that blocks. Verify that the system should theoretically check the context and abort the save, or at least that the orchestrator design allows for safe cancellation during failures.

### 6.2 Concurrent Task Retraction (Ghost Facts)
*   **Scenario**: The orchestrator asserts `task_error` facts into the kernel. It ignores errors from `o.kernel.Assert`.
*   **Impact**: If the kernel is currently resolving a complex query (fixpoint evaluation), it might reject synchronous assertions, or if the kernel mock returns an error (e.g., "store is read-only"), the fact is never stored. The Go state (`o.campaign`) says the task failed, but the Mangle state thinks the task is still pending or successful. This desynchronization breaks the JIT Clean Loop.
*   **Test Improvement**: Implement a `TestOrchestratorFailure_KernelDesync` test. Provide a MockKernel that returns an error on `Assert`. Verify that `handleTaskFailure` logs the severe error and perhaps triggers a panic or a campaign halt, rather than silently swallowing the error and entering a corrupted state.

### 6.3 Deadlock via Event Emission
*   **Scenario**: `o.emitEvent` writes to `o.eventChan`.
*   **Impact**: If `eventChan` is unbuffered and the reader (the CLI UI or a logging sidecar) is blocked, `handleTaskFailure` will block forever. Because it happens *after* `o.mu` is unlocked, it doesn't cause a global mutex deadlock, but it does freeze the specific goroutine executing the task.
*   **Test Improvement**: Initialize the orchestrator with an unbuffered, unread `eventChan`. Call `handleTaskFailure`. The test will hang. Use a goroutine and `select` with a timeout to detect the hang, proving the vulnerability. (The fix would be to ensure event channels are non-blocking or well-buffered).

### 6.4 The Forgotten Sender (Goroutine Leaks)
*   **Scenario**: If `o.replanner.Replan` is triggered asynchronously or starts background workers, and the campaign is subsequently canceled due to user extreme inputs (like a SIGINT).
*   **Impact**: As outlined in the `AGENTS.md` rules regarding Go tests for Mangle engines, un-drained channels block goroutines forever. If `handleTaskFailure` triggers a replan that leaks a goroutine upon early exit, repeated failures will exhaust system memory.
*   **Test Improvement**: Use `goleak` to test `handleTaskFailure` comprehensively. Ensure that when replanning is triggered due to failures, no goroutines are left lingering if the context is canceled immediately after the call.

## 8. Conclusion

The `handleTaskFailure` subsystem is fundamentally robust against standard happy-path and typical logic failures. However, it exhibits significant vulnerabilities when subjected to extreme user inputs, boundary values (0 limits, MaxInt limits), adversarial type coercions, and system state anomalies (time travel, kernel desyncs).

By injecting the `// TODO:` markers into `orchestrator_failure_test.go` and documenting these 7 specific test vectors, the codeNERD framework can be hardened against the very edge cases that cause AI agents to enter infinite, expensive, and destructive loops.
