## Subsystem Evaluated: Perception Transducer & Adversarial E2E Tests (`tests/e2e/perception_adversarial_e2e_test.go`)
### Executive Summary
This journal entry evaluates the adversarial test suite for the perception
transducer module within codeNERD. The analysis is driven by Boundary Value
Analysis (BVA) and Negative Testing methodologies. I have critically assessed
the current test coverage across multiple vectors: Null/Undefined/Empty
boundaries, Type Coercion, User Request Extremes, and State Conflicts. The focus
is to identify missing edge cases, elaborate on strategies to fortify the
existing test harness, and evaluate whether the underlying system is robust and
performant enough to handle these anomalies gracefully without system
degradation or state corruption.

### Vector 1: Null/Undefined/Empty Boundaries
#### Current State vs. Missing Coverage
The current test `TestE2E_Perception_Adversarial_NullAndEmptyVectors` evaluates
basic `null` usage for top-level fields like `primary_intent`. However, it fails
to deeply probe the transducer's handling of nested nulls within the `scope` and
`suggested_approach` objects.

#### Proposed Edge Cases
1. **Deep Scope Nullification:** Inject `{"understanding": {"scope": null}}`.
2. **Target Field Nullification:** Inject `{"understanding": {"scope": {"target": null}}}`.
3. **Empty Arrays vs Null Arrays:** Contrast `"tools_needed": []` with `"tools_needed": null`.
4. **Missing Keys Entirely:** Omit the `signals` object entirely rather than setting it to null.

#### Performance & Architectural Impact
If the system uses standard `encoding/json` with Go structs, fields typed as
strings will receive empty strings if null is parsed, unless they are pointers.
We must verify that `ParseIntentWithContext` behaves deterministically and does
not nil-panic when dereferencing scope variables. Performance-wise, Go's JSON
unmarshaler handles nested nulls with minimal overhead. The transducer will not
experience latency spikes during parsing, but subsequent logic (like mapping
actions) must use short-circuit evaluations to remain highly performant.

### Vector 2: Type Coercion
#### Current State vs. Missing Coverage
The suite currently tests passing a string boolean (`"true"`) to a boolean
field. This is insufficient. We need to test severe polymorphic type spoofing
and coercion cascades that could destabilize the JSON decoder.

#### Proposed Edge Cases
1. **Object Injection into String:** `{"primary_intent": {"injected": "intent"}}`.
2. **Numeric Arrays into String Arrays:** `"tools_needed": [1, 2, 3]`.
3. **Float Injection into String:** `"action_type": 3.14159`.
4. **Boolean Injection into Object:** `"scope": false`.

#### Performance & Architectural Impact
In Go, these injections typically result in an immediate `json.Unmarshal` error.
The system must gracefully catch this error and trigger a reliable fallback
intent (e.g., `/explain` or `/chat`) instead of crashing the transducer loop.
Because type mismatch failures occur rapidly during decoding, bad inputs are
rejected quickly. Thus, the system is highly performant under type coercion
stress and will not waste CPU cycles attempting to process malformed payloads
into Mangle queries.

### Vector 3: User Request Extremes
#### Current State vs. Missing Coverage
While `TestE2E_Perception_Adversarial_InputTruncation` handles a 100KB prompt,
it focuses on the raw prompt text, not the semantic extremes of the user's
*request* as interpreted by the LLM.

#### Proposed Edge Cases
1. **Infinite Monorepo Context:** A brownfield request demanding action across a 50 million line monorepo. The LLM outputs `"tools_needed": ["read_file"], "scope": {"target": "**/*.go"}`.
2. **Frontier Benchmark Questions:** Requests for extremely complex algorithm synthesis that might trigger a `godmode` or `root` shard response unexpectedly.
3. **Non-Existent Languages:** Requests to write code in "HyperLogica99", testing if the transducer correctly maps this to an unhandled or research intent.
4. **Massive Tool Chaining:** An intent suggesting 50 different tools in `tools_needed`.

#### Performance & Architectural Impact
The transducer itself only parses the intent JSON, so its raw processing
performance is unaffected by the semantic weight of the request. However, the
resulting `user_intent` fact must include safety constraints (e.g., clamping
context window targets) to ensure the downstream Virtual Store execution does
not trigger memory pressure alerts (OOM). If a massive wildcard like `**/*.go`
is passed downstream without perception-layer limits, the system will crash
during action execution.

### Vector 4: State Conflicts and Race Conditions
#### Current State vs. Missing Coverage
The transducer tests are currently completely isolated from temporal state. They
do not simulate what happens when the intent target becomes invalid between the
perception and action phases.

#### Proposed Edge Cases
1. **Deleted Resource Conflict:** The user requests to modify a file that a background autopoiesis loop just deleted.
2. **Simultaneous Intent Collision:** Two simultaneous requests modifying the same architectural component.
3. **Permissions Shift:** The user requests action on a file, but background security policies change immediately after intent parsing, invalidating the implicit assumptions.

#### Performance & Architectural Impact
The transducer's role is to faithfully record the intent (e.g.,
`user_intent(..., "modify", "deleted_file.go")`). The test suite must strictly
assert that the perception layer does NOT attempt to validate file existence via
stat calls—that is the explicit job of the kernel and Virtual Store. Keeping
perception stateless ensures extremely low latency. If the transducer performed
IO checks, it would become IO-bound, creating severe race conditions. The
current architecture correctly pushes conflict resolution to the Mangle
execution phase.

### Advanced Analysis: Mangle Safety and OODA Loop Integration
#### The Mangle Injection Vulnerability
The most critical finding during this analysis relates to how the perception
transducer bridges unstructured language and Mangle's rigid logical framework.
By outputting `user_intent` facts, it feeds directly into the JIT Clean Loop
architecture.

Adversarial testing (`TestE2E_Perception_Adversarial_MangleInjection`) reveals a
severe flaw: the `sanitizeFactArg` function preserves characters like `(`, `)`,
and `.` which have semantic and syntactic meaning in the Mangle language. This
is a critical security vulnerability, as it allows for fact injection via the
user constraints field (e.g., injecting `). safe_action(/write_file).`).

#### Required Remediation
To truly fix this, the system must either employ a strict allowlist for strings
converted to Mangle AST nodes (ensuring they are instantiated via `ast.String`
rather than raw string concatenation) or aggressively escape/strip these
characters at the grammar boundary. The tests correctly flag this, but the
remediation must be prioritized to prevent prompt-injection attacks from
bypassing the rulecourt.
