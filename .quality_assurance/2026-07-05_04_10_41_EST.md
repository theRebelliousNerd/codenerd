# QA Review: RuleCourt Validation System

## System Overview
The `RuleCourt` component in `internal/core/rule_court.go` is responsible for validating Mangle policy rules before they are incorporated into the system's active knowledge base (`RealKernel`). This component is extremely important, as evaluating poorly structured, excessively complex, or adversarial Mangle rules can result in infinite recursion (deadlock), out-of-memory errors, and bypassing of safety mechanisms (such as the `ask_user` hatch).

## Edge Cases Missing from Tests

The testing suite currently covers standard happy-path ratifications and a few failure modes (e.g., deadlock detection and string `ask_user` hatch bypasses). However, several critical edge cases related to input shape, size, types, and temporal limits are not verified:

### 1. Null/Undefined/Empty
*   **Nil Kernel:** `TestRuleCourt_NilKernel` exists but doesn't test the receiver form (`court.RatifyRule(rule)` when `court.kernel` is nil) or ensure that an explicit error (not a panic) is raised when the underlying state is completely missing.
*   **Zero-Width Spaces:** Although partially tested in `TestRuleCourt_WhitespaceOnly`, Mangle might treat specific UTF-8 whitespaces (like thin space, EM space) differently if they bypass the `strings.TrimSpace` check but produce syntactically valid (yet meaningless) rules that clog evaluation.
*   **Empty Fact Sequence:** If the underlying kernel returns an empty iterator from `GetFactsSnapshotSeq()`, does the sandbox correctly fall back without panicking during `LoadFactsSeq`?

### 2. Type Coercion
*   **Undeclared Schemas:** What happens if a proposed rule tries to assert a fact for an undeclared predicate? Mangle validation occurs during `Evaluate()`. The current tests check for bad syntax (e.g., `test_allowed(123 :- .`) but not semantically invalid logic (e.g., `undeclared_pred(X) :- other(X).`). The error should propagate clearly back through `RatifyRule`.
*   **String/Atom Dissonance:** Mangle heavily differentiates between Atoms (e.g., `/active`) and strings (e.g., `"active"`). If a proposed rule creates invalid type coercions (e.g., passing a string into a predicate slot requiring an Atom), does `Evaluate()` correctly fail and reject the rule?

### 3. User Request Extremes
*   **Enormous Rule Size (10MB+):** A malicious or hallucinated LLM output might generate an extremely large rule file. Can `sandbox.SetPolicy` and `Evaluate()` handle an enormous string input without causing a process-level Out-of-Memory (OOM) crash? This should ideally trigger a rejection due to size before even hitting the parser.
*   **Runaway Recursion / Timeout Verification:** `RatifyRule` employs a `ratifyEvalTimeout` to kill runaway recursion. However, this is *never tested*. There must be a test that artificially injects a recursive rule (e.g., `p(X+1) :- p(X).`), temporarily lowers `ratifyEvalTimeout` to `50ms`, and ensures the context timeout fires and returns the appropriate `VETO: sandbox evaluation timed out` error rather than hanging.

### 4. State Conflicts
*   **Heavy Concurrency during Snapshotting:** If `RuleCourt` validates a rule while another goroutine is aggressively writing facts to the base kernel, does the sequence generated by `GetFactsSnapshotSeq()` lock safely, or will it cause concurrent map read/write panics within the Mangle engine?
*   **False Positives on `ask_user`:** The safety hatch check is simply `strings.Contains(newRule, "ask_user")`. If a user proposes a completely valid and benign rule like `log_message("Did not ask_user_id yet").`, it will be falsely vetoed. The test suite needs to verify this false positive, and the implementation might need an update to use regex or word boundaries (e.g., `\bask_user\b`).

## Performance Under Extremes
Mangle evaluation inside the `sandbox.Evaluate()` is currently the primary bottleneck. Under extreme user requests (e.g., millions of facts generated from a monorepo analysis):
1.  **Snapshot Overhead:** `GetFactsSnapshotSeq()` is memory efficient as it returns an iterator, but loading millions of facts into a fresh sandbox kernel (`sandbox.LoadFactsSeq`) for *every single rule ratification* will cause immense GC pressure and CPU spikes.
2.  **Timeout Brittleness:** The 5-second `ratifyEvalTimeout` might fire not because the rule is recursive, but simply because evaluating a safe rule over 5 million facts takes longer than 5 seconds. This could lead to a scenario where codeNERD completely refuses to learn anything new when working on large codebases.

## Remediation Plan
1. Add tests for undeclared schemas and type dissonance.
2. Add a test that proves `ratifyEvalTimeout` actually catches infinite recursion (by temporarily modifying the timeout var).
3. Add a test to prove 10MB payloads are handled or cleanly rejected.
4. Add a test proving the `ask_user` safety hatch doesn't trigger on false positives like `ask_user_id`. (Will require fixing the implementation).


## Test Gaps Remediated
The test gaps identified above were resolved by:
1.  Creating `internal/core/rule_court_gaps_test.go` and implementing missing edge-case test combinations.
2.  Refactoring `RatifyRule` in `internal/core/rule_court.go`:
    *   **Max Rule Length Check:** Implemented a fast-path length bound (`maxRuleLength = 1MB`) prior to trimming strings, which avoids extreme buffer allocations.
    *   **Ask User Veto Fix:** Replaced standard substring search (`strings.Contains`) with a boundary regex (`\bask_user\b`) to eliminate false positives on subwords (e.g. `ask_user_id`), improving state consistency for valid Mangle variables.

Both regression tests (`go test -v ./internal/core -run TestRuleCourt`) pass and cover these vectors successfully.

## Expanding on Context Nullification and Rule Deadlocks

To further expand on this subject, it is important to realize the impact of rule additions during a running campaign orchestrator cycle.
When we dynamically insert rules via the transductive components, `RatifyRule` acts as the single choke-point for system deadlock avoidance.

### Extended Vector: Memory Saturation during GetFactsSnapshotSeq
`GetFactsSnapshotSeq()` is supposed to be memory-efficient, utilizing an iterator rather than a slice.
However, Go 1.23+ iterators (the `iter.Seq` pattern) can still cause significant allocation churn inside Mangle's evaluation engine when thousands of facts are streamed directly into `sandbox.LoadFactsSeq`.
If `RatifyRule` is triggered concurrently by 20 autopoiesis agents, each creating a sandbox kernel and streaming 100,000 facts, we'll see sudden multi-gigabyte spikes in heap allocations.
This vector falls under User Request Extremes: A user running codeNERD on a monorepo, generating immense context, might accidentally trigger an out-of-memory exception simply by proposing new logic rules.

### Extended Vector: Temporal Decay and Timeouts
The `ratifyEvalTimeout` is statically defined as `5 * time.Second`.
Under high CPU contention (e.g. Thunderdome tests running simultaneously on the same machine), an evaluation that normally takes 0.5s might stretch beyond 5 seconds.
This leads to a spurious VETO. The agent will falsely believe its newly synthesized rule causes runaway recursion, when in fact the underlying machine was just starved for CPU cycles.
This indicates a systemic flaw where `RatifyRule` is not context-aware. It should potentially scale its timeout based on the size of the fact snapshot (i.e., `100ms + (factCount * 0.1ms)`).

### Extended Vector: The ask_user Hatch with Internationalization
We modified the `ask_user` hatch check to use `\bask_user\b`. But what happens if the user defines a rule with an equivalent emergency escape hatch in another language, or uses camelCase (e.g., `askUser`)? The system currently hardcodes "ask_user" as the universal safe hatch. This is brittle. If a user sets their `user_intent` policy to rely on `/escalate_to_human`, `RatifyRule` won't protect that alternate hatch.

### Deep Dive: Atom vs. String Mangle Coercion
Let's consider the Atom vs String Dissonance gap in more detail. Mangle schema validation enforces that arguments conform to type boundaries.
If I have `Decl needs_string(Name.Type<String>).` and `needs_string(/hello).`, `Evaluate` will return an error because `/hello` is an Atom.
But what if the schema lacks explicit types? E.g. `Decl needs_anything(Name).`
In this case, Mangle allows both Strings and Atoms.
The danger here isn't the schema failing; the danger is semantic joins failing downstream.
If the `CampaignOrchestrator` asserts facts as strings (`"task_status"("active")`), but a new rule is proposed that checks `task_status(/active)`, the rule will *pass ratification* (it doesn't deadlock, it doesn't violate schema, it doesn't timeout).
But when it is deployed, it will never trigger. It's a silent logic failure, the hardest class of bugs to track down in Datalog systems.

### Further considerations
We must consider the security implications of `sandbox.SetPolicy(kernel.GetPolicy() + "\n\n# Proposed Rule (Legislator)\n" + newRule)`.
This concatenates the new rule at the end. Can a user use string injection to close the block early or interfere with previously defined macros?
Mangle is generally resilient to this as it lacks block-level scoping that can be trivially broken via string injection, but multi-line string literals inside `newRule` could theoretically consume subsequent EOF markers if the parser has a bug.
