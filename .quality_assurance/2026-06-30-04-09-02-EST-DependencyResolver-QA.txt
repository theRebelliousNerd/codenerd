QA Journal Entry: DependencyResolver in codenerd
Date: 2026-06-30 04:09:02 EST
System: internal/prompt/resolver.go
QA Engineer: Jules

1. Executive Summary
This journal entry documents a comprehensive Boundary Value Analysis and Negative Testing audit
of the DependencyResolver component (internal/prompt/resolver.go) within the codeNERD architecture.
The DependencyResolver is a critical subsystem responsible for topological sorting of PromptAtoms
based on their dependencies, conflict resolution, and cycle detection. If it fails, JIT prompt
compilation will either fail silently (missing context) or catastrophically (infinite loops, OOM).

2. System Context
The DependencyResolver uses Kahn's algorithm for topological sorting. It receives a list of
ScoredAtoms and returns an ordered list of OrderedAtoms. The inputs are presumed to have passed
through the Mangle kernel for schema validation and fact-based filtering, but the DependencyResolver
is the last line of defense before the LLM prompt is assembled.

3. Missing Edge Cases and Vulnerability Vectors

3.1 Null/Undefined/Empty Vector
- Nil ScoredAtom in Input Slice: The code has a check `if sa == nil || sa.Atom == nil || sa.Atom.ID == ""`
but the test suite lacks coverage for slices containing multiple nil elements, alternating nils, or an
entire slice of nil elements.
- Empty DependsOn Slice: What if `DependsOn` is an empty array `[]string{}` versus `nil`? Does the
JSON unmarshaler or Mangle mapping treat these identically? Kahn's algorithm should handle this, but
tests must verify.
- Empty String in DependsOn: `DependsOn: []string{""}`. The resolver checks `if seenDeps[depID]` but
an empty string ID could map to an invalid atom or falsely increment in-degree if an atom with ID "" exists.
- Self-Dependency via Empty String: If an atom has ID "" and depends on "", does it cause a self-cycle?

3.2 Type Coercion Vector
- Malformed Atom IDs: Mangle Atoms vs. Go Strings. The system uses strings for IDs, but Mangle Atoms
are distinct. If a raw string is used instead of a normalized Mangle Atom string, the dependency map
lookups will fail silently. A test should verify behavior when IDs contain unicode, spaces, or control chars.
- Score Coercion: Float64 precision limits. What if two atoms have scores that differ only at the
15th decimal place? Does the deterministic sort `queue[i].Combined > queue[j].Combined` handle IEEE 754
NaN or Infinity values properly? If `Combined` is NaN, the sort might panic or become non-deterministic.

3.3 User Request Extremes Vector
- Massive Dependency Chains: A user request to analyze a 50-million line monorepo could generate thousands
of PromptAtoms. What happens if we pass 1,000,000 ScoredAtoms to `Resolve()`?
- Kahn's Algorithm Performance: Kahn's algorithm is O(V + E). For 1M atoms with 10 dependencies each, V=1M, E=10M.
The current implementation builds `inDegree` (map), `seenDeps` (map per atom), and `dependents` (map of slices).
Memory allocation for these maps could cause an OOM.
- Deep Linear Dependency Chain: Atom A -> Atom B -> Atom C ... -> Atom 1,000,000. Stack depth is not an issue
since Kahn's is iterative, but the queue slice will grow linearly.
- Extreme Priority Values: `Priority` is an int. What if `Priority` is `math.MaxInt64` or `math.MinInt64`?

3.4 State Conflicts Vector
- Deterministic Sorting on Identical Scores: If two atoms have the EXACT same `IsMandatory` flag and EXACT
same `Combined` score, the current sort function `queue[i].Combined > queue[j].Combined` does NOT guarantee
stable ordering. It needs a tie-breaker, such as comparing `queue[i].Atom.ID < queue[j].Atom.ID`.
Failure to do this can lead to flakiness in prompt generation where identical inputs yield different LLM outputs
due to token position bias.
- Race Conditions: Is `DependencyResolver.Resolve` thread-safe? It mutates no internal state except `allowMissingDeps`.
However, if the incoming `ScoredAtom` pointers are modified concurrently by the `BudgetManager`, a race condition
will occur.

4. Detailed Analysis of Missing Tests

Test Cases to Implement:
- TestDependencyResolver_NilElementsInSlice
- TestDependencyResolver_EmptyStringInDependsOn
- TestDependencyResolver_SelfDependency
- TestDependencyResolver_ScoreNaNAndInfinity
- TestDependencyResolver_DeterministicSortTieBreaker
- TestDependencyResolver_ExtremeScale_OneMillionAtoms
- TestDependencyResolver_DeepLinearChain

5. Performance Implications
The use of `map[string]bool` for `seenDeps` inside the loops causes excessive heap allocations.
For extreme scenarios (100k atoms), this will trigger heavy GC pauses.
Optimization suggestion: Use a single map that is cleared or a slice-based approach if the average
degree is small.

6. Conclusion
The DependencyResolver is robust against basic inputs but lacks defensive programming and test coverage
for extreme scale and adversarial inputs. Addressing the deterministic sort tie-breaker is the most
critical immediate fix to ensure reproducible prompt generation.

7. System Check
Is the system performant enough? For typical JIT compilations (50-200 atoms), Kahn's algorithm with
map lookups executes in sub-millisecond time. However, for extreme user requests (100,000 atoms),
the map allocation overhead will likely cause latency spikes. A more memory-efficient graph representation
(e.g., using integer indices mapping to IDs) might be required if codeNERD scales to entire-codebase prompts.
