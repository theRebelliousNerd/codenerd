## System Analysis: Mangle and Orchestrator Dynamics
The codeNERD system heavily relies on `Mangle`, a Datalog dialect with stratified negation. The orchestrator uses Mangle to record facts about task execution and failures.
Crucially, as outlined in the `agents.md` documentation, the most expensive defect class is "Atom/String Dissonance". Mangle treats Atoms (e.g., `/logic`) and Strings (e.g., `"logic"`) as distinct types. If the Go orchestrator asserts a failure type as a string when Mangle expects an atom, the join fails silently, returning zero results. This violates the North Star invariant: "The agent's own status report must be worthless as a claim and valuable only as a citation. If it says a thing is done, there is a derivation showing it."

The `orchestrator_failure.go` module handles task retries, exponential backoff, and escalations (e.g., spawning repro tasks for persistent logic failures). It must interact flawlessly with the Mangle kernel (e.g., `o.kernel.Assert`) and maintain in-memory state (`o.campaign`) coherently.

## Identified Test Gaps & Boundary Analysis

### Vector 1: Null/Undefined/Empty

*   **Empty Error Strings:** The function `classifyTaskError(err error)` determines the failure bucket (`/logic`, `/transient`, etc.). What happens if `err.Error()` returns an empty string or just whitespace? Does it default to `/logic` correctly, or does it cause a panic during string matching?
*   **Empty Task ID:** When `handleTaskFailure` is invoked with a task that has an empty `ID` (`""`), it attempts to assert facts into Mangle (e.g., `task_error("", /logic)`). Is this valid in the Mangle schema? Does it corrupt the fact store or cause panics downstream when querying by ID?
*   **Zero-Value Timestamps:** In `shouldEscalateLogicFailure`, it iterates through `TaskAttempt` structs. If an attempt has a zero-value `Timestamp` (e.g., `time.Time{}`), does the time difference calculation underflow or produce nonsensical escalation triggers?
*   **Nil/Empty Slices:** Functions like `insertReproDiagnosticTaskLocked` and `findActiveReproTaskID` manipulate phase task lists. Calling these with uninitialized or empty slices must be strictly tested for nil-pointer panics or out-of-bounds access.

### Vector 2: Type Coercion and Mangle Dissonance

*   **Atom vs. String Mismatch in Assertions:** This is the most critical gap. When asserting `task_error`, the Go code MUST use `ast.Name(bucket)` (where bucket is `/logic` etc.) and NOT `ast.String(bucket)`. If the schema expects an Atom and gets a String, it's a silent failure. The tests must verify the *type* of the asserted fact in the mock kernel, not just the string representation.
*   **Timestamp Precision Coercion:** Mangle often works with float64 or specific int boundaries. When Go passes `time.Now().UnixNano()` or similar large integers as arguments to Mangle facts (e.g., `task_retry_at`), does it exceed Mangle's numeric capacity? Does it silently truncate, causing immediate retries instead of exponential backoff?

### Vector 3: User Request Extremes

*   **Massive Error Payloads:** An adversarial tool or a runaway compiler output might return a 50MB error string. If `handleTaskFailure` blindly passes this massive string to `o.kernel.Assert(task_error(ID, Type, MassiveString))`, it could exhaust memory or exceed SQLite/Mangle fact size limits, crashing the agent.
*   **Backoff Integer Overflow:** The exponential backoff calculation `computeRetryBackoff` uses bitwise shifts or multiplication. If `MaxRetries` is extremely high, or if `RetryBackoffBase` is artificially inflated (e.g., `math.MaxInt64`), the calculation could overflow, resulting in negative durations. A negative duration passed to `time.After` fires immediately, turning a throttled retry loop into a tight CPU-spinning death spiral.
*   **Infinite Repro Cascades:** If a task fails logically, it spawns a repro task. What if the *repro task itself* fails logically? Does it spawn a repro task for the repro task? This unbounded recursion would rapidly consume resources. The logic must explicitly prevent repro tasks from triggering further repro tasks.
*   **Performance under History Load:** `shouldEscalateLogicFailure` checks the history of attempts. What if a task has been retried 100,000 times (perhaps due to the overflow bug above)? Iterating this slice while holding the orchestrator lock (`o.mu`) could cause severe lock contention and starve the heartbeat loop.

### Vector 4: State Conflicts

*   **Kernel Assertion Failure Desynchronization:** If `o.kernel.Assert` returns an error (e.g., the SQLite DB is locked, or the fact violates schema), the in-memory `task.Attempts` is already appended, but the Mangle state is missing the fact. The orchestrator is now desynchronized from truth. The code must handle this transactionally: either both succeed, or neither do.
*   **Context Cancellation during Persistence:** If the context passed to `handleTaskFailure` is canceled *exactly* when `o.saveCampaign()` is called, does it save a corrupted partial state? Does it block forever if the persistence layer doesn't respect the context?
*   **Concurrent Mutators:** If `AbortCampaign` is called concurrently while `handleTaskFailure` is executing and modifying phase lists to insert repro tasks, does the locking strategy (`o.mu`) prevent race conditions?

## Performance Considerations
The codeNERD orchestrator is designed for high-performance, concurrent execution. However, operations within `handleTaskFailure` hold the `o.mu` sync.Mutex.
If the kernel assertion or the `saveCampaign` operation are synchronous and perform disk I/O, holding the main orchestrator lock during these operations limits the throughput to the disk write speed. For extreme scenarios (e.g., 100 concurrently failing tasks), this serialization will bottleneck the entire campaign execution. The architecture should eventually consider asynchronous fact buffering or finer-grained locking for state mutation versus persistence.

## Detailed Architecture Review: The Transactionality Problem

In reviewing the Mangle orchestration, a fundamental flaw exists in the transactionality between the in-memory state and the SQLite-backed fact store.
When `handleTaskFailure` is called, it mutates the Go struct `Task` by appending a `TaskAttempt`. It then attempts to assert facts into Mangle.

Consider the sequence of events:
1. Memory Append: `task.Attempts = append(task.Attempts, newAttempt)`
2. Mangle Assert: `o.kernel.Assert(task_error(task.ID, bucket))`
3. Disk Sync: `o.saveCampaign()`

If step 2 fails (e.g., schema validation error because a string was provided instead of an atom), the function might log the error and return, OR it might panic. If it returns without rolling back step 1, the in-memory state now diverges from the authoritative Datalog kernel. The agent believes it has recorded an attempt, but a query against the Mangle kernel will show no error for that task.

### The Phantom Repro Task

Escalation is even more dangerous. `shouldEscalateLogicFailure` might decide to spawn a repro task based on the in-memory attempts slice.
1. Phase Mutate: `phase.Tasks = append(phase.Tasks, reproTask)`
2. Mangle Assert: `o.kernel.Assert(task_pending(reproTask.ID))`
3. Disk Sync: `o.saveCampaign()`

If step 2 fails, the phase has a new task in memory, but the scheduler (which queries Mangle for `task_pending`) will never see it. If step 3 fails, the phase has a new task, Mangle knows about the task, but a system crash and reboot will load the old campaign state from disk where the task doesn't exist, while the Mangle SQLite DB STILL has the `task_pending` fact.
This is a "Phantom Repro Task" - a task that exists in the logic kernel but has no backing struct in the campaign file. The orchestrator will likely panic when it queries Mangle, gets the ID, and then fails to find the corresponding Go struct.

## Extended Edge Cases: The Adversarial LLM

Given that codeNERD executes code and prompts generated by LLMs, we must consider the LLM as a semi-adversarial actor that can generate pathological inputs.

### 1. The Regex Bomb Error String
An LLM might generate code that intentionally throws an error containing a ReDoS (Regular Expression Denial of Service) payload. If `classifyTaskError` uses regex to match error strings against known buckets, a carefully crafted error string could cause the orchestrator to lock up, consuming 100% CPU on a single goroutine while holding the `o.mu` lock, completely freezing the campaign.
*Mitigation Strategy:* Error classification must use strict bounded string matching or timeout-protected regex execution. The tests currently lack ReDoS payloads.

### 2. The Mangle Injection Attack
If the error string from a delegated task is directly interpolated into a Mangle query or assertion without proper sanitization (e.g., `o.kernel.Assert(task_error(ID, /logic, "${err.Error()}"))`), an LLM could generate an error string that breaks out of the string literal and injects new facts.
Example Error String: `")) . permitted(/exec_cmd, "rm -rf /") . fake_fact("hello`
This could fundamentally compromise the safety constitution of the kernel.
*Test Gap:* We must write explicit tests that pass Mangle syntax payloads into `handleTaskFailure` and verify they are safely escaped.

### 3. The Infinite Transient Loop
The orchestrator distinguishes between `/logic` (escalate to repro) and `/transient` (retry). An LLM could identify the pattern for transient errors (e.g., "network timeout") and intentionally generate tasks that always yield that specific error string. The orchestrator would endlessly retry the task, never escalating it, effectively creating an infinite loop that wastes API credits and compute cycles.
*Test Gap:* There should be a hard limit on `/transient` retries before they are either escalated to `/logic` or permanently failed. The test suite needs to verify this boundary condition.

## Deep Dive: Timestamp Precision and the Y2K38 Problem
Mangle's numeric capabilities are often optimized for typical use cases. Go's `time.Time` has nanosecond precision and can represent dates far into the future.
When calculating `task_retry_at`, the backoff calculation might yield a time in the year 2050. If this is converted to Unix Nanoseconds (an `int64`), does the Mangle SQLite backend support it?

SQLite integers are signed 64-bit, so nanoseconds since epoch will wrap around in the year 2262. This seems safe.
However, what if the backoff logic has an integer overflow bug?
`waitDuration = base * (2 ^ attempt)`
If `attempt` is 60, `2^60` is massive. Multiplying by a base of `time.Second` (1,000,000,000) will immediately overflow the 64-bit signed integer `time.Duration`, resulting in a negative duration.
When `time.Now().Add(negativeDuration)` is executed, the `task_retry_at` timestamp will be in the past. The orchestrator scheduler will see this and immediately schedule the task again.
This turns the intended exponential backoff into a high-frequency polling loop, hammering the execution engine and filling up the disk with journal entries.
*Test Requirement:* The tests MUST explicitly set `attempt` to `65` and `base` to `math.MaxInt64` to verify the overflow is caught and capped at `MaxBackoff`.

## The Mangle Execution Environment: Memory Limits

The orchestrator spawns repro tasks to debug logic failures. These repro tasks are delegated to sub-agents.
What happens if the sub-agent gets caught in a loop, continually appending massive text blocks to its context?
Eventually, the task fails with an Out Of Memory (OOM) error or context deadline exceeded.
When this failure propagates back to `handleTaskFailure`, the error string might contain the entire 50MB context that caused the OOM.
The orchestrator attempts to assert this 50MB string into the Mangle kernel: `task_error(ID, /logic, "50MB string...")`.
SQLite has a default limit of 1GB per string, but storing a 50MB string for a single fact will blow up the `.nerd` directory size rapidly. If a campaign has 1000 such failures, that's 50GB of disk space.
Furthermore, parsing a 50MB string into a Mangle AST in memory will cause massive garbage collection pauses in the Go runtime.
*Test Requirement:* We need a test that passes a 100MB string to `handleTaskFailure` and verifies that the error string is gracefully truncated (e.g., to 10KB) BEFORE it is asserted to the Mangle kernel.

### Architectural Deep Dive: The Role of Mangle in codeNERD

To fully understand the failure vectors, we must delve into why codeNERD uses Mangle. Mangle is not just a query language; it's a Datalog dialect with stratified negation and aggregation. This means it evaluates rules iteratively until a fixpoint is reached.

#### Stratified Negation and Escalation

In the orchestrator, failure escalation relies on the absence of a successful retry. This is classic stratified negation:
`escalate(Task) :- failed(Task), not(succeeded(Task)).`

The orchestrator Go code asserts `failed(Task)` into the kernel. If a subsequent retry succeeds, it asserts `succeeded(Task)`. The Mangle engine computes the difference.
The critical vulnerability here is the temporal nature of facts. If the `failed` fact is asserted, but the orchestrator crashes before the retry logic can assert `succeeded`, the system reboots into a state where Mangle believes the task has irrevocably failed.

#### Aggregation and Retry Limits

Mangle also supports aggregation, such as counting the number of attempts.
`retry_count(Task, C) :- C = fn:count(attempt(Task, _)).`

If `C` exceeds `config.MaxRetries`, the rule triggers a hard failure.
The boundary condition testing must explicitly target the synchronization between Go's `len(task.Attempts)` and Mangle's `fn:count(attempt(Task, _))`.
If the Go slice and the Mangle fact store diverge (e.g., due to a failed assertion that wasn't rolled back in Go memory), the system enters a split-brain state. The Go orchestrator might think it has 2 retries left, while Mangle triggers a hard failure rule because it counted differently based on a previous session's residual facts.

### Extreme Edge Case Vector Analysis

#### 1. The "Ghost Fact" Injection
When a sub-agent executes a task, it might generate Mangle facts as part of its output. If these facts are not properly sandboxed and are mistakenly loaded into the kernel's global state by the orchestrator, a malicious or hallucinating sub-agent could inject a "Ghost Fact".
Example: A sub-agent tasked with writing a test injects `admin_override("subagent_id")`.
If the orchestrator doesn't meticulously scrub the fact context of task returns, this ghost fact becomes part of the kernel's reality, bypassing security gates like the `permitted(Action)` rules defined in `README.md`.
*Test Gap:* The test suite must simulate a task returning adversarial facts and verify that `handleTaskFailure` and `handleTaskSuccess` strictly filter the namespace of asserted facts.

#### 2. The Resource Exhaustion Attack via Infinite Derivation
Mangle rules must be stratified to prevent infinite loops. However, an adversarial error string or a malformed task artifact might trigger a complex chain of rules that, while technically stratified, involves joining massive intermediate relations.
If `handleTaskFailure` asserts a fact that triggers such a rule, the Mangle engine (running in the same Go process) will consume all available CPU and RAM trying to compute the fixpoint.
*Test Gap:* We must introduce a Chaos Monkey test that asserts specifically crafted facts known to trigger heavy joins and verify that the kernel execution has a hard timeout and memory limit configured and enforced.

#### 3. The Disk-Space Denial of Service
SQLite is used to persist the Mangle facts. If a campaign is intentionally designed by an LLM to fail repeatedly in unique ways (e.g., by dynamically generating unique task IDs for every retry), `handleTaskFailure` will assert a new fact for every failure.
Over a long-running "weeks" session, this could result in millions of rows in the SQLite database, eventually exhausting disk space or exceeding the SQLite max DB size.
*Test Gap:* The test suite needs to simulate 10,000 unique task failures and measure the SQLite DB growth rate. It must verify that a fact-retirement or compaction policy exists and is triggered under pressure.

#### 4. The Concurrent Write Lock Starvation
SQLite operates with file-level or table-level locks. If the orchestrator is running highly concurrent tasks (e.g., 50 sub-agents in parallel), and they all fail simultaneously (perhaps due to a network outage hitting the LLM provider), all 50 goroutines will enter `handleTaskFailure` and attempt to call `o.kernel.Assert`.
If `Assert` blocks on the SQLite write lock, the entire orchestrator grinds to a halt. The `o.mu` sync.Mutex in the Go struct exacerbates this.
*Test Gap:* We must write a benchmark test that triggers 100 concurrent task failures and ensures that the lock contention does not cause the orchestrator's internal heartbeat or context deadline to expire.

### Mangle Integration Specifics

The integration between the imperative Go orchestrator and the declarative Mangle kernel is the most delicate seam in the architecture.

#### Fact Lifecycle Management
When does a fact expire? In a procedural system, a variable goes out of scope. In a Datalog kernel, a fact is true until retracted or until the session ends (if it's a transient fact).
The orchestrator's `handleTaskFailure` does not seem to retract older attempts. It just keeps appending `task_error` facts.
If a task is retried 5 times and finally succeeds, the 5 `task_error` facts remain in the database forever. While this is good for auditing, it slows down every subsequent join that involves the `task_error` relation.
*Recommendation:* Implement a fact-tiering system. Move detailed attempt data to a cold-storage relation (`task_error_history`) and keep only the active state in the hot kernel.

#### The `parse.Parse` Concurrency Bottleneck
As noted in `agents.md`, `mangle-go/parse.Unit` is not concurrency-safe. All production parsing must go through `parse_lock.go`.
If `handleTaskFailure` dynamically constructs a Mangle string to assert (e.g., formatting an error message into a fact string) and then calls `Parse` to convert it to an AST before asserting, it hits this global parse lock.
This means error handling across all concurrent tasks is serialized at the parser level, regardless of SQLite locking.
*Test Gap:* Verify that `handleTaskFailure` uses pre-compiled AST nodes (e.g., `ast.Atom(/logic)`) instead of string parsing to construct its facts, avoiding the `parse_lock` bottleneck entirely.

### Verification of the North Star
The README states: "The invariant: the agent's own status report must be worthless as a claim and valuable only as a citation. If it says a thing is done, there is a derivation showing it."

Does `handleTaskFailure` uphold this?
When a task fails, it asserts a fact. This is good. It's a citation.
However, when a task fails due to a *timeout*, how is that recorded? The error is `context.DeadlineExceeded`. The orchestrator records it. But what is the *evidence* of the timeout? There is no external witness to a lack of action.
This represents a philosophical gap in the North Star invariant. We can provide derivation for actions taken, but we cannot easily provide derivation for actions *not* taken within a timeframe, other than the orchestrator's own internal clock claim.
*Actionable Testable Item:* Ensure that timeout failures record the specific start and end timestamps in the Mangle fact, allowing a retrospective query to verify the duration mathematically, rather than just trusting the `/transient` label.

### Additional Thoughts on Testing the Orchestrator

The `orchestrator_failure_test.go` file relies heavily on unit tests with mocked kernels. While useful for rapid feedback, unit tests cannot catch the integration bugs that plague complex systems.

*   **Mock Kernel Limitations:** The `mockKernel` used in the tests likely uses an in-memory map to store facts. It does not enforce schema validation, type constraints, or SQLite locking semantics. A test that passes against the mock kernel might fail against the real SQLite-backed kernel due to a schema mismatch (the Atom vs String issue).
*   **Need for Integration Tests:** We desperately need end-to-end integration tests that spin up a real SQLite database, initialize the full Mangle schema, run the orchestrator, and then query the database to verify the facts.
*   **Property-Based Testing:** Given the massive state space of a multi-phase campaign with retries, property-based testing (using tools like `testing/quick` or `gopter`) would be highly effective. We could generate random sequences of task successes, transient failures, and logic failures, and assert invariants (e.g., "A phase never completes if any task has an active logic failure").

By addressing these architectural and testing gaps, we can harden the codeNERD orchestrator to survive the rigors of long-term autonomous execution.

### Deep Dive: Testing State Conflicts in `saveCampaign`

The `saveCampaign` function is the persistence bottleneck of the orchestrator. Let's analyze the edge cases required to thoroughly test this function, especially under concurrent mutation and failure scenarios.

#### The "Disk Full" Interruption
If `saveCampaign` attempts to write the `Campaign` struct to disk as JSON but the disk is full, the write operation will return an `ENOSPC` error.
However, what happens if the write was partially successful before the disk filled up? Does codeNERD use atomic writes (e.g., writing to a temporary file and then renaming)?
If it doesn't use atomic writes, a crash immediately after the `ENOSPC` error will leave the campaign file corrupted.
*Test Gap:* A test must mock the file system to intentionally fail mid-write and verify that the original campaign file is untouched, proving the write was atomic.

#### The Concurrent `AbortCampaign` Race
While `handleTaskFailure` is running, a user might send an abort signal, invoking `AbortCampaign`.
If `AbortCampaign` locks the orchestrator, mutates the campaign state to "ABORTED", and unlocks, it might interleave with `handleTaskFailure`.
If `handleTaskFailure` then calls `saveCampaign`, does it save the "ABORTED" state, or does it overwrite it with an older state it held in local variables?
*Test Gap:* Introduce a test that spawns a goroutine calling `AbortCampaign` with high frequency while another goroutine calls `handleTaskFailure`. The final state persisted to disk must be strictly deterministic and uncorrupted.

### Exploring the Boundary of Task ID Generation

Task IDs are the primary key linking the in-memory Go structs to the Mangle datalog facts. The integrity of these IDs is paramount.

#### The UUID Collision
While mathematically improbable, what happens if the Task ID generator (e.g., UUIDv4) produces a collision?
If a repro task is spawned with an ID that already exists in the phase, the in-memory struct will have two tasks with the same ID.
When `handleTaskFailure` queries the kernel for `task_pending(ID)`, it will get confused. The join might return two results, or the Go code might panic when expecting a single result.
*Test Gap:* Inject a deterministic mock ID generator that intentionally produces collisions and ensure the orchestrator rejects the new task creation with a specific error rather than corrupting the datalog store.

#### The Invalid Character Payload
If an ID contains characters that have special meaning in Datalog (e.g., quotes, slashes, or periods), and the ID is not properly sanitized before being passed to `ast.Name()`, the Mangle kernel will fail to parse it.
*Test Gap:* Generate an ID like `Task"ID/With.Bad,Chars` and pass it through the orchestrator's lifecycle. Ensure that all Mangle assertions safely escape these characters.

### Evaluating the 'Run for Weeks' Requirement

The North Star goal is for the agent to run unattended for weeks. This requires extreme memory discipline.

#### The Go Garbage Collector and Mangle AST
Every time the orchestrator asserts a fact, it creates Mangle AST nodes. If these nodes are not properly garbage collected (e.g., because the `mockKernel` or the real SQLite driver retains pointers to them in a cache), the agent will suffer a slow memory leak.
*Test Gap:* Run a continuous loop of `handleTaskFailure` 1,000,000 times in a test and monitor the `runtime.MemStats`. The heap profile must not show an unbounded growth of `ast.Node` objects.

#### The Goroutine Leak on Context Cancellation
When a task fails with `context.Canceled`, the orchestrator cleans up. But what if the task spawned background goroutines (e.g., for logging or metric collection) that don't respect the context?
Over weeks, these leaked goroutines will accumulate, eventually causing the runtime to crash with "too many concurrent operations".
*Test Gap:* Use `goleak.VerifyNone` in the test suite to ensure that after `handleTaskFailure` returns, absolutely no unexpected goroutines are left running.

### Architectural Recommendation: Separation of Concerns

Currently, `orchestrator_failure.go` mixes three distinct responsibilities:
1. Business Logic: Deciding whether to retry or escalate based on error types and history.
2. State Mutation: Appending items to Go slices and updating timestamps.
3. Persistence: Calling `o.kernel.Assert` and `o.saveCampaign`.

This tight coupling makes testing difficult because unit tests must mock both the datalog kernel and the file system.
By refactoring this module to use the Command Pattern, `handleTaskFailure` could simply return a list of `StateMutations` (e.g., `AddFact(task_error)`, `AppendTask(reproTask)`).
A separate, heavily tested `TransactionExecutor` could then apply these mutations atomically to both the Go struct and the Mangle kernel.
This would eliminate the split-brain state desynchronization issues discussed earlier and make the unit tests significantly faster and more reliable, fulfilling the core requirements of high-leverage QA engineering.

### Final Verification Checks
1. Ensure all `ast.Name` calls use the correct namespace.
2. Validate that `time.Duration` calculations cannot overflow into negative values.
3. Confirm that empty string inputs to `classifyTaskError` default safely.
4. Verify that `saveCampaign` uses a `.tmp` file and `os.Rename` for atomic writes on POSIX systems.
5. Check that all SQLite connections are properly pooled and closed to prevent file descriptor leaks over the multi-week runtime.

This comprehensive QA analysis provides a roadmap for securing the orchestrator against the most dangerous failure modes in the codeNERD architecture.

*Recommendation:* Replace all `time.Sleep` calls with deterministic synchronization primitives like `sync.WaitGroup` or channels. Line coverage is a misleading metric in a Datalog-backed system. A test might execute the line `o.kernel.Assert(task_error(...))` but fail to actually verify that the fact exists in the kernel afterwards.
*Recommendation:* Implement "Fact Coverage". Ensure that for every `Assert` call in the production code, there is a corresponding `Query` in the test suite that verifies the exact shape and content of the inserted fact.
