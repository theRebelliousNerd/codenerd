# QA Boundary Value Analysis & Edge Case Evaluation
## Subsystem: internal/tools (Registry & Tool Execution Framework)
**Date/Time (EST):** 2026-09-08 00:22:57 EDT

### 1. Executive Summary & Subsystem Selection
For this deep-dive boundary value analysis (BVA) and negative testing evaluation, I selected the `internal/tools` subsystem, specifically focusing on `registry.go` and `registry_boundary_test.go`. The tool registry is a critical juncture in the codeNERD architecture: it acts as the capability envelope (allowlists) and the execution boundary for all LLM-driven actions (shell commands, file reads/writes, code AST operations). Because codeNERD explicitly bounds agents through Mangle policies and execution guards, a failure in the registry's input validation or boundary handling could lead to unauthorized tool execution, sandbox escapes, or systemic panics affecting the deterministic executive.

My review of `registry_boundary_test.go` and `registry.go` reveals that while the baseline "Happy Path" and immediate nil-checks are well-handled (e.g., `TestRegistry_RegisterNilTool`, `TestRegistry_ExecuteNilContext`), the test suite lacks rigorous negative testing against state conflicts, extreme user inputs, edge-case type coercions, and race conditions during rapid registry mutation.

### 2. Missing Boundary Values & Edge Case Vectors

#### 2.1 Null/Undefined/Empty Vectors
- **Empty Map vs. Nil Args Execution**: The test `TestRegistry_Execute_NilArgs` verifies that `nil` args do not panic. However, it does not distinguish between `nil` and an initialized but empty map (`make(map[string]any)`), nor does it test how tools with no required schema but optional properties handle `nil` inputs when defaults are expected.
- **Empty Tool Name on Execute**: `Execute(ctx, "", args)` is not explicitly tested for boundary rejection in `registry_boundary_test.go`. While the safety checker in the session executor handles empty names, the registry itself must defensively reject empty tool strings before attempting map lookups.
- **Null Values Inside Valid Arg Maps**: What happens if a tool expects a string property (e.g., `"message"`) and receives a valid map structure but the value itself is explicitly Go `nil` (`map[string]any{"message": nil}`)? The type mismatch test only checks `int` vs `string`, but `nil` interface values can cause panics in unboxing logic if not handled by `validateArgs`.

#### 2.2 Type Coercion & Schema Violations
- **Array/Slice vs String Coercion**: The `validateArgs` method checks basic types (string, int). However, what if a user requests a tool that expects a string but passes a slice of strings or a slice of bytes? A frontend passing JSON `["arg1"]` instead of `"arg1"` might panic the type assertion logic (`v.(string)`).
- **Float to Int Coercion**: If a tool expects an `integer` but the JSON unmarshaler (often generating `map[string]any`) provides a `float64` (e.g., `42.0`), does `validateArgs` strictly reject it, or does it coerce it safely? Given the `float64` default for JSON numbers in Go, strict type checking might falsely reject valid integers, or loose checking might allow fractional values into integer-only tools.
- **Nested Schema Boundary**: Tools with complex nested arguments (e.g., JSON objects passed as strings vs nested maps). The type mismatch test only tests a flat structure.

#### 2.3 User Request Extremes & Performance
- **Extreme Payload Sizes (The Monorepo Edge Case)**: While the session executor limits payload size, if a direct programmatic caller (or an unrestrained agent in a different harness) passes a map containing a 1GB string into `Execute`, does the registry's logging, metrics collection, or fact sink serialization buffer overflow or block indefinitely?
- **Massive Tool Registration (Registry Bloat)**: If an agent dynamically registers 10,000 tools with long names, does `GetByCategory` or `FilterByIntent` degrade in performance to the point of causing timeouts in the deterministic executive loop?
- **Invalid UTF-8 Boundaries**: Passing malformed UTF-8 byte sequences masquerading as strings into tool arguments. If the tool writes this to the Mangle fact store or standard output, does it break JSON encoding downstream?

#### 2.4 State Conflicts & Concurrency Vectors
- **Race Condition on Registry Mutation**: The `Registry` struct uses a `sync.RWMutex` (`r.mu`). However, are there tests proving that 100 goroutines concurrently calling `Register()`, `Execute()`, and `SetAllowlist()` do not cause a deadlock or a dirty read where a tool is executed while its capabilities are being restricted?
- **Double Registration Conflict**: What happens if `Register` is called twice with the exact same tool name but different implementations? `Register` says it returns an error, but is there a negative test confirming the original tool remains intact and the second is rejected cleanly without corrupting the `byCategory` index?
- **Execution During Allowlist Mutation**: If `SetAllowlist` is called mid-execution of a long-running tool, does the tool's execution halt, or does it finish? The registry boundary should clearly define the state of inflight tools during policy changes.

### 3. Performance & System Resilience Evaluation
The `internal/tools/registry.go` system utilizes `sync.RWMutex` which provides excellent read performance for `Execute` and `GetByCategory`.
However, for the identified edge cases:
- **Type Coercion**: The current reflection/type-assertion based validation is performant enough to handle standard volumes, but might struggle under the "50 million line monorepo" edge case if deep validation of massive nested JSON maps is attempted on every tool call.
- **Concurrency**: The registry should easily handle the state conflict edge cases provided the RWMutex is correctly held during map writes and index updates. However, the lack of explicit concurrent mutation tests leaves a gap in proving this resilience.
- **Extreme Inputs**: The registry itself is lightweight, but the connected `FactSink` and `WriteGuard` could become bottlenecks if they synchronously process extreme payloads blockingly.

To harden this subsystem, I will inject TODO comments into `internal/tools/registry_boundary_test.go` outlining the implementation of these missing negative tests. This aligns with CodeNERD's rigorous standard for boundary value analysis, ensuring the execution envelope remains deterministic and safe under adversarial or extreme loads.
