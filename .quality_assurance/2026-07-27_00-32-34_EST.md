## Subsystem: internal/session (Executor & Tool Execution Safety Gate)

### 1. Executive Summary & Audit Objective
This journal entry documents a comprehensive, deep-dive Boundary Value Analysis (BVA) and Negative Testing audit of the `internal/session` subsystem within the codeNERD architecture. Specifically, the analysis targets the clean execution loop and its interaction with the `checkSafety` gate (`executor_tools.go`), which verifies ToolCalls against the Mangle-based Constitutional Gate.

The primary objective of this audit is to move beyond "Happy Path" testing to identify structural vulnerabilities, edge cases, and concurrency gaps that could manifest under adversarial conditions, malformed AI responses, or extreme system load. The findings are evaluated against four primary vectors:
1. Null/Undefined/Empty inputs
2. Type Coercion anomalies
3. User Request Extremes
4. State Conflicts

This audit is critical because the `internal/session` subsystem acts as the final arbiter before an AI agent is permitted to execute potentially destructive actions on the host machine. If a boundary value can bypass the safety gate, the entire sandboxing model is compromised.

### 2. CodeNERD & Mangle Architecture Context
Before delving into the specific subsystem, it is essential to ground this analysis in the broader architectural paradigms of codeNERD and its reliance on Mangle.

Mangle is a declarative, logic programming language (distinct from standard Datalog) utilized heavily within codeNERD for schema validation, capability routing, and safety assertions (the Constitutional Gate). The engine relies on monotonic, stateful evaluation to derive facts until it reaches a fixpoint.

In codeNERD's `internal/session` package, the "JIT Clean Loop" replaces the older, deprecated shard-based architecture (which relied on domain shards like coder, tester, etc.). The `Executor` acts as the unified orchestrator, utilizing JIT-compiled prompts and configurations to govern the AI agent. The LLM (acting as the creative center) generates responses, often containing tool requests. These requests must pass through the `checkSafety` gate, which converts the tool execution intent into Mangle facts (e.g., `pending_action`) and asserts them against the `types.Kernel` (the Mangle fact store).

If the Mangle evaluation derives a `permitted` fact based on the current context and policies, the tool is allowed. If not, it is blocked. This mechanism is highly sensitive to the exact structural composition of the facts being asserted. A discrepancy between the Go representation (e.g., `types.MangleAtom`) and the Mangle string evaluation can result in silent failures, often manifesting as an empty result set (meaning the tool is denied). Therefore, the boundaries of how Go data structures translate into Mangle facts via the `Executor` are critical risk areas.

### 3. Subsystem Selection: `internal/session` Executor and Tool Gate
The `internal/session` module, specifically `executor_tools.go` and its associated tests in `executor_boundary_test.go`, was selected for this audit due to its high material impact on system safety and its role as a choke point for all AI-driven actions. The `checkSafety` function serves as the ultimate Constitutional Gate.

The function takes a `ToolCall` struct, which contains an `ID`, a `Name` (representing the tool/action), and `Args` (a map of key-value pairs representing the JSON payload generated by the LLM). It normalizes these inputs, extracts a "target" string using the `extractTarget` helper, marshals the arguments into JSON bytes, and asserts a `pending_action` fact to the Mangle Kernel. It then queries the Kernel for a corresponding `permitted` fact.

While the existing `executor_boundary_test.go` provides coverage for several negative scenarios (e.g., oversized payloads, empty tool names, nil configs), a rigorous BVA reveals several subtle gaps that could bypass safety checks, cause panics, or corrupt the Mangle state over prolonged sessions.

### 4. Boundary Value Vector: Null / Undefined / Empty
The handling of missing or zero-value inputs is a classic source of runtime panics and logic errors. In the context of `checkSafety`, the inputs are primarily AI-generated JSON payloads, which are notoriously unpredictable, especially from smaller or faster LLMs.

**Gap 4.1: `extractTarget` with Nil Values in Candidate Keys**
The `extractTarget` function iterates through a hardcoded list of candidate keys (e.g., "path", "filename", "url") to identify the primary target of an action.
```go
func (e *Executor) extractTarget(args map[string]any) string {
	candidates := []string{"path", "filename", "filepath", "file", "url", "target", "query", "pattern", "glob", "dir", "directory"}
	for _, key := range candidates {
		if val, ok := args[key]; ok {
			return types.ExtractString(val)
		}
	}
	return "unknown"
}
```
*Vulnerability Analysis:* If the AI generates a payload where a candidate key exists but its value is explicitly `null` (which unmarshals to `nil` in Go's `map[string]any`), `args[key]` will yield `nil`, and the `ok` boolean will be `true`. The code then calls `types.ExtractString(nil)`.
Looking at `internal/types/extract.go`:
```go
	case nil:
		return ""
```
`ExtractString(nil)` returns an empty string `""`. Consequently, the extracted target becomes `""`, which is then asserted into the Mangle kernel as the target atom. An empty string might evade Mangle policies designed to block specific paths (e.g., policies blocking `/etc/shadow` will not match `""`), and policies requiring a valid atom may fail to evaluate entirely, leading to unexpected fail-open or silent fail-closed scenarios depending on the rule structure.
*Remediation & Testing Strategy:* Add boundary tests where the target key is present but `nil`, verifying the fallback behavior explicitly coerces it to `"unknown"` instead of returning an empty string. The test should assert that the resulting fact in the mock kernel contains "unknown".

**Gap 4.2: Deeply Nested Empty Structures**
The safety gate marshals `call.Args` into JSON to form the `payload` argument for the Mangle fact. While `call.Args = map[string]any{}` normalizes a completely missing argument object to `{}`, it does not handle deeply nested empty objects or arrays (e.g., `{"path": "foo", "options": {}}` or `{"files": []}`).
*Vulnerability Analysis:* Mangle's JSON parsing or subsequent fact matching might have specific limits or unexpected behaviors when encountering empty nested structures. If a policy checks for the absence of a key, but the key exists with an empty structure, the policy might incorrectly evaluate to false. The Go tests currently only verify `nil` args at the top level. We must test the boundary of nested empty slices and maps.
*Remediation & Testing Strategy:* Construct a `ToolCall` with `Args` containing `map[string]any{"config": map[string]any{}}` and verify that the safety gate correctly processes and asserts this without panicking, and that a corresponding Mangle policy can correctly pattern match against it.

**Gap 4.3: Empty Slices in Tool Outputs**
While this audit focuses on `checkSafety`, the flip side is handling tool outputs. If a tool returns an empty slice (e.g., a search command finding no results), JSON marshaling might output `null` (if the slice was uninitialized) or `[]` (if it was initialized but empty).
*Vulnerability Analysis:* This difference can cause brittle tests and inconsistent Mangle evaluations if policies attempt to parse tool outputs. As noted in the memory banks, tests should assert structural state (`len(slice) == 0`) rather than brittle string matching. In the context of `checkSafety`, if the LLM passes an uninitialized slice, it will be marshaled to `null`.
*Remediation & Testing Strategy:* Test boundary conditions where AI provides `{"files": null}` versus `{"files": []}`.

### 5. Boundary Value Vector: Type Coercion
Type coercion issues arise when the dynamic, schema-less nature of JSON intersects with the static typing of Go and the rigid, schema-bound atom/string distinction in Mangle. This is the most frequent cause of "Atom/String Dissonance" AI failure modes.

**Gap 5.1: Non-Primitive Targets in `extractTarget` causing Malformed Atoms**
As observed in `extractTarget`, if a candidate key exists, its value is passed to `types.ExtractString`. What happens if the AI incorrectly provides an array or an object for the "path" key? (e.g., `{"path": ["/etc/passwd", "/etc/shadow"]}`).
In `types/extract.go`:
```go
	default:
		return fmt.Sprintf("%v", v)
```
If `v` is a slice `[]interface{}`, `ExtractString` falls through to the default case and returns something like `[ /etc/passwd /etc/shadow ]`.
*Vulnerability Analysis:* The resulting string is highly irregular and does not conform to expected path formats or valid Mangle atom structures. When this malformed string is asserted into the Mangle kernel as a target, it will almost certainly fail to match any `permitted` rules, resulting in a denial. While this is a "safe" failure (it fails closed), it pollutes the Mangle fact store with malformed string representations of Go memory structures, potentially causing downstream issues for audit rules, log analyzers, or fact serialization that expect valid paths or atoms.
*Remediation & Testing Strategy:* Implement negative tests that pass complex structures (slices, nested maps) to candidate target keys. Verify that `extractTarget` either gracefully handles them by returning "unknown" or that `checkSafety` rejects the tool call outright before asserting the garbage data to the kernel.

**Gap 5.2: Float/Int Coercion Boundary in Go JSON Unmarshaling**
If a target is meant to be numeric (e.g., a port number in a network tool, or a line number in `sed`), JSON unmarshaling into Go's `any` defaults to `float64`. `types.ExtractString` handles this:
```go
	case float64:
		return fmt.Sprintf("%g", v)
```
*Vulnerability Analysis:* Formatting differences (e.g., `1.0` vs `1`) can cause Mangle join failures. Mangle treats numeric types very strictly. If the AI fluctuates between integer strings (e.g., `"1"`) and actual integers (e.g., `1`), the boundary between Go's coercion and Mangle's type strictness is tested. Furthermore, what if the AI passes extremely large floats (Infinity, NaN, which standard `json.Marshal` rejects, but custom unmarshalers might allow)?
*Remediation & Testing Strategy:* Provide boundary values like floating-point representations of integers (`1.0`), very large integers exceeding int32 bounds, and verify that `checkSafety` normalizes them consistently before asserting to Mangle.

**Gap 5.3: Boolean Coercion**
`types.ExtractString` coerces booleans to Mangle atoms:
```go
	case bool:
		if v {
			return "/true"
		}
		return "/false"
```
*Vulnerability Analysis:* If a target key happens to hold a boolean value (e.g., the AI hallucinated the argument structure and passed `{"target": true}`), the target becomes the atom `/true`. This is technically valid, but semantically meaningless. The test suite lacks coverage for boolean coercion within the safety gate's target extraction logic.
*Remediation & Testing Strategy:* Ensure tests exist that simulate this AI hallucination and verify `checkSafety` behavior.

**Gap 5.4: Stringly Typed Assertions in Tests**
As highlighted by memory, test logic must avoid stringly typed assertions when comparing results. We need to assert set membership of facts, not string matching, as datalog sets are unordered. The boundary here is where test expectations diverge from engine output formats under load.

### 6. Boundary Value Vector: User Request Extremes
The codeNERD system must remain resilient under extreme edge cases, often orchestrated by adversarial inputs or "frontier coding benchmark" level requests. These scenarios push memory, execution time, and logic evaluation bounds to their limits.

**Gap 6.1: Massive Single Target Strings causing Index Blowup**
The `checkSafety` function guards against massive total payloads:
```go
	if len(payloadBytes) > maxPayloadBytes {
        // deny ...
    }
```
However, the `target` string (extracted via `extractTarget`) is passed *separately* as an argument to the `pending_action` fact, alongside the payload string.
*Vulnerability Analysis:* If the AI generates an extremely long string specifically for the "path" key (e.g., a 90KB string containing garbage or a buffer overflow attempt), the overall JSON payload might be just under `maxPayloadBytes` (e.g., limit is 100KB). Thus, it passes the size check. But then this 90KB string is also passed as the `target` atom directly to `e.kernel.Assert`.
Mangle's internal fact indexing and unification algorithms might struggle with massive atom names or string arguments, potentially leading to Out-Of-Memory (OOM) errors or severe latency spikes during the fixpoint evaluation in `kernel.Query`.
*Remediation & Testing Strategy:* Create a negative test where the target string alone approaches the `maxPayloadBytes` limit, validating that the Mangle engine can handle massive atom values without performance degradation. Alternatively, implement a separate, much smaller length limit for the `target` string (e.g., 4096 bytes) before assertion.

**Gap 6.2: High-Frequency Tool Call Boundaries (The "50 Million Line Monorepo" Scenario)**
In a scenario where an AI is requested to process a massive monorepo from a resource-constrained environment (e.g., an 8GB RAM laptop), it might attempt to generate a massive array of concurrent or sequential tool calls (e.g., running `grep` 10,000 times).
*Vulnerability Analysis:* If 10,000 tool calls are sent through `checkSafety` in rapid succession within a single session turn, the repeated `json.Marshal`, string manipulation, and Mangle assertions will cause massive garbage collection pressure. More importantly, it tests the limits of Mangle's Extensional Database (EDB) growth within a single transaction. Asserting and retracting thousands of facts linearly will likely degrade evaluation performance exponentially.
*Remediation & Testing Strategy:* Implement a stress test that fires 10,000 consecutive `checkSafety` calls with varying, valid payloads, monitoring memory allocation and the execution time of `kernel.Query`. Ensure it operates within acceptable latency bounds (e.g., <5ms per check).

**Gap 6.3: Malicious Regex/Glob Patterns in Target**
Tools like `grep` or search functionalities often take glob or regex patterns. If these patterns are extracted as the "target", they are passed to Mangle.
*Vulnerability Analysis:* While Mangle strings are generally safe from standard injection, if Mangle policies utilize internal regex matching functions (e.g., `fn:match(Target, ".*")`), a maliciously crafted regex target (ReDoS) could cause the evaluation engine to hang indefinitely, resulting in a denial-of-service.
*Remediation & Testing Strategy:* Test `checkSafety` with target strings containing extreme ReDoS payloads (e.g., `((a+)+)+b`) to ensure the underlying Mangle evaluation times out gracefully rather than blocking the executor forever.

**Gap 6.4: Extremely Deep Nesting (Stack Overflow Risk)**
If the LLM provides JSON that is 500 levels deep, marshaling and unmarshaling can cause stack overflows.
*Remediation & Testing Strategy:* Add boundary tests verifying the system handles excessively deep JSON structures correctly and rejects them safely.

### 7. Boundary Value Vector: State Conflicts & Concurrency
The most critical vulnerabilities identified in this audit revolve around state conflicts and race conditions. The `Executor` is designed to be thread-safe, evidenced by the presence of `mu sync.RWMutex` on the struct definition.

**Gap 7.1: Unsynchronized Reads in `checkSafety`**
In `executor_tools.go`, the `checkSafety` function accesses internal state:
```go
func (e *Executor) checkSafety(call ToolCall) bool {
    // ...
	if e.kernel == nil {
		if e.config.EnableSafetyGate {
			// fail closed
			return false
		}
		return true // Gate disabled: allow
	}
    // ...
}
```
*Vulnerability Analysis:* The function reads `e.config.EnableSafetyGate` and `e.kernel` WITHOUT acquiring the read lock (`e.mu.RLock()`). Concurrently, the `Executor` provides configuration setters in `executor.go`:
```go
func (e *Executor) SetConfig(cfg ExecutorConfig) {
	e.mu.Lock()
	defer e.mu.Unlock()
	e.config = cfg
}
```
If a background process, a live-reloading configuration manager, or a concurrent subagent invokes `SetConfig` or updates the kernel while `checkSafety` is executing, a data race occurs. In Go, reading and writing a struct concurrently without synchronization leads to undefined behavior. If `e.config` was a map or contained pointers, this would lead to a fatal panic (`fatal error: concurrent map read and map write`). Even with simple structs, torn reads are possible.
*Remediation & Testing Strategy:*
1. Implement `RWMutex` locking (`e.mu.RLock()`) at the beginning of `checkSafety` (or at least around the state reads) to resolve data races on `e.config` and `e.kernel`.
2. Write a concurrency test in `executor_boundary_test.go` that runs `checkSafety` in a tight loop across multiple goroutines while another goroutine repeatedly calls `SetConfig`. Run this test with the `-race` flag to guarantee detection.

**Gap 7.2: Deferred Retraction Race with Context Cancellation**
`checkSafety` asserts a fact, queries the kernel, and then defers the retraction of the asserted fact:
```go
	defer func() {
		_ = e.kernel.Retract(pendingFact)
	}()
```
*Vulnerability Analysis:* This is a classic "Forgotten Sender" or resource leak variant in the context of logic engines. If the `ctx` is violently cancelled during the `e.kernel.Query(ctx, ...)` execution (e.g., due to a timeout from an extreme user request, or the user hitting Ctrl+C), the query returns an error immediately. The `defer` block then executes. However, `Retract` itself might rely on the cancelled context internally (if the kernel implementation changes), or it might fail if the Mangle engine is left in a corrupted or inconsistent state post-cancellation. The current logic ignores the error `_ = e.kernel.Retract(...)`. If `Retract` fails, it leaves "ghost facts" in the Mangle EDB.
These ghost `pending_action` facts will pollute subsequent evaluations for the remainder of the session, potentially triggering false positives in audit rules or interfering with identical tool calls made later.
*Remediation & Testing Strategy:* As noted in memory, "Mangle’s evaluation is monotonic and stateful. Reusing a store across tests leads to ghost facts". This applies to production too!
Test this by creating a mock kernel that simulates a context cancellation timeout during `Query`, and then forces `Retract` to fail. Verify the executor's error handling and state consistency. (There is already a `TODO: TEST_GAP` in `executor_test.go` for this, but the actual test implementation is missing).

**Gap 7.3: Subagent Intent Clashing (`/current_intent`)**
While not directly in `checkSafety`, the routing logic sets `/current_intent`.
*Vulnerability Analysis:* If multiple subagents share the same kernel instance and concurrently process inputs, they might overwrite each other's `/current_intent` facts. The code comments indicate that task runs get a unique ID to prevent this (`ProcessWithIntent`), but if the interactive loop (`Process`) is called concurrently with task execution, race conditions on the global state can occur, leading to incorrect policies being evaluated in `checkSafety`.
*Remediation & Testing Strategy:* Verify subagents and root agents do not share the exact same active intent state in a multi-threaded execution.

**Gap 7.4: Race conditions during JIT context compilation**
The JIT compiler reads session state to build compilation context. If state is modified by a background task while JIT runs, the generated policy might conflict with the immediate state.

### 8. Conclusion & Actionable Next Steps
The `internal/session` executor demonstrates strong defensive programming against common "Happy Path" errors, such as massive payloads and empty tool names, correctly asserting fail-closed behaviors. However, this rigorous Boundary Value Analysis exposes significant gaps in concurrency control (unsynchronized state reads), edge-case type coercions (handling of `nil` maps, complex nested targets, and large string atoms), and state management under context cancellation.

To secure the boundary and ensure production readiness against frontier AI models, the following steps must be taken:

**Action Items for Engineering:**
1. **Concurrency Fix:** Add `e.mu.RLock()` and `e.mu.RUnlock()` to `checkSafety` to protect reads of `e.kernel` and `e.config`.
2. **Nil Pointer/Empty Value Safety:** Update `extractTarget` to explicitly check for `nil` values inside candidate keys and return `"unknown"` instead of falling through to an empty string.
3. **Payload & Target Bounds:** Implement a separate, smaller length constraint specifically for the `target` string extracted before it is cast to a Mangle Atom, preventing engine OOMs on garbage target data.
4. **Test Implementation:** Add the missing `TODO: TEST_GAP` implementations in `executor_boundary_test.go` and `executor_test.go`, specifically covering the data race condition, the massive target string, and the context cancellation/retraction failure.

### Appendix B: Methodology Notes
Boundary Value Analysis focuses on the edges of equivalence partitions. For string inputs, this means testing empty strings, strings of size 1, very large strings, and strings containing special characters or null bytes. For object inputs, it means testing nil pointers, empty objects `{}`, and deeply nested objects. Negative testing intentionally attempts to break the system by providing invalid data, triggering error paths, and orchestrating race conditions. This audit combined both techniques, specifically tailored to the unique failure modes of the Mangle logic engine integration within codeNERD.

### Appendix C: Deep Dive into Structural Vulnerabilities

The Mangle kernel interacts heavily with Go's `any` interface, meaning that JSON representations coming from the LLM can cause subtle and often dangerous behavioral differences. The following detailed analysis explores the structural vulnerabilities further:

#### 1. Dissonance in Array Representation
When an LLM provides an array, `json.Unmarshal` will return a `[]any`. If this slice is passed to Mangle as part of a fact's argument list, it must be carefully serialized. Mangle itself natively supports lists, but the translation layer between Go's `types.Kernel` and the Mangle runtime must ensure that `[]any` correctly maps to Mangle's ListType.
If the safety gate passes a raw `[]any` to `ExtractString` (as detailed in Gap 5.1), it is stringified. However, if the policy expects a list of atoms, it will fail.
*Negative Test Approach:* Feed `ToolCall` arguments containing `[]any` and verify the exact fact structure emitted to the kernel logging interface. Ensure that no internal Mangle parser panics occur.

#### 2. Dissonance in Nested Map Representation
Similar to arrays, nested objects (JSON maps) unmarshal to `map[string]any`. Mangle supports StructTypes or mapping via predicates, but directly embedding a map within a single fact argument requires careful stringification.
*Negative Test Approach:* Create a `ToolCall` with `Args` like `{"data": {"key1": "val1", "key2": ["val2"]}}`. The BVA focus here is not just that it parses, but that the resulting stringification is deterministic. Since Go map iteration is random, `fmt.Sprintf("%v", map)` produces non-deterministic string output. If a Mangle policy attempts to match this string, it will be extremely flaky.
*Remediation:* The safety gate must either sort map keys before stringification or reject complex types in target extraction.

#### 3. Control Character Injection
Can an AI inject control characters (e.g., ` `, `
`, ``) into the `ToolCall.Name` or `ToolCall.Args` to exploit the stringification process?
*Negative Test Approach:* Submit `ToolCall{Name: "read file", Args: map[string]any{"path": "/etc/passwd
"}}`.
*Expected Outcome:* The system should either sanitize these characters or the Mangle kernel should reject the malformed atom safely without causing a parser exception or log forging.

#### 4. The 'Missing Key' vs 'Nil Key' Boundary
Mangle policies often check for the existence of keys.
* Scenario A: `{"path": "/etc"}`
* Scenario B: `{"path": null}`
* Scenario C: `{}` (no path key)
The BVA must ensure that `extractTarget` and the subsequent Mangle policy evaluation treat B and C differently if required by the logic, or safely conflate them if they mean the same thing. Gap 4.1 addresses this partially, but the policy side must also be verified.

### Appendix D: Final Risk Assessment
The `internal/session` package's `Executor` and `checkSafety` components represent a robust initial defense against AI misuse. However, the identified gaps in concurrency (Gap 7.1) and complex type coercion (Gap 5.1, Appendix C) elevate the risk profile under adversarial or high-stress conditions. By implementing the suggested negative test cases and BVA remediations, the system's resilience will be significantly enhanced, aligning with codeNERD's core philosophy of secure, deterministic AI execution.

### Appendix E: Mangle Execution State Transitions
Understanding Mangle's execution state transitions is pivotal. The JIT clean loop relies on transient facts asserted during a turn. If a boundary value input corrupts the fixpoint logic (e.g., by introducing an unstratifiable rule dynamically, though unlikely via `pending_action`, or by causing a join to hang on a massive string), the state transition fails.

1. **Pre-action state:** Clean EDB.
2. **Action assertion:** `pending_action` fact introduced.
3. **Fixpoint evaluation:** Mangle computes `permitted` or `denied`.
4. **Post-action state:** Retraction of `pending_action`.

The critical boundary is ensuring step 4 ALWAYS executes, even if step 3 panics due to a malformed target atom from step 2.

### Appendix F: Cross-Subsystem Interactions
The safety gate in `internal/session` does not exist in a vacuum. It interacts with:
* **The Parser:** Which initially parses the LLM's JSON.
* **The Virtual Store:** Which might wrap the kernel or add its own validators (as seen in `InteractiveExecutiveGate`).
* **The Mangle Runtime:** Which ultimately evaluates the rules.

A boundary value failure here ripples outwards. For example, if a `nil` target becomes `""`, and a tool executes, the subsequent `ValidateInteractiveToolResult` (if enabled) might fail to match the original action context, leading to a disconnected audit trail.

### Appendix G: Future Architectural Recommendations
While this audit focuses on immediate gaps, long-term architectural improvements should include:
1. **Strong Typing for Tool Calls:** Instead of `map[string]any`, use strongly typed schema validation BEFORE passing to the safety gate, ensuring that a "path" is always a valid path string and never a slice.
2. **Deterministic Serialization:** Implement a strict, deterministic JSON serializer for payload assertions to guarantee reproducible Mangle evaluations.
3. **Dedicated Target Extraction Logic:** Refine `extractTarget` into a more robust interface that can inspect tool schemas to determine the actual target, rather than relying on a hardcoded list of heuristic keys. This would prevent false positives and type coercion issues at the root.
