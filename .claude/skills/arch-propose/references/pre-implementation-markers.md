# Pre-Implementation Honesty Rules

Every document `/arch-propose` generates must be honest that no code exists yet. These
rules are enforced in the agent prompts (synthesizer, auditor, and the slash-command's
inline governance phase).

---

## Rule 1 — IMPLEMENTED_SPEC.md §3 All-Zero Status

Every row in `IMPLEMENTED_SPEC.md` Section 3 (Implementation Status) must be marked as
not-yet-implemented. Exact template:

```markdown
## 3. Implementation Status

> **Status: Pre-Implementation — no code exists yet. Every component below is a planned target.**

| Component | Status | Completion |
|-----------|--------|------------|
| {Component 1} | Not Implemented | **0%** |
| {Component 2} | Not Implemented | **0%** |
| ... | Not Implemented | **0%** |

**Overall: 0% complete**

Unblocking dependencies (none if greenfield; list parent subsystems that must ship first if the candidate depends on them):

| Dependency | Status | Gate |
|---|---|---|
| `internal/<parent-subsystem>/<Capability>` | {Exists / Planned} | {What must be true before this feature can start} |
```

If the candidate extends an existing subsystem whose code partially exists, the relevant
rows may cite the existing code with `file:line` — but every row that represents
NEW behavior stays at 0%.

---

## Rule 2 — Document Header Status Banner

The very first block after the H1 title in `IMPLEMENTED_SPEC.md` and every foundation doc
(00–04) must include this banner:

```markdown
# {Subsystem Name} — Current Architecture Spec

> Last verified against codebase: {YYYY-MM-DD}
> Status: Living Reference Document
> **⚠ Pre-Implementation — this spec describes target state; no code exists yet. Generated by /arch-propose.**
```

The warning glyph (⚠) is literal — the skill must emit it. It makes the pre-implementation
status visible at a glance for anyone scanning the corpus.

---

## Rule 3 — 02-CURRENT-STATE Must Not Invent Code

`02-CURRENT-STATE-<FEATURE>.md` is the single highest-risk file for a greenfield corpus.
Agents must not describe behavior that doesn't exist. Template:

```markdown
# {Feature} -- Current State

> **Status: Pre-Implementation.** No `internal/<feature>/` package exists yet.
> This document inventories adjacent code the feature will build on, and names
> the planned source location.

## 1. Planned Source Location

- Primary package: `internal/<feature>/` (does not yet exist)
- Supporting packages: `internal/<adjacent>/` (exists, will gain integration points)

## 2. Adjacent Subsystems Referenced by Planned Design

| Adjacent Subsystem | Location | Relationship |
|---|---|---|
| {Name} | `internal/<name>/` | {The feature will consume / extend / be consumed by this package} |

## 3. Existing Utilities Identified by Research

(From internal scout — utilities that will be reused rather than reinvented.)

| Utility | Location | Role in planned feature |
|---|---|---|
| `{func/type}` | `internal/<pkg>/<file>.go:<line>` | {How the feature will use it} |

## 4. Current State of the Feature Itself

**None. No code has been written. All behavior described in `01-VISION-<FEATURE>.md`
and deep-dives is a target, not an observation.**
```

Agents that fabricate current-behavior claims in this doc fail the verification gate
(Phase 7 journal check flags any section 4 claim that contradicts this template).

## Rule 4 — Alignment Scores Default to 0/5

`00-ALIGNMENT-VISION-REVIEW.md` scoring:

| Score | Meaning |
|---|---|
| 0 | Not started — no code |
| 1 | Conceptual only — mentioned but no implementation |
| 2 | Partial (<50%) — some code exists |
| 3 | Majority (50–75%) |
| 4 | Substantially complete (75–95%) |
| 5 | Fully realized with tests |

For a pure-greenfield feature, all OC and UV dimensions score **0** unless the
north-star captured concrete existing baseline (e.g., partial code in sibling packages
being absorbed). When any score is non-zero, it must cite the evidence file:line the
scout found.

Weighted composite = OC 60% + UV 40% = **0%** for pure greenfield. State the zero
explicitly; do not omit the composite.

## Rule 5 — Gap Analysis Frames Target-vs-Nothing

`03-GAP-ANALYSIS-<FEATURE>.md` is an implementation roadmap for a greenfield feature,
not a code-review artifact. Structure:

```markdown
# {Feature} -- Gap Analysis

> **Status: Pre-Implementation.** Gaps are the full delta between the 01-VISION target
> and the current nonexistence of `internal/<feature>/`. This document is the
> implementation roadmap, organized for phased delivery.

## Gap Categories

Gaps are grouped by **phase dependency**, not by calendar. Each phase unlocks the next
through explicit gates.

### Phase 1 — Foundational (no dependencies)
| ID | Gap | Rationale | Gate to Phase 2 |
|---|---|---|---|
| GAP-<FEATURE>-01 | {Core type/interface missing} | {Why needed first} | {What must be true to proceed} |

### Phase 2 — Core Behavior (depends on Phase 1 gates)
...

### Phase 3 — Integration (depends on Phase 2 gates)
...
```

Do not include week/sprint/story-point estimates anywhere (per
`.claude/rules/no-time-cost-estimates.md`).

## Rule 6 — Suspend file:line Citations in Foundation Docs

`arch-writer`'s normal rule is "every claim about code must include a `file:line`
reference." For greenfield features, there is no code to cite. The `arch-propose-auditor`
emits a preamble flag in `.code-audit.md`:

```markdown
# {Feature} — Synthetic Code Audit Report

> **Synthetic audit — no source code scanned.** Generated by arch-propose-auditor
> from research dossiers. The file:line citation rule is suspended for foundation
> docs (00–04). It remains enforced for:
>   - Section 2 "Existing Utilities Identified by Research" in 02-CURRENT-STATE (real files must cite real lines)
>   - Deep-dive references to adjacent subsystems (cite real file:line for the adjacent code)
>   - Cross-cutting docs (DEPENDENCY-MAP, CROSS-SYSTEM-WIRING-JOURNAL must cite real file:line for every referenced integration point)
```

`arch-writer` is expected to honor this preamble and skip citation-enforcement for
greenfield foundation content while keeping it for adjacent-code citations.

## Rule 7 — Docs/architecture/INDEX Proposed Section

A greenfield feature never enters a Tier 1/2/3 table until real code lands. Instead, add
or update a **Proposed Subsystems** section:

```markdown
## Proposed Subsystems (Pre-Implementation)

Subsystems with full architecture corpora but no `internal/<name>/` code yet. Graduating
into a tier requires code landing and IMPLEMENTED_SPEC sections 3/4 filling in.

| Directory | Docs | Generated By | Candidate Tier (on graduation) | Notes |
|---|---|---|---|---|
| `<feature>/` | {count} | /arch-propose <date> | {1/2/3 estimate} | {one-line summary} |
```

If the Proposed section does not yet exist in `Docs/architecture/INDEX.md`, the slash command creates
it immediately before the "Incomplete Directories" section.

## Rule 8 — CAMPAIGN_NARRATIVE-INTEGRATION Is a Pointer, Never Fabricated Coverage

The 10th cross-cutting doc, `{NN}-CAMPAIGN_NARRATIVE-INTEGRATION.md`, is decreed by
`Docs/architecture/demo/campaign narrative/07-WEAVE-STANDARD.md` §3.2. In a pre-implementation run,
**none of the five weave-contract parts (07-WEAVE-STANDARD §1 — story beat, seed fixture,
feature-matrix row, coverage row, render-walk test) exist yet.** The doc must therefore be an honest
*pointer*: it carries the PROPOSED `campaign narrative_beat` from the winning candidate, a single `planned`
coverage-row draft (mirrored into `Docs/architecture/demo/campaign narrative/06-FEATURE-COVERAGE.csv` by
Phase 6, step 6h), and the named follow-up owner (the downstream `corpus-build` run that will build
the beat). It never duplicates story prose — the story lives only in the campaign narrative corpus.

**Never fabricate a coverage status above `planned`.** `covered` and `partial` require artifacts
(a render-walk test, confirmed endpoints) that do not exist pre-implementation; asserting them is a
verification-gate failure. Exact template:

```markdown
# {NN} — Campaign narrative Integration: {Feature}

> **Status: Pre-Implementation.** Pointer doc — the story lives in
> `Docs/architecture/demo/campaign narrative/`, never duplicated here. Binding contract:
> `Docs/architecture/demo/campaign narrative/07-WEAVE-STANDARD.md`. None of the five weave-contract
> parts (§1) exist yet; the row below is a PROPOSED beat, not shipped coverage.

## 1. Proposed Coverage Row (draft — mirrored into 06-FEATURE-COVERAGE.csv by Phase 6h)

| feature_id | feature | status | scene / beat |
|---|---|---|---|
| {SWC-NNN} | {feature} | planned | {proposed case-side or analyst-frame beat, or not_covered rationale} |

## 2. Proposed Beat

{The winning candidate's campaign narrative_beat: which scene (case-side) or analyst-frame surface
(07-WEAVE-STANDARD §6) the feature will exercise, and why the beat narratively needs it. If
not_covered, the recorded rationale.}

## 3. Follow-Up Owner

{Named downstream owner — the `corpus-build <feature>` run that builds the beat, seed fixture,
feature-matrix row, and render-walk test.}
```

The status stays `planned` (or `not_covered` with a rationale) for the entire lifetime of the
pre-implementation corpus. Only a later `corpus-build` run that ships the five parts may raise it.

---

## Checking Compliance

After Phase 6 (governance), the slash command runs a compliance check:

1. Grep `Docs/architecture/<feature>/IMPLEMENTED_SPEC.md` for the banner "Pre-Implementation" — must appear.
2. Grep §3 for any `100%` or `Complete` — must be zero matches.
3. Grep `02-CURRENT-STATE-*.md` section 4 for any affirmative claim about `internal/<feature>/` — must be zero matches (the only acceptable text is the template sentence "None. No code has been written.").
4. Confirm `Docs/architecture/INDEX.md` contains the feature under "Proposed Subsystems" and NOT in any tier table.
5. Confirm a `*-CAMPAIGN_NARRATIVE-INTEGRATION.md` exists, references `07-WEAVE-STANDARD.md`, and that a `planned` coverage row for the feature was appended to `Docs/architecture/demo/campaign narrative/06-FEATURE-COVERAGE.csv` (Rule 8) — fail closed if any is missing.

Any failure halts the run and records the violation in the journal with a remediation note
for the next iteration.
